# task-dispatch Specification

## Purpose

规定 PM 和 Critic 派给子 agent 的 Task、子 agent 交回的 Result 的格式，以及 Agent 网关放行或拒绝任务的规则：任务清单、相同任务的复用、案件的股票、寻股派给谁、PM 的轮次和任务数、Critic 的补充研究额度，子 agent 的输出怎样变成 Result，并按案件数出派过的任务和用量。

## Requirements

### Requirement: 任务清单

任务类型 SHALL 是下表的八种之一，每种只属于一个子 agent；Task 的目标 agent 就是任务类型所属的子 agent，所以目标只能是 News、Quant、Fundamentals：

| 任务类型 | 目标 |
| --- | --- |
| 事件影响评估 | News |
| 某日期以来的新闻汇总 | News |
| 价格反应 | Quant |
| 趋势和支撑阻力 | Quant |
| 波动情况 | Quant |
| 财报对比预期 | Fundamentals |
| 指引变化 | Fundamentals |
| 估值位置 | Fundamentals |

- 每种任务的输出都是 signal-format spec 的信号或无信号
- 问题只补充具体关注点；某日期以来的新闻汇总把起始日期写在问题里

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中）
- 案件：K-1 是 BBB（关注）的关注股事件；K-2 是寻股；K-3 是 CCC（持仓）的持仓事件；K-4 是 BBB 的关注复查，在 K-1 结束以后运行
- 任务请求：
  - 价格请求：任务类型价格反应；股票 BBB；问题"财报后的放量上涨能否持续？"；输入 E-1
  - 新闻请求：任务类型事件影响评估；股票 BBB；问题"大客户续约对明年收入的影响有多大？"；输入 E-2
  - 财报请求：任务类型财报对比预期；股票 BBB；问题"毛利率超预期能否持续？"；输入 E-3 和 E-4
  - "价格请求 n"指问题改为"问题 n"的价格请求，n 不同就是不同的任务；"新闻请求 n"同理
  - "AAA 的价格请求"指只把价格请求的股票改为 AAA，其他请求和股票同理
- "PM 派发 a、b"指 PM 在 K-1 里调用一次 dispatch_tasks，依次请求 a、b；"Critic 派发 a"同理；在别的案件里派发另外写明
- 新生成的 Task 按先后依次是 T-1、T-2……，派发时刻都是当前时刻，截止时间是 2026-10-14 15:05Z
- "T-n 完成""T-n 无信号"指 T-n 不晚于截止时间收到 signal-format spec 的基准信号、基准无信号；"T-n 超时"指到截止时间仍没有输出，记为超时；"T-n 失败"指 T-n 收到评估窗口 4 的信号，记为失败
- "PM 用了 r 轮、n 个任务"指本案件 PM 用掉的轮次和任务数（见「本案件的任务和用量」）
- GIVEN 里的几步依次进行；一个 WHEN 里用"；"或"或者"隔开的几种情况，各自从 GIVEN 的数据开始，互不影响；用"再""接着"连接的依次进行

#### Scenario: 每种任务类型的目标

- **WHEN** 请求的任务类型是事件影响评估、某日期以来的新闻汇总
- **THEN** 目标都是 News
- **WHEN** 请求的任务类型是价格反应、趋势和支撑阻力、波动情况
- **THEN** 目标都是 Quant
- **WHEN** 请求的任务类型是财报对比预期、指引变化、估值位置
- **THEN** 目标都是 Fundamentals

#### Scenario: 不在清单里的任务类型

- **WHEN** 请求的任务类型是"行业对比"
- **THEN** 请求格式错误

### Requirement: 任务请求的格式

PM 和 Critic 派发任务时 SHALL 为每个任务写一个任务请求：

| 项 | 说明 |
| --- | --- |
| 任务类型 | 任务清单里的一种，它决定了目标 |
| 股票 | 股票代码 |
| 问题 | 文字：在任务类型之外补充的具体关注点 |
| 输入 | 状态库条目 ID 的列表，可以为空；每个 ID 是非空的文字 |

- 缺少任务类型、股票或问题，文字去掉首尾空白后为空，某项不符合上表，包含上表以外的项（包括目标 agent），都 MUST 是格式错误
- 格式错误的请求不生成 Task 和 Result，由调用方退回发起者
- 发起者不写在请求里：调用方按调用 dispatch_tasks 的是 PM 还是 Critic 给出

#### Scenario: 完整的请求

- **WHEN** 写价格请求、新闻请求、财报请求
- **THEN** 都格式正确
- **WHEN** 价格请求不写输入
- **THEN** 格式正确，输入为空

#### Scenario: 缺少一项或文字为空

- **WHEN** 价格请求分别缺少任务类型、股票、问题；问题是 "  "；股票是 ""；输入是 E-1 和 "  "
- **THEN** 都是格式错误

#### Scenario: 请求里写目标

- **WHEN** 价格请求另外写了目标 Quant
- **THEN** 格式错误

### Requirement: Task 的格式

Agent 网关 SHALL 为每个不复用的请求生成一个 Task，派发的和被拒绝的都有，包含：

| 项 | 说明 |
| --- | --- |
| task_id | 新生成 |
| 案件 ID | 派发任务的案件 |
| 发起者 | PM 或 Critic |
| 目标 agent | 任务类型所属的子 agent |
| 任务类型、股票、问题、输入 | 请求的原样内容 |
| 派发时刻 | 网关处理这次 dispatch_tasks 的时刻 |
| 截止时间 | 派发时刻加"任务时限"（见「派发的配置」） |
| PM 的轮次 | 发起者是 PM、并且派发出去的任务：这一次是 PM 在本案件的第几轮（见「PM 的轮次」）；Critic 的任务和被拒绝的任务没有 |

- 发起者不是 PM 或 Critic 时 MUST 报错：子 agent 和其他 agent 不能派任务
- Task 生成以后 SHALL NOT 被修改

#### Scenario: 派发出去的 Task

- **WHEN** PM 派发价格请求
- **THEN** 派发 T-1：案件 K-1，发起者 PM，目标 Quant，任务类型价格反应，股票 BBB，问题"财报后的放量上涨能否持续？"，输入 E-1，派发时刻 2026-10-14 15:00Z，截止时间 2026-10-14 15:05Z，PM 的第 1 轮

#### Scenario: 被拒绝的请求也有 Task

- **WHEN** PM 派发 AAA 的价格请求
- **THEN** 生成 T-1，股票 AAA，没有 PM 的轮次；T-1 的 Result 是被拒绝

#### Scenario: Critic 的任务没有轮次

- **WHEN** Critic 派发新闻请求
- **THEN** 派发 T-1：发起者 Critic，目标 News，没有 PM 的轮次

#### Scenario: 只有 PM 和 Critic 能派任务

- **WHEN** 发起者是 News；或者是 Reviewer
- **THEN** 都报错，不生成 Task

### Requirement: Result 的格式

每个 Task SHALL 只有一个 Result，用它的 task_id 标识：PM 和 Critic 引用 Result 时写它的 task_id。Result 包含 task_id、状态、输出、原因、说明、耗时和费用，各状态的内容如下：

| 状态 | 输出 | 原因 | 说明 |
| --- | --- | --- | --- |
| 完成 | 合法的信号 | 无 | 无 |
| 无信号 | 合法的无信号 | 无 | 无 |
| 超时 | 无 | 无 | 无 |
| 失败 | 无 | 格式不合法或调用失败 | 必填的文字 |
| 被拒绝 | 无 | 被拒绝的原因（见「派发的顺序」） | 无 |

- 引用的条目 ID 取自输出（信号或无信号的引用的条目）；没有输出时没有
- 耗时是生成 Result 的时刻减派发时刻；被拒绝的是 0
- 费用是调用方给出的这个任务调用模型的费用，不小于 0；被拒绝的是 0
- 和上表不符、耗时或费用小于 0，都 MUST 报错

#### Scenario: 完成和无信号的 Result

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:01:30Z 收到基准信号，费用 0.02
- **THEN** T-1 的 Result 是完成，输出是基准信号，引用的条目是 E-1 和 E-2，耗时 90 秒，费用 0.02
- **WHEN** 同样的时刻收到基准无信号，费用 0.02
- **THEN** T-1 的 Result 是无信号，输出是基准无信号，没有引用的条目

#### Scenario: 状态和内容不符

- **WHEN** 构造这些 Result：完成，没有输出；完成，输出是基准无信号；无信号，输出是基准信号；超时，输出是基准信号；失败，没有原因；失败，原因是格式不合法，没有说明；被拒绝，原因是格式不合法；无信号，原因是"轮次已用完"；完成，费用 -0.01
- **THEN** 都报错

### Requirement: 派发的顺序

PM 或 Critic 调用一次 dispatch_tasks 时，Agent 网关 SHALL 按请求的顺序逐个处理，每个请求得到下面三种结果之一：

- 复用：本案件有可以复用的相同任务（见「相同的任务」），给出那个 Task 和它的 Result，不再检查
- 被拒绝：按下表的顺序检查，第一项不通过时生成 Task 和被拒绝的 Result，原因是这一项的原因
- 派发：全部通过，生成 Task，由调用方交给目标子 agent

| 顺序 | 检查 | 适用于 | 不通过时的原因 |
| --- | --- | --- | --- |
| 1 | 单只股票的案件：任务的股票是案件的股票（见「案件的股票」） | PM、Critic | 股票不是案件的股票 |
| 2 | 寻股：目标是 Quant 或 Fundamentals（见「寻股派给谁」） | PM、Critic | 寻股只能派给 Quant 和 Fundamentals |
| 3 | 这一次的轮次不超过"PM 的轮次上限"（见「PM 的轮次」） | PM | 轮次已用完 |
| 4 | PM 在本案件派发出去的任务少于"PM 的任务数上限"（见「PM 的任务数」） | PM | 任务数已用完 |
| 5 | Critic 在本案件派发出去的任务少于"Critic 的补充研究额度"（见「Critic 的补充研究额度」） | Critic | 补充研究额度已用完 |

- 后面的请求按前面处理完以后的情况处理：前面派发的计入任务数，也能被后面相同的请求复用
- 被拒绝的 Result 直接交回发起者，不调用子 agent；发起者在缺少该信息的情况下继续

#### Scenario: 一次派发几个任务

- **WHEN** PM 派发价格请求、新闻请求、财报请求
- **THEN** 依次派发 T-1（目标 Quant）、T-2（News）、T-3（Fundamentals），都是 PM 的第 1 轮；PM 用了 1 轮、3 个任务

#### Scenario: 有的派发有的被拒绝

- **WHEN** PM 派发价格请求、AAA 的新闻请求、财报请求
- **THEN** 派发 T-1；T-2 被拒绝，原因是"股票不是案件的股票"；派发 T-3；PM 用了 1 轮、2 个任务

#### Scenario: 多项不通过时给出第一项

- **GIVEN** PM 派发价格请求，再派发新闻请求，已经用掉 2 轮
- **WHEN** PM 派发 AAA 的财报请求
- **THEN** 被拒绝，原因是"股票不是案件的股票"
- **GIVEN** PM 在 K-2 派发 DDD 的价格请求，再派发 EEE 的价格请求，已经用掉 2 轮
- **WHEN** PM 在 K-2 派发 DDD 的新闻请求
- **THEN** 被拒绝，原因是"寻股只能派给 Quant 和 Fundamentals"

### Requirement: 相同的任务

两个任务的任务类型、股票、问题都相同，输入的条目不论顺序也相同时，SHALL 算相同的任务，不论发起者是谁。本案件有相同的任务、并且它还没有 Result 或者 Result 是完成或无信号时，请求 SHALL 复用这个任务：

- 不生成新 Task，给出已有的 Task 和它的 Result；还没有 Result 时等它的 Result
- 复用不算任务数，也不算轮次
- Result 是超时、失败或被拒绝的任务 SHALL NOT 被复用：再派时按「派发的顺序」检查，派发出去就是新任务
- 只复用同一个案件的任务

#### Scenario: 复用完成的 Result

- **GIVEN** PM 派发价格请求，T-1 完成
- **WHEN** PM 派发价格请求
- **THEN** 复用 T-1，给出 T-1 的 Result，不生成新的 Task；PM 用了 1 轮、1 个任务

#### Scenario: 复用无信号，输入的顺序不同

- **GIVEN** PM 派发财报请求，T-1 无信号
- **WHEN** PM 派发财报请求，输入写成 E-4 和 E-3
- **THEN** 复用 T-1

#### Scenario: 不相同的任务不复用

- **GIVEN** PM 派发价格请求，T-1 完成
- **WHEN** PM 派发价格请求 1；输入改为 E-2 的价格请求；输入改为 E-1 和 E-2 的价格请求；任务类型改为趋势和支撑阻力的价格请求
- **THEN** 都派发 T-2，PM 的第 2 轮

#### Scenario: 同一次里的重复请求

- **WHEN** PM 派发价格请求、价格请求
- **THEN** 派发 T-1，第二个请求复用 T-1；PM 用了 1 轮、1 个任务
- **WHEN** 接着 T-1 完成
- **THEN** 两个请求得到的都是 T-1 的 Result

#### Scenario: 超时和失败的不复用

- **GIVEN** PM 派发价格请求，T-1 超时
- **WHEN** PM 派发价格请求
- **THEN** 派发 T-2，PM 的第 2 轮；PM 用了 2 轮、2 个任务
- **GIVEN** PM 派发价格请求，T-1 失败
- **WHEN** PM 派发价格请求
- **THEN** 派发 T-2

#### Scenario: 被拒绝的不复用

- **GIVEN** PM 派发 AAA 的价格请求，T-1 被拒绝
- **WHEN** PM 派发 AAA 的价格请求
- **THEN** 生成 T-2，同样被拒绝，原因是"股票不是案件的股票"

#### Scenario: Critic 复用 PM 的任务

- **GIVEN** PM 派发新闻请求，T-1 完成
- **WHEN** Critic 派发新闻请求
- **THEN** 复用 T-1；Critic 用了 0 个补充研究额度

#### Scenario: 轮次用完以后仍可以复用

- **GIVEN** PM 派发价格请求，再派发新闻请求，已经用掉 2 轮；T-1 和 T-2 都完成
- **WHEN** PM 派发价格请求
- **THEN** 复用 T-1，不被拒绝

#### Scenario: 不复用别的案件的任务

- **GIVEN** PM 在 K-1 派发价格请求，T-1 完成
- **WHEN** PM 在 K-4 派发价格请求
- **THEN** 派发 T-2，K-4 的第 1 轮

### Requirement: 案件的股票

寻股以外的案件都针对一只股票，SHALL 只能派发这只股票的任务，PM 和 Critic 都一样；寻股的任务针对 PM 指定的股票，SHALL NOT 检查它是否在粗筛出的名单里。

#### Scenario: 单只股票的案件

- **WHEN** PM 派发价格请求（股票 BBB）
- **THEN** 派发
- **WHEN** PM 派发 AAA 的价格请求；或者 Critic 派发 AAA 的新闻请求
- **THEN** 都被拒绝，原因是"股票不是案件的股票"

#### Scenario: 寻股由 PM 指定股票

- **WHEN** PM 在 K-2 派发 DDD 的价格请求、EEE 的财报请求
- **THEN** 都派发

### Requirement: 寻股派给谁

寻股 SHALL 只能派给 Quant 和 Fundamentals；其他案件可以派给三个子 agent。

#### Scenario: 寻股不能派给 News

- **WHEN** PM 在 K-2 派发 DDD 的新闻请求；或者派发任务类型是某日期以来的新闻汇总、股票是 DDD 的请求
- **THEN** 都被拒绝，原因是"寻股只能派给 Quant 和 Fundamentals"

#### Scenario: 寻股可以派给 Quant 和 Fundamentals

- **WHEN** PM 在 K-2 派发任务类型是波动情况、股票是 DDD 的请求，和任务类型是估值位置、股票是 DDD 的请求
- **THEN** 都派发

#### Scenario: 其他案件可以派给 News

- **WHEN** PM 派发新闻请求；或者 PM 在 K-3 派发 CCC 的新闻请求
- **THEN** 都派发

### Requirement: PM 的轮次

PM 的一次 dispatch_tasks 里至少有一个请求派发出去时，SHALL 算 PM 在本案件的一轮；全部被拒绝或者全部复用的一次不算。

- 这一次的轮次是 PM 在本案件已经用掉的轮次加 1，同一次里派发出去的任务都属于这一轮
- 这一次的轮次超过"PM 的轮次上限"（默认 2）时，这一次里不复用的请求 SHALL 被拒绝，原因是"轮次已用完"，除非已经因为股票或寻股被拒绝
- Critic 的任务不计轮次，也不受轮次上限限制
- 轮次和任务数按案件计，网关 SHALL NOT 按案件阶段区分：PM 在哪个阶段派发都计入同一个案件

#### Scenario: 两轮以后不能再派

- **GIVEN** PM 派发价格请求（第 1 轮），再派发新闻请求（第 2 轮）
- **WHEN** PM 派发财报请求、价格请求 1
- **THEN** 都被拒绝，原因是"轮次已用完"；PM 用了 2 轮、2 个任务

#### Scenario: 全部被拒绝的一次不算一轮

- **GIVEN** PM 派发价格请求（第 1 轮），再派发 AAA 的新闻请求（被拒绝）
- **WHEN** PM 派发新闻请求
- **THEN** 派发，PM 的第 2 轮

#### Scenario: 全部复用的一次不算一轮

- **GIVEN** PM 派发价格请求（第 1 轮），T-1 完成；PM 再派发价格请求，复用 T-1
- **WHEN** PM 派发新闻请求
- **THEN** 派发，PM 的第 2 轮

#### Scenario: 一次里有复用也有派发

- **GIVEN** PM 派发价格请求（第 1 轮），T-1 完成
- **WHEN** PM 派发价格请求、新闻请求
- **THEN** 第一个请求复用 T-1；第二个派发 T-2，PM 的第 2 轮；PM 用了 2 轮、2 个任务

#### Scenario: 不按阶段区分

- **GIVEN** PM 派发价格请求（第 1 轮），之后案件进入 Critic 审核、Critic 质询
- **WHEN** PM 回应时派发新闻请求
- **THEN** 派发，PM 的第 2 轮；PM 用了 2 轮、2 个任务

#### Scenario: Critic 不受轮次限制

- **GIVEN** PM 派发价格请求，再派发新闻请求，已经用掉 2 轮
- **WHEN** Critic 派发新闻请求 1
- **THEN** 派发，没有 PM 的轮次；PM 仍是 2 轮

### Requirement: PM 的任务数

PM 在本案件派发出去的任务 SHALL 不超过"PM 的任务数上限"（默认 6）：

- 派发出去的都算，不论 Result 是完成、无信号、超时还是失败，还在运行的也算；被拒绝的、复用的和 Critic 的不算
- 一次里按顺序检查，前面派发的计入：达到上限以后，这一次后面不复用的请求都被拒绝，原因是"任务数已用完"

#### Scenario: 任务数上限的边界

- **WHEN** PM 派发价格请求 1 到 6
- **THEN** 都派发
- **WHEN** 接着 PM 派发价格请求 7
- **THEN** 被拒绝，原因是"任务数已用完"

#### Scenario: 一次里超出的部分被拒绝

- **WHEN** PM 派发价格请求 1 到 7
- **THEN** 价格请求 1 到 6 派发（T-1 到 T-6），价格请求 7 被拒绝（T-7）；PM 用了 1 轮、6 个任务

#### Scenario: 第二轮部分超限

- **GIVEN** PM 派发价格请求 1 到 4
- **WHEN** PM 派发价格请求 5、6、7
- **THEN** 价格请求 5 和 6 派发，是 PM 的第 2 轮；价格请求 7 被拒绝，原因是"任务数已用完"

#### Scenario: 超时和失败的任务也算

- **GIVEN** PM 派发价格请求 1 到 6，T-1 超时，T-2 失败，其余还没有 Result
- **WHEN** PM 派发价格请求 7
- **THEN** 被拒绝，原因是"任务数已用完"

#### Scenario: 被拒绝的任务不算

- **GIVEN** PM 派发 AAA 的价格请求，被拒绝
- **WHEN** PM 派发价格请求 1 到 6
- **THEN** 都派发，PM 的第 1 轮

### Requirement: Critic 的补充研究额度

Critic 在本案件派发出去的任务 SHALL 不超过"Critic 的补充研究额度"（默认 2），按案件计，不按审核的次数计：

- 不占 PM 的任务数和轮次：PM 用满任务数和轮次以后，Critic 仍能派发
- 派发出去的都算，不论 Result 的状态；被拒绝的和复用的不算
- 超出时被拒绝，原因是"补充研究额度已用完"

#### Scenario: PM 用满以后 Critic 仍能派发

- **GIVEN** PM 派发价格请求 1 到 3（第 1 轮），再派发价格请求 4 到 6（第 2 轮）
- **WHEN** Critic 派发新闻请求 1
- **THEN** 派发；PM 仍是 2 轮、6 个任务，Critic 用了 1 个补充研究额度

#### Scenario: 补充研究额度的边界

- **WHEN** Critic 派发新闻请求 1、新闻请求 2
- **THEN** 都派发
- **WHEN** 接着 Critic 派发新闻请求 3
- **THEN** 被拒绝，原因是"补充研究额度已用完"

#### Scenario: 额度按案件累计

- **GIVEN** Critic 第一次审核时派发新闻请求 1，第二次审核时派发新闻请求 2
- **WHEN** Critic 第三次审核时派发新闻请求 3
- **THEN** 被拒绝，原因是"补充研究额度已用完"

### Requirement: 子 agent 的输出变成 Result

调用方 SHALL 把子 agent 的输出（JSON 文本）和这个任务的费用交给 Agent 网关，"现在"是收到输出的时刻。不晚于截止时间收到时，网关 SHALL 按 signal-format spec「收到输出时的校验」检查，按下表生成 Result；晚于截止时间的见「超时」：

| 收到的输出 | Result |
| --- | --- |
| 合法的信号 | 完成，输出是这个信号 |
| 合法的无信号 | 无信号，输出是这个无信号 |
| 不能解析成格式正确的信号或无信号（结构错误） | 失败，原因是格式不合法，说明指出是哪一项、为什么 |
| 格式正确的信号，评估窗口或数据截至时刻不通过 | 失败，原因是格式不合法，说明是 signal-format spec 给出的原因 |

格式不合法的 Result 就是这个任务最终的 Result：SHALL NOT 重新调用子 agent，也不切换备用模型；发起者可以之后再派（失败的不复用，见「相同的任务」）。

#### Scenario: 收到合法的信号和无信号

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:01:30Z 收到基准信号
- **THEN** T-1 完成，输出是基准信号
- **WHEN** 同样的时刻收到基准无信号
- **THEN** T-1 是无信号，输出是基准无信号

#### Scenario: 结构错误

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:01:30Z 收到缺少主要风险的基准信号
- **THEN** T-1 失败，原因是格式不合法，说明指出缺少主要风险
- **WHEN** 同样的时刻收到不是 JSON 的文字"看多，理由见上"；或者收到基准无信号另外写了评分 0
- **THEN** T-1 都失败，原因是格式不合法

#### Scenario: 评估窗口不在配置的选项里

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:01:30Z 收到评估窗口 4 的信号
- **THEN** T-1 失败，原因是格式不合法，说明是"评估窗口不在配置的选项里"

#### Scenario: 数据截至时刻晚于收到的时刻

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:01:30Z 收到数据截至 2026-10-14 15:01:31Z 的信号
- **THEN** T-1 失败，原因是格式不合法，说明是"数据截至时刻晚于现在"
- **WHEN** 同样的时刻收到数据截至 2026-10-14 15:01:30Z 的信号
- **THEN** T-1 完成

### Requirement: 超时

每个任务 SHALL 在截止时间（派发时刻加"任务时限"，默认 5 分钟）以前得到 Result，否则是超时：

- 晚于截止时间收到输出或调用失败时，Result 是超时，输出不用
- 到了截止时间仍没有 Result 时，调用方 SHALL 记超时，给出这个任务的费用；早于截止时间记超时 MUST 报错
- 超时的耗时是记下超时的时刻减派发时刻
- 超时的任务算任务数，也算派过任务；发起者在缺少该信息的情况下继续

#### Scenario: 截止时间的边界

- **GIVEN** PM 派发价格请求（T-1，截止时间 2026-10-14 15:05:00Z）
- **WHEN** 2026-10-14 15:05:00Z 收到基准信号
- **THEN** T-1 完成
- **WHEN** 2026-10-14 15:05:01Z 收到基准信号
- **THEN** T-1 超时，没有输出

#### Scenario: 到截止时间仍没有输出

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:05:00Z 记超时，费用 0.01
- **THEN** T-1 超时，耗时 5 分钟，费用 0.01

#### Scenario: 截止时间以前不能记超时

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:04:59Z 记超时
- **THEN** 报错，T-1 仍没有 Result

#### Scenario: 截止时间以后的调用失败

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:05:01Z 调用方给出调用失败
- **THEN** T-1 超时

### Requirement: 调用失败

调用子 agent 失败、不再重试时，调用方 SHALL 给出调用失败、说明和这个任务的费用；什么时候算调用失败由「备用模型」规定。不晚于截止时间时，Result SHALL 是失败，原因是调用失败，说明是调用方给的说明。

#### Scenario: 调用失败

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:02:00Z 调用方给出调用失败，说明"主模型和备用模型都失败"，费用 0
- **THEN** T-1 失败，原因是调用失败，说明"主模型和备用模型都失败"，耗时 2 分钟

### Requirement: 一个任务只有一个 Result

任务 SHALL 只有一个 Result，先到的为准：已经有 Result 的任务再收到输出、调用失败或者记超时，SHALL NOT 改变 Result，给出已有的 Result。

#### Scenario: 超时以后才收到输出

- **GIVEN** PM 派发价格请求（T-1），2026-10-14 15:05:00Z 记超时
- **WHEN** 同样在 2026-10-14 15:05:00Z 收到基准信号
- **THEN** T-1 仍是超时，没有输出

#### Scenario: 完成以后再收到

- **GIVEN** PM 派发价格请求（T-1），2026-10-14 15:01:30Z 完成
- **WHEN** 2026-10-14 15:02:00Z 收到评估窗口 20 的信号；或者给出调用失败；或者 15:05:00Z 记超时
- **THEN** T-1 的 Result 都不变：完成，输出是基准信号

#### Scenario: 被拒绝的任务

- **GIVEN** PM 派发 AAA 的价格请求，T-1 被拒绝
- **WHEN** 收到基准信号
- **THEN** T-1 仍是被拒绝

### Requirement: 本案件的任务和用量

Agent 网关 SHALL 按案件给出：

- 本案件的任务和它们的 Result（还在运行的没有），按生成的先后
- 用量：PM 用掉的轮次和任务数、Critic 用掉的补充研究额度
- 派过任务的子 agent：本案件派发出去的任务的目标，不论 Result 的状态，还在运行的也算，被拒绝的不算；调用方交给 case-types spec「结论的校验」
- 状态是完成的 Result 出自哪个子 agent，按 Result 的 task_id；同样交给结论的校验

#### Scenario: 派过任务的子 agent 和完成的 Result

- **GIVEN** PM 派发价格请求、新闻请求、AAA 的财报请求；T-1 完成，T-2 超时，T-3 被拒绝
- **WHEN** 取得 K-1 的任务和用量
- **THEN** 任务依次是 T-1（完成）、T-2（超时）、T-3（被拒绝）
- **AND** 派过任务的子 agent 是 Quant 和 News；状态是完成的 Result 只有 T-1，出自 Quant
- **AND** PM 用了 1 轮、2 个任务，Critic 用了 0 个补充研究额度

#### Scenario: 还在运行和无信号的任务

- **GIVEN** PM 派发价格请求、财报请求；T-1 无信号，T-2 还没有 Result
- **WHEN** 取得 K-1 的任务和用量
- **THEN** 派过任务的子 agent 是 Quant 和 Fundamentals；没有状态是完成的 Result

#### Scenario: 案件之间互不影响

- **GIVEN** PM 在 K-1 派发价格请求 1 到 3，再派发价格请求 4 到 6
- **WHEN** PM 在 K-2 派发 DDD 的价格请求
- **THEN** 派发，K-2 的第 1 轮；K-2 的 PM 用了 1 轮、1 个任务，K-1 仍是 2 轮、6 个任务
- **WHEN** 取得 K-3 的任务和用量
- **THEN** 没有任务，用量都是 0，没有派过任务的子 agent

### Requirement: 派发的配置

派发的阈值 SHALL 是可配置项：

| 配置项 | 说明 | 默认值 | 要求 |
| --- | --- | --- | --- |
| PM 的任务数上限 | 每个案件 PM 派发出去的任务最多这么多个 | 6 | 正整数 |
| PM 的轮次上限 | 每个案件 PM 最多派这么多轮 | 2 | 正整数 |
| Critic 的补充研究额度 | 每个案件 Critic 派发出去的任务最多这么多个 | 2 | 正整数 |
| 任务时限 | 截止时间是派发时刻加这么久 | 5 分钟 | 大于 0 |

不满足要求时 MUST 配置报错。

#### Scenario: 默认配置

- **WHEN** 不传任何配置项新建配置
- **THEN** PM 的任务数上限 6，PM 的轮次上限 2，Critic 的补充研究额度 2，任务时限 5 分钟

#### Scenario: 配置不合法

- **WHEN** PM 的任务数上限配置为 0；PM 的轮次上限配置为 0；Critic 的补充研究额度配置为 0；任务时限配置为 0 秒
- **THEN** 都配置报错

#### Scenario: 改成别的值

- **GIVEN** PM 的轮次上限配置为 1
- **WHEN** PM 派发价格请求，再派发新闻请求
- **THEN** 新闻请求被拒绝，原因是"轮次已用完"
- **GIVEN** PM 的任务数上限配置为 1
- **WHEN** PM 派发价格请求、新闻请求
- **THEN** 价格请求派发，新闻请求被拒绝，原因是"任务数已用完"
- **GIVEN** Critic 的补充研究额度配置为 1
- **WHEN** Critic 派发新闻请求 1、新闻请求 2
- **THEN** 新闻请求 1 派发，新闻请求 2 被拒绝，原因是"补充研究额度已用完"
- **GIVEN** 任务时限配置为 10 分钟
- **WHEN** PM 派发价格请求
- **THEN** T-1 的截止时间是 2026-10-14 15:10Z
