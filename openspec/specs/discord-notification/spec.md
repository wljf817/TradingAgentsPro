# discord-notification Specification

## Purpose
通知模块让交易侧的流程能找到人：往 Discord 的一个频道推送告警，发出带「确认」「拒绝」按钮的交易方案确认请求，只接受指定用户的操作，并把人的选择交给注入的回调。

## Requirements

### Requirement: 确认请求和截止时刻

请求确认时 SHALL 给出交易方案和它的风控结果，并按下面的规则算出截止时刻：

- 截止时刻 = 请求确认时的时刻 + 确认超时
- 确认超时可以配置，默认 30 分钟，MUST 大于 0
- 风控结果为拒绝的方案 MUST NOT 请求确认：报调用错误，不发消息

请求成功时 SHALL 返回确认消息的标识和截止时刻；之后报告结果时用这个标识指向这条消息。超过截止时刻还没有结果的确认，由调用方报告已超时（见「结束确认」）。

确认的结果只有四种：

| 结果 | 怎样得出 | 是否交给回调 |
| --- | --- | --- |
| 已确认 | 配置的用户在截止时刻之前按「确认」，并且回调成功 | 是 |
| 已拒绝 | 配置的用户在截止时刻之前按「拒绝」，并且回调成功 | 是 |
| 已超时 | 调用方报告；或者配置的用户在截止时刻或之后按按钮 | 否 |
| 已作废 | 调用方报告 | 否 |

本 spec 的场景除非另有说明，都使用下面的基准数据：

- 配置的用户 ID 1001（场景里叫「本人」），另一个用户 4004（「别人」）；频道 2002，属于服务器 3003
- 方案 P1：买入 AAPL，科技板块，100 股，限价单，限价 180.50，止损价 171.00，没填紧急阈值、有效期和允许价格偏离；方案 ID 0b7c2d4e-3f5a-4b6c-8d9e-0f1a2b3c4d5e
- P1 的风控结果：通过，100 股，紧急阈值 0.08，有效期 2026-10-08 20:00Z
- 请求确认的时刻 2026-10-08 14:00Z，确认超时用默认值

#### Scenario: 默认 30 分钟的截止时刻

- **WHEN** 请求确认 P1
- **THEN** 发出一条确认消息，截止时刻 2026-10-08 14:30Z
- **AND** 返回这条消息的标识和截止时刻 14:30Z

#### Scenario: 改确认超时

- **GIVEN** 确认超时配置为 10 分钟
- **WHEN** 请求确认 P1
- **THEN** 截止时刻 2026-10-08 14:10Z

#### Scenario: 被风控拒绝的方案

- **GIVEN** P1 的风控结果是拒绝
- **WHEN** 请求确认 P1
- **THEN** 报调用错误，没有发出任何消息

#### Scenario: 确认超时不是正数

- **WHEN** 确认超时配置为 0 或 -1 分钟
- **THEN** 构造配置时报错

### Requirement: Discord 配置

Discord 适配器的配置 SHALL 如下，前 4 项从环境变量读取：

| 配置 | 环境变量 | 要求 |
| --- | --- | --- |
| 机器人 token | `DISCORD_BOT_TOKEN` | 必填，非空 |
| 服务器 ID | `DISCORD_GUILD_ID` | 必填，正整数 |
| 频道 ID | `DISCORD_CHANNEL_ID` | 必填，正整数；告警和确认都发到这个频道 |
| 用户 ID | `DISCORD_USER_ID` | 必填，正整数；只接受这个用户按按钮，告警和确认都 @ 他 |
| 连接超时 | 无 | 默认 30 秒，大于 0 |
| 发送超时 | 无 | 默认 10 秒，大于 0 |

环境变量没有或者为空，都算缺少。缺少时 SHALL 报配置错误，列出缺少的全部变量名。

token MUST NOT 出现在代码、仓库里的文件、日志、错误信息、配置的字符串形式和测试输出里。

#### Scenario: 4 个环境变量齐全

- **GIVEN** 环境变量 `DISCORD_BOT_TOKEN`=某个 token，`DISCORD_GUILD_ID`=3003，`DISCORD_CHANNEL_ID`=2002，`DISCORD_USER_ID`=1001
- **WHEN** 从环境变量读配置
- **THEN** 服务器 3003、频道 2002、用户 1001，连接超时 30 秒，发送超时 10 秒

#### Scenario: 缺少环境变量

- **GIVEN** 没有 `DISCORD_GUILD_ID`，`DISCORD_USER_ID` 为空字符串，另外两个齐全
- **WHEN** 从环境变量读配置
- **THEN** 报配置错误，错误信息里有 `DISCORD_GUILD_ID` 和 `DISCORD_USER_ID`，没有 token

#### Scenario: ID 不是正整数

- **WHEN** `DISCORD_CHANNEL_ID` 是 "general" 或 "0"
- **THEN** 报配置错误，错误信息里有 `DISCORD_CHANNEL_ID`，没有 token

#### Scenario: token 不外露

- **GIVEN** token 是 "abc.def.ghi"
- **WHEN** 读出配置，把配置转成字符串，并在缺少或非法的变量上报错
- **THEN** 字符串形式和错误信息里都没有 "abc.def.ghi"

#### Scenario: 超时不是正数

- **WHEN** 连接超时或发送超时配置为 0 秒
- **THEN** 构造配置时报错

### Requirement: 启动和关闭

启动 SHALL 登录 Discord、建立连接，并核对配置的频道存在、机器人看得到、属于配置的服务器；全部完成以后才返回。以下情况启动 SHALL 失败，报通知不可用并写明原因（不含 token）：

- 登录失败（比如 token 无效）
- 频道不存在、机器人看不到，或者不属于配置的服务器
- 超过连接超时还没完成

关闭 SHALL 断开连接。启动之前和关闭以后，告警、请求确认和报告结果都 SHALL 报通知不可用。

#### Scenario: 正常启动

- **GIVEN** token 有效，频道 2002 属于服务器 3003
- **WHEN** 启动
- **THEN** 启动返回，之后可以推送告警

#### Scenario: token 无效

- **WHEN** 用无效的 token 启动
- **THEN** 启动失败，原因是登录失败，错误信息里没有 token

#### Scenario: 频道不对

- **GIVEN** 频道 2002 属于另一个服务器，或者机器人看不到它
- **WHEN** 启动
- **THEN** 启动失败，错误信息里有频道 2002

#### Scenario: 连不上

- **GIVEN** Discord 一直连不上
- **WHEN** 启动
- **THEN** 30 秒后启动失败，原因是连接超时

#### Scenario: 启动之前或关闭以后调用

- **WHEN** 还没启动或已经关闭时推送告警、请求确认或报告结果
- **THEN** 报通知不可用，不等发送超时

### Requirement: 告警

推送告警 SHALL 往配置的频道发一条消息：开头 @ 配置的用户，后面是调用方给的文字。

- 只有配置的用户会被 @ 到：文字里写了 @everyone、@here 或别人的 @，也不会通知任何其他人
- 整条消息超过 Discord 的 2000 字上限时，SHALL 把文字截短，使整条消息正好 2000 字，最后一个字是「…」

通知模块的用例推送告警时，发不出去（通知不可用）SHALL 只写一条错误日志（含告警文字），不抛错，调用方照常继续。

#### Scenario: 推送告警

- **WHEN** 推送告警「AAPL 没有止损单：挂单失败」
- **THEN** 频道 2002 收到一条消息，内容是 @本人 加上这句话
- **AND** 本人收到通知（手机推送）

#### Scenario: 文字里有 @everyone

- **WHEN** 推送告警「对账不一致 @everyone <@4004>」
- **THEN** 消息照原样发出，只有本人被通知，频道里的其他人和 4004 都没有被通知

#### Scenario: 文字太长

- **WHEN** 推送一条 2500 字的告警
- **THEN** 消息正好 2000 字，开头是 @本人，最后一个字是「…」

#### Scenario: 告警发不出去

- **GIVEN** Discord 报错或超过发送超时
- **WHEN** 通知模块的用例推送告警
- **THEN** 写一条错误日志，内容有告警文字和失败原因
- **AND** 用例正常返回，不抛错

### Requirement: 确认消息

请求确认 SHALL 往配置的频道发一条确认消息，带「确认」和「拒绝」两个按钮。消息 SHALL 依次写明：

| 内容 | 说明 |
| --- | --- |
| @配置的用户和动作 | 第一行：@用户，然后「请确认：」加动作、股票和风控给出的最终股数（清仓也写股数） |
| 订单类型和价格 | 限价单写限价和金额（最终股数 × 限价，保留两位小数）；市价单写「市价」 |
| 止损价、紧急阈值 | 只有买入和加仓有；紧急阈值用风控给出的生效值，写成百分数 |
| 允许价格偏离 | 方案填了才写，百分数 |
| 板块、有效期 | 有效期用风控给出的生效有效期 |
| 已被风控调整 | 只在风控结果为调整时写：「已被风控调整」、方案原来的股数和调整后的股数，以及每条不通过的规则名称和说明 |
| 截止时刻 | 过了截止时刻按超时处理 |
| 方案 ID | |

时刻（有效期、截止时刻）SHALL 用 Discord 的时间戳标记，每个人按自己设备的时区看到。只有配置的用户会被 @ 到。

#### Scenario: 买入方案通过风控

- **WHEN** 请求确认 P1
- **THEN** 第一行是 @本人 和「请确认：买入 AAPL 100 股」
- **AND** 消息写了限价 180.50、金额 18,050.00、止损价 171.00、紧急阈值 8%、科技板块、有效期 2026-10-08 20:00Z、截止时刻 2026-10-08 14:30Z 和方案 ID
- **AND** 没有「已被风控调整」，没有允许价格偏离
- **AND** 消息带「确认」「拒绝」两个按钮

#### Scenario: 加仓方案被风控调整

- **GIVEN** 方案 P2：加仓 MSFT，科技板块，200 股，限价 410.00，止损价 395.00，允许价格偏离 0.05
- **AND** 风控结果：调整为 120 股，紧急阈值 0.075，不通过的规则是「单笔计划风险：MSFT 的计划风险将是 3,040.00，超过上限 2,000.00」和「组合合计风险：组合合计风险将是 9,000.00，超过上限 8,000.00」
- **WHEN** 请求确认 P2
- **THEN** 第一行是「请确认：加仓 MSFT 120 股」
- **AND** 消息写了金额 49,200.00、紧急阈值 7.5%、允许价格偏离 5%
- **AND** 消息写了「已被风控调整」、200 股调整为 120 股，以及这两条规则的名称和说明

#### Scenario: 市价减仓

- **GIVEN** 方案 P3：减仓 AAPL 60 股，市价单；风控结果通过，60 股，有效期 2026-10-08 20:00Z
- **WHEN** 请求确认 P3
- **THEN** 第一行是「请确认：减仓 AAPL 60 股」，消息写「市价」
- **AND** 没有金额、止损价和紧急阈值

#### Scenario: 限价清仓

- **GIVEN** 方案 P4：清仓 AAPL，限价 185.00；风控结果通过，股数 100（全部可卖）
- **WHEN** 请求确认 P4
- **THEN** 第一行是「请确认：清仓 AAPL 100 股」，消息写限价 185.00、金额 18,500.00

### Requirement: 重复请求同一个方案

同一个进程里，同一个方案再次请求确认（比如上一次调用超过发送超时以后重试）SHALL NOT 再发一条消息，而是返回第一次那条消息的标识和截止时刻；第一次发送失败了的，重新发送。

#### Scenario: 超时以后重试

- **GIVEN** 请求确认 P1 时 Discord 很慢，调用超过发送超时报了通知不可用，但这条消息随后发了出去
- **WHEN** 再次请求确认 P1
- **THEN** 频道里只有一条 P1 的确认消息
- **AND** 返回这条消息的标识和截止时刻 14:30Z

#### Scenario: 第一次发送失败

- **GIVEN** 第一次请求确认 P1 时 Discord 报错，没有发出消息
- **WHEN** 再次请求确认 P1
- **THEN** 发出一条确认消息

### Requirement: 按钮的处理

有人按下确认消息上的按钮时，适配器 SHALL 按下面的顺序处理：

| 情况 | 处理 | 交给回调 |
| --- | --- | --- |
| 不是配置的用户 | 回复一条只有他自己能看到的提示：只有配置的用户可以操作 | 否 |
| 这条消息已经有结果 | 回复仅自己可见的提示，写明已有的结果 | 否 |
| 这条消息上一次按下还在处理 | 回复仅自己可见的提示：还在处理 | 否 |
| 已经过了截止时刻（不早于截止时刻） | 消息去掉按钮，显示已超时 | 否 |
| 其他 | 先应答 Discord，再调用回调，交给它方案 ID 和「确认」或「拒绝」 | 是 |

- 每次按下 SHALL 在 3 秒内应答 Discord：应答之前只做内存里的判断。回调 SHALL 在 Discord 的事件处理之外运行，回调运行期间，别的按钮、告警和确认请求照常处理
- 回调成功：消息去掉按钮，显示结果（已确认或已拒绝）和得出结果的时刻
- 回调抛错：保留按钮，回复按的人一条仅自己可见的提示，请他再按一次；写错误日志
- 按钮自带方案 ID、选择和截止时刻：进程重启以后，重启前发出的确认消息上的按钮照样能用
- 别的功能的按钮或命令（不是确认消息的按钮）不处理、不应答
- 每次按下 SHALL 写一条日志：谁、哪个方案、按了什么、怎样处理的

#### Scenario: 本人按确认

- **GIVEN** P1 的确认消息，截止时刻 14:30Z
- **WHEN** 本人在 14:05Z 按「确认」
- **THEN** 回调收到 P1 的方案 ID 和「确认」
- **AND** 消息去掉按钮，显示已确认和 14:05Z

#### Scenario: 本人按拒绝

- **WHEN** 本人在 14:05Z 按「拒绝」
- **THEN** 回调收到 P1 的方案 ID 和「拒绝」
- **AND** 消息去掉按钮，显示已拒绝

#### Scenario: 别人按按钮

- **WHEN** 别人（4004）按「确认」
- **THEN** 他看到一条只有自己能看到的提示，说只有本人可以操作
- **AND** 回调没有被调用，消息不变，按钮还在

#### Scenario: 连按两次

- **GIVEN** 本人按了「确认」，回调还没返回
- **WHEN** 本人又按了一次「确认」或「拒绝」
- **THEN** 第二次只得到仅自己可见的提示「还在处理」
- **AND** 回调只被调用一次

#### Scenario: 已经有结果以后再按

- **GIVEN** 本人按「确认」，回调成功，消息显示已确认
- **WHEN** 去掉按钮之前又收到本人对这条消息的一次按下
- **THEN** 他得到仅自己可见的提示，写明已确认
- **AND** 回调没有再被调用

#### Scenario: 截止前一秒按下

- **WHEN** 本人在 14:29:59Z 按「确认」
- **THEN** 回调收到「确认」，消息显示已确认

#### Scenario: 截止时刻或之后按下

- **WHEN** 本人正好在 14:30:00Z 按「确认」，或者在 14:45Z 按「拒绝」
- **THEN** 回调没有被调用
- **AND** 消息去掉按钮，显示已超时

#### Scenario: 先应答再调用回调

- **GIVEN** 回调要运行很久才返回
- **WHEN** 本人按「确认」
- **THEN** 适配器在调用回调之前已经应答了 Discord
- **AND** 回调运行期间，推送告警和别的按钮照常处理
- **AND** 回调不在 Discord 的事件处理所在的线程里运行

#### Scenario: 回调抛错

- **GIVEN** 回调抛错（比如数据库暂时连不上）
- **WHEN** 本人按「确认」
- **THEN** 本人看到仅自己可见的提示：没有送达，请再按一次
- **AND** 消息上的按钮还在，没有显示结果；写了一条错误日志
- **WHEN** 回调恢复正常后本人再按「确认」
- **THEN** 回调收到「确认」，消息显示已确认

#### Scenario: 重启以后按旧消息的按钮

- **GIVEN** 进程在 14:02Z 重启，重启前发出了 P1 的确认消息
- **WHEN** 本人在 14:05Z 按这条消息的「确认」
- **THEN** 回调收到 P1 的方案 ID 和「确认」，消息显示已确认

#### Scenario: 别的按钮或命令

- **WHEN** 收到一个不是确认消息按钮的交互（比如以后的斜杠命令）
- **THEN** 不应答、不调用回调

### Requirement: 结束确认

调用方 SHALL 能报告一条确认消息的结果为已超时或已作废。报告以后：

- 消息去掉按钮，显示报告的结果和报告的时刻
- 报告的结果覆盖消息上已经显示的结果：调用方是按它实际采用的结果报告的
- 之后再有人按这条消息的按钮（比如按钮还没来得及去掉），按「这条消息已经有结果」处理
- 报告时按下的按钮正在调用回调的，回调返回以后不再改消息
- 确认消息已经被删掉时，什么也不做，不报错

通知模块的用例报告结果时，发不出去（通知不可用）SHALL 只写一条错误日志，不抛错。

#### Scenario: 报告超时

- **GIVEN** P1 的确认消息没有人按
- **WHEN** 调用方在 14:30Z 报告已超时
- **THEN** 消息去掉按钮，显示已超时和 14:30Z

#### Scenario: 报告作废

- **WHEN** 调用方在 14:10Z 报告已作废
- **THEN** 消息去掉按钮，显示已作废

#### Scenario: 按钮的结果和调用方的结果不一致

- **GIVEN** 本人在 14:09Z 按了「确认」，回调成功，消息显示已确认
- **AND** 调用方先收到的是作废，没有采用这次确认
- **WHEN** 调用方报告已作废
- **THEN** 消息显示已作废

#### Scenario: 报告时回调还在运行

- **GIVEN** 本人按了「确认」，回调还在运行
- **WHEN** 调用方报告已作废，然后回调返回
- **THEN** 消息显示已作废，不会再改成已确认

#### Scenario: 报告以后再按

- **GIVEN** 调用方已经报告已作废
- **WHEN** 又收到本人对这条消息的一次按下
- **THEN** 他得到仅自己可见的提示，写明已作废；回调没有被调用

#### Scenario: 消息已被删掉

- **GIVEN** 本人删掉了 P1 的确认消息
- **WHEN** 调用方报告已超时
- **THEN** 什么也不做，不报错

#### Scenario: 报告发不出去

- **GIVEN** Discord 报错
- **WHEN** 通知模块的用例报告已超时
- **THEN** 写一条错误日志，用例正常返回

### Requirement: 同步调用和失败

推送告警、请求确认和报告结果 SHALL 能从任何线程同步调用，调用会等到 Discord 完成为止，但最多等发送超时（默认 10 秒）。以下情况 SHALL 报通知不可用，错误信息写明原因、不含 token：

- 超过发送超时
- Discord 报错（服务器错误、限流重试用完、没有权限）或者网络不通
- 还没启动、已经关闭，或者连接意外中止（比如 token 被重置）：立即报，不等发送超时；连接意外中止时写一条错误日志

一次调用失败不影响之后的调用：网络恢复以后，不用重新启动就能照常发送。和 Discord 的连接中断时适配器自动重连；中断期间按下的按钮由 Discord 提示交互失败，按钮保留，重连以后可以再按。

通知模块的用例请求确认失败时 SHALL 原样抛出通知不可用，由调用方决定怎样处理。

#### Scenario: 从多个线程同时调用

- **WHEN** 两个线程同时各推送一条告警
- **THEN** 两条消息都发出，两个调用都正常返回

#### Scenario: 超过发送超时

- **GIVEN** Discord 一直没有响应
- **WHEN** 请求确认 P1
- **THEN** 10 秒后报通知不可用，原因是超时

#### Scenario: Discord 报错

- **GIVEN** Discord 对发消息返回服务器错误或没有权限
- **WHEN** 请求确认 P1
- **THEN** 报通知不可用，错误信息里有 Discord 给的原因

#### Scenario: 网络中断以后恢复

- **GIVEN** 网络中断期间推送告警，报了通知不可用
- **WHEN** 网络恢复以后再推送一条告警
- **THEN** 这条告警正常发出，不需要重新启动

#### Scenario: 连接意外中止

- **GIVEN** 启动以后，和 Discord 的连接因为不可恢复的错误中止（比如 token 被重置）
- **WHEN** 推送告警
- **THEN** 立即报通知不可用，原因是连接已中止
- **AND** 连接中止时写了一条错误日志

#### Scenario: 请求确认失败时用例抛错

- **GIVEN** Discord 报错
- **WHEN** 通知模块的用例请求确认 P1
- **THEN** 用例抛出通知不可用
