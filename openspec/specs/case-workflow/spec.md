# case-workflow Specification

## Purpose
案件工作流把一个开始运行的案件从开始跑到结束：生成快照、组出案件上下文、唤醒 PM 研究和提交结论、检查结论并让它生效、交给 Critic 审核和 PM 回应、把交易方案交给下单那一侧、跑复盘、写案件记录，并把案件的进展发给队列。agent 只经 Agent 网关调用，案件状态的转换照 case-stages spec。

## Requirements

### Requirement: 开始运行一个案件

调用方（「排队运行」）SHALL 给出案件 ID、开始时确定的案件类型（case-types spec「开始运行时确定案件类型」：类型、股票、问题、事件要求的子 agent）、触发（case-types spec「触发」）和触发时刻，开始运行这个案件。一个案件 ID 只运行一次：同一个案件 ID 再开始时 SHALL NOT 再运行一个，已经在运行的照常继续。

开始运行时案件工作流 SHALL 依次：

1. 按案件类型新建案件状态（case-stages spec「案件的状态」）
2. 写案件记录的开始运行（case-records spec「写入的时刻」）：触发的种类、触发原因、股票、触发时刻、案件类型
3. 写程序日志的开案件（program-log spec「调度器的动作」），发布案件的进展（见「案件的进展」）
4. 生成第 1 版快照（见「快照」），之后复盘案件见「复盘案件」，其他案件见「PM 的研究」

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中），交易日历是纽交所日历；今天（现在归属的交易日）是 2026-10-14
- 股票池：AAA 候选，板块 XLK；BBB 关注，板块 XLV，关注论点是 stock-pool spec 的基准关注论点，上次复查的那一天 2026-10-07；CCC 持仓，板块 XLE，投资论点是 case-types spec 的基准投资论点，上次复查的那一天 2026-10-07
- 券商账户：CCC 100 股，均价 80；行情：BBB 最新价 52，CCC 最新价 85
- 案件：
  - K-1：BBB 的关注股事件，触发是 BBB 的入场条件满足事件，要求的子 agent 是 Quant
  - K-2：寻股，快照的粗筛名单依次是 DDD、EEE
  - K-3：CCC 的持仓事件，触发是 CCC 的新闻事件，要求的子 agent 是 News
  - K-4：CCC 的持仓复查
  - K-5：每周复盘
  - K-6：AAA 的候选评估
  - K-7：CCC 的卖出复盘
- 结论用 case-types spec 的基准数据（基准信号、基准方案条款、基准投资论点、基准跟进申请）；"K-1 的开仓结论"指 K-1 的关注的结论：开仓方案，基准方案条款，附基准投资论点，引用的 Result 来自 Quant 和 Fundamentals
- 任务请求用 task-dispatch spec 的价格请求（Quant）、新闻请求（News）、财报请求（Fundamentals），新生成的 Task 依次是 T-1、T-2……；新生成的方案 ID 是 P-1
- agent 的回复按场景写的顺序给出；"PM 不可用""Critic 不可用""Reviewer 不可用"指这个 agent 的主模型和备用模型全部不可用（agent-calls spec「一次调用」给出调用失败）
- "下单那一侧"是「方案接下单」实现的交接，场景里它给出的结果按场景写的给出
- "正常走完"指之后每一步都按基准数据里最简单的路径进行：PM 不派任务就提交结论、Critic 通过、风控通过、已确认、订单已提交

#### Scenario: 开始一个案件

- **WHEN** 2026-10-14 15:00Z 开始运行 K-1，触发时刻 2026-10-14 14:58Z
- **THEN** K-1 的案件记录是进行中：触发是事件，股票 BBB，触发时刻 2026-10-14 14:58Z，案件类型关注股事件，开始时刻 2026-10-14 15:00Z
- **AND** 程序日志有一条开案件，对象是 K-1
- **AND** K-1 的进展是：关注股事件，BBB，阶段唤醒 PM，在调用模型，没有方案
- **AND** 生成了 K-1 的第 1 版快照

#### Scenario: 同一个案件开始两次

- **GIVEN** K-1 已经开始运行，在唤醒 PM
- **WHEN** 再以 K-1 开始运行
- **THEN** 只有一个 K-1 在运行；案件记录、程序日志和快照都没有多出来的

### Requirement: 案件的进展

案件工作流 SHALL 在案件开始和案件状态每次变化以后发布这个案件的进展，调用方（「排队运行」）按案件 ID 读最新的进展，组出队列的快照（case-queue spec「队列的输入和决定」）：

| 项 | 内容 |
| --- | --- |
| 案件类型 | 开始时确定的案件类型 |
| 股票 | 寻股和每周复盘没有 |
| 案件状态 | case-stages spec「案件的状态」；由它推出是否还在调用模型的阶段和方案的阶段 |
| 现在的方案 | 方案 ID、股票、动作和条款；PM 修改过的条款已经代入；没有方案时没有 |

- 案件已经结束、没有这个案件、或者案件的运行出错停下时，SHALL 没有进展：它不是运行中的案件
- 进展只给调用方读，调用方 SHALL NOT 用它推进案件

#### Scenario: 开仓案件的进展

- **GIVEN** K-1 开始运行
- **WHEN** PM 提交 K-1 的开仓结论并通过；Critic 通过；下单那一侧给出风控通过、要人工确认；送回已确认
- **THEN** K-1 的进展依次是：唤醒 PM、在调用模型、没有方案；Critic 审核、在调用模型、方案 P-1 在审核；风控、不在调用模型、P-1 在审核；等人工确认、P-1 在等人工确认；等下单、P-1 在等下单
- **WHEN** 接着送回订单已提交
- **THEN** K-1 没有进展

#### Scenario: 没有方案的案件

- **GIVEN** K-6 开始运行
- **WHEN** PM 提交候选的结论：保持，通过
- **THEN** K-6 先后的进展是唤醒 PM、没有方案；之后没有进展

#### Scenario: 没有开始的案件

- **WHEN** 读 K-9 的进展，K-9 没有开始运行过
- **THEN** 没有进展

### Requirement: 快照

案件工作流 SHALL 在案件开始时生成这个案件的第 1 版快照（state-snapshot spec「每种案件的快照」），之后本案件的 agent 都读最新的一版；Critic 要求补充研究时生成新的一版（见「Critic 审核」）。

生成快照时数据读不到（state-snapshot spec「数据读不到时」：券商账户、行情、寻股的粗筛数据源不可用）时，案件 SHALL 按系统故障结束（case-stages spec「系统故障」），不唤醒任何 agent；第 1 版读不到时没有结论。

#### Scenario: 读同一版快照

- **WHEN** K-1 开始运行，PM 派发价格请求，再提交结论
- **THEN** PM 两次调用和 T-1 都读 K-1 的第 1 版快照

#### Scenario: 第 1 版读不到

- **WHEN** K-1 开始运行，读券商账户超时；或者行情源超时；K-2 开始运行，粗筛的日线数据源不可用
- **THEN** 三个案件都结束：系统故障，没有结论；没有唤醒 PM
- **AND** 案件记录写了结束，Task 数和调用次数都是 0

### Requirement: 案件上下文

由 PM 处理的案件开始时，案件工作流 SHALL 组出一份案件上下文（agent-calls spec「每个 agent 的输入和输出」），本案件 PM 和 Critic 的每次调用都用这一份：

| 项 | 来源 |
| --- | --- |
| 问题 | 开始时确定的案件类型的问题；跟进案件是申请时写下的问题 |
| 事件类别 | 事件案件的触发里的事件类别 |
| 事件要求的子 agent | 开始时确定的案件类型 |
| 关注论点 | 案件股票是关注时，股票池里现在的关注论点 |
| 投资论点 | 案件股票是持仓时，股票池里现在的投资论点 |
| 最近结束的案件 | 这只股票已经结束的案件（case-records spec「读取案件记录」），按结束时刻从晚到早，最多"近期案件数"个；每个写案件类型、结束时刻、结束原因和结论（没有结论的不写） |
| 待执行的跟进 | 这只股票待执行的跟进的申请（follow-ups spec「跟进的记录」），按触发时间排列 |

不针对单只股票的案件（寻股）只有问题。

#### Scenario: 关注股事件的上下文

- **WHEN** K-1 开始运行，BBB 没有结束过的案件，也没有待执行的跟进
- **THEN** 案件上下文：问题"入场机会是否出现？"，事件类别入场条件满足，事件要求的子 agent 是 Quant，关注论点是基准关注论点；没有投资论点、最近结束的案件和待执行的跟进

#### Scenario: 持仓的上下文

- **GIVEN** CCC 已经结束的案件依次是：K-11（持仓复查，2026-10-07 结束，没有交易方案，结论是持有）、K-12（持仓事件，2026-10-09 结束，系统故障，没有结论）；CCC 有一个待执行的跟进，申请是基准跟进申请
- **WHEN** K-3 开始运行
- **THEN** 案件上下文：问题"这个事件是否削弱或推翻了论点？"，事件类别新闻，事件要求的子 agent 是 News，投资论点是基准投资论点
- **AND** 最近结束的案件依次是 K-12（系统故障，没有结论）、K-11（没有交易方案，结论持有）；待执行的跟进是基准跟进申请

#### Scenario: 近期案件数的边界

- **GIVEN** CCC 已经结束了 4 个案件
- **WHEN** K-3 开始运行
- **THEN** 最近结束的案件是结束时刻最晚的"近期案件数"个
- **GIVEN** 近期案件数配置为 0
- **WHEN** K-3 开始运行
- **THEN** 没有最近结束的案件

#### Scenario: 寻股和跟进案件的上下文

- **WHEN** K-2 开始运行
- **THEN** 案件上下文只有问题"补充哪些候选？"
- **WHEN** CCC 的跟进开出的持仓跟进开始运行，申请时写下的问题是"大单公布 3 小时后盘中反应如何？"
- **THEN** 问题是"大单公布 3 小时后盘中反应如何？"，没有事件类别和事件要求的子 agent

### Requirement: PM 的研究

唤醒 PM 阶段，案件工作流 SHALL 按案件上下文、最新一版快照和 PM 在本案件的对话（agent-calls spec「对话的每一轮」）调用 PM（研究），按 PM 的回复：

| 回复 | 处理 |
| --- | --- |
| 派发任务 | 以 PM 为发起者经 Agent 网关派发（task-dispatch spec「派发的顺序」）；派发出去的任务同时交给目标子 agent 运行，读派发时最新的一版快照（agent-calls spec「子 agent 的任务」）；全部有了 Result 以后，把这次回复和每个请求的 Task 和 Result（按请求的顺序）作为一轮加进对话，再调用 PM |
| 提交结论 | 按「结论的检查」检查 |
| 调用失败 | 见「模型全部不可用」 |

- 被拒绝和复用的请求 SHALL NOT 交给子 agent；超时、失败的任务照样交回 PM，PM 在缺少这些信息的情况下继续
- 调用预算用完 SHALL NOT 影响运行中的案件（call-budget spec「已经开始的案件」）

#### Scenario: 派发以后提交结论

- **GIVEN** K-1 开始运行
- **WHEN** PM 派发价格请求和财报请求；T-1、T-2 完成；PM 提交 K-1 的开仓结论
- **THEN** T-1、T-2 都交给了子 agent；PM 第二次调用时对话有一轮：派发任务，交回 T-1、T-2 和它们完成的 Result
- **AND** 结论按「结论的检查」检查

#### Scenario: 任务同时运行

- **WHEN** K-1 的 PM 派发价格请求和财报请求
- **THEN** T-2 在 T-1 有 Result 以前就开始运行

#### Scenario: 被拒绝和复用的请求

- **GIVEN** K-1 的 PM 已经派发过价格请求（T-1 完成）
- **WHEN** PM 再派发 AAA 的新闻请求和价格请求
- **THEN** AAA 的新闻请求被拒绝（不是案件的股票），价格请求复用 T-1；没有任务交给子 agent
- **AND** PM 下一次调用时对话的第二轮依次交回被拒绝的 Task 和 Result、T-1 和它完成的 Result

#### Scenario: 超时的任务照样交回

- **WHEN** K-3 的 PM 派发新闻请求，T-1 超时；PM 提交持仓的结论：持有
- **THEN** PM 第二次调用时对话交回 T-1 和超时的 Result；结论照常检查，News 算派过任务

#### Scenario: 普通预算用完以后照常运行

- **GIVEN** K-6 开始运行以后，普通预算用完
- **WHEN** K-6 的 PM 派发价格请求，再提交结论
- **THEN** 任务照常派发和运行，PM 照常调用

### Requirement: 结论的检查

PM 提交结论以后，案件工作流 SHALL 按下表的顺序检查，给出第一项不通过的原因：

| 顺序 | 检查 | 依据 |
| --- | --- | --- |
| 1 | 结论里的信号 | signal-format spec「结论里的信号」；"现在"是收到结论的时刻 |
| 2 | 备用模型的限制 | model-fallback spec「备用模型的限制」：提交结论的这次调用用的模型 |
| 3 | 结论的校验 | case-types spec「结论的校验」：派过任务的子 agent 和状态是完成的 Result 取本案件的（task-dispatch spec「本案件的任务和用量」） |
| 4 | 寻股加入的股票在粗筛名单里 | 寻股的结论里每只加入的股票都在本案件快照的粗筛名单里（state-snapshot spec「寻股的粗筛结果」）；不通过的原因写明哪只不在名单里 |
| 5 | 论点里的日期 | review-dates spec「检查论点里的日期」：结论里每一份新写的论点（见下面） |
| 6 | 跟进审批 | follow-ups spec「审批的输入和结果」：结论附了跟进申请时 |

第 5 项检查的论点和传入的事实：

| 结论和决定 | 论点 | 情形 |
| --- | --- | --- |
| 关注的结论，开仓方案 | 附的投资论点 | 新设 |
| 候选的结论，升级 | 附的关注论点 | 新设 |
| 持仓的结论，清仓，去向转为关注 | 附的关注论点 | 新设 |
| 持仓的结论，持有、加仓或减仓，附论点更新 | 论点更新 | 复查类案件里是续期，其他是平时调整；原来的论点和上次复查的那一天取股票池现在的 |
| 关注的结论，继续关注，附论点更新 | 论点更新 | 同上 |

- 今天：检查时现在归属的交易日
- 持仓的浮动盈亏比例：（快照里案件股票的最新价 − 快照的账户里这只持仓的均价）÷ 均价；没有最新价时用前一交易日收盘价；快照里没有它的行情时不传
- 日程项的日期：新论点的催化剂引用日程项时，按日程项的 ID 在本案件的快照里查条目，是财报发布的条目时取它的发布日；查不到或者不是财报发布时不传
- 跟进审批的催化剂：结论附了论点更新时是论点更新里的，否则是股票池现在的论点里的

不通过时 SHALL 按 case-stages spec「唤醒 PM 和结论」处理：重交次数没用完就把结论和原因作为一轮加进对话，再调用 PM；用完以后按结论无效结束。不通过的结论 SHALL NOT 生效：不记评分、不改股票池；跟进审批排在最后，前面不通过时跟进申请不审批，审批不通过时也不保存。

全部通过时见「结论生效」。

#### Scenario: 信号不合法退回

- **WHEN** K-6 的 PM 提交候选的结论：保持，信号是评估窗口 10 的信号
- **THEN** 退回 PM，原因写明结论里的信号不合法、评估窗口不在配置的选项里；重交次数 1

#### Scenario: 备用模型的限制退回

- **WHEN** K-1 的 PM 用备用模型 p-2 提交 K-1 的开仓结论
- **THEN** 退回 PM，原因是"用备用模型时不能提这个决定"
- **WHEN** 接着 PM 用 p-2 提交关注的结论：继续关注
- **THEN** 通过

#### Scenario: 研究不足退回以后再交

- **WHEN** K-1 的 PM 只派发价格请求（T-1 完成），提交开仓结论，只引用 T-1
- **THEN** 退回 PM，原因是"研究不足"；PM 下一次调用时对话依次有：派发任务和 T-1；提交的结论和原因"研究不足"
- **WHEN** 接着 PM 派发财报请求（T-2 完成），再提交开仓结论，引用 T-1 和 T-2
- **THEN** 通过

#### Scenario: 寻股只能加名单里的股票

- **WHEN** K-2 的 PM 提交寻股的结论：加入 DDD（评分 1）和 ZZZ（评分 2），ZZZ 不在粗筛名单里
- **THEN** 退回 PM，原因写明 ZZZ 不在粗筛名单里；DDD 没有加入股票池
- **WHEN** 接着 PM 提交寻股的结论：加入 DDD 和 EEE
- **THEN** 通过

#### Scenario: 论点里的日期退回

- **WHEN** K-4 的 PM 提交持仓的结论：持有，论点更新是基准投资论点的复查日改为 2026-11-12（今天之后第 21 个交易日）
- **THEN** 退回 PM，原因是"复查日太远"；CCC 的投资论点不变

#### Scenario: 亏损的持仓续期

- **GIVEN** 快照里 CCC 的最新价是 72（浮动盈亏比例 -0.10）
- **WHEN** K-4 的 PM 提交持仓的结论：持有，论点更新是基准投资论点的复查日改为 2026-10-22（今天之后第 6 个交易日）
- **THEN** 退回 PM，原因是"亏损时不能推后复查日"
- **GIVEN** 快照里 CCC 的最新价是 85
- **WHEN** 提交同样的结论
- **THEN** 通过

#### Scenario: 引用日程项的催化剂

- **GIVEN** K-1 的第 1 版快照有财报发布条目 s1/earnings/BBB:2026Q4，发布日 2027-01-26
- **WHEN** K-1 的 PM 提交开仓结论，投资论点的催化剂引用日程项 s1/earnings/BBB:2026Q4，截止日期 2027-01-27
- **THEN** 日程项的日期是 2027-01-26，按 review-dates spec 检查截止日期
- **WHEN** 催化剂改为引用日程项 S-9
- **THEN** 退回 PM，原因是"引用的日程项不存在"

#### Scenario: 跟进审批最后检查

- **WHEN** K-3 的 PM 派过 News 的任务以后提交持仓的结论：持有，附基准跟进申请，引用的对象去掉
- **THEN** 退回 PM，原因是"没有引用具体对象"
- **AND** CCC 的评分和投资论点不变，没有新的跟进
- **WHEN** K-3 的 PM 派过 News 的任务以后提交持仓的结论：持有，附基准跟进申请，但信号是评估窗口 10 的信号
- **THEN** 退回 PM，原因是信号不合法；跟进申请没有审批

### Requirement: 结论生效

结论通过检查以后，案件工作流 SHALL 推进案件状态（case-stages spec「唤醒 PM 和结论」），写案件记录的结论和给出它的模型（有交易方案时连同方案，见「交易方案」），然后按下表让结论生效。评分（signal-format spec「结论里的信号」）SHALL 在改变股票状态以前记下：

| 结论 | 决定 | 生效 |
| --- | --- | --- |
| 持仓的结论 | 持有、加仓、减仓 | 记评分；附论点更新时更新投资论点，上次复查的那一天按 review-dates spec「上次复查的那一天」；加仓、减仓的方案进入 Critic 审核 |
| 持仓的结论 | 清仓 | 记评分；方案进入 Critic 审核。清仓后的去向和关注论点在清仓完成时由下单那一侧交给股票池 |
| 关注的结论 | 开仓方案 | 记评分；方案进入 Critic 审核。投资论点在买入成交时由下单那一侧交给股票池 |
| 关注的结论 | 继续关注 | 记评分；附论点更新时更新关注论点，上次复查的那一天同上 |
| 关注的结论 | 降为候选 | 记评分；降为候选；通过时作废这只股票待执行的跟进（follow-ups spec「股票状态往下走时作废」） |
| 关注的结论 | 移出 | 记评分；删除，理由是结论的理由；通过时作废跟进；写一项发现 |
| 候选的结论 | 升级 | 记评分；以附的关注论点升级，上次复查的那一天是今天 |
| 候选的结论 | 保持 | 记评分；保持 |
| 候选的结论 | 移出 | 记评分；删除，理由是结论的理由；写一项发现 |
| 寻股的结论 | 加入和删除 | 按结论里的顺序先加入、后删除：加入的来源是 PM 探索，上市信息取快照粗筛名单里这只股票的；加入通过时记它的评分；删除通过时作废它的跟进；每一项写一项发现 |

- 发现照 case-records spec「股票池增删的发现」写，在增删执行以后
- 股票池不通过的操作（stock-pool spec 的拒绝原因）SHALL NOT 改变结论、SHALL NOT 退回 PM：操作不生效，由股票池写程序日志；增删写进发现
- 跟进申请在「结论的检查」第 6 项获批时已经保存
- 没有交易方案的结论生效以后案件结束：没有交易方案

### Requirement: 交易方案

结论有交易方案时，案件工作流 SHALL 按 case-types spec「PM 写的交易方案」补上方案 ID（新生成）、股票（案件的股票）和板块（股票池里这只股票的板块），连同决定给出的动作变成交易方案，作为现在的方案进入 Critic 审核。一个案件最多一个方案。

#### Scenario: 补上方案 ID、股票和板块

- **AND** 案件记录的方案记录是 P-1

### Requirement: Critic 审核

Critic 审核阶段，案件工作流 SHALL 按案件上下文、最新一版快照、结论、PM 在本案件派过的任务和 Result（按派发的先后）和 Critic 在本案件的对话调用 Critic，按回复：

| 回复 | 处理 |
| --- | --- |
| 补充研究（派发任务） | 生成本案件新的一版快照，原因写明是 Critic 第几次补充研究；以 Critic 为发起者经 Agent 网关派发，派发出去的任务读新的一版、同时运行；全部有了 Result 以后作为一轮加进 Critic 的对话，再调用 Critic。之后本案件 Critic 和 PM 的调用都读新的一版 |
| 审核 | 写案件记录的审核和 Critic 用的模型，按 case-stages spec「Critic 审核开仓类方案」「Critic 审核退出类方案」推进案件状态 |
| 调用失败 | 见「模型全部不可用」 |

- 审核是质询、进入 PM 回应时，见「PM 回应」；进入风控时，见「交给下单」
- 补充研究这一次审核的 Task 和 Result 在 PM 回应时交给 PM
- 生成新的一版快照时数据读不到，案件 SHALL 按系统故障结束（有结论）

- **THEN** 生成了 K-1 的第 2 版快照，原因写明 Critic 第 1 次补充研究；T-3 的发起者是 Critic，读第 2 版

- **AND** K-1 进入风控，质询轮次 0

### Requirement: PM 回应

PM 回应阶段，案件工作流 SHALL 调用 PM（回应），对话的最后一轮是 PM 上一次的回复（提交的结论，或者上一轮的回应）和交回的质询：这次审核，以及这次审核里补充研究的 Task 和 Result（agent-calls spec「对话的每一轮」）。按回应（case-stages spec「PM 回应」）：

| 回应 | 处理 |
| --- | --- |
| 维持 | 回到 Critic 审核；Critic 的对话加一轮：这次质询和 PM 的回应 |
| 修改 | 修改后的条款代替现在的方案的条款，方案 ID 和动作不变；回到 Critic 审核，Critic 的对话同上 |
| 撤回 | 结束：PM 撤回 |
| 调用失败 | 见「模型全部不可用」 |

每次回应 SHALL 写案件记录的回应和 PM 用的模型。

#### Scenario: 维持以后再审

- **THEN** PM 回应时对话的最后一轮是：提交的结论，交回这次质询和 T-3 的 Task 和 Result

- **WHEN** PM 撤回
- **THEN** 结束：PM 撤回，有结论

- **WHEN** 依次：Critic 质询、PM 维持、Critic 质询、PM 修改、Critic 质询
- **THEN** PM 第二次回应时对话的最后一轮是：第一次的回应，交回第二次质询

### Requirement: 交给下单

方案进入风控阶段时，案件工作流 SHALL 把案件 ID、现在的方案和 Critic 审核的结果交给下单那一侧，它给出风控结果（risk-rules spec「风控的输入和判定」）和要不要人工确认（confirmation-rules spec「案件方案的确认」），或者风控检查出错。风控结果写进案件记录，案件状态按下表转换（case-stages spec「风控」）：

| 下单那一侧给出 | 案件状态 |
| --- | --- |
| 风控通过或调整，要人工确认 | 进入等人工确认 |
| 风控通过或调整，不要人工确认 | 进入等下单 |
| 风控拒绝 | 结束：风控拒绝 |
| 风控检查出错 | 结束：系统故障 |

之后案件工作流 SHALL 等下单那一侧按案件 ID 送回结果，每收到一个按下表转换，直到案件结束：

| 送回的结果 | 适用的阶段 | 案件状态 |
| --- | --- | --- |
| 已确认 | 等人工确认 | 进入等下单 |
| 已拒绝 | 等人工确认 | 结束：人工拒绝 |
| 已超时（包括确认请求发不出去） | 等人工确认 | 结束：确认超时 |
| 订单已提交 | 等下单 | 结束：订单已提交 |
| 再校验作废 | 等下单 | 结束：再校验作废 |
| 方案被作废（order-flow spec「作废案件的方案」） | 等人工确认、等下单 | 结束：方案被作废 |
| 出错 | 等人工确认、等下单 | 结束：系统故障 |

- 等待的时候不调用模型，案件工作流不设等待的时限：确认超时和方案的有效期由下单那一侧处理
- 送回的结果不适用于当前阶段时 SHALL 报错，案件的运行出错停下
- 释放预留由下单那一侧负责（case-stages spec「结束原因」的"要释放预留"）

### Requirement: 复盘案件

复盘案件（每周复盘、卖出复盘）开始以后，案件工作流 SHALL 按最新一版快照调用 Reviewer，不组案件上下文、不唤醒 PM：交回复盘报告时按 case-stages spec「复盘案件」结束：复盘完成，报告的总结写进程序日志；调用失败见「模型全部不可用」。

### Requirement: 模型全部不可用

调用 PM、Critic、Reviewer 时，Agent 网关给出调用失败（agent-calls spec「一次调用」），案件工作流 SHALL 推送一条告警（discord-notification spec「告警」），写明案件、agent 和网关给出的说明，并按下表处理：

| agent | 阶段 | 处理 |
| --- | --- | --- |
| PM（研究） | 唤醒 PM | 结束：系统故障，没有结论 |
| PM（回应） | PM 回应 | 结束：系统故障，有结论 |
| Critic | Critic 审核，开仓类方案 | 结束：系统故障，有结论；案件记录写 Critic 不可用 |
| Critic | Critic 审核，退出类方案 | 跳过 Critic，进入风控，Critic 审核的结果是 Critic 不可用；案件记录写 Critic 不可用 |
| Reviewer | 复盘 | 结束：系统故障 |

子 agent 全部不可用时只是这个任务的 Result 是失败（agent-calls spec「子 agent 的任务」），SHALL NOT 告警，PM 照常继续。

#### Scenario: PM 不可用

- **WHEN** K-4 开始运行，PM 不可用
- **THEN** 结束：系统故障，没有结论；告警写明 K-4、PM 和说明

#### Scenario: PM 回应时不可用

- **GIVEN** K-1 的方案 P-1 被质询一次，在 PM 回应
- **WHEN** PM 不可用
- **THEN** 结束：系统故障，有结论；有一条告警

#### Scenario: Critic 不可用

- **GIVEN** K-1 的方案 P-1 在 Critic 审核；另一种情况下 K-3 的减仓方案在 Critic 审核
- **WHEN** Critic 不可用
- **THEN** K-1 结束：系统故障，有结论，方案没有交给下单那一侧
- **AND** K-3 进入风控，Critic 审核的结果是 Critic 不可用，交给下单那一侧
- **AND** 两个案件都有一条告警，案件记录都写了 Critic 不可用

#### Scenario: Reviewer 不可用

- **WHEN** K-5 开始运行，Reviewer 不可用
- **THEN** 结束：系统故障；有一条告警

#### Scenario: 子 agent 不可用不告警

- **WHEN** K-3 的 PM 派发新闻请求，News 的模型全部不可用
- **THEN** T-1 失败；没有告警；PM 照常再调用

### Requirement: 案件结束

案件结束时（案件状态变为已结束），案件工作流 SHALL：

- 写案件记录的结束：结束原因；Task 数是本案件 PM 派发出去的任务数加 Critic 用掉的补充研究额度（task-dispatch spec「本案件的任务和用量」）；调用次数是 Agent 网关为本案件记下的费用记录条数（call-budget spec「一个案件的费用记录」）
- 告诉 Agent 网关这个案件结束了（model-fallback spec「案件内不切回」）
- 写程序日志的案件阶段变化，写明结束原因
- 之后不再有进展（见「案件的进展」）

#### Scenario: Task 数和调用次数

- **GIVEN** K-1 的 PM 派发了 T-1、T-2，第二次派发里一个请求被拒绝；Critic 补充研究派发了 T-3；网关为 K-1 记下了 7 条费用记录
- **WHEN** K-1 结束：订单已提交
- **THEN** K-1 的案件记录：结束原因订单已提交，Task 数 3，调用次数 7

#### Scenario: 下一个案件从主模型开始

- **GIVEN** K-3 的 PM 用备用模型 p-2 调用成功
- **WHEN** K-3 结束，CCC 的下一个案件开始运行
- **THEN** 下一个案件的 PM 的第一次请求发给主模型 p-1

### Requirement: 崩溃恢复

进程重启以后，案件工作流 SHALL 从每个运行中的案件最后完成的一步接着运行：

- 已经交回的 agent 调用 SHALL NOT 再调用，对话和交回的一样
- 已经有 Result 的任务 SHALL NOT 再运行（agent-calls spec「子 agent 的任务」）
- 已经生成的快照版本不重新读数据（state-snapshot spec「同一版再生成」）
- 在等下单那一侧结果的案件接着等，重启以后送回的结果照常生效

#### Scenario: 派发以后重启

- **GIVEN** K-1 的 PM 派发价格请求和财报请求，T-1、T-2 都完成以后进程退出
- **WHEN** 进程重启
- **THEN** K-1 接着调用 PM，对话有派发任务的一轮；PM 第一次调用和 T-1、T-2 都没有再运行，网关没有多出费用记录

#### Scenario: 等人工确认时重启

- **GIVEN** K-1 在等人工确认时进程退出
- **WHEN** 进程重启以后送回已确认
- **THEN** K-1 进入等下单

### Requirement: 案件工作流的配置

案件工作流 SHALL 有下面的可配置项：

| 配置项 | 含义 | 默认值 | 取值 |
| --- | --- | --- | --- |
| 近期案件数 | 案件上下文里最多放这只股票最近结束的几个案件 | 3 | 不小于 0 |

结论最多重交次数和质询最多轮数用 case-stages spec「案件阶段的配置」的。取值不合法时 MUST 配置报错。

#### Scenario: 默认配置

- **WHEN** 不传任何配置项新建配置
- **THEN** 近期案件数是 3

#### Scenario: 配置不合法

- **WHEN** 近期案件数配置为 -1
- **THEN** 配置报错
