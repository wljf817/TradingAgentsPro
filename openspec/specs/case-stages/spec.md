# case-stages Specification

## Purpose

调度器用一个案件状态记录案件从唤醒 PM 到提交订单走到了哪一步：按 PM 的结论、Critic 的审核、PM 的回应、风控、人工确认、下单前再校验和下单的结果推进阶段，并记下案件以什么原因结束、结束时是否有结论。

## Requirements

### Requirement: 案件的状态

调度器 SHALL 用案件状态记录一个案件进行到哪里。状态只随收到的事件变化，每个事件给出新的状态，不读写存储。状态包含：

| 项 | 内容 |
| --- | --- |
| 阶段 | 见「案件的阶段」 |
| 方案的动作 | 结论里交易方案的动作：买入、加仓、减仓或清仓；没有方案时没有。买入、加仓是开仓类方案，减仓、清仓是退出类方案 |
| 有结论 | 是否已经有通过校验的结论，见「结束原因」 |
| 重交次数 | 结论校验不通过、退回 PM 重交的次数 |
| 质询轮次 | 开仓类方案被 Critic 质询、交给 PM 回应的次数 |
| Critic 审核的结果 | 方案离开 Critic 审核时的结果：通过、有分歧或 Critic 不可用；还没离开时没有 |
| 结束原因 | 结束以后才有，见「结束原因」 |

调用模型、方案的阶段由阶段推出（见「案件的阶段」），要释放预留由阶段、方案的动作和结束原因推出（见「结束原因」）。

新案件 SHALL 按开始时确定的案件类型（case-types spec「案件类型」）开始：复盘案件（每周复盘、卖出复盘）从复盘开始，其他案件从唤醒 PM 开始；都没有方案、没有结论，重交次数和质询轮次都是 0，没有 Critic 审核的结果和结束原因。

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 开仓案件：BBB（关注）的关注股事件，PM 的结论是开仓方案：买入 BBB，条款和 case-types spec 的基准方案条款相同（100 股，限价单，限价 50，止损价 45，紧急阈值 0.08）
- 退出案件：CCC（持仓）的持仓事件，PM 的结论是减仓（60 股，市价单）
- "开仓案件在 Critic 审核"指开仓案件的结论已经通过、进入 Critic 审核，还没有被质询过；退出案件同理
- "依次收到"指按列出的顺序把事件交给案件状态；THEN 里的"依次"对应每个事件之后的状态

#### Scenario: 新案件从唤醒 PM 开始

- **WHEN** 开仓案件开始；寻股开始
- **THEN** 阶段都是唤醒 PM，没有方案，没有结论，重交次数和质询轮次都是 0，没有 Critic 审核的结果和结束原因

#### Scenario: 复盘案件从复盘开始

- **WHEN** CCC 的卖出复盘开始；每周复盘开始
- **THEN** 阶段都是复盘，没有方案，没有结论

### Requirement: 案件的阶段

案件 SHALL 处于下表的阶段之一。"调用模型"就是 case-queue spec「并发上限」里的"还在调用模型的阶段"，"方案的阶段"就是 case-queue spec「队列的输入和决定」里方案的阶段，调用方用这两项组出队列的快照：

| 阶段 | 含义 | 调用模型 | 方案的阶段 |
| --- | --- | --- | --- |
| 唤醒 PM | PM 研究并提交结论；校验不通过时修改再提交 | 是 | 没有方案 |
| Critic 审核 | Critic 审核方案，包括它要求的补充研究 | 是 | 审核 |
| PM 回应 | PM 逐条回应 Critic 的质询 | 是 | 审核 |
| 风控 | 等风控检查的结果 | 否 | 审核 |
| 等人工确认 | 已经通过风控，等人确认 | 否 | 等人工确认 |
| 等下单 | 已经确认，等开盘和下单前再校验 | 否 | 等下单 |
| 复盘 | Reviewer 处理复盘案件 | 是 | 没有方案 |
| 已结束 | 案件结束，有结束原因 | 否：不再是运行中的案件 | 没有：方案已经提交订单或者随案件结束 |

- 复盘以外的案件离开调用模型的阶段以后 SHALL NOT 再回到调用模型的阶段
- 方案的阶段 SHALL 只往前走：审核 → 等人工确认 → 等下单

#### Scenario: 开仓案件走完各阶段

- **GIVEN** 开仓案件在唤醒 PM
- **WHEN** 依次收到：结论通过（买入）、Critic 通过、风控通过、已确认、订单已提交
- **THEN** 阶段依次是 Critic 审核、风控、等人工确认、等下单、已结束
- **AND** 调用模型依次是：是、否、否、否、否
- **AND** 方案的阶段依次是：审核、审核、等人工确认、等下单、没有

#### Scenario: PM 回应也在调用模型

- **GIVEN** 开仓案件在 Critic 审核
- **WHEN** Critic 质询
- **THEN** 阶段是 PM 回应，调用模型，方案的阶段是审核

#### Scenario: 唤醒 PM 和复盘调用模型、没有方案

- **WHEN** 开仓案件开始；CCC 的卖出复盘开始
- **THEN** 都调用模型，都没有方案的阶段

### Requirement: 唤醒 PM 和结论

唤醒 PM 阶段 SHALL 按 PM 提交的结论和它的校验结果转换。校验不通过包括两种：case-types spec「结论的校验」不通过；PM 用备用模型时提了被限制的决定（model-fallback spec「备用模型的限制」）。两种的转换相同：

| 事件 | 条件 | 结果 |
| --- | --- | --- |
| 结论校验不通过 | 重交次数小于"结论最多重交次数" | 留在唤醒 PM，重交次数加 1：退回 PM，带着不通过的原因在同一个案件里修改再提交 |
| 结论校验不通过 | 重交次数不小于"结论最多重交次数" | 结束：结论无效 |
| 结论通过 | 没有交易方案 | 结束：没有交易方案；有结论 |
| 结论通过 | 有交易方案 | 进入 Critic 审核，记下方案的动作；有结论 |

- 没有交易方案的结论（无动作、论点更新、跟进申请、升降级、股票池增删）SHALL NOT 经过 Critic
- 结论本身格式不合法（比如开仓方案没写止损价）由 Agent 网关校验输出格式时处理，不是这里的"校验不通过"

#### Scenario: 校验不通过时退回 PM 重交

- **GIVEN** 开仓案件在唤醒 PM
- **WHEN** 依次收到：结论校验不通过（研究不足）、结论校验不通过（研究不足）、结论通过（买入）
- **THEN** 依次是：唤醒 PM，重交次数 1；唤醒 PM，重交次数 2；Critic 审核，重交次数 2，有结论

#### Scenario: 备用模型的限制也退回 PM 重交

- **GIVEN** 开仓案件在唤醒 PM
- **WHEN** 依次收到：结论校验不通过（用备用模型时不能提这个决定）、结论通过（继续关注）
- **THEN** 依次是：唤醒 PM，重交次数 1；结束：没有交易方案，有结论

#### Scenario: 重交次数用完

- **GIVEN** 开仓案件在唤醒 PM，已经重交 2 次
- **WHEN** 结论校验不通过
- **THEN** 结束：结论无效，没有结论

#### Scenario: 不允许重交

- **GIVEN** 结论最多重交次数配置为 0，开仓案件在唤醒 PM
- **WHEN** 结论校验不通过
- **THEN** 结束：结论无效，没有结论

#### Scenario: 没有交易方案的结论直接结束

- **WHEN** BBB 的关注股事件结论通过（继续关注）；AAA 的候选评估结论通过（升级）；寻股结论通过（加入 DDD）
- **THEN** 都结束：没有交易方案，有结论，没有经过 Critic

#### Scenario: 有交易方案的结论进入 Critic 审核

- **WHEN** 开仓案件结论通过（买入）；退出案件结论通过（减仓）
- **THEN** 都进入 Critic 审核，有结论；方案的动作分别是买入、减仓

### Requirement: Critic 审核开仓类方案

Critic 审核买入或加仓方案时，SHALL 按 Critic 的结论和质询轮次转换：

| Critic 的结论 | 质询轮次 | 结果 |
| --- | --- | --- |
| 通过 | 任意 | 进入风控，Critic 审核的结果是通过 |
| 否决 | 任意 | 结束：Critic 否决 |
| 质询 | 小于"质询最多轮数" | 进入 PM 回应，质询轮次加 1 |
| 质询 | 不小于"质询最多轮数" | 进入风控，Critic 审核的结果是有分歧 |

- 一轮质询与回应是 Critic 质询一次、PM 回应一次；PM 维持或修改以后回到 Critic 审核（见「PM 回应」）。所以默认配置下 Critic 最多审 3 次，第 3 次只能通过、否决，或者仍然质询（有分歧）
- Critic 要求的补充研究在这一次审核中经 Agent 网关派发，结果回来以后 Critic 才给出结论；补充研究 SHALL NOT 算一轮质询，结果在 PM 回应时一并交给 PM
- 有分歧的方案照常经过风控，在人工确认时由人决定（见「人工确认」）

#### Scenario: 第一次审核就通过

- **GIVEN** 开仓案件在 Critic 审核
- **WHEN** Critic 通过
- **THEN** 进入风控，Critic 审核的结果是通过，质询轮次 0

#### Scenario: 质询以后交给 PM 回应

- **GIVEN** 开仓案件在 Critic 审核
- **WHEN** Critic 质询
- **THEN** 进入 PM 回应，质询轮次 1

#### Scenario: 两轮以后仍有分歧

- **GIVEN** 开仓案件在 Critic 审核
- **WHEN** 依次收到：Critic 质询、PM 维持、Critic 质询、PM 修改、Critic 质询
- **THEN** 依次是：PM 回应，轮次 1；Critic 审核；PM 回应，轮次 2；Critic 审核；风控，Critic 审核的结果是有分歧，轮次 2

#### Scenario: 最后一次审核通过或否决

- **GIVEN** 开仓案件质询满两轮，PM 第 2 次回应以后回到 Critic 审核
- **WHEN** Critic 通过
- **THEN** 进入风控，Critic 审核的结果是通过
- **WHEN** 同样的情况下 Critic 否决
- **THEN** 结束：Critic 否决

#### Scenario: 否决开仓方案

- **GIVEN** 开仓案件在 Critic 审核
- **WHEN** Critic 否决
- **THEN** 结束：Critic 否决，有结论

#### Scenario: 加仓也是开仓类方案

- **GIVEN** CCC 的持仓事件结论通过（加仓），在 Critic 审核
- **WHEN** Critic 质询
- **THEN** 进入 PM 回应，质询轮次 1
- **WHEN** 同样的情况下 Critic 否决
- **THEN** 结束：Critic 否决

#### Scenario: 补充研究不算一轮

- **GIVEN** 开仓案件在 Critic 审核，Critic 经 Agent 网关要求补充研究
- **WHEN** 补充研究的结果回来以前
- **THEN** 阶段仍是 Critic 审核，质询轮次 0
- **WHEN** 结果回来以后 Critic 质询
- **THEN** 进入 PM 回应，质询轮次 1

#### Scenario: 质询最多一轮

- **GIVEN** 质询最多轮数配置为 1，开仓案件在 Critic 审核
- **WHEN** 依次收到：Critic 质询、PM 维持、Critic 质询
- **THEN** 依次是：PM 回应，轮次 1；Critic 审核；风控，Critic 审核的结果是有分歧

### Requirement: PM 回应

PM 回应阶段 SHALL 按 PM 的回应转换：

| PM 的回应 | 结果 |
| --- | --- |
| 维持 | 回到 Critic 审核 |
| 修改 | 修改后的方案代替原来的方案，回到 Critic 审核 |
| 撤回 | 结束：PM 撤回 |

- 修改只改方案条款（见「Critic 审核和 PM 回应的格式」），方案的动作不变；要改决定、动作或论点，PM 撤回，在以后的案件里再提
- 只有开仓类方案会进入 PM 回应：退出类方案不交给 PM 回应（见「Critic 审核退出类方案」）

#### Scenario: PM 维持

- **GIVEN** 开仓案件被质询一次，在 PM 回应
- **WHEN** PM 维持
- **THEN** 回到 Critic 审核，质询轮次 1，方案的动作仍是买入

#### Scenario: PM 修改

- **GIVEN** 开仓案件被质询一次，在 PM 回应
- **WHEN** PM 修改，股数从 100 改为 60
- **THEN** 回到 Critic 审核，质询轮次 1，方案的动作仍是买入
- **AND** 60 股的方案代替原来的方案，Critic 下一次审核的是它

#### Scenario: PM 撤回

- **GIVEN** 开仓案件被质询一次，在 PM 回应
- **WHEN** PM 撤回
- **THEN** 结束：PM 撤回，有结论

### Requirement: Critic 审核退出类方案

Critic 审核减仓或清仓方案时只审一次，SHALL 按下表转换，不交给 PM 回应：

| Critic 的结论 | 结果 |
| --- | --- |
| 通过 | 进入风控，Critic 审核的结果是通过 |
| 质询（有异议） | 进入风控，Critic 审核的结果是有分歧 |
| 否决 | 和质询相同：Critic 不能否决退出类方案，按有异议处理 |

退出类方案的质询轮次 SHALL 一直是 0。

#### Scenario: 退出方案通过

- **GIVEN** 退出案件在 Critic 审核
- **WHEN** Critic 通过
- **THEN** 进入风控，Critic 审核的结果是通过

#### Scenario: 退出方案有异议

- **GIVEN** 退出案件在 Critic 审核
- **WHEN** Critic 质询
- **THEN** 进入风控，Critic 审核的结果是有分歧，质询轮次 0，没有经过 PM 回应

#### Scenario: Critic 否决退出方案按异议处理

- **GIVEN** 退出案件在 Critic 审核；另一个案件是 CCC 的持仓复查，结论通过（清仓，去向移出），在 Critic 审核
- **WHEN** 两个案件的 Critic 都否决
- **THEN** 都进入风控，Critic 审核的结果是有分歧，案件不结束

### Requirement: Critic 不可用

Critic 审核阶段，Critic 的主模型和备用模型全部不可用（Agent 网关对 Critic 返回失败）时，SHALL 按方案的动作转换，不论是第几次审核：

| 方案 | 结果 |
| --- | --- |
| 退出类 | 跳过 Critic，进入风控，Critic 审核的结果是 Critic 不可用 |
| 开仓类 | 结束：系统故障；有结论 |

Critic 不可用是系统故障，SHALL NOT 当作 Critic 的判断：开仓类方案不算被否决，退出类方案不算有异议。

#### Scenario: 退出方案跳过 Critic

- **GIVEN** 退出案件在 Critic 审核
- **WHEN** Critic 不可用
- **THEN** 进入风控，Critic 审核的结果是 Critic 不可用

#### Scenario: 开仓方案的案件按系统故障结束

- **GIVEN** 开仓案件在 Critic 审核
- **WHEN** Critic 不可用
- **THEN** 结束：系统故障，有结论
- **GIVEN** 开仓案件质询满两轮，PM 第 2 次回应以后回到 Critic 审核
- **WHEN** Critic 不可用
- **THEN** 结束：系统故障，有结论

### Requirement: 风控

风控阶段 SHALL 按风控的结果（risk-rules spec「风控的输入和判定」）转换：

| 风控的结果 | 结果 |
| --- | --- |
| 通过 | 进入等人工确认 |
| 调整 | 进入等人工确认；确认消息标明已被风控调整及原因（discord-notification spec） |
| 拒绝 | 结束：风控拒绝 |

- 风控拒绝 SHALL NOT 在同一个案件里退回 PM 重来：案件结束并记下原因，PM 在这只股票的下一个案件里看到
- Critic 审核的结果是有分歧或 Critic 不可用的方案，照常经过风控，结果不变

#### Scenario: 风控通过

- **GIVEN** 开仓案件 Critic 通过，在风控
- **WHEN** 风控通过
- **THEN** 进入等人工确认，Critic 审核的结果仍是通过

#### Scenario: 风控调整

- **GIVEN** 开仓案件 Critic 通过，在风控
- **WHEN** 风控调整（股数从 100 调为 40）
- **THEN** 进入等人工确认

#### Scenario: 风控拒绝

- **GIVEN** 开仓案件 Critic 通过，在风控
- **WHEN** 风控拒绝；或者处于降级模式，风控因为降级模式拒绝
- **THEN** 结束：风控拒绝，有结论

#### Scenario: 有分歧的方案照常过风控

- **GIVEN** 开仓案件质询满两轮仍有分歧，在风控
- **WHEN** 风控通过
- **THEN** 进入等人工确认，Critic 审核的结果仍是有分歧

### Requirement: 人工确认

本变更里所有交易方案（开仓类和退出类）SHALL 在通过风控以后进入等人工确认；哪些方案可以不经确认由「人工确认的规则」决定。等人工确认阶段 SHALL 按确认的结果转换：

| 确认的结果 | 结果 |
| --- | --- |
| 已确认 | 进入等下单 |
| 已拒绝 | 结束：人工拒绝 |
| 已超时 | 结束：确认超时 |

调用方 SHALL 按 Critic 审核的结果在确认消息里附上说明；人按确认就算对分歧做了决定：

| Critic 审核的结果 | 确认消息附上 |
| --- | --- |
| 通过 | 不附 |
| 有分歧 | PM 和 Critic 双方的意见：PM 的方案理由和各轮回应，Critic 的质询或异议 |
| Critic 不可用 | 注明 Critic 不可用，方案没有经过审核 |

确认请求发不出去时按确认超时处理（discord-notification spec）。

#### Scenario: 人工确认

- **GIVEN** 开仓案件 Critic 通过、风控通过，在等人工确认
- **WHEN** 已确认
- **THEN** 进入等下单
- **AND** 确认消息不附双方意见

#### Scenario: 人工拒绝

- **GIVEN** 开仓案件在等人工确认
- **WHEN** 已拒绝
- **THEN** 结束：人工拒绝，有结论

#### Scenario: 确认超时

- **GIVEN** 退出案件在等人工确认
- **WHEN** 已超时，或者确认请求发不出去
- **THEN** 结束：确认超时，有结论

#### Scenario: 有分歧的方案带着双方意见交给人

- **GIVEN** 开仓案件质询满两轮仍有分歧；退出案件 Critic 有异议；两个案件都通过风控，在等人工确认
- **WHEN** 调用方发出确认请求
- **THEN** 两条确认消息都附上 PM 和 Critic 双方的意见
- **WHEN** 人按了确认
- **THEN** 都进入等下单

#### Scenario: Critic 不可用的退出方案注明

- **GIVEN** 退出案件因为 Critic 不可用跳过审核，通过风控，在等人工确认
- **WHEN** 调用方发出确认请求
- **THEN** 确认消息注明 Critic 不可用

### Requirement: 等下单

等下单阶段 SHALL 按下单前再校验（pre-order-recheck spec）和下单的结果转换：

| 事件 | 结果 |
| --- | --- |
| 订单已提交：再校验通过或调整，执行模块已经建立订单 | 结束：订单已提交 |
| 再校验作废：再校验的结论是拒绝（超过有效期、价格偏离过大、跌破止损价、规则不通过、方案已结束） | 结束：再校验作废 |

- 再校验调整时按更小的股数下单，不重新人工确认，案件同样以订单已提交结束
- 盘后确认的方案在等下单阶段等到开盘；券商断线、再校验暂时做不了时也留在等下单。这期间案件仍然占着这只股票（case-queue spec「同一只股票一次一个案件」）
- 订单提交以后由执行模块跟踪到终态，和案件无关
- 再校验作废和风控拒绝一样，SHALL NOT 在同一个案件里重来

#### Scenario: 订单已提交

- **GIVEN** 开仓案件在等下单
- **WHEN** 再校验通过，订单已提交
- **THEN** 结束：订单已提交，有结论

#### Scenario: 再校验调整后照样提交

- **GIVEN** 开仓案件在等下单
- **WHEN** 再校验调整（股数从 100 调为 40），按 40 股提交订单
- **THEN** 结束：订单已提交，没有重新进入等人工确认

#### Scenario: 再校验作废

- **GIVEN** 开仓案件在等下单
- **WHEN** 再校验因为价格偏离过大作废
- **THEN** 结束：再校验作废，有结论

#### Scenario: 盘后确认、断线时留在等下单

- **GIVEN** 退出案件 2026-10-14 21:00Z（盘后）确认，在等下单
- **WHEN** 2026-10-15 开盘前；开盘以后券商断线、还没有再校验的结果
- **THEN** 都仍在等下单，不调用模型，方案的阶段是等下单
- **WHEN** 恢复以后再校验因为超过有效期作废
- **THEN** 结束：再校验作废

### Requirement: 方案被作废和紧急退出中止

案件 SHALL 按下表因为队列的决定结束：

| 事件 | 适用的阶段 | 结果 |
| --- | --- | --- |
| 方案被作废：这只股票有新案件排队（case-queue spec「新案件排队时作废开仓方案」） | 等人工确认、等下单 | 结束：方案被作废 |
| 紧急退出中止（case-queue spec「紧急退出」） | 复盘以外的任何运行中的阶段 | 结束：紧急退出中止 |

- 紧急退出时调用方 SHALL 只中止案件，不再对它的方案报方案被作废，结束原因是紧急退出中止
- 新案件的 PM 想买，就重新提方案、重新确认

#### Scenario: 等人工确认时被作废

- **GIVEN** 开仓案件在等人工确认
- **WHEN** BBB 的新闻事件排队，方案被作废
- **THEN** 结束：方案被作废，有结论

#### Scenario: 等下单时被作废

- **GIVEN** 开仓案件在等下单
- **WHEN** 方案被作废
- **THEN** 结束：方案被作废

#### Scenario: 唤醒 PM 时被紧急退出中止

- **GIVEN** CCC 的持仓复查在唤醒 PM
- **WHEN** CCC 触发紧急退出，案件被中止
- **THEN** 结束：紧急退出中止，没有结论

#### Scenario: 结论以后被紧急退出中止

- **GIVEN** 退出案件在等人工确认；另一种情况下退出案件在等下单；另一种情况下 CCC 的持仓事件结论是加仓，在风控
- **WHEN** CCC 触发紧急退出，案件被中止
- **THEN** 都结束：紧急退出中止，有结论

### Requirement: 系统故障

案件 SHALL 能在任何运行中的阶段（包括复盘）因系统故障结束，结束原因是系统故障。系统故障包括：PM 或 Reviewer 的调用失败（Agent 网关返回失败，比如主模型和备用模型全部超时或不可用）、开仓类方案的 Critic 不可用（见「Critic 不可用」）、风控检查或下单流程出错。

- 系统故障 SHALL NOT 被当作投资判断：故障发生在结论通过校验以前的，案件没有结论；以后的，结论仍然算数，只是方案不执行
- 调用预算用完不是系统故障：Agent 网关不因为预算用完拒绝运行中案件的调用，开始了的案件照常运行到结束（call-budget spec「已经开始的案件」）

#### Scenario: PM 的调用失败

- **GIVEN** CCC 的持仓复查在唤醒 PM
- **WHEN** PM 的主模型和备用模型都超时，Agent 网关返回失败
- **THEN** 结束：系统故障，没有结论

#### Scenario: PM 回应时调用失败

- **GIVEN** 开仓案件被质询一次，在 PM 回应
- **WHEN** PM 的调用失败
- **THEN** 结束：系统故障，有结论

#### Scenario: 风控和下单流程出错

- **GIVEN** 开仓案件在风控；另一种情况下退出案件在等下单
- **WHEN** 风控检查出错；下单流程出错
- **THEN** 都结束：系统故障，有结论

### Requirement: 复盘案件

复盘案件 SHALL 只有开始和结束，复盘阶段按下表转换：

| 事件 | 结果 |
| --- | --- |
| 复盘完成 | 结束：复盘完成 |
| 系统故障 | 结束：系统故障 |

复盘案件不会被紧急退出中止（case-queue spec「紧急退出」），也没有结论。

#### Scenario: 复盘完成

- **GIVEN** CCC 的卖出复盘在复盘
- **WHEN** 复盘完成
- **THEN** 结束：复盘完成，没有结论

#### Scenario: 复盘失败

- **GIVEN** 每周复盘在复盘
- **WHEN** Reviewer 的调用失败
- **THEN** 结束：系统故障，没有结论

### Requirement: 结束原因

结束原因 SHALL 是下表之一：

| 结束原因 | 含义 | 从哪个阶段结束 | 有结论 |
| --- | --- | --- | --- |
| 没有交易方案 | 结论通过校验，没有交易方案 | 唤醒 PM | 是 |
| 订单已提交 | 再校验通过或调整，订单已经建立 | 等下单 | 是 |
| Critic 否决 | Critic 否决开仓类方案 | Critic 审核 | 是 |
| PM 撤回 | PM 回应时撤回方案 | PM 回应 | 是 |
| 风控拒绝 | 风控的结果是拒绝 | 风控 | 是 |
| 人工拒绝 | 人按了拒绝 | 等人工确认 | 是 |
| 确认超时 | 确认超时，或者确认请求发不出去 | 等人工确认 | 是 |
| 再校验作废 | 下单前再校验的结论是拒绝 | 等下单 | 是 |
| 方案被作废 | 这只股票有新案件排队 | 等人工确认、等下单 | 是 |
| 紧急退出中止 | 这只股票触发紧急风险退出 | 复盘以外的运行中的阶段 | 唤醒 PM 时中止的否，其余是 |
| 结论无效 | 结论重交用完仍不通过 | 唤醒 PM | 否 |
| 系统故障 | 调用失败、开仓类方案的 Critic 不可用、风控或下单流程出错 | 任何运行中的阶段 | 结论通过以前否，以后是；复盘否 |
| 复盘完成 | Reviewer 完成复盘 | 复盘 | 否 |

- 有结论：结论通过校验时就有了，之后不论怎样结束都 SHALL NOT 改变
- 复盘以外的案件结束时没有结论（结论通过以前因系统故障或紧急退出中止，或者结论无效），SHALL NOT 当作投资判断：到期的复查日和催化剂截止日期不算不续期，由「收盘检查」顺延
- 案件以订单已提交以外的原因结束、并且有方案时，状态 SHALL 给出"要释放预留"，调用方据此释放这个方案的预留（risk-reservations spec「方案或订单结束时释放预留」，没有预留时什么都不做）；其他情况都不要释放
- 结束原因记进案件记录，这只股票下一个案件的上下文里能看到

#### Scenario: 没有结论就结束

- **WHEN** CCC 的持仓复查在唤醒 PM 时因系统故障结束；因紧急退出中止；重交用完以后结论无效
- **THEN** 三种情况都没有结论，不当作不续期

#### Scenario: 结论以后的系统故障不改变有结论

- **GIVEN** CCC 的持仓复查结论通过（加仓，附论点更新），在 Critic 审核
- **WHEN** Critic 不可用
- **THEN** 结束：系统故障，有结论；论点更新仍然算数，加仓方案不执行

#### Scenario: 结束时释放预留

- **GIVEN** 开仓案件在等人工确认，方案已经预留
- **WHEN** 已超时，案件结束
- **THEN** 要释放预留，调用方释放方案的预留
- **GIVEN** 开仓案件在 Critic 审核，方案还没有预留
- **WHEN** Critic 否决，案件结束
- **THEN** 要释放预留；调用方释放时什么都不做，也不报错
- **GIVEN** 开仓案件在等下单
- **WHEN** 订单已提交，案件结束
- **THEN** 不要释放预留，预留由订单的成交和结束更新
- **WHEN** BBB 的关注股事件结论通过（继续关注）；开仓案件在唤醒 PM 时因系统故障结束；开仓案件还在 Critic 审核
- **THEN** 都不要释放预留：前两个没有方案，最后一个还没结束

### Requirement: 已结束的案件和不适用的事件

已结束的案件收到任何事件 SHALL 原样不变，不报错。运行中的案件收到不适用于当前阶段的事件 SHALL 报错，状态不变。每个事件适用的阶段：

| 事件 | 适用的阶段 |
| --- | --- |
| 结论校验不通过、结论通过 | 唤醒 PM |
| Critic 的结论、Critic 不可用 | Critic 审核 |
| PM 的回应 | PM 回应 |
| 风控的结果 | 风控 |
| 已确认、已拒绝、已超时 | 等人工确认 |
| 订单已提交、再校验作废 | 等下单 |
| 方案被作废 | 等人工确认、等下单 |
| 紧急退出中止 | 复盘以外的运行中的阶段 |
| 系统故障 | 任何运行中的阶段 |
| 复盘完成 | 复盘 |

#### Scenario: 已结束的案件不变

- **GIVEN** 开仓案件在等人工确认时被紧急退出中止
- **WHEN** 之后才到已确认；方案被作废；系统故障
- **THEN** 都不报错，案件仍然是紧急退出中止

#### Scenario: 不适用的事件报错

- **WHEN** 开仓案件在唤醒 PM 时收到 Critic 通过、PM 维持、风控通过、已确认、订单已提交、方案被作废、复盘完成
- **THEN** 都报错，状态不变
- **WHEN** 开仓案件在等下单时收到结论通过、Critic 不可用、已确认
- **THEN** 都报错，状态不变
- **WHEN** 开仓案件在风控时收到方案被作废；CCC 的卖出复盘在复盘时收到紧急退出中止、结论通过
- **THEN** 都报错，状态不变

### Requirement: Critic 审核和 PM 回应的格式

Critic 的每次审核 SHALL 包含：

| 项 | 要求 |
| --- | --- |
| 结论 | 通过、质询或否决 |
| 理由 | 不能为空 |
| 质询 | 逐条写出的问题，每条不能为空；结论是质询时至少一条，通过和否决不写 |
| 引用的 Result | Result ID，可以为空；补充研究的 Result 也在这里引用 |

PM 对一轮质询的回应 SHALL 包含：

| 项 | 要求 |
| --- | --- |
| 决定 | 维持、修改或撤回 |
| 逐条回应 | 至少一条，每条不能为空 |
| 修改后的方案条款 | 只有修改写，维持和撤回不写；按开仓方案检查（case-types spec 和 risk-rules spec「交易方案的格式」）：股数、限价单和限价、止损价、紧急阈值必须写，有效期和允许价格偏离可以不写，价格符合最小变动单位 |

不符合时 SHALL 报格式错误。回应的条数和质询的条数是否一致不检查。

#### Scenario: 合法的审核

- **WHEN** Critic 给出：质询，理由"止损太近"，质询两条"止损价 45 离限价只有 10%，财报前波动更大""引用的 R-2 是三天前的数据"，引用 R-5
- **THEN** 格式合法
- **WHEN** Critic 给出：通过，理由"风险收益比合理"，不写质询
- **THEN** 格式合法

#### Scenario: 质询和结论不一致

- **WHEN** Critic 给出：质询，不写质询；或者通过，写了一条质询；或者否决，写了一条质询
- **THEN** 都报格式错误

#### Scenario: 审核的理由或质询为空

- **WHEN** Critic 给出：否决，理由为空；或者质询，其中一条质询为空
- **THEN** 都报格式错误

#### Scenario: 合法的回应

- **WHEN** PM 回应：修改，两条回应，新的方案条款是 60 股、限价单、限价 50、止损价 46、紧急阈值 0.08
- **THEN** 格式合法
- **WHEN** PM 回应：撤回，一条回应，不写方案条款
- **THEN** 格式合法

#### Scenario: 修改和方案条款不一致

- **WHEN** PM 回应：修改，不写方案条款；或者维持，写了方案条款
- **THEN** 都报格式错误

#### Scenario: 修改后的方案条款按开仓方案检查

- **WHEN** PM 回应：修改，新的方案条款分别是：市价单；限价单但没写止损价；没写紧急阈值；没写股数；限价 50.005
- **THEN** 都报格式错误

#### Scenario: 没有回应

- **WHEN** PM 回应：维持，回应为空；或者其中一条回应为空
- **THEN** 都报格式错误

### Requirement: 案件阶段的配置

案件阶段 SHALL 有下面的可配置项：

| 配置项 | 含义 | 默认值 | 取值 |
| --- | --- | --- | --- |
| 结论最多重交次数 | 结论校验不通过时，PM 在同一个案件里最多重交几次 | 2 | 不小于 0 |
| 质询最多轮数 | 开仓类方案的质询与回应最多几轮 | 2 | 不小于 1 |

取值不合法时 MUST 配置报错。

#### Scenario: 默认配置

- **WHEN** 不传任何配置项新建配置
- **THEN** 结论最多重交次数是 2，质询最多轮数是 2

#### Scenario: 配置不合法

- **WHEN** 结论最多重交次数配置为 -1；质询最多轮数配置为 0
- **THEN** 都配置报错

#### Scenario: 改配置改变转换

- **WHEN** 结论最多重交次数配置为 0，或者质询最多轮数配置为 1
- **THEN** 转换分别如「不允许重交」「质询最多一轮」所述
