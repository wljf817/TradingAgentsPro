# case-queue Specification

## Purpose

调度器根据一份快照决定下一个启动哪些排队的案件、哪些排队的案件不再运行，以及新案件排队或紧急风险退出时作废哪些还没提交订单的方案、中止哪个正在运行的案件。

## Requirements

### Requirement: 队列的输入和决定

调度器 SHALL 提供两个决定，都只根据调用方给出的一份快照计算，不读写存储：

- 队列的决定：启动哪些排队的案件（每个带开始时确定的案件类型，按启动的先后排列）、哪些排队的案件不再运行、作废哪些方案
- 紧急退出的决定：给定一只股票，中止哪个运行中的案件、作废哪些方案（见「紧急退出」）

快照包含：

| 项 | 内容 |
| --- | --- |
| 排队的案件 | 案件 ID、触发（case-types spec「触发」）、触发时刻；按入队的先后排列 |
| 运行中的案件 | 案件 ID、开始时确定的案件类型、股票（寻股和每周复盘没有）、是否还在调用模型的阶段（见「并发上限」） |
| 还没提交订单的方案 | 案件给出的方案：方案 ID、股票、动作、阶段（见下表）。手工录入的方案不在里面 |
| 股票的状态 | 股票池里的股票和持仓各自的状态；不在里面的股票既不在股票池也不是持仓 |
| 正在紧急退出的股票 | 紧急风险退出的清仓卖单还没结束（成交、被拒或撤销）的股票 |
| 是否处于降级模式 | degraded-mode spec「进入和退出降级模式」：降级和等待对账都算 |
| 普通预算是否用完、寻股预算是否用完 | 由调用预算给出 |

方案的阶段：

| 阶段 | 含义 |
| --- | --- |
| 审核 | PM 写出方案以后、交给人工确认以前：Critic 审核、风控检查 |
| 等人工确认 | 已经通过风控，在等人工确认 |
| 等下单 | 已经确认，等开盘或下单前再校验，还没提交订单 |

动作是买入、加仓的是开仓类方案，减仓、清仓的是退出类方案。

调用方 SHALL 在快照的任何一项变化以后（新案件排队、案件结束、方案进入新的阶段、股票状态变化、紧急退出结束、降级模式或预算标志变化）取得队列的决定并执行：先作废方案、释放预留，再结束不再运行的案件，最后按顺序启动案件。

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 股票：AAA、DDD 是候选；BBB 是关注；CCC、EEE 是持仓
- 触发时刻都在 2026-10-14（周三），只写时刻；排队的案件按列出的顺序入队
- 没有运行中的案件，没有还没提交订单的方案，没有股票在紧急退出，不处于降级模式，普通预算和寻股预算都没用完
- 方案：P-1 是 BBB 的买入方案，P-2 是 CCC 的加仓方案，P-3 是 CCC 的减仓方案
- 运行中的案件写明"调用模型"（还在调用模型的阶段）或"等人工确认"（已经过了这个阶段，方案在等人工确认）
- 用触发称呼排队的案件，比如"CCC 的新闻事件"；用开始时确定的案件类型称呼启动的案件，比如"CCC 的持仓事件"
- 场景里没有写到的启动、不再运行、作废和中止，都是没有

#### Scenario: 队列为空

- **WHEN** 没有排队的案件，取得队列的决定
- **THEN** 不启动案件，没有不再运行的案件，不作废方案

#### Scenario: 启动的案件带开始时确定的类型

- **GIVEN** 排队：BBB 的关注复查日到期（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 BBB 的关注复查：问题"是否还值得关注？"，优先级 5

### Requirement: 排队的案件按现在的状态确定类型

每次取得队列的决定时，SHALL 对每个排队的案件按这时的股票状态确定案件类型（case-types spec「开始运行时确定案件类型」）：

- 确定不了类型的案件 SHALL 不再运行，不等轮到它
- 确定得了类型的案件按这时的类型和优先级排队；启动时 SHALL 用这次确定的类型

#### Scenario: 排队期间状态变了按新的类型排

- **GIVEN** 并发上限配置为 1；排队：AAA 的新闻事件（13:00Z）、BBB 的新闻事件（14:00Z）
- **WHEN** BBB 买入成交、变为持仓以后，取得队列的决定
- **THEN** 启动 BBB 的持仓事件（优先级 2）；AAA 的新闻事件（候选股事件，优先级 6）留在队列里

#### Scenario: 确定不了类型的马上不再运行

- **GIVEN** 运行中：CCC 的持仓事件（调用模型）；排队：CCC 的持仓复查日到期（20:00Z）
- **WHEN** CCC 的止损单成交、变为候选以后，取得队列的决定
- **THEN** CCC 的持仓复查日到期不再运行，虽然 CCC 的案件还在运行、本来也轮不到它

#### Scenario: 不在股票池的股票的事件不再运行

- **GIVEN** 排队：AAA 的新闻事件（14:00Z）
- **WHEN** AAA 被删除以后，取得队列的决定
- **THEN** AAA 的新闻事件不再运行

### Requirement: 启动的顺序

队列的决定 SHALL 按下表的顺序依次检查排队的案件（这次不再运行的除外），能启动的就启动，直到达到并发上限；不能启动的跳过，接着看下一个：

| 顺序 | 比较 | 先启动 |
| --- | --- | --- |
| 1 | 优先级（case-types spec「案件类型」） | 数字小的 |
| 2 | 触发时刻 | 早的 |
| 3 | 入队的先后 | 先入队的 |

能不能启动见「同一只股票一次一个案件」「降级模式」「调用预算」，名额见「并发上限」。

#### Scenario: 不同股票按优先级启动

- **GIVEN** 排队：AAA 的有新候选（13:00Z）、BBB 的新闻事件（14:00Z）、CCC 的新闻事件（15:00Z）
- **WHEN** 并发上限配置为 1，取得队列的决定
- **THEN** 启动 CCC 的持仓事件
- **WHEN** 用默认的并发上限，取得队列的决定
- **THEN** 依次启动 CCC 的持仓事件、BBB 的关注股事件、AAA 的候选评估

#### Scenario: 同优先级按触发时刻

- **GIVEN** 并发上限配置为 1；排队：AAA 的新闻事件（15:00Z）、DDD 的价格和成交量异动事件（14:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 DDD 的候选股事件

#### Scenario: 触发时刻相同按入队的先后

- **GIVEN** 并发上限配置为 1；排队：DDD 的有新候选（20:00Z）、AAA 的有新候选（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 DDD 的候选评估

### Requirement: 并发上限

运行中还在调用模型的案件 SHALL 不超过并发上限（见「队列配置」）。是否还在调用模型的阶段由调用方给出：

| 运行中的案件所处的阶段 | 计入并发上限 |
| --- | --- |
| 唤醒 PM 到 Critic 审核结束 | 计入 |
| 风控、等人工确认、等下单 | 不计入 |
| 复盘案件 | 一直计入 |

- 这次最多启动"并发上限减去调用模型的案件数"个案件，不大于 0 时不启动
- 被跳过的案件不占名额
- 上限只限制启动：队列的决定 SHALL NOT 中止运行中的案件，超出上限时（比如调低并发上限以后重启）只是不再启动

#### Scenario: 并发上限的边界

- **GIVEN** 运行中：EEE 的持仓复查（调用模型）、寻股（调用模型）；排队：BBB 的新闻事件（14:00Z）、AAA 的有新候选（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 BBB 的关注股事件；AAA 的有新候选留在队列里
- **WHEN** 另有每周复盘也在运行，取得队列的决定
- **THEN** 不启动

#### Scenario: 等人工确认的案件不计入

- **GIVEN** 运行中：EEE 的持仓复查（调用模型）、CCC 的持仓事件（等人工确认，P-3 等人工确认）、BBB 的关注股事件（等人工确认，P-1 等人工确认）；排队：AAA 的有新候选（20:00Z）、DDD 的有新候选（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 依次启动 AAA 的候选评估、DDD 的候选评估

#### Scenario: 复盘案件计入

- **GIVEN** 运行中：CCC 的卖出复盘、每周复盘、EEE 的持仓复查，都在调用模型；排队：BBB 的新闻事件（14:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不启动

#### Scenario: 超出上限不中止

- **GIVEN** 调低并发上限以后重启，运行中：CCC 的持仓事件、EEE 的持仓复查、寻股、每周复盘，都在调用模型；排队：BBB 的新闻事件（14:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不启动；四个运行中的案件照常运行

### Requirement: 同一只股票一次一个案件

排队的案件 SHALL 在下表的情况下不能启动：

| 排队的案件 | 不能启动的情况 |
| --- | --- |
| 针对单只股票、复盘以外的案件 | 这只股票有复盘以外的案件在运行（不论在哪个阶段）；这只股票正在紧急退出；这次已经启动了这只股票的案件 |
| 寻股 | 有寻股在运行，或者这次已经启动了一个 |
| 复盘案件 | 没有：不看这只股票有没有案件在运行；它运行时也不挡这只股票的其他案件 |

- 不能启动的跳过，不挡别的股票的案件
- 运行中的案件 SHALL NOT 被打断，优先级更高的案件也只能排队；紧急退出除外（见「紧急退出」）
- 股票空闲以后，它排队的案件按「启动的顺序」一次启动一个

#### Scenario: 股票忙时跳过，不挡别的股票

- **GIVEN** 运行中：CCC 的持仓复查（调用模型）；排队：CCC 的价格和成交量异动事件，标注为持仓风险级别（14:00Z）；BBB 的新闻事件（15:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 BBB 的关注股事件；CCC 的事件留在队列里，CCC 的持仓复查照常运行

#### Scenario: 等人工确认的案件也占着这只股票

- **GIVEN** 运行中：CCC 的持仓事件（等人工确认，P-3 等人工确认）；排队：CCC 的持仓复查日到期（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不启动，虽然名额没满

#### Scenario: 同一只股票排队的案件依次运行

- **GIVEN** 排队：CCC 的持仓复查日到期（20:00Z）、CCC 的新闻事件（14:00Z）
- **WHEN** 取得队列的决定
- **THEN** 只启动 CCC 的持仓事件
- **WHEN** CCC 的持仓事件结束以后，取得队列的决定
- **THEN** 启动 CCC 的持仓复查

#### Scenario: 正在紧急退出的股票

- **GIVEN** CCC 正在紧急退出；排队：CCC 的跟进（13:00Z）、CCC 的价格和成交量异动事件，标注为持仓风险级别（15:00Z）、BBB 的新闻事件（15:01Z）
- **WHEN** 取得队列的决定
- **THEN** 只启动 BBB 的关注股事件
- **WHEN** CCC 的清仓卖单成交、CCC 变为候选、紧急退出结束以后，取得队列的决定
- **THEN** CCC 的跟进不再运行；启动 CCC 的候选股事件

#### Scenario: 寻股同一时间只跑一个

- **GIVEN** 运行中：寻股；排队：股票池候选不足（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不启动
- **GIVEN** 没有运行中的案件；排队：股票池候选不足（14:00Z）、股票池候选不足（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 只启动 14:00Z 的寻股

#### Scenario: 复盘案件不受限制

- **GIVEN** 运行中：CCC 的持仓事件（调用模型）；排队：CCC 的卖出成交（15:00Z）、每周固定时间（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 依次启动 CCC 的卖出复盘、每周复盘
- **GIVEN** 运行中：CCC 的卖出复盘；排队：CCC 的新闻事件（15:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 CCC 的持仓事件
- **GIVEN** CCC 正在紧急退出；排队：CCC 的卖出成交（15:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 CCC 的卖出复盘

### Requirement: 降级模式

处于降级模式时，队列的决定 SHALL 不启动任何案件：

| 降级模式 | 启动 | 不再运行和作废 |
| --- | --- | --- |
| 处于（降级或等待对账） | 不启动，排队的案件留在队列里 | 照常 |
| 不处于 | 按「启动的顺序」 | 照常 |

- 新的触发照常排队；运行中的案件不中止
- 退出降级模式（对账完成、健康监控回到正常）以后，积压的整个队列按「启动的顺序」启动：持仓案件优先级最高，自然在前；非持仓的案件也照常启动
- 紧急退出的决定不看降级模式（见「紧急退出」）

#### Scenario: 降级期间不启动

- **GIVEN** 处于降级模式；运行中：EEE 的持仓复查（调用模型）；排队：AAA 的有新候选（20:00Z）、BBB 的关注复查日到期（20:00Z）、CCC 的持仓复查日到期（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不启动；EEE 的持仓复查照常运行

#### Scenario: 降级期间照常不再运行和作废

- **GIVEN** 处于降级模式；运行中：BBB 的关注股事件（等下单），P-1 等下单；排队：BBB 的新闻事件（14:00Z）、CCC 的持仓复查日到期（20:00Z）
- **WHEN** CCC 的止损单成交、变为候选以后，取得队列的决定
- **THEN** CCC 的持仓复查日到期不再运行；作废 P-1；不启动

#### Scenario: 恢复后按优先级运行积压的案件

- **GIVEN** 排队的案件同「降级期间不启动」，EEE 的持仓复查已经结束
- **WHEN** 退出降级模式以后，取得队列的决定
- **THEN** 依次启动 CCC 的持仓复查、BBB 的关注复查、AAA 的候选评估
- **WHEN** 并发上限配置为 2，取得队列的决定
- **THEN** 依次启动 CCC 的持仓复查、BBB 的关注复查；AAA 的有新候选留在队列里

### Requirement: 调用预算

排队的案件 SHALL 按案件类型用的预算决定能不能启动：

| 案件类型 | 用的预算 | 普通预算用完 | 寻股预算用完 |
| --- | --- | --- | --- |
| 持仓风险事件、持仓事件、持仓复查、持仓催化剂复查、持仓跟进 | 普通预算，用完后改用持仓保留预算 | 照常启动 | 照常启动 |
| 关注股事件、关注复查、关注催化剂复查、关注跟进、候选股事件、候选评估 | 普通预算 | 留在队列里 | 照常启动 |
| 寻股 | 寻股预算 | 照常启动 | 留在队列里 |
| 每周复盘、卖出复盘 | 普通预算 | 留在队列里 | 照常启动 |

- 留在队列里的案件跳过，不占名额；预算恢复（下一个交易日）以后按「启动的顺序」启动
- 预算怎么算、什么时候算用完不在本 spec 的范围内；持仓保留预算也用完时，健康监控进入降级模式（见「降级模式」）

#### Scenario: 普通预算用完后持仓案件照常启动

- **GIVEN** 普通预算用完；排队：CCC 的价格和成交量异动事件，标注为持仓风险级别（14:00Z）；EEE 的持仓复查日到期（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 依次启动 CCC 的持仓风险事件、EEE 的持仓复查

#### Scenario: 普通预算用完后关注和候选的案件留在队列里

- **GIVEN** 普通预算用完；排队：BBB 的新闻事件（14:00Z）、AAA 的有新候选（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不启动

#### Scenario: 普通预算用完不挡寻股

- **GIVEN** 普通预算用完；并发上限配置为 1；排队：BBB 的新闻事件（14:00Z）、股票池候选不足（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动寻股

#### Scenario: 寻股预算用完

- **GIVEN** 寻股预算用完；排队：股票池候选不足（14:00Z）、AAA 的有新候选（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 启动 AAA 的候选评估；寻股留在队列里

#### Scenario: 复盘用普通预算

- **GIVEN** 普通预算用完；排队：CCC 的卖出成交（15:00Z）、每周固定时间（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不启动

#### Scenario: 预算恢复后按优先级运行

- **GIVEN** 普通预算用完；排队：每周固定时间（20:00Z）、AAA 的有新候选（20:00Z）、BBB 的新闻事件（14:00Z）；取得队列的决定时不启动
- **WHEN** 普通预算恢复以后，取得队列的决定
- **THEN** 依次启动 BBB 的关注股事件、AAA 的候选评估、每周复盘

### Requirement: 新案件排队时作废开仓方案

队列的决定 SHALL 按下表作废方案。"这只股票有案件在排队"指这只股票有复盘以外的案件在排队，并且这次确定得了类型；因为股票忙、降级、预算或并发上限暂时启动不了的也算，这次启动的也算：

| 方案 | 阶段 | 这只股票有案件在排队 | 结果 |
| --- | --- | --- | --- |
| 开仓类 | 审核 | 有 | 不作废：属于运行中的案件，运行中不打断 |
| 开仓类 | 等人工确认 | 有 | 作废 |
| 开仓类 | 等下单 | 有 | 作废 |
| 开仓类 | 任何阶段 | 没有，或者只有复盘在排队 | 不作废 |
| 退出类 | 任何阶段 | 有 | 不作废；排队的案件等运行中的案件结束再运行 |

- 这是随时成立的条件：每次决定都检查，所以新案件排队时、方案进入等人工确认时都会作废
- 作废以后，调用方 SHALL 释放方案的预留（risk-reservations spec「方案或订单结束时释放预留」）；方案所属的案件怎么结束不在本 spec 的范围内。新案件的 PM 想买，就重新提方案、重新确认

#### Scenario: 还在审核的开仓方案不作废

- **GIVEN** 运行中：BBB 的关注股事件（调用模型），P-1 在审核；排队：BBB 的关注复查日到期（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不作废；不启动

#### Scenario: 等人工确认时有新案件排队就作废

- **GIVEN** 运行中：BBB 的关注股事件（等人工确认），P-1 等人工确认
- **WHEN** BBB 的新闻事件（15:00Z）排队以后，取得队列的决定
- **THEN** 作废 P-1；不启动，BBB 的新闻事件等 BBB 的关注股事件结束

#### Scenario: 已经确认的开仓方案也作废

- **GIVEN** 运行中：BBB 的关注股事件（等下单），P-1 等下单
- **WHEN** BBB 的关注复查日到期（20:00Z）排队以后，取得队列的决定
- **THEN** 作废 P-1；不启动
- **WHEN** BBB 的关注股事件因方案被作废结束以后，取得队列的决定
- **THEN** 启动 BBB 的关注复查

#### Scenario: 方案进入等人工确认时已经有案件在排队

- **GIVEN** 运行中：BBB 的关注股事件（调用模型），P-1 在审核；排队：BBB 的新闻事件（15:00Z）
- **WHEN** P-1 通过风控、进入等人工确认，BBB 的关注股事件不再调用模型以后，取得队列的决定
- **THEN** 作废 P-1

#### Scenario: 加仓也是开仓类

- **GIVEN** 运行中：CCC 的持仓复查（等人工确认），P-2 等人工确认；排队：CCC 的新闻事件（15:00Z）
- **WHEN** 取得队列的决定
- **THEN** 作废 P-2

#### Scenario: 只有复盘在排队不作废

- **GIVEN** 运行中：CCC 的持仓复查（等人工确认），P-2 等人工确认；排队：CCC 的卖出成交（15:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不作废；启动 CCC 的卖出复盘

#### Scenario: 退出类方案不作废

- **GIVEN** 运行中：CCC 的持仓事件（等人工确认），P-3 等人工确认；排队：CCC 的持仓复查日到期（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不作废；不启动
- **WHEN** P-3 确认、进入等下单以后，取得队列的决定
- **THEN** 不作废；不启动
- **WHEN** P-3 的订单提交、CCC 的持仓事件结束以后，取得队列的决定
- **THEN** 启动 CCC 的持仓复查

#### Scenario: 暂时启动不了的排队案件也算

- **GIVEN** 普通预算用完；运行中：BBB 的关注股事件（等下单），P-1 等下单；排队：BBB 的关注复查日到期（20:00Z）
- **WHEN** 取得队列的决定
- **THEN** 作废 P-1；不启动

#### Scenario: 确定不了类型的排队案件不算

- **GIVEN** 运行中：BBB 的关注股事件（等人工确认），P-1 等人工确认；排队：BBB 的有新候选（20:00Z，BBB 还是候选时开出，之后升级为关注）
- **WHEN** 取得队列的决定
- **THEN** BBB 的有新候选不再运行；不作废

#### Scenario: 别的股票的案件不影响

- **GIVEN** 运行中：BBB 的关注股事件（等人工确认），P-1 等人工确认；排队：AAA 的新闻事件（15:00Z）
- **WHEN** 取得队列的决定
- **THEN** 不作废；启动 AAA 的候选股事件

### Requirement: 紧急退出

一只股票触发紧急风险退出（emergency-exit spec）时，调用方 SHALL 在撤单和生成清仓方案之前取得这只股票的紧急退出的决定，中止决定里的案件、作废决定里的方案并释放预留，然后把这只股票记为正在紧急退出，直到清仓卖单结束。紧急退出的决定 SHALL 按下表给出：

| 对象 | 结果 |
| --- | --- |
| 这只股票正在运行的、复盘以外的案件 | 中止，不论在哪个阶段 |
| 这只股票正在运行的复盘案件 | 不中止 |
| 这只股票还没提交订单的方案 | 全部作废：开仓类和退出类，不论阶段 |
| 这只股票排队的案件 | 不动：留在队列里，紧急退出结束后按新的状态运行（见「同一只股票一次一个案件」） |
| 别的股票的案件和方案 | 不动 |

- 不看降级模式、预算和并发上限
- 中止的案件怎么结束不在本 spec 的范围内
- 组合熔断清仓全部持仓时，对每只持仓各取一次

#### Scenario: 中止运行中的案件并作废它的方案

- **GIVEN** 运行中：CCC 的持仓事件（等人工确认），P-3 等人工确认
- **WHEN** CCC 触发紧急退出，取得 CCC 的紧急退出的决定
- **THEN** 中止 CCC 的持仓事件；作废 P-3

#### Scenario: 开仓类和退出类、各个阶段的方案都作废

- **GIVEN** 运行中：CCC 的持仓复查（调用模型），P-3 在审核
- **WHEN** 取得 CCC 的紧急退出的决定
- **THEN** 中止 CCC 的持仓复查；作废 P-3
- **GIVEN** 运行中：CCC 的持仓事件（等下单），P-2 等下单
- **WHEN** 取得 CCC 的紧急退出的决定
- **THEN** 中止 CCC 的持仓事件；作废 P-2

#### Scenario: 复盘案件不中止

- **GIVEN** 运行中：CCC 的卖出复盘，以及 CCC 的持仓事件（等下单），P-2 等下单
- **WHEN** 取得 CCC 的紧急退出的决定
- **THEN** 中止 CCC 的持仓事件，不中止 CCC 的卖出复盘；作废 P-2

#### Scenario: 排队的案件和别的股票不动

- **GIVEN** 排队：CCC 的新闻事件（15:00Z）；运行中：BBB 的关注股事件（等人工确认），P-1 等人工确认
- **WHEN** 取得 CCC 的紧急退出的决定
- **THEN** 不中止，不作废；CCC 的新闻事件留在队列里

#### Scenario: 降级模式和预算用完时照常

- **GIVEN** 处于降级模式，普通预算用完；运行中：CCC 的持仓事件（等人工确认），P-3 等人工确认
- **WHEN** 取得 CCC 的紧急退出的决定
- **THEN** 中止 CCC 的持仓事件；作废 P-3

### Requirement: 队列配置

并发上限 SHALL 是可配置项：同一时间还在调用模型的案件最多这么多个。默认值 3，MUST 至少为 1，否则配置报错。

#### Scenario: 默认配置

- **WHEN** 不传任何配置项新建配置
- **THEN** 并发上限是 3

#### Scenario: 配置不合法

- **WHEN** 并发上限配置为 0
- **THEN** 配置报错

#### Scenario: 改成 1

- **GIVEN** 并发上限配置为 1；排队：BBB 的新闻事件（14:00Z）、AAA 的新闻事件（15:00Z）
- **WHEN** 取得队列的决定
- **THEN** 只启动 BBB 的关注股事件
