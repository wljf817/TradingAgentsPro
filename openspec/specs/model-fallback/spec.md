# model-fallback Specification

## Purpose

规定 Agent 网关怎样在主模型不可用时按顺序切换备用模型：每个 agent 的模型配置和厂商校验，什么算不可用、每次尝试的超时，切换顺序、案件内不切回、按模型的熔断，并给出 PM 和 Critic 是否还有可用的模型、实际使用的模型、切换的事件，以及 PM 用备用模型时不能提的决定。

## Requirements

### Requirement: 模型的配置

Agent 网关 SHALL 从配置得到六个 agent（PM、News、Quant、Fundamentals、Critic、Reviewer）各自的模型：一个主模型，加上按顺序的 0 个或多个备用模型。每个模型写：

| 项 | 要求 |
| --- | --- |
| 厂商 | 模型出自哪家公司，不是调用的平台；非空的文字，去掉首尾空白并转成小写 |
| 模型名 | 非空的文字，去掉首尾空白，大小写不变 |

- 厂商和模型名都相同就是同一个模型；不同 agent 可以用同一个模型
- 缺少任何一个 agent、某项不符合上表、同一个 agent 的主模型和备用模型里出现同一个模型，都 MUST 配置报错
- 配置在启动时读取，运行中不变

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 当前时刻 2026-10-14 15:00Z
- 基准模型的配置，模型写作"厂商/模型名"，下文只写模型名，比如 p-1 就是 anthropic/p-1：

  | agent | 主模型 | 备用模型（按顺序） |
  | --- | --- | --- |
  | PM | anthropic/p-1 | anthropic/p-2、google/p-3 |
  | Critic | openai/c-1 | openai/c-2 |
  | News、Quant、Fundamentals | google/s-1 | openai/s-2 |
  | Reviewer | anthropic/p-1 | 没有 |

- 案件 K-1、K-2。"PM 在 K-1 调用"指为 K-1 的 PM 开始一次调用，Critic、Reviewer 同理，都没有截止时间；"News 在 K-1 为 T-1 调用"指为 News 的任务 T-1 开始一次调用，T-1 的截止时间是 2026-10-14 15:05Z
- "p-1 失败（限流）"指正在进行的这次尝试失败，调用错误是限流；"p-1 成功"指这次尝试拿到了输出
- "p-1 不可用（限流）"指 p-1 在这次调用里的两次尝试都失败，第二次的调用错误是限流；括号省略时是超时。"p-1 在 t 不可用"指在某次调用里，p-1 在时刻 t 不可用
- 开始时所有模型都正常，没有不可用过；"p-1 冷却到 t"指 p-1 在冷却中，冷却结束的时刻是 t
- 时刻没有写明时，都是当前时刻
- GIVEN 里的几步依次进行；一个 WHEN 里用"；"或"或者"隔开的几种情况，各自从 GIVEN 的数据开始；同一个场景里的几组 WHEN、THEN，除非写"接着"，也各自从 GIVEN 的数据开始

#### Scenario: 基准配置

- **WHEN** 用基准模型的配置
- **THEN** 配置正确；PM 的模型依次是 p-1、p-2、p-3；Reviewer 只有主模型 p-1；Reviewer 和 PM 的主模型是同一个模型

#### Scenario: 厂商去掉空白、转成小写

- **WHEN** PM 的主模型的厂商写成 " Anthropic "
- **THEN** 配置正确，厂商是 anthropic，PM 和 Reviewer 的主模型仍是同一个模型

#### Scenario: 配置不合法

- **WHEN** 不配 Reviewer；News 的主模型的厂商是 "  "；Critic 的备用模型的模型名是 ""；PM 的备用模型依次是 p-2、p-1；PM 的备用模型依次是 p-2、p-2；PM 的备用模型是 Anthropic/p-1
- **THEN** 都配置报错

### Requirement: 厂商校验

Critic 的主模型和备用模型 SHALL 都和 PM 的主模型和备用模型不同厂商，按转成小写以后的厂商比较；不满足时 MUST 配置报错。只校验 Critic 和 PM 之间，子 agent 和 Reviewer 用什么厂商都可以。bootstrap 启动时读取配置，配置报错就 SHALL 拒绝启动。

#### Scenario: 基准配置通过

- **WHEN** 用基准模型的配置：PM 是 anthropic 和 google，Critic 是 openai；News 的备用模型 s-2 也是 openai，Reviewer 也是 anthropic
- **THEN** 配置正确

#### Scenario: Critic 和 PM 有相同的厂商

- **WHEN** Critic 的备用模型改为 google/c-2（PM 的 p-3 也是 google）；或者 PM 的备用模型 p-3 改为 openai/p-3；或者 Critic 的主模型改为 Anthropic/c-1
- **THEN** 都配置报错

### Requirement: 什么算不可用

一次调用是网关为一个 agent 拿一次输出，可能经过几个模型、每个模型几次尝试；一次尝试是向一个模型发一次请求。尝试 SHALL 是下面两种结果之一：

- 成功：模型给出了输出。输出格式不合法也是成功：task-dispatch spec 记失败、不重新调用、不切换模型
- 失败：没有拿到输出，调用错误是下表之一

| 调用错误 | 含义 |
| --- | --- |
| 超时 | 超过这次尝试的超时（见「尝试的超时」）仍没有输出 |
| 连接失败 | 连不上厂商的服务 |
| 限流 | 厂商因为请求太频繁拒绝 |
| 额度或余额用完 | 厂商因为账户的额度或余额用完拒绝；本系统的调用预算用完不在此列 |
| 认证失败 | 厂商因为密钥无效或没有权限拒绝 |
| 服务端出错 | 厂商的服务出错或过载 |
| 其他调用错误 | 以上之外、没有拿到输出的错误 |

- 尝试失败以后 SHALL 重试同一个模型：每个模型在一次调用里最多尝试"重试次数"加 1 次（默认 2 次），重试前不等待，不分调用错误的种类
- 一个模型的尝试都失败，就是这个模型在这次调用里不可用，按「切换顺序」换下一个；不可用的原因是最后一次尝试的调用错误
- 模型的每次不可用和每次成功都计入它的熔断状态（见「熔断」）；重试中间的失败不单独计

#### Scenario: 失败以后重试

- **GIVEN** PM 在 K-1 调用，先试 p-1
- **WHEN** p-1 失败（限流）
- **THEN** 重试 p-1，这是 p-1 的第 2 次尝试
- **WHEN** 接着 p-1 成功
- **THEN** 调用成功，实际使用的模型是 p-1，没有切换；p-1 正常，没有记下不可用

#### Scenario: 重试用完才不可用

- **GIVEN** PM 在 K-1 调用
- **WHEN** p-1 失败（超时），再失败（连接失败）
- **THEN** p-1 不可用，原因是连接失败；换到 p-2，这是 p-2 的第 1 次尝试

#### Scenario: 每种调用错误都算

- **GIVEN** PM 在 K-1 调用
- **WHEN** p-1 的两次尝试都失败，调用错误分别是超时、连接失败、限流、额度或余额用完、认证失败、服务端出错、其他调用错误
- **THEN** 都是 p-1 不可用，原因是这个调用错误，换到 p-2

#### Scenario: 格式不合法不算不可用

- **GIVEN** News 在 K-1 为 T-1 调用
- **WHEN** s-1 成功，输出是不是 JSON 的文字"看多，理由见上"
- **THEN** 调用成功，实际使用的模型是 s-1，不切换；s-1 正常，没有记下不可用
- **AND** T-1 的 Result 是失败，原因是格式不合法，模型是 s-1（task-dispatch spec）

### Requirement: 尝试的超时

每次尝试 SHALL 有超时：

| agent | 每次尝试的超时 |
| --- | --- |
| News、Quant、Fundamentals | "子 agent 的单次调用超时"（默认 60 秒）和离任务截止时间还剩的时间，两者中较短的 |
| PM、Critic、Reviewer | "PM、Critic、Reviewer 的单次调用超时"（默认 180 秒） |

- 子 agent 的调用带任务的截止时间（task-dispatch spec「超时」）。现在不早于截止时间时 SHALL NOT 再开始尝试，这次调用停止：停止不是全部不可用，不给出调用失败，也不告警，这个任务由 task-dispatch spec「超时」记超时
- 停止时那次失败已经让模型不可用的，照样计入熔断
- PM、Critic、Reviewer 的调用没有截止时间
- 配置保证子 agent 的主模型和第一个备用模型的全部尝试放得进任务时限（见「备用模型的配置」）

#### Scenario: 两类 agent 的超时

- **WHEN** News 在 K-1 为 T-1 调用
- **THEN** 先试 s-1，超时 60 秒
- **WHEN** PM 在 K-1 调用；或者 Critic 在 K-1 调用；或者 Reviewer 在 K-1 调用
- **THEN** 第一次尝试的超时都是 180 秒

#### Scenario: 主模型和第一个备用模型放得进任务时限

- **GIVEN** News 在 K-1 为 T-1 调用
- **WHEN** s-1 在 15:01:00Z 失败，在 15:02:00Z 又失败
- **THEN** s-1 不可用，换到 s-2，超时 60 秒
- **WHEN** 接着 s-2 在 15:03:00Z 失败，在 15:04:00Z 又失败
- **THEN** 全部不可用，说明是"模型都不可用：google/s-1 超时；openai/s-2 超时"

#### Scenario: 超时不超过离截止时间还剩的时间

- **WHEN** 2026-10-14 15:04:30Z 才开始 News 为 T-1 的调用
- **THEN** 先试 s-1，超时 30 秒
- **WHEN** 2026-10-14 15:04:00Z 开始
- **THEN** 先试 s-1，超时 60 秒

#### Scenario: 到了截止时间就停止

- **GIVEN** 2026-10-14 15:04:00Z 开始 News 为 T-1 的调用，s-1 在 15:04:10Z 失败（连接失败），重试 s-1
- **WHEN** 15:05:00Z s-1 又失败
- **THEN** 这次调用停止：不换 s-2，不是全部不可用；s-1 记下一次不可用
- **WHEN** 15:04:59Z s-1 又失败
- **THEN** s-1 不可用，换到 s-2，超时 1 秒
- **WHEN** 2026-10-14 15:05:00Z 才开始 News 为 T-1 的调用
- **THEN** 停止，不尝试任何模型

#### Scenario: PM、Critic、Reviewer 没有截止时间

- **GIVEN** PM 在 K-1 调用
- **WHEN** 2026-10-14 16:00Z p-1 失败
- **THEN** 重试 p-1，超时 180 秒

### Requirement: 切换顺序

一次调用 SHALL 从本案件这个 agent 的起点（见「案件内不切回」）开始，按配置的顺序逐个尝试：

- 冷却中的模型（见「熔断」）SHALL 直接跳过、不尝试；被跳过的模型在这次调用里也算不可用，原因是冷却中，但不计入熔断
- 一个模型不可用或者被跳过以后，换到配置顺序里它后面的下一个模型，这是一次切换（见「切换的事件」）
- 起点和它后面的模型都不可用时，这次调用 SHALL 是全部不可用，给出调用失败和说明，作为告警的依据：子 agent 的任务由调用方交给 task-dispatch spec「调用失败」；PM、Critic、Reviewer 由调用方交给案件状态（case-stages spec「Critic 不可用」「系统故障」）
- 说明 SHALL 按先后列出这次调用里每个不可用的模型和原因，形如"模型都不可用：anthropic/p-1 超时；anthropic/p-2 冷却中；google/p-3 限流"

#### Scenario: 主模型不可用，换第一个备用模型

- **GIVEN** PM 在 K-1 调用
- **WHEN** p-1 不可用，再 p-2 成功
- **THEN** 调用成功，实际使用的模型是 p-2，是备用模型

#### Scenario: 按配置顺序逐个换

- **GIVEN** PM 在 K-1 调用
- **WHEN** p-1 不可用，p-2 不可用（限流），再 p-3 成功
- **THEN** 依次试了 p-1、p-2、p-3，实际使用的模型是 p-3，是备用模型

#### Scenario: 全部不可用

- **GIVEN** PM 在 K-1 调用
- **WHEN** p-1 不可用，p-2 不可用（限流），p-3 不可用（连接失败）
- **THEN** 全部不可用，说明是"模型都不可用：anthropic/p-1 超时；anthropic/p-2 限流；google/p-3 连接失败"

#### Scenario: 没有备用模型

- **GIVEN** Reviewer 在 K-1 调用
- **WHEN** p-1 不可用（服务端出错）
- **THEN** 全部不可用，说明是"模型都不可用：anthropic/p-1 服务端出错"

#### Scenario: 跳过冷却中的模型

- **GIVEN** p-2 冷却到 15:05Z，PM 在 K-1 调用
- **WHEN** p-1 不可用
- **THEN** 跳过 p-2，换到 p-3
- **WHEN** 接着 p-3 不可用（限流）
- **THEN** 全部不可用，说明是"模型都不可用：anthropic/p-1 超时；anthropic/p-2 冷却中；google/p-3 限流"

#### Scenario: 起点在冷却中

- **GIVEN** p-1 冷却到 15:05Z
- **WHEN** PM 在 K-1 调用
- **THEN** 跳过 p-1，第一次尝试是 p-2

#### Scenario: 全部在冷却中

- **GIVEN** p-1、p-2、p-3 都冷却到 15:05Z
- **WHEN** PM 在 K-1 调用
- **THEN** 不尝试任何模型，全部不可用，说明是"模型都不可用：anthropic/p-1 冷却中；anthropic/p-2 冷却中；google/p-3 冷却中"

### Requirement: 案件内不切回

一个 agent 在一个案件里 SHALL 有一个起点，开始时是主模型：

- 调用成功用的模型在配置顺序里排在起点后面时，起点 SHALL 改为这个模型；排在前面或者就是起点时不变。起点只往后移，比如同一个 agent 并行的两次调用
- 本案件这个 agent 之后的调用都从起点开始，SHALL NOT 尝试配置顺序里起点前面的模型，即使它们已经恢复
- 全部不可用、到了截止时间停止，都不改变起点
- 起点按案件和 agent 分开：别的 agent、别的案件不受影响，新的案件从主模型开始
- 网关 SHALL 给出本案件一个 agent 的起点和它是不是备用模型
- 案件结束时调用方 SHALL 告诉网关，网关清掉这个案件的起点

#### Scenario: 切到备用模型以后不切回

- **GIVEN** PM 在 K-1 调用，p-1 不可用，p-2 成功
- **WHEN** PM 在 K-1 再调用一次
- **THEN** K-1 的 PM 的起点是 p-2，是备用模型；第一次尝试是 p-2，不试 p-1

#### Scenario: 起点不可用时只往后换

- **GIVEN** PM 在 K-1 调用，p-1 不可用，p-2 成功
- **WHEN** PM 在 K-1 调用，p-2 不可用，p-3 成功
- **THEN** K-1 的 PM 的起点改为 p-3
- **WHEN** 接着 PM 在 K-1 调用，p-3 不可用
- **THEN** 全部不可用，说明是"模型都不可用：google/p-3 超时"，不回到 p-1 和 p-2

#### Scenario: 用主模型成功不改变起点

- **WHEN** PM 在 K-1 调用，p-1 成功
- **THEN** K-1 的 PM 的起点是 p-1，不是备用模型

#### Scenario: 全部不可用不改变起点

- **GIVEN** PM 在 K-1 调用，p-1、p-2、p-3 都不可用
- **WHEN** PM 在 K-1 再调用一次
- **THEN** K-1 的 PM 的起点仍是 p-1，第一次尝试是 p-1

#### Scenario: 并行的调用不让起点往回移

- **GIVEN** News 在 K-1 为 T-1 和 T-2 各开始一次调用，都先试 s-1
- **WHEN** T-1 的调用里 s-1 不可用，s-2 成功；再 T-2 的调用里 s-1 成功
- **THEN** K-1 的 News 的起点是 s-2；T-2 的调用实际使用的模型是 s-1，不是备用模型

#### Scenario: 按案件和 agent 分开

- **GIVEN** News 在 K-1 为 T-1 调用，s-1 不可用，s-2 成功
- **WHEN** Quant 在 K-1 调用；或者 News 在 K-2 调用
- **THEN** 第一次尝试都是 s-1

#### Scenario: 案件结束以后清掉

- **GIVEN** K-1 和 K-2 的 PM 都是 p-1 不可用、p-2 成功，起点都是 p-2
- **WHEN** K-1 结束
- **THEN** K-1 的 PM 的起点是 p-1；K-2 的 PM 的起点仍是 p-2

### Requirement: 熔断

每个模型 SHALL 有一个熔断状态，按模型计，不分 agent 和案件：几个 agent 共用一个模型时，它们的不可用和成功都计入同一个状态。状态是下面三种之一：

- 正常：记着上次成功以来连续的不可用
- 冷却中：现在早于冷却结束的时刻，调用时直接跳过
- 冷却结束：现在不早于冷却结束的时刻，之后还没有成功过；调用时可以再试

状态只在这个模型不可用和成功时变化，被跳过不算：

| 当前状态 | 事件 | 之后的状态 |
| --- | --- | --- |
| 正常 | 成功 | 正常，连续的不可用清零 |
| 正常 | 不可用，算上这次，连续的不可用不到"熔断的连续不可用次数"（默认 3） | 正常，记下这次 |
| 正常 | 不可用，最近连续的 3 次里最早一次到这次超过"熔断的时间窗口"（默认 10 分钟） | 正常，记下这次 |
| 正常 | 不可用，最近连续的 3 次里最早一次到这次不超过时间窗口 | 冷却中，冷却到这次的时刻加"冷却时间"（默认 5 分钟）；连续的不可用清零 |
| 冷却中 | 不可用 | 冷却中，冷却结束的时刻不变 |
| 冷却中 | 成功 | 正常 |
| 冷却结束 | 不可用 | 冷却中，冷却到这次的时刻加冷却时间 |
| 冷却结束 | 成功 | 正常 |

- 冷却中收到的不可用和成功，来自冷却开始以前已经在进行的调用
- 状态 SHALL 放在内存里：网关新建以后所有模型都是正常，进程重启以后从头算；案件内的起点（见「案件内不切回」）同样放在内存里
- 网关 SHALL 给出冷却中的模型和各自冷却结束的时刻，由调用方交给健康监控记录

#### Scenario: 不到 3 次不冷却

- **WHEN** p-1 在 14:58Z、15:00Z 不可用
- **THEN** p-1 正常，连续不可用 2 次；PM 在 K-2 调用时先试 p-1

#### Scenario: 连续 3 次不可用就冷却

- **WHEN** p-1 在 14:52Z、14:56Z、15:00Z 不可用
- **THEN** p-1 冷却到 15:05Z

#### Scenario: 时间窗口的边界

- **WHEN** p-1 在 14:50:00Z、14:55Z、15:00:00Z 不可用
- **THEN** p-1 冷却到 15:05Z
- **WHEN** p-1 在 14:49:59Z、14:55Z、15:00:00Z 不可用
- **THEN** p-1 正常
- **WHEN** 接着 p-1 在 15:01Z 不可用
- **THEN** p-1 冷却到 15:06Z：最近连续的 3 次是 14:55Z、15:00Z、15:01Z

#### Scenario: 成功让连续的不可用清零

- **WHEN** p-1 在 14:56Z、14:58Z 不可用，14:59Z 成功，15:00Z 不可用
- **THEN** p-1 正常，连续不可用 1 次
- **WHEN** s-1 在 14:56Z、14:58Z 不可用，14:59Z 给出格式不合法的输出，15:00Z 不可用
- **THEN** s-1 正常，连续不可用 1 次

#### Scenario: 冷却中再不可用不延长

- **GIVEN** p-1 在 14:52Z、14:56Z、15:00Z 不可用，冷却到 15:05Z
- **WHEN** 15:03Z p-1 在冷却以前就开始的调用里不可用
- **THEN** p-1 仍冷却到 15:05Z

#### Scenario: 冷却中成功就恢复

- **GIVEN** p-1 冷却到 15:05Z
- **WHEN** 15:03Z p-1 在冷却以前就开始的调用里成功
- **THEN** p-1 正常；15:03Z PM 在 K-2 调用时先试 p-1

#### Scenario: 冷却结束的边界

- **GIVEN** p-1 冷却到 15:05Z
- **WHEN** 15:04:59Z PM 在 K-1 调用
- **THEN** 跳过 p-1，第一次尝试是 p-2
- **WHEN** 15:05:00Z PM 在 K-1 调用
- **THEN** 第一次尝试是 p-1

#### Scenario: 冷却结束以后又不可用就再冷却

- **GIVEN** p-1 冷却到 15:05Z
- **WHEN** 15:06Z p-1 不可用
- **THEN** p-1 冷却到 15:11Z

#### Scenario: 冷却结束以后成功就恢复正常

- **GIVEN** p-1 冷却到 15:05Z
- **WHEN** 15:06Z p-1 成功，接着 15:07Z p-1 不可用
- **THEN** p-1 正常，连续不可用 1 次

#### Scenario: 几个 agent 共用一个模型

- **WHEN** PM 的调用里 p-1 在 14:52Z、14:56Z 不可用，Reviewer 的调用里 p-1 在 15:00Z 不可用
- **THEN** p-1 冷却到 15:05Z
- **AND** 15:01Z PM 在 K-2 调用时跳过 p-1；Reviewer 在 K-2 调用时全部不可用，说明是"模型都不可用：anthropic/p-1 冷却中"

#### Scenario: 被跳过不计入熔断

- **GIVEN** p-1 冷却到 15:05Z
- **WHEN** 15:01Z PM 在 K-1 调用、15:02Z PM 在 K-2 调用，都跳过 p-1
- **THEN** p-1 仍冷却到 15:05Z

#### Scenario: 给出冷却中的模型

- **GIVEN** p-1 冷却到 15:05Z，c-1 冷却到 15:08Z
- **WHEN** 15:00Z 取冷却中的模型
- **THEN** p-1 冷却到 15:05Z，c-1 冷却到 15:08Z
- **WHEN** 15:05Z 取冷却中的模型
- **THEN** 只有 c-1，冷却到 15:08Z

#### Scenario: 进程重启以后从头算

- **GIVEN** p-1 冷却到 15:05Z；K-1 的 PM 的起点是 p-2
- **WHEN** 进程重启、网关新建以后，15:01Z PM 在 K-1 调用
- **THEN** 没有冷却中的模型，第一次尝试是 p-1

### Requirement: 还有可用的模型

网关 SHALL 给出一个 agent 是否还有可用的模型：它的主模型或者任何一个备用模型不在冷却中就算有。

- 只看熔断状态，不看案件里的起点：不可用过、但没有冷却的模型仍算可用
- PM 和 Critic 的这一项就是 degraded-mode spec「健康检查」的"PM 是否还有可用的模型"和"Critic 是否还有可用的模型"，由调用方交给健康监控

#### Scenario: 都正常

- **WHEN** 取 PM 和 Critic 是否还有可用的模型
- **THEN** 都还有

#### Scenario: 还有一个不在冷却中就算有

- **GIVEN** p-1 和 p-2 冷却到 15:05Z
- **WHEN** 取 PM 是否还有可用的模型
- **THEN** 还有

#### Scenario: 全部在冷却中

- **GIVEN** p-1、p-2、p-3 都冷却到 15:05Z
- **WHEN** 15:00Z 取 PM 和 Critic 是否还有可用的模型
- **THEN** PM 没有，Critic 还有
- **WHEN** 15:05Z 取 PM 是否还有可用的模型
- **THEN** 还有
- **GIVEN** c-1 和 c-2 都冷却到 15:05Z
- **WHEN** 15:00Z 取 Critic 是否还有可用的模型
- **THEN** 没有

#### Scenario: 不可用但没有冷却仍算可用

- **GIVEN** PM 在 K-1 调用，p-1、p-2、p-3 都不可用
- **WHEN** 取 PM 是否还有可用的模型
- **THEN** 还有：三个模型都只不可用一次，都不在冷却中

### Requirement: 实际使用的模型

调用成功时网关 SHALL 给出实际使用的模型：成功的那个模型，以及它是不是这个 agent 的备用模型（不是这个 agent 的主模型就是备用模型）。调用方把它写进子 agent 任务的 Result（task-dispatch spec「Result 的格式」）；PM 的结论和 Critic 的审核用的模型，由调用方写进案件记录。

#### Scenario: 主模型和备用模型

- **WHEN** PM 在 K-1 调用，p-1 成功
- **THEN** 实际使用的模型是 p-1，不是备用模型
- **WHEN** PM 在 K-1 调用，p-1 不可用，p-2 成功
- **THEN** 实际使用的模型是 p-2，是备用模型
- **WHEN** News 在 K-1 为 T-1 调用，s-1 不可用，s-2 成功
- **THEN** 实际使用的模型是 s-2，是备用模型

#### Scenario: 按 agent 判断是不是备用模型

- **WHEN** Reviewer 在 K-1 调用，p-1 成功
- **THEN** 实际使用的模型是 p-1，不是备用模型

### Requirement: 切换的事件

每次切换网关 SHALL 给出一个切换的事件，调用方写进程序日志：

| 项 | 内容 |
| --- | --- |
| 案件、agent | 这次调用所属的案件和 agent |
| 从 | 不可用或者被跳过的模型 |
| 到 | 配置顺序里它后面的下一个模型 |
| 原因 | "从"的模型最后一次尝试的调用错误；被跳过时是冷却中 |
| 时刻 | 切换的时刻 |

- 一次换一个：连续跳过几个冷却中的模型，就有几个事件
- 重试不是切换；最后一个模型不可用以后没有下一个，不给出切换的事件，全部不可用由调用方告警和写日志

#### Scenario: 不可用以后切换

- **GIVEN** PM 在 K-1 调用
- **WHEN** 15:02Z p-1 不可用（限流）
- **THEN** 切换的事件：K-1，PM，从 p-1 到 p-2，原因是限流，时刻 15:02Z

#### Scenario: 跳过冷却中的模型也是切换

- **GIVEN** p-2 冷却到 15:05Z，PM 在 K-1 调用
- **WHEN** 15:01Z p-1 不可用（连接失败）
- **THEN** 依次两个切换的事件：从 p-1 到 p-2，原因是连接失败；从 p-2 到 p-3，原因是冷却中；时刻都是 15:01Z

#### Scenario: 一开始就跳过

- **GIVEN** p-1 冷却到 15:05Z
- **WHEN** PM 在 K-1 调用
- **THEN** 切换的事件：K-1，PM，从 p-1 到 p-2，原因是冷却中，时刻 15:00Z

#### Scenario: 重试和全部不可用没有切换的事件

- **WHEN** PM 在 K-1 调用，p-1 失败一次，重试成功
- **THEN** 没有切换的事件
- **WHEN** Reviewer 在 K-1 调用，p-1 不可用
- **THEN** 没有切换的事件，全部不可用

### Requirement: 备用模型的限制

收到 PM 的结论时，提交结论的那次调用实际使用的是备用模型的话，网关 SHALL 检查结论的决定（case-types spec 持仓、关注、候选的结论）：决定在"PM 用备用模型时不能提的决定"（默认开仓方案、加仓、升级）里时，给出被限制的决定；否则通过。

- 用主模型时不限制；寻股的结论没有决定，不限制；PM 以外的 agent 不限制
- 被限制时，调用方 SHALL 把它当作结论校验不通过交给案件状态（case-stages spec「唤醒 PM 和结论」）：退回 PM 在同一个案件里修改再提交，原因是"用备用模型时不能提这个决定"，计入重交次数。PM 仍从这个备用模型开始（见「案件内不切回」），可以改提其他决定
- 调用方先查这一项，通过以后再做 case-types spec「结论的校验」

结论用 case-types spec 的基准数据。

#### Scenario: 用备用模型时被限制的决定

- **GIVEN** 提交结论的调用实际使用的模型是 p-2
- **WHEN** PM 提交关注的结论：开仓方案；或者持仓的结论：加仓；或者候选的结论：升级
- **THEN** 都被限制，分别给出开仓方案、加仓、升级

#### Scenario: 用备用模型时其他决定都通过

- **GIVEN** 提交结论的调用实际使用的模型是 p-3
- **WHEN** PM 提交持仓的结论：持有、减仓、清仓；关注的结论：继续关注（附论点更新和跟进申请）、降为候选、移出；候选的结论：保持、移出；寻股的结论：加入 DDD
- **THEN** 都通过

#### Scenario: 用主模型时不限制

- **GIVEN** 提交结论的调用实际使用的模型是 p-1
- **WHEN** PM 提交关注的结论：开仓方案；或者持仓的结论：加仓
- **THEN** 都通过

#### Scenario: 被限制以后退回 PM 重交

- **GIVEN** BBB 的关注股事件 K-1 在唤醒 PM；PM 在 K-1 调用，p-1 不可用，p-2 成功，提交开仓方案，被限制
- **WHEN** 调用方把它当作结论校验不通过交给案件状态
- **THEN** 案件留在唤醒 PM，重交次数 1，退回 PM 的原因是"用备用模型时不能提这个决定"
- **WHEN** 接着 PM 在 K-1 调用
- **THEN** 第一次尝试是 p-2

#### Scenario: 不限制或者只限制一部分

- **GIVEN** PM 用备用模型时不能提的决定配置为空
- **WHEN** 提交结论的调用实际使用的模型是 p-2，PM 提交关注的结论：开仓方案
- **THEN** 通过
- **GIVEN** PM 用备用模型时不能提的决定配置为只有开仓方案
- **WHEN** 提交结论的调用实际使用的模型是 p-2，PM 提交持仓的结论：加仓
- **THEN** 通过

### Requirement: 备用模型的配置

备用模型的阈值 SHALL 是可配置项：

| 配置项 | 说明 | 默认值 | 要求 |
| --- | --- | --- | --- |
| 重试次数 | 一个模型在一次调用里失败以后，最多再试这么多次 | 1 | 不小于 0 的整数 |
| 子 agent 的单次调用超时 | News、Quant、Fundamentals 每次尝试最多等这么久 | 60 秒 | 大于 0 |
| PM、Critic、Reviewer 的单次调用超时 | 这三个 agent 每次尝试最多等这么久 | 180 秒 | 大于 0 |
| 熔断的连续不可用次数 | 连续这么多次不可用就冷却 | 3 | 正整数 |
| 熔断的时间窗口 | 这几次里最早一次到最后一次不超过这么久才冷却 | 10 分钟 | 大于 0 |
| 冷却时间 | 冷却这么久 | 5 分钟 | 大于 0 |
| PM 用备用模型时不能提的决定 | case-types spec 的决定 | 开仓方案、加仓、升级 | 可以为空 |

- 另外 MUST 满足：（重试次数 + 1）× 子 agent 的单次调用超时 × 2 不超过任务时限（task-dispatch spec「派发的配置」，默认 5 分钟），保证子 agent 的主模型和第一个备用模型的全部尝试都放得进截止时间
- 不满足要求时 MUST 配置报错
- 各 agent 的模型见「模型的配置」，没有默认值

#### Scenario: 默认配置

- **WHEN** 不传任何配置项新建配置
- **THEN** 重试次数 1，子 agent 的单次调用超时 60 秒，PM、Critic、Reviewer 的单次调用超时 180 秒，熔断的连续不可用次数 3，熔断的时间窗口 10 分钟，冷却时间 5 分钟，PM 用备用模型时不能提的决定是开仓方案、加仓、升级

#### Scenario: 配置不合法

- **WHEN** 重试次数配置为 -1；子 agent 的单次调用超时配置为 0 秒；PM、Critic、Reviewer 的单次调用超时配置为 0 秒；熔断的连续不可用次数配置为 0；熔断的时间窗口配置为 0 秒；冷却时间配置为 0 秒
- **THEN** 都配置报错

#### Scenario: 放得进任务时限的边界

- **WHEN** 子 agent 的单次调用超时配置为 75 秒（2 × 75 秒 × 2 = 5 分钟）；或者重试次数配置为 0、子 agent 的单次调用超时配置为 150 秒；或者重试次数配置为 2、任务时限配置为 6 分钟
- **THEN** 都配置正确
- **WHEN** 子 agent 的单次调用超时配置为 76 秒；或者重试次数配置为 2（3 × 60 秒 × 2 = 6 分钟）
- **THEN** 都配置报错

#### Scenario: 改成别的值

- **GIVEN** 熔断的连续不可用次数配置为 1
- **WHEN** p-1 在 15:00Z 不可用
- **THEN** p-1 冷却到 15:05Z
- **GIVEN** 熔断的时间窗口配置为 5 分钟
- **WHEN** p-1 在 14:52Z、14:56Z、15:00Z 不可用
- **THEN** p-1 正常
- **GIVEN** 冷却时间配置为 1 分钟
- **WHEN** p-1 在 14:52Z、14:56Z、15:00Z 不可用
- **THEN** p-1 冷却到 15:01Z
- **GIVEN** PM、Critic、Reviewer 的单次调用超时配置为 300 秒
- **WHEN** PM 在 K-1 调用
- **THEN** 第一次尝试的超时是 300 秒
