# program-log Specification

## Purpose

程序日志按时间先后记下风控引擎、执行模块、人、系统、股票池、调度器和 Agent 网关的每个动作，只追加、不修改、不删除，用来排查故障、审计和复现；以后的模块和 agent 用同一个写入接口加上自己的动作。

## Requirements

### Requirement: 程序日志的条目

程序 SHALL 把每个动作写成程序日志的一条记录。程序日志存在状态库所在的数据库里（表 `programlog_entries`，state-store spec「表的归属和迁移」），只由程序日志模块写入：别的模块、流程和启动程序都经它写，不直接写表。每条记录有：

| 字段 | 内容 |
| --- | --- |
| 编号 | 按写入的先后递增 |
| 时间 | 写入时从时钟读取的时刻；存为带时区的时刻，读回的是同一时刻，和数据库服务器、本机的时区都无关 |
| 行为者 | 风控引擎、执行模块、人、系统、股票池、调度器、Agent 网关，各自的动作见下面以「<行为者>的动作」为名的要求；以后的变更加别的行为者和动作 |
| 动作 | 行为者的一个动作 |
| 对象 | 动作针对的东西的标识：方案 ID、止损单的客户端订单 ID、股票代码、跟进 ID、task_id；针对整个券商账户写 `account`，针对整个程序写 `system` |
| 案件 ID | 动作所属的案件；不属于案件时为空 |
| 输入的引用、输出的引用 | 动作用到的、产生的东西的标识，比如确认消息的标识、交易日、状态库条目 ID；各是一组文字，可以为空 |
| 说明 | 动作的内容和结果，中文；可以为空 |
| 耗时、token、费用 | 可以为空；费用是金额，原样保存每一位小数 |

行为者和动作各是一组固定的值。案件 ID、耗时、token 和费用只在动作的要求写明时才有，其余为空。

#### Scenario: 写一条

- **GIVEN** 进程的本机时区是 UTC+14；时钟是 2026-10-14T15:00:00.123Z
- **WHEN** 写一条：行为者是人，动作是确认，对象是方案 ID P1，输入的引用是确认消息的标识 M1，说明是"买入 BBB"
- **THEN** 程序日志多了一条，读回的时间是 2026-10-14T15:00:00.123Z，行为者、动作、对象、输入的引用和说明都是写入的值
- **AND** 输出的引用为空，案件 ID、耗时、token、费用为空

#### Scenario: 可以为空的字段原样读回

- **WHEN** 写一条带案件 ID、耗时 1.5 秒、token 1200、费用 0.0123 的条目
- **THEN** 读回的案件 ID、耗时、token 和费用都和写入的相同，费用仍是 0.0123

### Requirement: 只追加

程序日志 SHALL 只追加：

- 写入的条目 MUST NOT 被修改或删除：程序日志只有追加和读取，没有修改和删除
- 后写入的条目编号更大；几个线程同时写入时，每一条都写进去，编号各不相同
- 进程重启以后接着往后写，之前的条目不变
- 读最近的一条时，给出编号最大的那条

#### Scenario: 后写入的编号更大

- **WHEN** 先后写入两条
- **THEN** 两条都在，第二条的编号比第一条大，第一条没有变化
- **AND** 读最近的一条，读到第二条

#### Scenario: 同时写入

- **WHEN** 两个线程同时各写一条
- **THEN** 两条都在，编号不同

#### Scenario: 重启以后接着写

- **GIVEN** 程序日志里有 3 条
- **WHEN** 用同一个数据库新建程序日志（相当于进程重启），再写一条
- **THEN** 4 条都在，新的一条编号最大，前 3 条不变

### Requirement: 写入失败

写入时数据库出错（连不上、表不存在、语句报错），程序日志 SHALL 报错，MUST NOT 当作已经写入，也 MUST NOT 跳过。

- 出错的这一步由调用方照它自己的规则处理，比如巡检的一项写 ERROR、跳过这一项（session-patrol spec「一轮里的失败」），启动的一步算启动失败（bootstrap spec「启动失败」）
- 条目在动作做完以后写，和动作不在同一个事务里：写条目出错时，已经做了的动作不撤回

#### Scenario: 数据库连不上

- **GIVEN** 数据库连不上
- **WHEN** 写一条
- **THEN** 报错

#### Scenario: 表不存在

- **GIVEN** 空数据库，没有升级
- **WHEN** 写一条
- **THEN** 报错，不当作已经写入

#### Scenario: 巡检里写条目出错

- **GIVEN** session-patrol spec 的基准数据；P1 已经提交，订单已提交；写程序日志时数据库会出错一次
- **WHEN** 券商回报 P1 变为已受理、累计成交 30，做一轮
- **THEN** P1 的订单已经保存为部分成交、累计成交 30
- **AND** 巡检写一条 ERROR，带异常栈；这一轮照常做完其余各项

### Requirement: 风控引擎的动作

风控引擎的下面这些动作 SHALL 各写一条，行为者是风控引擎：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 风控检查 | 首次检查得出结果：`/plan` 的提交接口（order-flow spec「提交方案」）；紧急退出检查当天的清仓方案（emergency-exit-flow spec「一只股票的清仓」第 4 步） | 方案 ID | 没有 | 动作和股票；结果（通过、调整、拒绝）和最终股数；每条不通过的规则和它的说明，没有列出的规则都通过；通过或调整时写明按最终股数预留 |
| 下单前再校验 | 再校验得出结果，并且这一次没有转去等重试或等开盘：下单流程再校验以后作废或者提交了订单（order-flow spec「下单前再校验和提交」「提交的结果」）；紧急退出（同上第 4 步） | 方案 ID | 没有 | 结果和最终股数；不通过的规则和说明；通过或调整时写明预留改为最终股数；拒绝时写明方案作废 |
| 释放预留 | 流程释放一个方案剩下的预留，并且这个方案这时有有效预留（risk-reservations spec） | 方案 ID | 没有 | 原因，见下 |

释放预留的原因：

- 下单流程：人工拒绝；确认超时；确认请求没有发出去；到了有效期还没下单（写上最近一次没能下单的原因，有的话）；最近一次对账有不一致；启动下单流程失败
- 巡检的同步预留（session-patrol spec「每一轮」第 2 步）：订单进入终态，写上订单的状态和累计成交
- 紧急退出：作废这只股票还没下单的方案，写上是哪只股票的紧急退出；到收盘还没有清仓单

没有有效预留时释放什么也不改，SHALL NOT 写释放预留：比如订单全部成交、预留已经随成交用完，或者方案已经被紧急退出作废。再校验拒绝时预留由再校验释放，写在下单前再校验的说明里，也不另写释放预留。

#### Scenario: 风控检查通过

- **GIVEN** order-flow spec 的基准数据
- **WHEN** 提交 P1
- **THEN** 程序日志有一条风控检查，对象 P1，说明写明买入 BBB、通过、20 股、按 20 股预留

#### Scenario: 风控检查调整

- **GIVEN** order-flow spec 的基准数据；券商现金改为 505
- **WHEN** 提交 P1
- **THEN** 风控检查的说明写明调整、10 股，不通过的规则是"已结算资金"和它的说明，按 10 股预留

#### Scenario: 风控检查拒绝

- **GIVEN** order-flow spec 的基准数据；处于降级模式
- **WHEN** 提交 P1
- **THEN** 风控检查的说明写明拒绝、不通过的规则是"降级模式"，没有写预留

#### Scenario: 紧急退出的清仓方案

- **GIVEN** emergency-exit-flow spec 的基准数据；AAA 最新价 92
- **WHEN** 做一轮
- **THEN** 程序日志有 AAA 当天的清仓方案的风控检查和下单前再校验，都是通过、50 股

#### Scenario: 再校验通过

- **GIVEN** order-flow spec 的基准数据；已经提交 P1
- **WHEN** 按确认
- **THEN** 程序日志有一条下单前再校验，对象 P1，说明写明通过、20 股

#### Scenario: 再校验拒绝

- **GIVEN** order-flow spec 的基准数据；当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认
- **WHEN** 2026-10-15 13:30Z，BBB 最新价 53
- **THEN** 下单前再校验的说明写明拒绝、"价格偏离"和它的说明、方案作废
- **AND** 没有 P1 的释放预留

#### Scenario: 人工拒绝时释放

- **GIVEN** order-flow spec 的基准数据；已经提交 P1
- **WHEN** 按拒绝
- **THEN** 程序日志有一条释放预留，对象 P1，原因是人工拒绝

#### Scenario: 订单结束时释放剩下的预留

- **GIVEN** session-patrol spec 的基准数据；P1 已经提交，订单已提交，预留 100 股
- **WHEN** 券商回报 P1 变为撤销、累计成交 30，做一轮
- **THEN** 程序日志有一条释放预留，对象 P1，原因写明订单已撤销、累计成交 30 / 100

#### Scenario: 全部成交时不写释放

- **GIVEN** session-patrol spec 的基准数据；P1 已经提交，订单已提交
- **WHEN** 券商回报 P1 变为全部成交、累计成交 100，做一轮
- **THEN** 程序日志有 P1 的订单变化（已提交变为全部成交），没有 P1 的释放预留

#### Scenario: 紧急退出作废方案时释放

- **GIVEN** emergency-exit-flow spec 的基准数据；P3：加仓 AAA 5 股，在等确认，预留 5 股，没有订单
- **WHEN** AAA 最新价 92，做一轮
- **THEN** 程序日志有一条释放预留，对象 P3，原因写明 AAA 的紧急退出作废还没下单的方案

#### Scenario: 已经没有预留的方案被拒绝

- **GIVEN** order-flow spec 的基准数据；已经提交 P1，在等确认；P1 的预留已经释放（比如被紧急退出作废）
- **WHEN** 按拒绝
- **THEN** 程序日志有人的拒绝，没有新的 P1 的释放预留

### Requirement: 执行模块的动作

执行模块的下面这些动作 SHALL 各写一条，行为者是执行模块：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 提交订单 | 下单流程、紧急退出提交订单，执行模块返回订单；下单流程发现这个方案已经有订单，交给盘中巡检 | 方案 ID（就是订单的客户端订单 ID） | 输出：券商订单号，券商受理过才有 | 动作、股票、委托股数、订单类型和限价、返回时订单的状态；已经有订单的写明交给盘中巡检 |
| 订单变化 | 执行模块跟进一笔订单以后，状态或累计成交和跟进以前不同：巡检的跟进；撤单以后的那次跟进；启动对账、收盘对账、恢复后的对账跟进的订单 | 方案 ID | 没有 | 股票、买卖方向、变化前后的状态、累计成交和委托股数；有成交时写成交均价和累计费用 |
| 撤单 | 紧急退出要求撤掉订单：熔断撤掉全部买单（emergency-exit-flow spec「单日亏损熔断」）；一只股票清仓前撤掉它没结束的订单（「一只股票的清仓」第 3 步）。只写这一次新记下撤单要求的订单 | 方案 ID | 没有 | 原因（熔断，或者哪只股票的紧急退出）、股票、买卖方向、委托股数 |
| 止损单变化 | 巡检第 3 步处理一只股票以后，当前止损单和巡检上次看到的不同（session-patrol spec「订单和止损单变化的日志」） | 止损单的客户端订单 ID | 没有 | 股票、状态、未成交股数、止损价；有成交时写累计成交和成交均价 |
| 无保护仓位 | 巡检第一次看到一段无保护，和无保护仓位的告警同时（session-patrol spec「无保护仓位的告警」） | 股票 | 没有 | 无保护开始的时刻 |
| 无保护解除 | 告警过的股票不再是无保护仓位 | 股票 | 没有 | 空 |
| 对账 | 启动对账（bootstrap spec「启动对账」）、收盘对账（close-reconciliation spec「结果消息」）、恢复后的对账（health-monitoring spec「恢复后的对账」）做完 | `account` | 收盘对账：输出是交易日 | 哪一种对账；没有不一致，或者每一条不一致一行，写法和 close-reconciliation spec「结果消息」的差异行相同；收盘对账是结果消息的全文 |
| 等开盘 | 下单流程确认以后、或者重试以前不在交易时段，要等到下一个开盘（order-flow spec「等开盘」） | 方案 ID | 没有 | 等到的时刻（UTC） |

- 券商拒绝受理的订单记为订单的状态（已拒绝）；止损单挂单、改单被拒记为无保护仓位
- 对账跟进的订单先写订单变化，再写对账
- 下单流程等重试的原因（order-flow spec「下单前再校验和提交」「提交的结果」）不写程序日志，见「不写进程序日志的」

#### Scenario: 提交订单

- **GIVEN** order-flow spec 的基准数据；已经提交 P1
- **WHEN** 按确认，券商受理 P1
- **THEN** 程序日志有一条提交订单，对象 P1，说明写明买入 BBB 20 股、限价单、限价 50、已提交
- **AND** 输出的引用是 P1 的券商订单号

#### Scenario: 券商拒绝受理

- **GIVEN** order-flow spec 的基准数据；已经提交 P1；券商会拒绝受理 P1
- **WHEN** 按确认
- **THEN** 提交订单的说明写明已拒绝，没有输出的引用

#### Scenario: 已经有订单时交给巡检

- **GIVEN** order-flow spec 的基准数据；已经提交 P1；提交 P1 时券商回答 401，P1 的订单已经建立、还是待提交
- **WHEN** 2026-10-14 15:05Z 按确认，15:05:30Z 重试
- **THEN** 15:05:30Z 程序日志有一条提交订单，说明写明已经有订单、待提交、交给盘中巡检

#### Scenario: 巡检看到订单成交

- **GIVEN** session-patrol spec 的基准数据；P1 已经提交，订单已提交
- **WHEN** 券商回报 P1 变为已受理、累计成交 30、成交均价 49.98，做一轮
- **THEN** 程序日志有一条订单变化，对象 P1，说明写明 BBB、买入、已提交变为部分成交、累计成交 30 / 100、成交均价 49.98

#### Scenario: 停机期间成交，启动对账时写

- **GIVEN** bootstrap spec 的基准数据；状态库里有一笔已提交的买单 P1（买入 BBB 100 股）；停机期间 P1 全部成交
- **WHEN** 正常启动
- **THEN** 程序日志先有 P1 的订单变化（已提交变为全部成交、100 / 100），再有启动对账的对账

#### Scenario: 撤单

- **GIVEN** emergency-exit-flow spec 的基准数据；P2 的订单已提交；AAA-STOP-1 已经改为 30 股
- **WHEN** AAA 最新价 92，做一轮
- **THEN** 程序日志有一条撤单，对象 P2，说明写明 AAA 的紧急退出、卖出、20 股
- **WHEN** 券商回报 P2 仍是已受理，之后一轮
- **THEN** 没有新的撤单

#### Scenario: 熔断撤买单

- **GIVEN** emergency-exit-flow spec 的基准数据；P5 的订单已提交；当前权益 9,300
- **WHEN** 做一轮
- **THEN** 程序日志有一条撤单，对象 P5，说明写明熔断、买入 CCC 100 股

#### Scenario: 止损单成交

- **GIVEN** session-patrol spec 的基准数据；持有 BBB 100 股，止损单已对齐；巡检已经做过一轮
- **WHEN** 券商回报 BBB-STOP-1 全部成交、累计成交 100、成交均价 44.9，券商持仓变为 0，做一轮
- **THEN** 程序日志有一条止损单变化，对象 BBB-STOP-1，说明写明 BBB、已经结束、累计成交 100、成交均价 44.9

#### Scenario: 无保护仓位和解除

- **GIVEN** session-patrol spec 的基准数据；P1 已经提交，订单已提交；券商会一直拒绝挂单
- **WHEN** 券商回报 P1 变为已受理、累计成交 30，券商持仓变为 30 股，15:00Z 做一轮
- **THEN** 程序日志有一条无保护仓位，对象 BBB，说明写明从 2026-10-14 15:00Z 起
- **WHEN** 券商恢复正常受理，之后一轮
- **THEN** 程序日志有一条无保护解除，对象 BBB

#### Scenario: 启动对账

- **GIVEN** bootstrap spec 的基准数据；Alpaca 模拟盘持有 CCC 100 股，状态库里没有 CCC 的订单
- **WHEN** 正常启动
- **THEN** 程序日志有一条对账，对象 `account`，说明写明启动对账、来历不明的持仓 CCC 100 股

#### Scenario: 收盘对账

- **GIVEN** close-reconciliation spec 的基准数据；持有 BBB 100 股，止损单已对齐；有 2026-10-13 连续天数 2 的记录
- **WHEN** 2026-10-14 20:10Z 巡检做一轮
- **THEN** 程序日志有一条对账，对象 `account`，输出的引用是 2026-10-14，说明是推送的结果消息的全文

#### Scenario: 等开盘

- **GIVEN** order-flow spec 的基准数据；当前时刻 2026-10-14 21:00Z；提交 P1
- **WHEN** 2026-10-14 21:05Z 按确认
- **THEN** 程序日志有一条等开盘，对象 P1，说明写明等到 2026-10-15 13:30 UTC

### Requirement: 人的动作

人的下面这些动作 SHALL 各写一条，行为者是人：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 录入方案 | `/plan` 解析出方案、交给提交接口时，在风控检查之前（order-flow spec「提交方案」） | 方案 ID | 没有 | 动作、股票、板块，以及填了的股数、订单类型、限价、止损价、紧急阈值、有效期、允许价格偏离 |
| 确认 | 下单流程收下确认（order-flow spec「确认的结果」）；紧急退出流程收下确认（emergency-exit-flow spec「紧急退出的人工确认」） | 方案 ID | 输入：确认消息的标识 | 动作和股票；紧急退出写紧急退出和股票 |
| 拒绝 | 同上，收下拒绝 | 方案 ID | 输入：确认消息的标识 | 同上 |

- **THEN** 程序日志有一条清仓，对象 CCC，没有案件 ID，说明写明 PM 发起、转为关注、复查日 2026-10-21、催化剂截止日期 2026-10-29、上次复查的那一天 2026-10-14

- **THEN** 程序日志有一条清仓，对象 CCC，没有案件 ID，说明写明 PM 发起、移出

#### Scenario: 报错的操作不写

- **WHEN** 加入 DDD

### Requirement: 调度器的动作

调度器的下面这些动作 SHALL 各写一条，行为者是调度器。现在只有跟进审批的动作（follow-ups spec）：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 批准跟进 | 跟进申请通过审批，新的跟进保存以后（follow-ups spec「审批的输入和结果」） | 新跟进的 ID | 没有 | 跟进的内容 |
| 拒绝跟进 | 跟进申请没有通过审批（follow-ups spec「审批的顺序」） | 股票 | 没有 | 不通过的原因；申请的内容，写法和跟进的内容相同，没写引用的写明没有引用 |
| 替换跟进 | 批准的跟进替换了这只股票原因相同的待执行跟进（follow-ups spec「原因相同时替换」），写在这次的批准跟进之后 | 被替换的跟进的 ID | 输入：替换它的新跟进的 ID | 被替换的跟进的内容 |
| 作废跟进 | 股票状态往下走，这只股票待执行的跟进作废（follow-ups spec「股票状态往下走时作废」）：每个作废的跟进一条，按作废时给出的顺序 | 跟进 ID | 没有 | 之前和之后的状态，不在股票池也不是持仓的写不在股票池；跟进的内容 |
| 触发跟进 | 到点触发把跟进记为已触发（follow-ups spec「到点触发」）：每个一条，按给出的顺序 | 跟进 ID | 没有 | 跟进的内容 |

跟进的内容：股票、原因类型、引用的对象、触发时间（UTC）、要回答的问题、可能采取的动作。

- 批准、拒绝和替换跟进的案件 ID 是提出申请的案件；作废和触发跟进不属于案件，案件 ID 为空
- 每个跟进保存以后才写它的条目；写条目出错时照「写入失败」处理，已经保存的跟进不撤回
- 取得待执行的跟进、没有跟进到点的到点触发、不作废跟进的状态变化 SHALL NOT 写程序日志

### Requirement: Agent 网关的动作

Agent 网关的下面这些动作 SHALL 各写一条，行为者是 Agent 网关，对象是 task_id，案件 ID 是任务所属的案件：

| 动作 | 什么时候写 | 引用 | 说明 | 耗时、费用 |
| --- | --- | --- | --- | --- |
| 派发任务 | 一个请求派发出去，生成 Task（task-dispatch spec「派发的顺序」） | 输入：Task 的输入 | 发起者、目标、任务类型、股票、问题、截止时间（UTC）；PM 派发出去的任务写第几轮 | 空 |
| 拒绝任务 | 一个请求被拒绝，生成 Task 和被拒绝的 Result | 输入：Task 的输入 | 被拒绝的原因；发起者、目标、任务类型、股票、问题 | 空 |
| 生成 Result | 派发出去的任务生成 Result：完成、无信号、超时、失败（task-dispatch spec「子 agent 的输出变成 Result」「超时」「调用失败」） | 输入：Result 引用的条目 | 状态；完成写评分、置信度和评估窗口，无信号写原因，失败写原因和说明；有模型的写模型和是不是备用模型 | Result 的耗时和费用 |

- 先写入 Task 或 Result，再写条目；一次派发里的条目按请求的顺序写
- 每个 Task SHALL 只有一条派发任务或拒绝任务，每个 Result SHALL 只有一条：被拒绝的 Result 写在拒绝任务里，不另写生成 Result；已经有 Result 的任务再收到输出、调用失败或者记超时，SHALL NOT 再写；同时生成的两个 Result，只有写入了的那个写（task-dispatch spec「一个任务只有一个 Result」）
- 复用（task-dispatch spec「相同的任务」）和格式错误的请求不生成 Task，SHALL NOT 写
- 这三种条目的 token 为空

本 requirement 的场景使用 task-dispatch spec 的基准数据；子 agent 的主模型是 google/s-1，备用模型是 openai/s-2（model-fallback spec 的基准模型的配置）。

#### Scenario: 派发任务

- **THEN** 程序日志有一条派发任务：行为者 Agent 网关，对象 T-1，案件 K-1，输入的引用 E-1，说明写明 PM 派给 Quant、价格反应、BBB、问题"财报后的放量上涨能否持续？"、截止时间 2026-10-14 15:05:00 UTC、PM 的第 1 轮

- **AND** 拒绝任务的说明写明"股票不是案件的股票"、PM 派给 News、事件影响评估、AAA；没有 T-2 的生成 Result
