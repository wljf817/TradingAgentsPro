# order-flow Specification

## Purpose
下单流程把人手工录入的交易方案从风控检查一路带到执行模块：通过或调整的方案预留额度、请求人工确认，确认以后在常规交易时段内再校验并提交订单，订单交给盘中巡检跟进；方案在下单以前结束时释放预留。下单流程的进度保存在数据库里，进程重启或程序更新以后从断点继续。

## Requirements

### Requirement: 提交方案

`/plan` 的提交接口（manual-plans spec「提交接口」）SHALL 按下面的顺序处理一个方案：

1. 读执行模块的账户数据（trade-records spec「账户数据」）和持仓股票的行情，拼成风控用的账户数据，见「风控用的账户数据」。这一步不拿锁
2. 拿锁（见「执行模块和风控的调用串行」），用风控检查方案并预留（risk-rules spec、risk-reservations spec）。单日亏损熔断是否触发取紧急退出的当前状态（emergency-exit spec），是否处于降级模式取健康监控的当前状态（degraded-mode spec）
3. 结论为拒绝：返回风控结果，不启动下单流程
4. 结论为通过或调整：启动这个方案的下单流程，返回风控结果，不等人工确认。下单流程以方案 ID 为标识，同一个方案 ID 只有一个下单流程

| 情况 | 处理 |
| --- | --- |
| 读券商账户超时、断线或出错 | 报错：不检查、不预留、不启动下单流程 |
| 启动下单流程失败（比如数据库出错） | 拿锁释放这个方案的预留，报错 |
| 同一个方案 ID 再次提交 | 风控返回第一次的结果（risk-reservations spec「同一方案重复检查」），不另起下单流程 |

报错以后 `/plan` 按 manual-plans spec「提交接口」回复提交出错。

本 spec 的场景除非另有说明，都使用下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中；当天 13:30Z 开盘、20:00Z 收盘），交易日历是纽交所日历
- 风控配置、执行配置（买单和止损单错开关闭）、通知配置（确认超时 30 分钟）、下单流程配置（重试间隔 30 秒）都用默认值；风控的每笔佣金是默认的 2
- 执行模块已经完成一次对账，没有不一致；单日亏损熔断没有触发；不处于降级模式
- 券商账户：权益 10,000，现金 10,000，没有未结算的卖出款，前一交易日收盘时的权益 10,000；持有 AAA 10 股，均价 100
- AAA 的开仓订单：板块"科技"，止损价 90，紧急阈值 0.08，最近成交日 2026-10-12；AAA 的止损单已对齐
- 行情：AAA 最新价 110，前一交易日收盘价 108；BBB 最新价 50，前一交易日收盘价 49.5
- 方案（都没填有效期、紧急阈值和允许价格偏离）：
  - P1：买入 BBB，板块"医疗"，20 股，限价单，限价 50，止损价 45。在当前时刻检查，结论为通过，最终 20 股，生效的有效期 2026-10-14 20:00Z
  - P2：减仓 AAA 4 股，市价单。检查结论为通过，最终 4 股
  - P3：清仓 AAA，市价单。检查结论为通过，最终 10 股
  - P4：加仓 AAA 5 股，限价单，限价 110，止损价 100。检查结论为通过，最终 5 股
- "提交 P1"指本人用 `/plan` 录入 P1，提交接口收到它；"按确认""按拒绝"指本人在截止时刻之前按 P1 的确认消息上的按钮，按钮的结果送达下单流程
- "券商收到 P1 的订单"指券商收到客户端订单 ID 是 P1 的提交；没有另外说明时券商正常受理，订单不成交
- "锁"指 session-patrol spec「执行模块和风控的调用串行」的那把锁

- **GIVEN** 读券商账户时超时
- **WHEN** 提交 P1

- **GIVEN** 启动下单流程时数据库出错
- **WHEN** 提交 P1
- **THEN** 提交接口报错
- **AND** BBB 没有有效预留，没有确认消息

#### Scenario: 同一个方案提交两次

- **WHEN** 用同一个方案 ID 再提交一次 P1
- **THEN** 提交接口返回通过，最终 20 股
- **AND** BBB 仍然只有一份 20 股的预留，频道里只有一条 P1 的确认消息

### Requirement: 查持仓的板块

减仓和清仓时 `/plan` 查持仓的板块（manual-plans spec「减仓和清仓的板块」），提交接口 SHALL 这样回答，不拿锁：

| 账户数据 | 回答 |
| --- | --- |
| 执行模块的账户数据里有这只股票的持仓 | 它的板块（开仓订单的板块） |
| 账户数据里没有这只股票（没有持仓，或者持仓找不到有成交的开仓订单） | 没有 |
| 读券商账户超时、断线或出错 | 报错 |

#### Scenario: 减仓有持仓的股票

- **WHEN** 本人运行 `/plan reduce symbol:AAA quantity:4`
- **THEN** 查到板块"科技"，提交接口收到 P2 这样的方案：减仓 AAA 4 股，板块"科技"

#### Scenario: 清仓没有持仓的股票

- **WHEN** 本人运行 `/plan close symbol:XYZ`
- **THEN** 回复没有 XYZ 的持仓，没有提交

#### Scenario: 查持仓时券商不可用

- **GIVEN** 读券商账户超时
- **WHEN** 本人运行 `/plan close symbol:AAA`
- **THEN** 回复查持仓出错，没有提交

### Requirement: 风控用的账户数据

首次检查和下单前再校验用的账户数据 SHALL 按下表拼成，结构见 risk-rules spec「风控的输入和判定」：

| 项 | 取值 |
| --- | --- |
| 权益、已结算资金、每只股票的最近成交日 | 执行模块的账户数据 |
| 持仓的股票、板块、股数、均价、止损价 | 执行模块的账户数据：只有能找到开仓订单的持仓 |
| 持仓的最新价 | 这只股票的行情的最新价；没有最新价（盘前，或者当天开盘后还没有成交）时用前一交易日收盘价；取不到这只股票的行情（行情不可用，或者行情源没有它）时用均价，并写一条 WARNING，写明股票和原因 |

- 只取持仓股票的行情，一次取完；没有持仓时不取行情
- 取不到行情时首次检查照常进行：持仓按均价估市值只影响单只仓位上限和板块集中度的估算，开仓方案在下单前还会用实时数据再校验，见「下单前再校验和提交」

#### Scenario: 盘中的账户数据

- **WHEN** 提交 P1
- **THEN** 风控用的账户数据：权益 10,000，已结算资金 10,000；持仓 AAA：板块"科技"，10 股，均价 100，最新价 110，止损价 90；AAA 的最近成交日 2026-10-12

#### Scenario: 盘前用前一交易日收盘价

- **GIVEN** 当前时刻 2026-10-14 12:00Z（开盘前）；AAA 的行情没有最新价
- **WHEN** 提交 P1
- **THEN** 风控用的账户数据里 AAA 的最新价是 108

#### Scenario: 取不到行情时用均价

- **GIVEN** 取行情时行情不可用
- **WHEN** 提交 P1
- **THEN** 风控用的账户数据里 AAA 的最新价是 100
- **AND** 有一条 WARNING 写明 AAA 和行情不可用
- **AND** 提交接口返回通过，最终 20 股

#### Scenario: 行情源没有这只股票

- **GIVEN** 行情源没有 AAA 的数据
- **WHEN** 提交 P1
- **THEN** 风控用的账户数据里 AAA 的最新价是 100，有一条 WARNING 写明 AAA

#### Scenario: 没有持仓时不取行情

- **GIVEN** 券商没有持仓
- **WHEN** 提交 P1
- **THEN** 没有向行情源取行情，提交接口返回通过

### Requirement: 请求人工确认

下单流程开始以后，`/plan` 录入的方案 SHALL 立即请求人工确认（discord-notification spec「确认请求和截止时刻」「确认消息」），四种动作（买入、加仓、减仓、清仓）都要；案件的方案 SHALL 按「案件的方案」的决定：要人工确认的立即请求，不要的不请求，直接进入「等开盘」。确认消息用提交时的风控结果：股数是最终股数，调整时写明已被风控调整和原因。截止时刻是请求的时刻加上确认超时。

案件的方案的确认消息 SHALL 按 Critic 审核的结果附上案件的意见（case-stages spec「人工确认」，discord-notification spec「确认消息」），在请求确认时从案件记录读：

| Critic 审核的结果 | 附上 |
| --- | --- |
| 通过 | 不附 |
| 有分歧 | 这个案件的结论的理由（PM 的方案理由），方案记录里 Critic 的每次审核和 PM 的每轮回应，按先后 |
| Critic 不可用 | 注明 Critic 不可用，方案没有经过审核 |

请求确认时 MUST NOT 拿着锁。

确认请求发不出去（通知不可用：Discord 报错、超过发送超时、没有连接）时，SHALL 按确认超时处理（Proposal「技术栈与部署」）：释放这个方案的全部预留，写一条 ERROR，写明方案 ID 和原因；下单流程结束，不再请求。案件的方案「案件的方案」决定确认超时以后告警的，SHALL 推送告警（见「告警」）；其余不告警。

#### Scenario: 四种动作都请求确认

- **WHEN** 先后提交 P1、P2、P3、P4
- **THEN** 频道里依次出现四条确认消息：买入 BBB 20 股、减仓 AAA 4 股、清仓 AAA 6 股（扣除 P2 的 4 股卖出预留）、加仓 AAA 5 股
- **AND** 四条消息的截止时刻都是 2026-10-14 15:30Z

#### Scenario: 确认请求发不出去

- **GIVEN** Discord 对发消息报错
- **WHEN** 提交 P1
- **THEN** 提交接口返回通过，最终 20 股
- **AND** 之后 BBB 没有有效预留；有一条 ERROR 写明 P1 的确认请求没有发出去和原因
- **AND** 券商没有收到 P1 的订单，P1 的下单流程已经结束

#### Scenario: 有分歧的案件方案附上双方意见

- **GIVEN** K1 的结论的理由是"新品周期带动收入加速"；K1 的方案记录依次有：Critic 质询（理由"止损太近"，质询"止损价 45 离限价只有 10%"）、PM 维持（回应"财报前不调整"）、Critic 质询（理由"仍然太近"，质询"波动率上升"）、PM 修改（回应"止损放宽到 44"，新的条款止损价 44）、Critic 质询（理由"仍有分歧"，质询"仓位偏大"）
- **WHEN** K1 交来修改后的 P1（止损价 44），Critic 审核的结果是有分歧
- **THEN** P1 的确认消息附上：K1 的结论的理由，以及按先后的三次审核和两轮回应

#### Scenario: Critic 不可用的退出方案

- **WHEN** K3 交来 P3，Critic 审核的结果是 Critic 不可用
- **THEN** P3 的确认消息注明 Critic 不可用、方案没有经过审核

#### Scenario: 退出方案的确认请求发不出去

- **GIVEN** Discord 对发消息报错
- **WHEN** K3 交来 P3
- **THEN** AAA 没有 P3 的有效预留；推送告警，写明 P3 没有执行、止损单照挂；告警也没有发出去，有一条错误日志
- **AND** 券商没有收到 P3 的订单

### Requirement: 确认的结果

下单流程 SHALL 等确认的结果，按下表处理：

| 结果 | 处理 |
| --- | --- |
| 截止时刻之前按确认 | 进入「等开盘」；不再请求确认 |
| 截止时刻之前按拒绝 | 释放全部预留；下单流程结束；不告警 |
| 到截止时刻没有结果 | 报告确认消息已超时（discord-notification spec「结束确认」），释放全部预留；下单流程结束。案件的方案「案件的方案」决定超时以后告警的推送告警（见「告警」），其余不告警 |
| 确认请求发不出去 | 见「请求人工确认」 |

#### Scenario: 盘中确认后立即下单

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按确认
- **THEN** 确认消息显示已确认
- **AND** 券商收到 P1 的订单：买入 BBB 20 股，限价单，限价 50，当日有效
- **AND** BBB 的预留仍是 20 股：之后由盘中巡检跟进 P1 的订单（session-patrol spec）

#### Scenario: 人工拒绝

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按拒绝
- **THEN** 确认消息显示已拒绝；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单，没有告警

#### Scenario: 确认超时

- **GIVEN** 已经提交 P1，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 确认消息显示已超时；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单，没有告警

#### Scenario: 案件的退出方案确认超时

- **GIVEN** K3 交来 P3，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 确认消息显示已超时；AAA 没有 P3 的有效预留
- **AND** 推送一条告警，写明 P3 确认超时、没有执行、持仓的止损单照挂

#### Scenario: 案件的开仓方案确认超时不告警

- **GIVEN** K1 交来 P1，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 确认消息显示已超时；没有告警

#### Scenario: 截止前一刻确认

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:29:59Z 按确认
- **THEN** 券商收到 P1 的订单

#### Scenario: 调整的方案按调整后的股数确认

- **GIVEN** 券商现金改为 505，已经提交 P1，结论为调整，最终 10 股
- **WHEN** 按确认，下单前再校验通过，最终 10 股（请求股数是预留的 10 股）
- **THEN** 券商收到 P1 的订单：买入 BBB 10 股

### Requirement: 按钮的结果只送给在等确认的方案

确认按钮的回调（discord-notification spec「按钮的处理」）SHALL 按这个方案的下单流程的状态处理：

| 下单流程 | 处理 |
| --- | --- |
| 正在等确认：已经开始请求确认，还没有得出结果 | 把确认或拒绝送给它 |
| 不存在（方案 ID 没有下单流程，比如以前的测试留下的消息） | 报错：这个方案没有在等确认 |
| 已经得出确认的结果（确认、拒绝、超时、确认请求发不出去），或者已经结束 | 报错：这个方案没有在等确认 |

- 报错时按钮按 discord-notification spec 提示没有送达，消息上的按钮还在，不会显示已确认
- 回调送达和确认超时同时发生、下单流程先得出超时的：下单流程按超时处理，并报告确认消息已超时；按 discord-notification spec「结束确认」，消息最后显示已超时，不下单
- 程序重启以后，重启以前还在等确认的方案仍然算在等确认（见「持久化和恢复」）

#### Scenario: 在等确认时送达

- **GIVEN** 已经提交 P1，下单流程在等确认
- **WHEN** 本人按确认
- **THEN** 回调没有报错，下单流程收到确认

#### Scenario: 方案没有下单流程

- **GIVEN** 频道里有一条方案 X 的确认消息，还没到截止时刻，X 没有下单流程
- **WHEN** 本人按确认
- **THEN** 回调报错，写明 X 没有在等确认
- **AND** 按钮提示没有送达，消息上的按钮还在

#### Scenario: 已经确认过的方案

- **GIVEN** 已经提交 P1，按了确认，券商收到了 P1 的订单；之后程序重启，P1 的确认消息上的按钮还能按（还没到截止时刻）
- **WHEN** 本人再按确认
- **THEN** 回调报错，写明 P1 没有在等确认
- **AND** 券商仍然只有一笔 P1 的订单

#### Scenario: 确认请求超时以后消息才发出去

- **GIVEN** 提交 P1 时 Discord 很慢，请求确认超过发送超时，按发不出去处理，BBB 没有有效预留；随后这条确认消息出现在频道里
- **WHEN** 本人按确认
- **THEN** 回调报错，按钮提示没有送达
- **AND** 券商没有收到 P1 的订单

#### Scenario: 按钮和超时同时

- **GIVEN** 已经提交 P1，下单流程在 2026-10-14 15:30Z 得出超时
- **WHEN** 本人的确认在下单流程得出超时以后才送到
- **THEN** 确认消息最后显示已超时；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单

### Requirement: 等开盘

确认以后，以及每一次重试之前（见「提交的结果」），下单流程 SHALL 按当前时刻决定：

| 当前时刻 | 处理 |
| --- | --- |
| 不早于提交时风控给出的生效有效期 | 方案作废，原因是有效期；释放全部预留（这个方案已经有订单的除外，见「提交的结果」）；告警；下单流程结束 |
| 在常规交易时段内 | 立即做「下单前再校验和提交」 |
| 不在常规交易时段内（盘前、盘后、休市日），早于生效的有效期 | 等到下一个开盘时刻，再按这张表 |

- 先看有效期：到了有效期，不论在不在盘中都作废
- 等开盘跨重启：程序重启以后只等剩下的时间；停机期间已经过了开盘时刻的，重启以后立即按这张表处理
- 生效的有效期是某个交易日的收盘时刻（risk-rules spec），所以早于有效期时，下一个开盘时刻一定早于有效期

### Requirement: 下单前再校验和提交

在常规交易时段内，下单流程 SHALL 依次：

1. 这个方案已经有订单（之前已经提交过）：不再校验，不再提交，订单交给盘中巡检，下单流程结束
2. 读实时账户数据（见「风控用的账户数据」）。开仓方案还要这只股票当天的最新价；减仓和清仓不需要这只股票的最新价，取不到行情也照常再校验（风控不看退出方案的最新价，pre-order-recheck spec「价格偏离」「跌破止损价」）
3. 拿锁，用风控做下单前再校验（pre-order-recheck spec），熔断和降级的取法同「提交方案」
4. 通过或调整：在同一次拿锁里，按再校验的结果提交订单（order-lifecycle spec「提交订单」），结果见「提交的结果」。调整只会往小调，SHALL NOT 再请求确认
5. 拒绝（有效期、价格偏离、跌破止损价、单日亏损熔断、降级模式、可卖数量、方案已结束等）：方案作废，预留已经由再校验释放；告警写明每条不通过的规则；下单流程结束

取不到数据时 SHALL 等一个重试间隔，再从「等开盘」的表开始：

| 情况 | 处理 |
| --- | --- |
| 开仓方案这只股票没有当天的最新价（刚开盘还没有成交），或者取行情时行情不可用、行情源没有它 | 写一条 WARNING；等重试间隔 |
| 读券商账户超时或断线 | 写一条 WARNING；等重试间隔 |

### Requirement: 提交的结果

按再校验的结果提交订单以后，下单流程 SHALL 按下表处理：

| 提交的结果 | 处理 |
| --- | --- |
| 返回订单：已提交、部分成交、全部成交或状态未知 | 订单交给盘中巡检；下单流程结束 |
| 返回订单：已拒绝（券商拒绝受理） | 告警；下单流程结束。预留由盘中巡检释放（session-patrol spec「每一轮」第 2 步） |
| 还没完成过对账 | 等重试间隔，从「等开盘」的表重来 |
| 这只股票有待提交或状态未知的订单 | 等重试间隔，从「等开盘」的表重来 |
| 加仓的股票是无保护仓位 | 等重试间隔，从「等开盘」的表重来：补挂成功以后下单，到有效期还没补挂成功就按有效期作废 |
| 不在常规交易时段（再校验以后刚好收盘） | 从「等开盘」的表重来 |
| 最近一次对账有不一致（只有买入、加仓会这样） | 方案作废，原因是对账不一致；释放全部预留；告警；下单流程结束 |
| 别的错误：券商认证错误、数据库出错、意外的异常 | 写一条 ERROR，带异常栈；这个方案第一次出这种错时告警；等重试间隔，从「等开盘」的表重来 |

- 读实时数据、再校验出了别的错误（数据库出错、意外的异常），也按表的最后一行处理
- 等重试间隔、按有效期作废时，告警写上最近一次没能下单的原因
- 作废时这个方案已经有订单（比如提交时出了意外的错，订单已经建立）：不释放预留，订单交给盘中巡检

### Requirement: 告警

下单流程 SHALL 只为下面这些结果推送告警（discord-notification spec「告警」）：

| 结果 | 告警的内容 |
| --- | --- |
| 已经确认的方案作废：再校验拒绝、到有效期还没下单、对账不一致、排队运行作废（「作废案件的方案」） | 方案作废、不会下单；动作、股票、股数、方案 ID；原因：再校验拒绝的写每条不通过的规则和说明，到有效期的写最近一次没能下单的原因（有的话），对账不一致的写暂停开仓，排队运行作废的写这只股票有新案件排队 |
| 下单被券商拒绝 | 下单被券商拒绝；动作、股票、股数、方案 ID |
| 这个方案第一次出意外的错 | 下单出错和错误；动作、股票、方案 ID；每隔重试间隔重试，到有效期为止 |
| 案件的方案确认超时或确认请求发不出去，「案件的方案」决定超时以后告警（退出类方案） | 确认超时（或者确认请求没有发出去）、方案没有执行；动作、股票、股数、方案 ID；持仓的止损单照挂 |

不要人工确认的方案作废时，按第一行告警。

### Requirement: 持久化和恢复

下单流程 SHALL 把每一步的结果保存在数据库里。进程退出或崩溃以后，下次启动 SHALL 从断点继续：

- 已经做完的步骤不再做：不重复请求确认、不重复再校验和提交、不重复告警和释放
- 等确认的按剩下的时间接着等；停机期间过了截止时刻的，重启以后按确认超时处理
- 等开盘、等重试的接着等；停机期间已经到了的，重启以后立即接着做
- 程序更新以后重启，进行中的下单流程照样恢复

- **WHEN** 程序在 15:10Z 停止，15:40Z 启动
- **THEN** 启动以后 P1 按确认超时处理：确认消息显示已超时，BBB 没有有效预留

#### Scenario: 等开盘时重启

- **GIVEN** 当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认，下单流程在等 2026-10-15 13:30Z
- **WHEN** 程序在 2026-10-14 23:00Z 重启
- **THEN** 2026-10-15 13:30Z 券商收到 P1 的订单，此前没有收到

#### Scenario: 停机期间过了开盘

- **GIVEN** 当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认
- **WHEN** 程序在 2026-10-14 23:00Z 停止，2026-10-15 14:00Z 启动，BBB 最新价 50
- **THEN** 启动以后立即再校验，券商收到 P1 的订单

#### Scenario: 提交以后、记下结果之前进程退出

- **GIVEN** 已经提交 P1，按了确认；券商受理了 P1 的订单，下单流程还没记下这一步的结果时进程退出
- **WHEN** 程序重启
- **THEN** P1 已经有订单：不再校验、不再提交
- **AND** 券商仍然只有一笔 P1 的订单

#### Scenario: 程序更新以后恢复

- **GIVEN** 当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认
- **WHEN** 程序更新到新版本（下单流程的步骤没有变）并重启
- **THEN** 2026-10-15 13:30Z 券商收到 P1 的订单

### Requirement: 执行模块和风控的调用串行

下单流程和提交接口里，风控的检查、下单前再校验、释放预留，以及执行模块的提交订单 SHALL 拿着锁进行：

- 读账户数据、行情、熔断和降级的当前状态、一个方案的订单 SHALL NOT 拿锁
- 再校验和按它的结果提交订单 SHALL 在同一次拿锁里完成
- 请求确认、报告确认结果、推送告警，以及等确认、等开盘、等重试时 MUST NOT 拿着锁

#### Scenario: 别的调用拿着锁时检查等待

- **GIVEN** 另一个线程拿着锁（比如盘中巡检正在对齐一只股票）
- **WHEN** 提交 P1
- **THEN** 那个线程放开锁之前，BBB 没有预留
- **WHEN** 那个线程放开锁
- **THEN** 提交接口返回通过，BBB 有一份 20 股的预留

#### Scenario: 再校验和提交之间别人拿不到锁

- **GIVEN** 已经提交 P1
- **WHEN** 按确认，再校验通过，另一个线程这时要拿锁
- **THEN** 那个线程在券商收到 P1 的订单以后才拿到锁

#### Scenario: 请求确认时不拿锁

- **GIVEN** 提交 P1 时 Discord 发确认消息一直没有响应
- **WHEN** 下单流程还在等这次发送
- **THEN** 另一个线程可以立即拿到锁

### Requirement: 日志

下单流程和提交接口 SHALL 把每一步写进程序日志（program-log spec），对象是方案 ID：录入的方案（人的录入方案，只有 `/plan` 的方案有）、检查的结果（风控检查）、不要人工确认的方案的自动执行（系统的自动执行，在风控检查之后）、确认的结果（人的确认、拒绝、超时）、等开盘（等到的时刻）、再校验的结果（下单前再校验，转去等重试或等开盘的那几次不写）、提交的结果（提交订单：订单的状态和委托股数）、释放预留和原因。请求确认、报告确认已超时和推送告警由通知模块写（program-log spec「系统的动作」）。

- 等重试写 Python 日志的 WARNING 或 ERROR（见「下单前再校验和提交」「提交的结果」），不写程序日志；到有效期作废时，释放预留的原因写上最近一次没能下单的原因
- 送回案件的结果不另写程序日志：案件阶段的变化由案件工作流写（program-log spec「调度器的动作」）
- 进程重启以后，已经做完的步骤 SHALL NOT 再写一次

#### Scenario: 盘中下单的日志

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按确认，券商受理 P1
- **THEN** 程序日志依次有：P1 的录入方案、风控检查（通过 20 股）、请求确认（截止 2026-10-14 15:30Z）、确认、下单前再校验（通过 20 股）、提交订单（已提交 20 股）

#### Scenario: 自动执行的日志

- **GIVEN** 模型退出自动执行打开
- **WHEN** K3 交来 P3，P3 有订单
- **THEN** 程序日志依次有：P3 的风控检查（通过 10 股）、自动执行、下单前再校验（通过 10 股）、提交订单
- **AND** 没有录入方案、请求确认和人的确认

#### Scenario: 人工拒绝的日志

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按拒绝
- **THEN** 请求确认之后，程序日志依次有 P1 的拒绝、释放预留（人工拒绝）

#### Scenario: 到有效期作废的日志

- **GIVEN** 已经提交 P4；AAA 一直是无保护仓位；2026-10-14 19:59Z 按确认
- **WHEN** 到了 2026-10-14 20:00Z 以后
- **THEN** 程序日志有 P4 的释放预留，原因写明到了有效期还没下单、最近一次没能下单的原因是 AAA 是无保护仓位
- **AND** 等重试的几次只有 Python 日志的 WARNING，没有程序日志

#### Scenario: 重启以后不重复写日志

- **GIVEN** 当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认，程序日志已经有等到 2026-10-15 13:30Z 的等开盘
- **WHEN** 程序在 2026-10-14 23:00Z 重启
- **THEN** 重启以后程序日志里没有再写 P1 的请求确认、确认和等开盘

- **WHEN** 2026-10-14 15:05Z 按 P1 的确认
- **THEN** 2026-10-14 15:05:10Z 再读一次账户，券商收到 P1 的订单

### Requirement: 案件的方案

案件工作流把一个方案交给下单流程时（case-workflow spec「交给下单」），给出案件 ID、方案和 Critic 审核的结果（case-stages spec「案件的状态」：通过、有分歧、Critic 不可用）。下单流程 SHALL 按「提交方案」的第 1、2 步读账户数据、拿锁检查并预留，再按下表处理：

| 情况 | 处理 | 交给案件 |
| --- | --- | --- |
| 读券商账户超时、断线或出错 | 不检查、不预留、不启动下单流程；写一条 WARNING，写明方案 ID 和原因 | 风控检查出错 |
| 风控拒绝 | 不启动下单流程 | 风控结果 |
| 风控通过或调整 | 按 confirmation-rules spec「案件方案的确认」决定要不要人工确认、确认超时以后要不要告警，是否处于降级模式用这次检查读到的；以方案 ID 启动这个方案的下单流程，带上案件 ID、Critic 审核的结果和这两项决定 | 风控结果，以及要不要人工确认 |

- 不要人工确认的方案（模型退出自动执行）：风控检查以后写一条程序日志的自动执行（program-log spec「系统的动作」）；下单流程不请求确认，直接进入「等开盘」
- 案件的方案不写录入方案：录入方案是人用 `/plan` 的动作
- 案件工作流重放时（case-workflow spec「崩溃恢复」）不再检查、不另起下单流程，交给案件的仍是第一次的结果
- 之后的确认、等开盘、再校验和提交、告警、持久化和恢复，和 `/plan` 的方案相同，不同的地方写在「请求人工确认」「确认的结果」「告警」「日志」和「结果送回案件」里

本要求和「结果送回案件」的场景另外使用下面的数据：

- 案件 K1 交来 P1，Critic 审核的结果是通过；案件 K3 交来 P3，Critic 审核的结果是通过。"K1 交来 P1"指案件工作流以案件 ID K1、方案 P1 和 Critic 审核的结果交给下单流程
- "送回"指下单流程按案件 ID 送给案件的结果（case-workflow spec「交给下单」）
- 模型退出自动执行没有说明时是关闭的（默认值）

#### Scenario: 案件的开仓方案通过

- **WHEN** K1 交来 P1
- **THEN** 交给 K1 的是风控通过、最终 20 股、要人工确认
- **AND** BBB 有一份 20 股的开仓预留；频道里出现 P1 的确认消息，不附案件的意见
- **AND** 程序日志有 P1 的风控检查，没有录入方案

#### Scenario: 案件的方案被风控拒绝

- **GIVEN** 处于降级模式
- **WHEN** K1 交来 P1
- **THEN** 交给 K1 的是风控拒绝，原因是"降级模式"
- **AND** BBB 没有预留，频道里没有 P1 的确认消息，P1 没有下单流程

#### Scenario: 风控检查出错

- **GIVEN** 读券商账户时超时
- **WHEN** K1 交来 P1
- **THEN** 交给 K1 的是风控检查出错
- **AND** BBB 没有预留，没有确认消息；有一条 WARNING 写明 P1 和券商不可用

#### Scenario: 自动执行的退出方案

- **GIVEN** 模型退出自动执行打开
- **WHEN** K3 交来 P3
- **THEN** 交给 K3 的是风控通过、最终 10 股、不要人工确认
- **AND** 频道里没有 P3 的确认消息；程序日志在 P3 的风控检查以后有一条自动执行
- **AND** P3 有订单：卖出 AAA 10 股，市价单（止损单让出股数以后券商才收到，stop-protection spec「卖单先让出股数」）

#### Scenario: 自动执行打开时仍要确认的方案

- **GIVEN** 模型退出自动执行打开
- **WHEN** K1 交来 P1；K3 交来 P3，Critic 审核的结果是有分歧
- **THEN** 交给 K1、K3 的都是要人工确认，频道里各有一条确认消息
- **AND** 程序日志没有自动执行

#### Scenario: 降级模式下的退出方案要确认

- **GIVEN** 模型退出自动执行打开；处于降级模式
- **WHEN** K3 交来 P3
- **THEN** 交给 K3 的是风控通过、最终 10 股、要人工确认；频道里出现 P3 的确认消息

### Requirement: 结果送回案件

案件的方案的下单流程 SHALL 在下表的每个结局把结果按案件 ID 送回案件，`/plan` 录入的方案不送：

| 下单流程 | 送回 |
| --- | --- |
| 收下确认（「确认的结果」） | 已确认 |
| 收下拒绝 | 已拒绝 |
| 确认超时；确认请求发不出去 | 已超时 |
| 订单交给盘中巡检：提交返回订单（包括券商拒绝受理、状态未知），或者作废时这个方案已经有订单 | 订单已提交 |
| 确认以后（或者不要确认的方案）作废：再校验拒绝、到有效期还没下单、对账不一致 | 再校验作废 |
| 排队运行要求作废，在等确认、等开盘或者等重试（「作废案件的方案」） | 方案被作废 |
| 意料之外的错误让下单流程停下（比如释放预留时状态库出错） | 出错；送回以后下单流程停下 |

- 已确认在确认以后立即送回，然后才等开盘；不要确认的方案不送已确认
- 每个结局只送一次：进程重启以后已经送回的不再送
- 释放预留、告警和程序日志照「确认的结果」「下单前再校验和提交」「提交的结果」「告警」「日志」，送回结果不改变它们
- 等开盘、等重试时，除了被作废，不送回：案件在等下单时一直等（case-stages spec「等下单」）

#### Scenario: 确认以后下单

- **GIVEN** K1 交来 P1
- **WHEN** 2026-10-14 15:05Z 按确认，券商受理 P1
- **THEN** 依次送回 K1：已确认、订单已提交

#### Scenario: 拒绝和超时

- **GIVEN** K1 交来 P1
- **WHEN** 按拒绝
- **THEN** 送回 K1：已拒绝；BBB 没有有效预留
- **WHEN** 同样的情况下一直没有人按到 2026-10-14 15:30Z
- **THEN** 送回 K1：已超时

#### Scenario: 确认请求发不出去

- **GIVEN** Discord 对发消息报错
- **WHEN** K1 交来 P1
- **THEN** 送回 K1：已超时；BBB 没有有效预留

#### Scenario: 盘后确认等到开盘

- **GIVEN** 当前时刻 2026-10-14 21:00Z；K1 交来 P1，生效的有效期 2026-10-15 20:00Z
- **WHEN** 21:05Z 按确认
- **THEN** 送回 K1：已确认；没有别的结果
- **WHEN** 到了 2026-10-15 13:30Z，BBB 最新价 50，券商受理 P1
- **THEN** 送回 K1：订单已提交

#### Scenario: 再校验作废

- **GIVEN** 当前时刻 2026-10-14 21:00Z；K1 交来 P1，21:05Z 按确认
- **WHEN** 2026-10-15 13:30Z，BBB 最新价 53
- **THEN** P1 作废，原因是"价格偏离"；依次送回 K1：已确认、再校验作废

#### Scenario: 到有效期作废

- **GIVEN** 案件 K4 交来 P4，Critic 审核的结果是通过；AAA 一直是无保护仓位
- **WHEN** 2026-10-14 19:59Z 按确认，到了 20:00Z 以后
- **THEN** P4 作废，原因是有效期；依次送回 K4：已确认、再校验作废

#### Scenario: 被排队运行作废

- **GIVEN** K1 交来 P1
- **WHEN** 等确认时排队运行要求作废 P1
- **THEN** 送回 K1：方案被作废
- **WHEN** 另一种情况下，当前时刻 2026-10-14 21:00Z，21:05Z 按确认，在等开盘时排队运行要求作废 P1
- **THEN** 依次送回 K1：已确认、方案被作废

#### Scenario: 券商拒绝受理也是订单已提交

- **GIVEN** K1 交来 P1；券商会拒绝受理 P1

- **WHEN** 程序在 2026-10-14 23:00Z 重启；2026-10-15 13:30Z 券商受理 P1
- **THEN** K1 一共收到两个结果：已确认、订单已提交

#### Scenario: /plan 的方案不送回

- **WHEN** 本人用 `/plan` 提交 P1，按确认，券商受理 P1
- **THEN** 没有送给任何案件的结果

### Requirement: 作废案件的方案

排队运行要求作废一个案件的方案时（queue-runner spec「作废方案」），这个方案的下单流程 SHALL 按它这时在做什么处理：

| 下单流程 | 处理 | 送回案件 |
| --- | --- | --- |
| 在等确认 | 报告确认消息已作废（discord-notification spec「结束确认」）；拿锁释放全部预留；下单流程结束；不告警 | 方案被作废 |
| 已经确认，在等开盘或者等重试 | 拿锁释放全部预留；报告确认消息已作废（消息上的已确认改为已作废）；推送告警（见「告警」）；下单流程结束 | 方案被作废 |
| 正在做一步（请求确认、再校验和提交），或者在两步之间 | 这一步做完再看：接下来要等确认、等开盘或者等重试的，按上面两行作废；这一步提交了订单、作废了方案的，按下一行 | 按上面两行或者下一行 |
| 已经结束：拒绝、确认超时、确认请求发不出去、订单交给盘中巡检、再校验作废 | 不再处理 | 不再送回 |

- 作废时这个方案已经有订单（比如提交时出了意外的错，订单已经建立）：不释放预留、不报告确认消息、不告警，订单交给盘中巡检，送回订单已提交（同「提交的结果」）
- 释放预留写程序日志的释放预留，原因写明这只股票有新案件排队、方案作废；报告确认消息已作废由通知模块写程序日志的结束确认（program-log spec「系统的动作」）
- 作废和确认按钮的结果都送到时，按下单流程收到的先后处理：先收到确认的照常进入「等开盘」，盘中马上提交了订单的，之后的作废不再处理
- 作废送到以后、处理以前进程退出：重启以后照样作废（见「持久化和恢复」）
- 只有案件的方案会被排队运行作废：`/plan` 录入的方案不会

本要求的场景使用「案件的方案」的数据。

#### Scenario: 等确认时作废

- **GIVEN** K1 交来 P1，P1 的确认消息已经发出，截止时刻 2026-10-14 15:30Z
- **WHEN** 15:05Z 排队运行要求作废 P1
