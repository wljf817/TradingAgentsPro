# order-flow Specification

## Purpose
下单流程把人手工录入的交易方案从风控检查一路带到执行模块：通过或调整的方案预留额度、请求人工确认，确认以后在常规交易时段内再校验并提交订单，订单交给盘中巡检跟进；方案在下单以前结束时释放预留。下单流程的进度保存在数据库里，进程重启或程序更新以后从断点继续。

## Requirements

### Requirement: 提交方案

`/plan` 的提交接口（manual-plans spec「提交接口」）SHALL 按下面的顺序处理一个方案：

1. 读执行模块的账户数据（trade-records spec「账户数据」）和持仓股票的行情，拼成风控用的账户数据，见「风控用的账户数据」。这一步不拿锁
2. 拿锁（见「执行模块和风控的调用串行」），用风控检查方案并预留（risk-rules spec、risk-reservations spec）。单日亏损熔断是否触发取紧急退出的当前状态（emergency-exit spec），是否处于降级模式取健康监控的当前状态（degraded-mode spec）
3. 结论为拒绝：返回风控结果，不启动下单流程
4. 结论为通过或调整：启动这个方案的下单流程，返回风控结果，不等人工确认。下单流程以方案 ID 为标识，同一个方案 ID 只有一个下单流程

| 情况 | 处理 |
| --- | --- |
| 读券商账户超时、断线或出错 | 报错：不检查、不预留、不启动下单流程 |
| 启动下单流程失败（比如数据库出错） | 拿锁释放这个方案的预留，报错 |
| 同一个方案 ID 再次提交 | 风控返回第一次的结果（risk-reservations spec「同一方案重复检查」），不另起下单流程 |

报错以后 `/plan` 按 manual-plans spec「提交接口」回复提交出错。

本 spec 的场景除非另有说明，都使用下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中；当天 13:30Z 开盘、20:00Z 收盘），交易日历是纽交所日历
- 风控配置、执行配置（买单和止损单错开关闭）、通知配置（确认超时 30 分钟）、下单流程配置（重试间隔 30 秒）都用默认值；风控的每笔佣金是默认的 2
- 执行模块已经完成一次对账，没有不一致；单日亏损熔断没有触发；不处于降级模式
- 券商账户：权益 10,000，现金 10,000，没有未结算的卖出款，前一交易日收盘时的权益 10,000；持有 AAA 10 股，均价 100
- AAA 的开仓订单：板块"科技"，止损价 90，紧急阈值 0.08，最近成交日 2026-10-12；AAA 的止损单已对齐
- 行情：AAA 最新价 110，前一交易日收盘价 108；BBB 最新价 50，前一交易日收盘价 49.5
- 方案（都没填有效期、紧急阈值和允许价格偏离）：
  - P1：买入 BBB，板块"医疗"，20 股，限价单，限价 50，止损价 45。在当前时刻检查，结论为通过，最终 20 股，生效的有效期 2026-10-14 20:00Z
  - P2：减仓 AAA 4 股，市价单。检查结论为通过，最终 4 股
  - P3：清仓 AAA，市价单。检查结论为通过，最终 10 股
  - P4：加仓 AAA 5 股，限价单，限价 110，止损价 100。检查结论为通过，最终 5 股
- "提交 P1"指本人用 `/plan` 录入 P1，提交接口收到它；"按确认""按拒绝"指本人在截止时刻之前按 P1 的确认消息上的按钮，按钮的结果送达下单流程
- "券商收到 P1 的订单"指券商收到客户端订单 ID 是 P1 的提交；没有另外说明时券商正常受理，订单不成交
- "锁"指 session-patrol spec「执行模块和风控的调用串行」的那把锁

#### Scenario: 通过后启动下单流程

- **WHEN** 提交 P1
- **THEN** 提交接口返回通过，最终 20 股
- **AND** BBB 有一份 20 股的开仓预留
- **AND** 频道里出现 P1 的确认消息，写明买入 BBB 20 股、截止时刻 2026-10-14 15:30Z

- **AND** BBB 没有预留，频道里没有 P1 的确认消息，P1 没有下单流程

#### Scenario: 熔断触发后提交开仓方案

- **GIVEN** 今天的单日亏损熔断已经触发
- **WHEN** 提交 P1
- **THEN** 提交接口返回拒绝，原因是"单日亏损熔断"，没有确认消息

#### Scenario: 降级模式下提交退出方案

- **GIVEN** 处于降级模式
- **WHEN** 提交 P3
- **THEN** 提交接口返回通过，最终 10 股
- **AND** 频道里出现 P3 的确认消息

#### Scenario: 风控调整的方案

- **GIVEN** 券商现金改为 505
- **WHEN** 提交 P1
- **THEN** 提交接口返回调整，最终 10 股，原因是"已结算资金"
- **AND** BBB 有一份 10 股的开仓预留，P1 的确认消息写明已被风控调整、20 股调整为 10 股

#### Scenario: 读券商账户超时

- **GIVEN** 读券商账户时超时
- **WHEN** 提交 P1
- **THEN** 提交接口报错，原因写明券商不可用
- **AND** BBB 没有预留，没有确认消息

#### Scenario: 启动下单流程失败

- **GIVEN** 启动下单流程时数据库出错
- **WHEN** 提交 P1
- **THEN** 提交接口报错
- **AND** BBB 没有有效预留，没有确认消息

#### Scenario: 同一个方案提交两次

- **GIVEN** 已经提交 P1
- **WHEN** 用同一个方案 ID 再提交一次 P1
- **THEN** 提交接口返回通过，最终 20 股
- **AND** BBB 仍然只有一份 20 股的预留，频道里只有一条 P1 的确认消息

### Requirement: 查持仓的板块

减仓和清仓时 `/plan` 查持仓的板块（manual-plans spec「减仓和清仓的板块」），提交接口 SHALL 这样回答，不拿锁：

| 账户数据 | 回答 |
| --- | --- |
| 执行模块的账户数据里有这只股票的持仓 | 它的板块（开仓订单的板块） |
| 账户数据里没有这只股票（没有持仓，或者持仓找不到有成交的开仓订单） | 没有 |
| 读券商账户超时、断线或出错 | 报错 |

#### Scenario: 减仓有持仓的股票

- **WHEN** 本人运行 `/plan reduce symbol:AAA quantity:4`
- **THEN** 查到板块"科技"，提交接口收到 P2 这样的方案：减仓 AAA 4 股，板块"科技"

#### Scenario: 清仓没有持仓的股票

- **WHEN** 本人运行 `/plan close symbol:XYZ`
- **THEN** 回复没有 XYZ 的持仓，没有提交

#### Scenario: 查持仓时券商不可用

- **GIVEN** 读券商账户超时
- **WHEN** 本人运行 `/plan close symbol:AAA`
- **THEN** 回复查持仓出错，没有提交

### Requirement: 风控用的账户数据

首次检查和下单前再校验用的账户数据 SHALL 按下表拼成，结构见 risk-rules spec「风控的输入和判定」：

| 项 | 取值 |
| --- | --- |
| 权益、已结算资金、每只股票的最近成交日 | 执行模块的账户数据 |
| 持仓的股票、板块、股数、均价、止损价 | 执行模块的账户数据：只有能找到开仓订单的持仓 |
| 持仓的最新价 | 这只股票的行情的最新价；没有最新价（盘前，或者当天开盘后还没有成交）时用前一交易日收盘价；取不到这只股票的行情（行情不可用，或者行情源没有它）时用均价，并写一条 WARNING，写明股票和原因 |

- 只取持仓股票的行情，一次取完；没有持仓时不取行情
- 取不到行情时首次检查照常进行：持仓按均价估市值只影响单只仓位上限和板块集中度的估算，开仓方案在下单前还会用实时数据再校验，见「下单前再校验和提交」

#### Scenario: 盘中的账户数据

- **WHEN** 提交 P1
- **THEN** 风控用的账户数据：权益 10,000，已结算资金 10,000；持仓 AAA：板块"科技"，10 股，均价 100，最新价 110，止损价 90；AAA 的最近成交日 2026-10-12

#### Scenario: 盘前用前一交易日收盘价

- **GIVEN** 当前时刻 2026-10-14 12:00Z（开盘前）；AAA 的行情没有最新价
- **WHEN** 提交 P1
- **THEN** 风控用的账户数据里 AAA 的最新价是 108

#### Scenario: 取不到行情时用均价

- **GIVEN** 取行情时行情不可用
- **WHEN** 提交 P1
- **THEN** 风控用的账户数据里 AAA 的最新价是 100
- **AND** 有一条 WARNING 写明 AAA 和行情不可用
- **AND** 提交接口返回通过，最终 20 股

#### Scenario: 行情源没有这只股票

- **GIVEN** 行情源没有 AAA 的数据
- **WHEN** 提交 P1
- **THEN** 风控用的账户数据里 AAA 的最新价是 100，有一条 WARNING 写明 AAA

#### Scenario: 没有持仓时不取行情

- **GIVEN** 券商没有持仓
- **WHEN** 提交 P1
- **THEN** 没有向行情源取行情，提交接口返回通过

### Requirement: 请求人工确认

下单流程开始以后 SHALL 立即为方案请求人工确认（discord-notification spec「确认请求和截止时刻」「确认消息」），四种动作（买入、加仓、减仓、清仓）都要。确认消息用提交时的风控结果：股数是最终股数，调整时写明已被风控调整和原因。截止时刻是请求的时刻加上确认超时。

请求确认时 MUST NOT 拿着锁。

确认请求发不出去（通知不可用：Discord 报错、超过发送超时、没有连接）时，SHALL 按确认超时处理（Proposal「技术栈与部署」）：释放这个方案的全部预留，写一条 ERROR，写明方案 ID 和原因；下单流程结束，不再请求，不告警。

#### Scenario: 四种动作都请求确认

- **WHEN** 先后提交 P1、P2、P3、P4
- **THEN** 频道里依次出现四条确认消息：买入 BBB 20 股、减仓 AAA 4 股、清仓 AAA 6 股（扣除 P2 的 4 股卖出预留）、加仓 AAA 5 股
- **AND** 四条消息的截止时刻都是 2026-10-14 15:30Z

#### Scenario: 确认请求发不出去

- **GIVEN** Discord 对发消息报错
- **WHEN** 提交 P1
- **THEN** 提交接口返回通过，最终 20 股
- **AND** 之后 BBB 没有有效预留；有一条 ERROR 写明 P1 的确认请求没有发出去和原因
- **AND** 券商没有收到 P1 的订单，P1 的下单流程已经结束

### Requirement: 确认的结果

下单流程 SHALL 等确认的结果，按下表处理：

| 结果 | 处理 |
| --- | --- |
| 截止时刻之前按确认 | 进入「等开盘」；不再请求确认 |
| 截止时刻之前按拒绝 | 释放全部预留；下单流程结束；不告警 |
| 到截止时刻没有结果 | 报告确认消息已超时（discord-notification spec「结束确认」），释放全部预留；下单流程结束；不告警 |
| 确认请求发不出去 | 见「请求人工确认」 |

#### Scenario: 盘中确认后立即下单

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按确认
- **THEN** 确认消息显示已确认
- **AND** 券商收到 P1 的订单：买入 BBB 20 股，限价单，限价 50，当日有效
- **AND** BBB 的预留仍是 20 股：之后由盘中巡检跟进 P1 的订单（session-patrol spec）

#### Scenario: 人工拒绝

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按拒绝
- **THEN** 确认消息显示已拒绝；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单，没有告警

#### Scenario: 确认超时

- **GIVEN** 已经提交 P1，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 确认消息显示已超时；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单，没有告警

#### Scenario: 截止前一刻确认

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:29:59Z 按确认
- **THEN** 券商收到 P1 的订单

#### Scenario: 调整的方案按调整后的股数确认

- **GIVEN** 券商现金改为 505，已经提交 P1，结论为调整，最终 10 股
- **WHEN** 按确认，下单前再校验通过，最终 10 股（请求股数是预留的 10 股）
- **THEN** 券商收到 P1 的订单：买入 BBB 10 股

### Requirement: 按钮的结果只送给在等确认的方案

确认按钮的回调（discord-notification spec「按钮的处理」）SHALL 按这个方案的下单流程的状态处理：

| 下单流程 | 处理 |
| --- | --- |
| 正在等确认：已经开始请求确认，还没有得出结果 | 把确认或拒绝送给它 |
| 不存在（方案 ID 没有下单流程，比如以前的测试留下的消息） | 报错：这个方案没有在等确认 |
| 已经得出确认的结果（确认、拒绝、超时、确认请求发不出去），或者已经结束 | 报错：这个方案没有在等确认 |

- 报错时按钮按 discord-notification spec 提示没有送达，消息上的按钮还在，不会显示已确认
- 回调送达和确认超时同时发生、下单流程先得出超时的：下单流程按超时处理，并报告确认消息已超时；按 discord-notification spec「结束确认」，消息最后显示已超时，不下单
- 程序重启以后，重启以前还在等确认的方案仍然算在等确认（见「持久化和恢复」）

#### Scenario: 在等确认时送达

- **GIVEN** 已经提交 P1，下单流程在等确认
- **WHEN** 本人按确认
- **THEN** 回调没有报错，下单流程收到确认

#### Scenario: 方案没有下单流程

- **GIVEN** 频道里有一条方案 X 的确认消息，还没到截止时刻，X 没有下单流程
- **WHEN** 本人按确认
- **THEN** 回调报错，写明 X 没有在等确认
- **AND** 按钮提示没有送达，消息上的按钮还在

#### Scenario: 已经确认过的方案

- **GIVEN** 已经提交 P1，按了确认，券商收到了 P1 的订单；之后程序重启，P1 的确认消息上的按钮还能按（还没到截止时刻）
- **WHEN** 本人再按确认
- **THEN** 回调报错，写明 P1 没有在等确认
- **AND** 券商仍然只有一笔 P1 的订单

#### Scenario: 确认请求超时以后消息才发出去

- **GIVEN** 提交 P1 时 Discord 很慢，请求确认超过发送超时，按发不出去处理，BBB 没有有效预留；随后这条确认消息出现在频道里
- **WHEN** 本人按确认
- **THEN** 回调报错，按钮提示没有送达
- **AND** 券商没有收到 P1 的订单

#### Scenario: 按钮和超时同时

- **GIVEN** 已经提交 P1，下单流程在 2026-10-14 15:30Z 得出超时
- **WHEN** 本人的确认在下单流程得出超时以后才送到
- **THEN** 确认消息最后显示已超时；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单

### Requirement: 等开盘

确认以后，以及每一次重试之前（见「提交的结果」），下单流程 SHALL 按当前时刻决定：

| 当前时刻 | 处理 |
| --- | --- |
| 不早于提交时风控给出的生效有效期 | 方案作废，原因是有效期；释放全部预留（这个方案已经有订单的除外，见「提交的结果」）；告警；下单流程结束 |
| 在常规交易时段内 | 立即做「下单前再校验和提交」 |
| 不在常规交易时段内（盘前、盘后、休市日），早于生效的有效期 | 等到下一个开盘时刻，再按这张表 |

- 先看有效期：到了有效期，不论在不在盘中都作废
- 等开盘跨重启：程序重启以后只等剩下的时间；停机期间已经过了开盘时刻的，重启以后立即按这张表处理
- 生效的有效期是某个交易日的收盘时刻（risk-rules spec），所以早于有效期时，下一个开盘时刻一定早于有效期

#### Scenario: 盘后确认，下一个交易日开盘下单

- **GIVEN** 当前时刻 2026-10-14 21:00Z（盘后）；提交 P1，结论为通过，生效的有效期 2026-10-15 20:00Z
- **WHEN** 2026-10-14 21:05Z 按确认
- **THEN** 券商没有收到 P1 的订单，下单流程等到 2026-10-15 13:30Z
- **WHEN** 到了 2026-10-15 13:30Z，BBB 最新价 50
- **THEN** 券商收到 P1 的订单：买入 BBB 20 股，截止时刻 2026-10-15 20:00Z

#### Scenario: 周五盘后确认，等到周一开盘

- **GIVEN** 当前时刻 2026-10-16 21:00Z（周五盘后）；提交 P1，生效的有效期 2026-10-19 20:00Z
- **WHEN** 2026-10-16 21:05Z 按确认
- **THEN** 下单流程等到 2026-10-19 13:30Z（周一开盘）才再校验

#### Scenario: 盘前确认等当天开盘

- **GIVEN** 当前时刻 2026-10-14 12:00Z（开盘前）；提交 P1，生效的有效期 2026-10-14 20:00Z
- **WHEN** 2026-10-14 12:05Z 按确认
- **THEN** 下单流程等到 2026-10-14 13:30Z，然后券商收到 P1 的订单

#### Scenario: 确认时已经过了有效期

- **GIVEN** 当前时刻 2026-10-14 19:50Z；提交 P1，生效的有效期 2026-10-14 20:00Z，截止时刻 20:20Z
- **WHEN** 2026-10-14 20:05Z 按确认
- **THEN** P1 作废，原因是有效期；BBB 没有有效预留
- **AND** 推送一条告警，写明 P1 作废、不会下单和原因
- **AND** 券商没有收到 P1 的订单

### Requirement: 下单前再校验和提交

在常规交易时段内，下单流程 SHALL 依次：

1. 这个方案已经有订单（之前已经提交过）：不再校验，不再提交，订单交给盘中巡检，下单流程结束
2. 读实时账户数据（见「风控用的账户数据」）。开仓方案还要这只股票当天的最新价；减仓和清仓不需要这只股票的最新价，取不到行情也照常再校验（风控不看退出方案的最新价，pre-order-recheck spec「价格偏离」「跌破止损价」）
3. 拿锁，用风控做下单前再校验（pre-order-recheck spec），熔断和降级的取法同「提交方案」
4. 通过或调整：在同一次拿锁里，按再校验的结果提交订单（order-lifecycle spec「提交订单」），结果见「提交的结果」。调整只会往小调，SHALL NOT 再请求确认
5. 拒绝（有效期、价格偏离、跌破止损价、单日亏损熔断、降级模式、可卖数量、方案已结束等）：方案作废，预留已经由再校验释放；告警写明每条不通过的规则；下单流程结束

取不到数据时 SHALL 等一个重试间隔，再从「等开盘」的表开始：

| 情况 | 处理 |
| --- | --- |
| 开仓方案这只股票没有当天的最新价（刚开盘还没有成交），或者取行情时行情不可用、行情源没有它 | 写一条 WARNING；等重试间隔 |
| 读券商账户超时或断线 | 写一条 WARNING；等重试间隔 |

### Requirement: 提交的结果

按再校验的结果提交订单以后，下单流程 SHALL 按下表处理：

| 提交的结果 | 处理 |
| --- | --- |
| 返回订单：已提交、部分成交、全部成交或状态未知 | 订单交给盘中巡检；下单流程结束 |
| 返回订单：已拒绝（券商拒绝受理） | 告警；下单流程结束。预留由盘中巡检释放（session-patrol spec「每一轮」第 2 步） |
| 还没完成过对账 | 等重试间隔，从「等开盘」的表重来 |
| 这只股票有待提交或状态未知的订单 | 等重试间隔，从「等开盘」的表重来 |
| 加仓的股票是无保护仓位 | 等重试间隔，从「等开盘」的表重来：补挂成功以后下单，到有效期还没补挂成功就按有效期作废 |
| 不在常规交易时段（再校验以后刚好收盘） | 从「等开盘」的表重来 |
| 最近一次对账有不一致（只有买入、加仓会这样） | 方案作废，原因是对账不一致；释放全部预留；告警；下单流程结束 |
| 别的错误：券商认证错误、数据库出错、意外的异常 | 写一条 ERROR，带异常栈；这个方案第一次出这种错时告警；等重试间隔，从「等开盘」的表重来 |

- 读实时数据、再校验出了别的错误（数据库出错、意外的异常），也按表的最后一行处理
- 等重试间隔、按有效期作废时，告警写上最近一次没能下单的原因
- 作废时这个方案已经有订单（比如提交时出了意外的错，订单已经建立）：不释放预留，订单交给盘中巡检

### Requirement: 持久化和恢复

### Requirement: 执行模块和风控的调用串行

- **THEN** 请求确认之后，程序日志依次有 P1 的拒绝、释放预留（人工拒绝）

#### Scenario: 到有效期作废的日志

- **GIVEN** 已经提交 P4；AAA 一直是无保护仓位；2026-10-14 19:59Z 按确认
- **WHEN** 到了 2026-10-14 20:00Z 以后
- **THEN** 程序日志有 P4 的释放预留，原因写明到了有效期还没下单、最近一次没能下单的原因是 AAA 是无保护仓位
- **AND** 等重试的几次只有 Python 日志的 WARNING，没有程序日志

#### Scenario: 重启以后不重复写日志

- **GIVEN** 当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认，程序日志已经有等到 2026-10-15 13:30Z 的等开盘
- **WHEN** 程序在 2026-10-14 23:00Z 重启
- **THEN** 重启以后程序日志里没有再写 P1 的请求确认、确认和等开盘

### Requirement: 下单流程配置

下单流程的阈值 SHALL 可以配置：

| 配置项 | 默认值 | 要求 | 理由 |
| --- | --- | --- | --- |
| 重试间隔 | 30 秒 | 大于 0 | 状态未知的订单 30 秒后再查（order-lifecycle spec「执行配置」），盘中巡检 15 秒一轮；每次重试读一次账户和行情、做一次再校验，几次 Alpaca 请求 |

确认超时用通知配置的（默认 30 分钟，discord-notification spec），不在这里另设。

#### Scenario: 默认配置

- **WHEN** 不改下单流程配置
- **THEN** 重试间隔是 30 秒

#### Scenario: 修改重试间隔

- **GIVEN** 重试间隔改为 10 秒；已经提交 P1；再校验之前读券商账户会超时一次
- **WHEN** 2026-10-14 15:05Z 按 P1 的确认
- **THEN** 2026-10-14 15:05:10Z 再读一次账户，券商收到 P1 的订单

#### Scenario: 重试间隔不大于 0

- **WHEN** 重试间隔设为 0 秒或 -1 秒
- **THEN** 配置报错
