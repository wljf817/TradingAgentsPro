# Proposal

## Why

Proposal 要求每日的模型调用预算分普通预算和持仓保留预算两部分，寻股另用一个单独的预算，都按案件侧的"每日"（交易日）算。前面的变更已经把用的地方都备好了：case-queue spec 的快照要"普通预算是否用完""寻股预算是否用完"两个标志，并按案件类型决定用完以后哪些案件留在队列里；degraded-mode spec 的健康检查要"持仓保留预算是否用完"；task-dispatch spec 的 Result 有费用一项，"怎么算由「调用预算」定"；model-fallback spec 规定本系统的调用预算用完不算模型不可用。但现在没有东西记下每次模型调用花了多少钱，也没有东西算出三个预算还剩多少、什么时候算用完。

本变更的目的只有一个：**记下每次模型调用的费用，按案件侧的"每日"算普通预算、持仓保留预算和寻股预算还剩多少，给出队列和健康监控要的"预算用完"标志。**

引用的 Proposal（完整版）章节：

- 「调度器与运行模块」：运行模块表的 Agent 网关一行（检查预算）和健康监控一行（监控调用预算）；运行约束的每日模型调用预算一条（分普通和持仓保留两部分，普通预算用完以后只处理持仓相关的案件，持仓保留预算也用完才进入降级模式，寻股只看寻股预算，复盘用普通预算）和"案件侧按天计的上限按交易日算"一条
- 「股票池与寻股」：寻股使用单独的调用预算
- 「触发 · 3. 自定义跟进」：每天的申请次数有上限，计入调用预算
- 「Task / Result 通信」：Result 的耗时和费用；PM 派发的任务受调用预算约束
- 「故障处理」：健康监控负责调用预算；降级模式不开始新案件

## What Changes

- 记下每次模型调用的费用：调用方每次向模型发出的请求拿到厂商给出的 token 用量以后，交给 Agent 网关记下一条，包括案件 ID、案件类型、agent、模型、用量、费用、记到哪个预算、记下的时刻。拿不到用量的请求（连接失败、超时）不记。记录只追加，放在存储里，进程重启以后接着算
- 费用的算法：输入 token 数乘输入单价加输出 token 数乘输出单价，单价是每百万 token 多少美元，精确计算不舍入。单价写在模型的配置里，每个模型一份；任何 agent 用到的模型没有单价、同一个模型配了两份单价都是配置报错，启动时拒绝启动
- 费用记到哪个预算，按记之前的情况整笔记到一个预算，不拆分：

  | 案件类型 | 记之前普通预算没用完 | 记之前普通预算已经用完 |
  | --- | --- | --- |
  | 寻股 | 寻股预算 | 寻股预算 |
  | 持仓的五种（含持仓跟进） | 普通预算 | 持仓保留预算 |
  | 关注、候选的六种（含关注跟进）和两种复盘 | 普通预算 | 普通预算 |

- 每日的划分：按记下的时刻归属的交易日（trading-calendar spec「时刻归属的交易日」），收盘那一刻三个预算一起恢复
- 预算用完：今天记到这个预算的费用不小于它的额度。给出现在归属的交易日、每个预算今天记下的费用和用完的预算；普通预算、寻股预算是否用完交给队列，持仓保留预算是否用完交给健康监控
- 已经开始的案件：网关不因为预算用完拒绝任务和调用。预算只在案件开始时由队列看（以及健康监控据此进入降级模式），开始了的案件跑完，它的调用照常记下，预算可以超出一点，超出的部分受每个案件的任务数、轮次、重交次数和质询轮次限制
- 子 agent 任务的费用：Result 的费用是这个任务各次模型调用记下的费用之和（包括重试和备用模型），调用方算好交给任务派发
- 可配置项：普通预算 2.00 美元、持仓保留预算 1.00 美元、寻股预算 0.50 美元，都是每个交易日，必须大于 0
- contracts：`contracts/model.py` 加 token 用量 `TokenUsage`；`contracts/task.py` 的 Result 的费用只改注释，写明怎么算
- case-stages spec「系统故障」只改措辞：网关不因为预算用完拒绝运行中案件的调用，去掉"因为预算用完拒绝 PM 的调用"这种情况

## Non-goals

- 队列在预算用完时哪些案件留在队列里、恢复以后按优先级运行：case-queue spec「调用预算」已经规定
- 持仓保留预算用完以后进入降级模式、恢复以后等对账：degraded-mode spec 已经规定
- 每天的跟进申请次数：follow-ups spec「每天的申请次数」已经规定，本变更不另外限制（「需要人决定」第 9 条）
- 「人工确认的规则」
- M4：
  - 费用记录的表和 repo，只追加
  - 把普通预算、寻股预算是否用完填进队列的快照，持仓保留预算是否用完填进健康信号；某个预算刚用完、交易日收盘预算恢复时重新取得队列的决定、让健康监控判定
  - 每条费用记录写进程序日志（Agent 网关的 token 和费用、系统的调用预算消耗）；预算用完时告警
  - bootstrap 从配置文件读取单价和三个额度；第一次健康判定改用这里给出的持仓保留预算是否用完
- M5：从模型的返回里取 token 用量；每次请求以后记下费用；把一个任务的费用之和交给任务派发
- 按 agent、模型或案件类型统计费用：M6 复盘需要时再加

## Capabilities

### New Capabilities

- `call-budget`：费用的记录；模型的单价；费用的算法；费用记到哪个预算；每日的划分；预算用完；已经开始的案件；子 agent 任务的费用；预算的配置

### Modified Capabilities

- `case-stages`：「系统故障」写明预算用完时网关不拒绝运行中案件的调用，「PM 的调用失败」去掉"网关因为预算用完拒绝 PM 的调用"（只改措辞，调度器代码不改）

## 需要人决定

已决定（2026-10-08）：

1. **预算按什么算**：按美元费用算，不按调用次数。各模型的价格差很多，按次数算不准
2. **案件侧的"每日"**：一个交易日从上一个交易日收盘到这个交易日收盘，周末和休市日并进下一个交易日（trading-calendar spec 的时刻归属的交易日）
3. **普通预算用完以后**：只有持仓相关的案件照常启动，改用持仓保留预算；非持仓案件留在队列里，等下一个交易日预算恢复后按优先级运行。寻股用单独的预算；复盘案件用普通预算（case-queue spec 已经落实）

新发现的，已按推荐做法写进 spec，不同意可以改：

4. **已经开始的案件怎么办**：Proposal 写网关"检查……预算"、PM 的任务"受……调用预算约束"，没说预算在案件中途用完时怎样。推荐只在案件开始时由队列看预算标志（持仓保留预算由健康监控看，用完就进入降级模式、不开始新案件），网关不因为预算用完拒绝任务和调用；开始了的案件跑完，调用照常记下，预算可以超出一点。理由：中途拒绝会让案件因系统故障结束，已经花掉的钱白花，持仓案件还可能在提出退出方案以前被打断；超出的部分受每个案件的任务数（PM 6 个、Critic 2 个）、轮次（2 轮）、重交次数（2 次）、质询轮次（2 轮）和并发上限（3 个）限制，通常不到一美元，最坏是三个并发的案件都用满上限，两三美元。Proposal 的这两处改措辞；case-stages spec 去掉"网关因为预算用完拒绝 PM 的调用"
5. **费用怎么算**：推荐每个模型配输入和输出两个单价（美元/百万 token），费用是用量乘单价，精确计算不舍入；用量由调用方从模型的返回里取（M5），推理 token 算输出，缓存命中的 token 按普通输入单价算（偏高、偏保守，用不用缓存由 M5 定）。只记拿到用量的请求：连接失败、限流、超时这类请求拿不到用量，厂商通常也不收费。单价写在模型的配置里，任何 agent 用到的模型没有单价就配置报错、拒绝启动，免得运行中才发现算不出费用
6. **持仓案件记到哪个预算、一次调用跨过额度**：推荐每次调用按记之前的情况整笔记到一个预算，不拆分：记之前普通预算没用完就记普通预算（这一笔可以让它超出额度），已经用完就记持仓保留预算。案件开始以后普通预算才用完的持仓案件，之后的调用也改记持仓保留预算。非持仓案件只能用普通预算，普通预算用完以后还在跑的照常记普通预算。拆成两笔要多一种记录，超出的只是一次调用的钱
7. **"用完"的边界**：推荐今天记到这个预算的费用不小于额度就算用完，正好花到额度时不再启动新案件
8. **三个额度的默认值**：推荐普通预算 2.00 美元、持仓保留预算 1.00 美元、寻股预算 0.50 美元，每个交易日。理由：一个案件大约 0.2 到 0.4 美元（PM 调用 3 次左右，每次 2 万输入 token、2 千输出 token，单价 2 到 3 美元和 10 到 15 美元每百万 token；子 agent 用便宜模型，几个任务合计几美分；交易方案另有 Critic 1 到 3 次）。普通预算够平常一天的 5 到 10 个案件（几个事件、最多 3 个候选评估、复查日、跟进）；持仓保留预算够普通预算用完以后 3 到 4 个持仓案件，坏日子里几只持仓的风险事件能处理，止损单和紧急风险退出本来不靠模型；寻股有 3 个交易日的冷却期，0.50 美元够一次寻股。每天最多约 3.5 美元，一个月约 75 美元，是 2000 美元账户的 4% 左右，平常用不满。模拟盘阶段按 M5 的实际用量再调
9. **自定义跟进"计入调用预算"的含义**：推荐跟进案件的模型调用和其他案件一样按案件类型计入预算（持仓跟进按持仓案件，关注跟进用普通预算），每天申请次数的上限由跟进审批管（follow-ups spec 已经规定），这里不另外限制、不另外计数。Proposal 改为"跟进案件的模型调用按案件类型计入调用预算"
10. **预算放在存储里**：推荐费用记录只追加、放在存储里（M4 建表），三个预算从当天的记录算出来，进程重启以后接着算。放在内存里的话，重启就重新给一整天的额度。记录同时是程序日志里 token 和费用的来源
11. **Result 的费用**：推荐是这个任务各次模型调用记下的费用之和，包括重试和备用模型的；被拒绝和复用的任务没有调用，是 0。task-dispatch spec 写的是"调用方给出的这个任务调用模型的费用"，不用改。Proposal 的 Result 一行补上
