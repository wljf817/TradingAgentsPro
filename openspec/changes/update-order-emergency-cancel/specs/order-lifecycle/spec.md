# Spec Delta

## ADDED Requirements

### Requirement: 提前撤单

执行模块 SHALL 支持两种提前撤单。任何时刻都可以调用，也可以重复调用；不要求已经完成对账，也不要求在常规交易时段内：

| 提前撤单 | 撤哪些订单 |
| --- | --- |
| 撤掉一只股票的订单 | 这只股票全部没结束的订单，买单和卖单都算 |
| 撤掉全部买单 | 所有股票全部没结束的买单 |

调用时，执行模块给这些订单记下撤单要求并保存，再各跟进一次（见「订单状态和券商回报」），返回跟进之后的这些订单。已经结束的订单不变，也不返回。紧急风险退出前撤掉这只股票的订单；单日亏损熔断时撤掉全部买单。

有撤单要求的订单，之后每次跟进 SHALL 按下表处理，直到进入终态：

| 订单状态 | 跟进时的处理 |
| --- | --- |
| 已提交、部分成交 | 按券商回报更新之后仍未结束，就请求撤单 |
| 待提交；券商从没受理过的状态未知 | 按「先查询再提交」先查询：查到就按券商回报处理，仍未结束就请求撤单；查不到就不再提交，截止时刻之前结束为已撤销，之后结束为已过期 |
| 受理过的状态未知 | 按「券商调用失败时状态未知」，满等待时长之前不调用券商；之后查询，查到仍未结束就请求撤单 |

状态未知的订单都要满等待时长才调用券商，和没有撤单要求时一样。每笔订单只请求一次撤单，到期撤单也算在内，请求失败的除外（见「券商调用失败时状态未知」）。请求之后订单状态不变，直到券商回报撤销或失效，那时按「订单状态和券商回报」记为已撤销（截止时刻之前）或已过期。撤单之前和之后的成交照常计入累计成交。

有撤单要求的方案再次提交时，同样只跟进已有的订单，SHALL NOT 再提交给券商。

#### Scenario: 撤掉挂着的订单

- **GIVEN** 基准方案已经提交，订单已提交
- **WHEN** 2026-10-14 15:10Z 撤掉 BBB 的订单
- **THEN** 券商收到 P1 的撤单请求
- **AND** 返回 P1 的订单，仍是已提交，有撤单要求
- **WHEN** 券商回报变为撤销、累计成交 0，2026-10-14 15:10:05Z 跟进订单
- **THEN** 订单已撤销，累计成交 0

#### Scenario: 部分成交后撤单，撤单生效之前又有成交

- **GIVEN** 基准方案已经提交，订单部分成交，累计成交 30
- **WHEN** 撤掉 BBB 的订单
- **THEN** 券商收到 P1 的撤单请求
- **WHEN** 券商回报变为已受理、累计成交 50，跟进订单
- **THEN** 订单部分成交，累计成交 50，券商没有收到第二次撤单请求
- **WHEN** 券商回报变为撤销、累计成交 50，跟进订单
- **THEN** 订单已撤销，累计成交 50

#### Scenario: 撤掉还在等止损单让出股数的卖单

- **GIVEN** 基准数据，P1 全部成交，券商持仓 BBB 100 股，止损单 BBB-STOP-1 挂着 100 股；减仓 BBB 60 股的方案 P3 已经提交，止损单还没让出股数，P3 的订单待提交
- **WHEN** 撤掉 BBB 的订单
- **THEN** 券商收到按 P3 的查询，查不到，没有收到 P3 的提交
- **AND** P3 的订单已撤销，累计成交 0
- **AND** BBB 的止损目标恢复为 100 股（见 stop-protection spec「止损目标」）

#### Scenario: 提交超时、券商没有收到的订单

- **GIVEN** 基准数据，提交超时，券商没有收到，P1 的订单状态未知，记下 2026-10-14 15:00Z
- **WHEN** 2026-10-14 15:00:10Z 撤掉 BBB 的订单
- **THEN** 不调用券商，订单仍是状态未知，有撤单要求
- **WHEN** 2026-10-14 15:00:30Z 跟进订单
- **THEN** 券商收到按 P1 的查询，查不到，没有收到 P1 的提交
- **AND** 订单已撤销，累计成交 0

#### Scenario: 提交超时、券商其实收到了的订单

- **GIVEN** 基准数据，提交超时，券商其实收到了，P1 的订单状态未知，记下 2026-10-14 15:00Z
- **WHEN** 2026-10-14 15:00:10Z 撤掉 BBB 的订单，2026-10-14 15:00:30Z 跟进订单
- **THEN** 查到这笔订单已受理，券商收到 P1 的撤单请求
- **AND** 订单已提交，券商只有一笔 P1 的订单

#### Scenario: 受理过的订单状态未知

- **GIVEN** 基准方案已经提交，订单已提交；2026-10-14 15:10Z 跟进时断线，订单状态未知
- **WHEN** 2026-10-14 15:10:10Z 撤掉 BBB 的订单
- **THEN** 不调用券商
- **WHEN** 2026-10-14 15:10:30Z 跟进订单，券商回报仍是已受理、累计成交 0
- **THEN** 订单已提交，券商收到 P1 的撤单请求

#### Scenario: 有撤单要求，截止时刻之后才确认券商没有收到

- **GIVEN** 基准数据，基准结果的生效有效期改为 2026-10-14 16:00Z，2026-10-14 15:59:50Z 提交基准方案，提交超时，券商没有收到
- **WHEN** 2026-10-14 15:59:55Z 撤掉 BBB 的订单，2026-10-14 16:00:20Z 跟进订单
- **THEN** 券商没有收到 P1 的提交，订单已过期，累计成交 0

#### Scenario: 提前撤单的请求失败

- **GIVEN** 基准方案已经提交，订单已提交
- **WHEN** 2026-10-14 15:10Z 撤掉 BBB 的订单，撤单请求超时，券商没有收到
- **THEN** 订单状态未知，记下的时刻是 2026-10-14 15:10Z，有撤单要求
- **WHEN** 2026-10-14 15:10:30Z 跟进订单，券商回报仍是已受理、累计成交 0
- **THEN** 订单已提交，券商再次收到 P1 的撤单请求

#### Scenario: 撤单之前已经全部成交

- **GIVEN** 基准方案已经提交，订单已提交；券商回报变为全部成交、累计成交 100
- **WHEN** 撤掉 BBB 的订单
- **THEN** 返回 P1 的订单，全部成交，累计成交 100
- **AND** 券商没有收到 P1 的撤单请求

#### Scenario: 只撤这只股票的订单

- **GIVEN** 基准方案已经提交，订单已提交；加仓 AAA 50 股的方案 P2 已经提交，订单已提交
- **WHEN** 撤掉 BBB 的订单
- **THEN** 只返回 P1 的订单；券商收到 P1 的撤单请求，没有收到 P2 的
- **AND** P2 的订单没有撤单要求

#### Scenario: 撤掉全部买单

- **GIVEN** 基准方案已经提交，订单已提交；加仓 AAA 50 股的方案 P2、减仓 AAA 60 股的方案 P3 都已经提交，订单都已提交
- **WHEN** 撤掉全部买单
- **THEN** 返回 P1 和 P2 的订单；券商收到 P1 和 P2 的撤单请求，没有收到 P3 的
- **AND** P3 的订单没有撤单要求

#### Scenario: 重复撤单和已经结束的订单

- **GIVEN** 基准方案已经提交，订单已提交；2026-10-14 15:10Z 撤掉 BBB 的订单
- **WHEN** 2026-10-14 15:10:05Z 再撤掉一次 BBB 的订单，券商回报仍是已受理
- **THEN** 券商只收到一次 P1 的撤单请求
- **WHEN** 券商回报变为撤销，跟进订单，订单已撤销；之后再撤掉一次 BBB 的订单
- **THEN** 不返回任何订单，券商没有收到和 P1 有关的调用

#### Scenario: 有撤单要求的方案再次提交

- **GIVEN** 基准数据，提交超时，券商没有收到，P1 的订单状态未知，记下 2026-10-14 15:00Z；2026-10-14 15:00:10Z 撤掉 BBB 的订单
- **WHEN** 2026-10-14 15:00:30Z 再次提交基准方案
- **THEN** 不新建订单，券商没有收到 P1 的提交
- **AND** P1 的订单已撤销

#### Scenario: 还没对账时也可以撤单

- **GIVEN** 基准方案已经提交，订单已提交；进程重启，执行模块还没有完成对账
- **WHEN** 撤掉 BBB 的订单
- **THEN** 券商收到 P1 的撤单请求

## MODIFIED Requirements

### Requirement: 先查询再提交

执行模块每次向券商提交订单之前，SHALL 先按客户端订单 ID 查询：

- 查到：采用券商回报（见「订单状态和券商回报」），不再提交
- 查不到，当前时刻早于截止时刻，没有撤单要求：提交，客户端订单 ID 不变
- 查不到，当前时刻早于截止时刻，有撤单要求（见「提前撤单」）：不再提交，订单结束为已撤销，累计成交 0
- 查不到，当前时刻不早于截止时刻：不再提交，订单结束为已过期，累计成交 0

需要提交的订单只有两种：待提交的订单；券商从没受理过（没有券商订单号）的状态未知订单，见「券商调用失败时状态未知」。券商受理过的订单 MUST NOT 重新提交。

卖单查不到、当前时刻早于截止时刻、没有撤单要求时，SHALL 先按 stop-protection spec「卖单先让出股数」确认这只股票的止损单已经让出股数，才提交；还没让出时这次不提交，订单状态不变。

券商拒绝受理时，订单结束为已拒绝，没有券商订单号。

#### Scenario: 首次提交时先查询

- **GIVEN** 基准数据
- **WHEN** 提交基准方案
- **THEN** 券商先收到按 P1 的查询，查不到，再收到提交

#### Scenario: 券商拒绝受理

- **GIVEN** 基准数据，券商会拒绝受理这笔订单（比如购买力不足）
- **WHEN** 提交基准方案
- **THEN** 订单已拒绝，累计成交 0，没有券商订单号

#### Scenario: 止损单还没让出股数时不提交卖单

- **GIVEN** 基准数据，P1 全部成交，券商持仓 BBB 100 股，止损单 BBB-STOP-1 挂着 100 股
- **WHEN** 提交减仓 BBB 60 股的方案 P3
- **THEN** 券商收到按 P3 的查询，查不到，但没有收到 P3 的提交；P3 的订单待提交

#### Scenario: 提交之后、保存结果之前进程退出

- **GIVEN** 存储里有基准方案的待提交订单，券商已经受理了客户端订单 ID 是 P1 的订单（进程在提交后、保存结果前退出）
- **WHEN** 进程重启后，2026-10-14 15:05Z 跟进这笔订单
- **THEN** 不再提交，券商仍然只有一笔 P1 的订单
- **AND** 订单已提交，记下了券商订单号

#### Scenario: 提交之前进程退出

- **GIVEN** 存储里有基准方案的待提交订单，券商没有 P1 的订单
- **WHEN** 进程重启后，2026-10-14 15:05Z 跟进这笔订单
- **THEN** 券商收到 P1 的提交，订单已提交

#### Scenario: 停机到截止时刻之后

- **GIVEN** 存储里有基准方案的待提交订单，截止时刻 2026-10-14 20:00Z，券商没有 P1 的订单
- **WHEN** 进程在 2026-10-15 13:00Z 重启后跟进这笔订单
- **THEN** 不提交，订单已过期，累计成交 0

### Requirement: 券商调用失败时状态未知

查询、提交、撤单中任何一次券商调用超时或断线，订单 SHALL 变为状态未知，记下这个时刻；已经记录的券商订单号和累计成交保留。跟进时券商查不到一笔受理过（有券商订单号）的订单，订单 SHALL 同样变为状态未知。

状态未知的订单，从记下的时刻起满等待时长（见「执行配置」）之前，跟进时 SHALL NOT 调用券商。满等待时长之后跟进，按客户端订单 ID 查询：

- 查到：采用券商回报；之后仍未结束、并且到了截止时刻的，按「到期撤单」请求撤单；有撤单要求的，按「提前撤单」请求撤单
- 查不到，券商从没受理过：按「先查询再提交」的规则提交，或者结束为已撤销、已过期
- 查不到，券商受理过：仍是状态未知，重新计时，等对账处理，MUST NOT 重新提交
- 查询又失败：仍是状态未知，从这次失败的时刻重新计时

#### Scenario: 提交超时，券商其实收到了

- **GIVEN** 基准数据，券商会受理这笔订单，但提交的响应超时
- **WHEN** 提交基准方案
- **THEN** 订单状态未知，记下的时刻是 2026-10-14 15:00Z
- **WHEN** 2026-10-14 15:00:29Z 跟进订单
- **THEN** 不调用券商，订单仍是状态未知
- **WHEN** 2026-10-14 15:00:30Z 跟进订单
- **THEN** 查到这笔订单，订单已提交，券商只有一笔 P1 的订单

#### Scenario: 提交超时，券商没有收到

- **GIVEN** 基准数据，提交超时，券商没有收到这笔订单
- **WHEN** 提交基准方案
- **THEN** 订单状态未知
- **WHEN** 2026-10-14 15:00:30Z 跟进订单
- **THEN** 券商收到客户端订单 ID 仍是 P1 的提交，订单已提交，券商只有一笔 P1 的订单

#### Scenario: 查询又失败时重新计时

- **GIVEN** 基准数据，提交超时，券商其实收到了，订单状态未知，记下 2026-10-14 15:00Z
- **WHEN** 2026-10-14 15:00:30Z 跟进订单，查询超时
- **THEN** 订单仍是状态未知，记下的时刻是 2026-10-14 15:00:30Z
- **WHEN** 2026-10-14 15:00:59Z 跟进订单
- **THEN** 不调用券商
- **WHEN** 2026-10-14 15:01:00Z 跟进订单，券商恢复正常
- **THEN** 查到这笔订单，订单已提交

#### Scenario: 截止时刻之后才确认券商没有收到

- **GIVEN** 基准数据，基准结果的生效有效期改为 2026-10-14 16:00Z，2026-10-14 15:59:50Z 提交基准方案，提交超时，券商没有收到
- **WHEN** 2026-10-14 16:00:20Z 跟进订单
- **THEN** 券商没有收到提交，订单已过期，累计成交 0

#### Scenario: 跟进时断线

- **GIVEN** 基准方案已经提交，订单部分成交，累计成交 30
- **WHEN** 2026-10-14 15:10Z 跟进订单，查询时断线
- **THEN** 订单状态未知，累计成交 30，券商订单号不变
- **WHEN** 券商恢复，回报变为已受理、累计成交 60，2026-10-14 15:10:30Z 跟进订单
- **THEN** 订单部分成交，累计成交 60

#### Scenario: 撤单请求失败

- **GIVEN** 截止时刻 2026-10-14 16:00Z，订单已提交
- **WHEN** 2026-10-14 16:00Z 跟进订单，撤单请求超时，券商没有收到
- **THEN** 订单状态未知，记下的时刻是 2026-10-14 16:00Z
- **WHEN** 2026-10-14 16:00:30Z 跟进订单，券商回报仍是已受理、累计成交 0
- **THEN** 订单已提交，券商再次收到撤单请求

#### Scenario: 券商受理过的订单查不到

- **GIVEN** 基准方案已经提交，订单已提交，记下了券商订单号
- **WHEN** 2026-10-14 15:10Z 跟进订单，券商查不到 P1
- **THEN** 订单状态未知，记下的时刻是 2026-10-14 15:10Z
- **WHEN** 2026-10-14 15:10:30Z 跟进订单，仍然查不到
- **THEN** 订单仍是状态未知，券商没有收到提交

### Requirement: 保存订单

执行模块 SHALL 把每笔订单的最新状态保存在存储中，每次变化都保存。订单记录包括：

- 方案 ID（即客户端订单 ID）、股票、买卖方向、订单类型、限价、委托股数、止损价
- 截止时刻、创建时刻
- 状态、券商订单号、累计成交股数、成交均价
- 跟进需要的状态：变为状态未知的时刻、是否已经请求撤单、是否有撤单要求（见「提前撤单」）

进程重启后，执行模块 SHALL 从存储读出订单，继续跟进。

#### Scenario: 重启后继续跟进

- **GIVEN** 基准方案已经提交，订单已提交
- **WHEN** 进程重启（用同一个存储重新创建执行模块），券商回报变为全部成交、累计成交 100、成交均价 50，跟进订单
- **THEN** 订单全部成交，累计成交 100，成交均价 50

#### Scenario: 重启后不重复撤单

- **GIVEN** 截止时刻 2026-10-14 16:00Z，16:00Z 已经请求撤单，订单已提交
- **WHEN** 进程重启，券商回报仍是已受理，2026-10-14 16:00:05Z 跟进订单
- **THEN** 券商没有收到第二次撤单请求，订单仍是已提交

#### Scenario: 重启后继续提前撤单

- **GIVEN** 基准方案已经提交，订单已提交；2026-10-14 15:10Z 撤掉 BBB 的订单，撤单请求超时，券商没有收到，订单状态未知
- **WHEN** 进程重启，2026-10-14 15:10:30Z 跟进订单，券商回报仍是已受理、累计成交 0
- **THEN** 券商再次收到 P1 的撤单请求，订单已提交，有撤单要求
