# Proposal

## Why

Proposal 规定定时心跳每个交易日收盘检查一次，不调用模型，只有发现事项到期才开案件：持仓和关注股的复查日、催化剂截止日期到期开复查类案件，有新候选开候选评估（每天有上限），股票池候选不足开寻股（有冷却期），每周开一次每周复盘。前面的变更已经备好了零件：case-types spec 定了七种心跳案件类型和定时心跳的触发（`HeartbeatTrigger`），review-dates spec 保证复查日和催化剂截止日期都是交易日，case-queue spec 定了同优先级、同触发时刻的案件按入队的先后启动、降级期间照常排队，case-stages spec 把"没有结论时到期事项顺延"留给「收盘检查」。但还没有东西决定"今天收盘开哪些案件"。

本变更的目的只有一个：**每个交易日收盘时，找出到期的事项并决定开哪些定时心跳案件（复查、催化剂复查、候选评估、寻股、每周复盘）。**

引用的 Proposal（完整版）章节：

- 「触发」开头的驱动表：定时心跳"每日收盘检查"
- 「触发 · 2. 定时心跳」全节：心跳本身是纯代码；检查项表；候选评估的上限；代码直接完成、不开案件的事；每周复盘；故障处理（复查到期但因系统故障没有结论时顺延，不当作不续期）
- 「股票池与寻股」：寻股触发的三个条件、两次寻股之间的冷却期；候选超期由代码移出
- 「持仓与退出」：持仓周期（复查日和催化剂截止日期任一到期都开持仓复查，因系统故障没有结论时不视为不续期）；清仓后的股票状态（代码触发的清仓转为候选，当天收盘开候选评估）
- 「故障处理」的降级模式：到期但因故障没有结论的事项顺延；不开始新案件，新的触发照常排队，恢复后按优先级运行积压的全部案件

## What Changes

- 定时心跳模块 `modules/heartbeat/` 增加收盘检查的纯逻辑，仍然没有 service、ports 和存储。输入是收盘后的一份快照，输出是这次要开的检查项：
  - 快照：刚收盘的交易日；每只持仓和关注股的复查日、催化剂截止日期；股票池里的每只候选（最新评分、过期时间、是不是新候选）；上一次寻股的那一天；在排队或运行的心跳案件（案件类型和股票）
  - 输出：检查项（案件类型和股票，寻股和每周复盘没有股票）的列表，按开的顺序；和调度器的 `HeartbeatTrigger` 一一对应，M4 按顺序转换、入队
- 规则概要：

  | 检查项 | 开的条件 | 不开的情况 |
  | --- | --- | --- |
  | 复查类（持仓、关注各两种） | 催化剂截止日期不晚于今天开催化剂复查；只有复查日不晚于今天开复查；每只股票最多一个 | 这只股票有复查类案件在排队或运行 |
  | 候选评估 | 新候选（调用方给出）按最新评分从高到低，在排队或运行的加上这次开的不超过每天的上限 | 这只股票的候选评估在排队或运行 |
  | 寻股 | 有效候选不足、评分 ≥ 1 的候选不足、多数候选临近过期，任一项 | 有寻股在排队或运行；冷却期内 |
  | 每周复盘 | 今天是这周最后一个交易日（下一个交易日在下一周） | 有每周复盘在排队或运行 |

- 顺延不单独记：到期而还没有续期的事项每次收盘检查都算到期，已经在排队或运行的不重复开。收盘检查不看降级模式和调用预算，照常开，案件留在队列里；案件没有结论就结束的，事项仍然到期，下一次收盘检查再开
- 可配置项（和复查日与催化剂的配置是同一份）：每天的候选评估上限 3；有效候选的下限 5 只；好候选（评分 ≥ 1）的下限 2 只；临近过期的期限 3 个交易日；寻股的冷却期 3 个交易日
- contracts 和 shared 不改：案件类型、股票状态已经在 contracts，交易日历已经有按交易日推算的查询

## Non-goals

- 到点的跟进开跟进案件：属于「跟进审批」
- 普通预算、寻股预算怎么算、什么时候算用完：属于「调用预算」；收盘检查不看预算，预算用完时案件由队列留着
- 降级期间不启动、恢复后按优先级运行：case-queue spec 已经规定；案件开始运行时股票已经不在那个状态就不运行：case-types spec 已经规定
- 代码直接完成、不开案件的事：候选超期移出（stock-pool spec 已经有"移出到期的候选"）、和券商全量对账（M2 的「收盘对账」）、评估窗口到期后计算收益（M6）
- 寻股流程本身（量化粗筛、探索模式）：M4 定数据源，M5 写 PM 的提示
- M4：
  - 每天收盘什么时候调用、只调用一次；先移出到期的候选、对账，再做收盘检查的先后
  - 组出快照：从论点取复查日和催化剂截止日期，从股票池取候选，从案件记录判断谁是新候选、上一次寻股的那一天，从队列和运行中的案件取在排队或运行的心跳案件
  - 把检查项转成 `HeartbeatTrigger` 入队，取得队列的决定
- M6：每周复盘的内容；评估窗口到期后的收益汇总进每周复盘

## Capabilities

### New Capabilities

- `close-check`：收盘检查的快照和输出；复查日和催化剂截止日期到期开复查类案件；在排队或运行的不重复开；没有结论时顺延；候选评估的上限和顺序；寻股的条件和冷却期；每周复盘；开的顺序；收盘检查的配置

### Modified Capabilities

无。case-stages spec「结束原因」已经写明没有结论时由「收盘检查」顺延，case-types spec 的心跳触发不变。

## 需要人决定

已决定（2026-10-08）：

1. **同一只股票同一天几项到期**：比如复查日和催化剂截止日期同一天到期，Proposal 的检查项表两行都开持仓复查。决定：一次收盘检查每只股票最多开一个案件；催化剂到期时用催化剂复查（它的问题本来就包含"论点是否仍然成立"）
2. **降级期间开不开新案件**（案件队列已定）：降级期间不开始新案件，新的触发照常排队，恢复以后整个队列按优先级运行。收盘检查因此不看降级模式，照常开

新发现的，已按推荐做法写进 spec，不同意可以改：

3. **顺延的做法**：Proposal 写因系统故障没有结论时，到期事项顺延到恢复后的第一个交易日。推荐：到期而还没有续期的事项，每次收盘检查都算到期（日期不晚于今天）；已经在排队或运行的同一事项不重复开。降级期间收盘检查照常开，案件留在队列里，恢复以后由队列运行；案件以没有结论结束（系统故障、紧急退出中止、结论无效）的，事项仍然到期，下一次收盘检查再开。这样不需要单独记"顺延"，也不用 recovery_day；不当作不续期
4. **已经有复查类案件在排队或运行**：比如昨天开的持仓复查还在排队，今天催化剂也到期了。推荐：这次收盘检查不再给这只股票开别的复查类案件，在跑的那个案件续期时就会处理催化剂（review-dates spec：续期时到期的催化剂必须换新的）
5. **什么算"有新候选"**：Proposal 没有定义。推荐：加入股票池或者代码触发的清仓转为候选以后，还没有候选评估案件得出结论的候选；PM 自己把关注降为候选的不算，PM 刚在关注案件里做了判断，紧接着再问"是否升级"是多余的；股票池不加字段，由调用方从案件记录判断。候选股事件得出结论不算；候选评估没有结论就结束的，下一次收盘检查接着开
6. **候选评估的上限**：推荐每天 3 个（可配置），在排队或运行的候选评估也算在里面：预算用完或降级时候选评估留在队列里，不算的话每天再开 3 个，恢复以后积压的一起运行，正是上限要避免的集中消耗。寻股一次最多加入 10 只（每天增删次数上限），两次寻股的收盘检查至少相隔 4 个交易日（第 10 条），平均每天不到 3 只，积压不会越来越多；候选 10 个交易日后过期，过期前能评估 30 只，等于池子容量
7. **评分相同或没有评分时谁先开**：推荐没有评分的（手动添加、还没有 PM 结论的）排在最后；评分相同的，过期时间早的先开，免得快过期的还没评估就被移出；再相同按股票代码
8. **代码触发的清仓当天开候选评估**：Proposal 写"当天收盘的定时心跳会为它开候选评估案件"，和每天的上限有冲突。推荐当作普通的新候选，和其他新候选一起按评分排进上限；新候选很少超过上限，通常当天就开
9. **寻股的三个条件**：推荐：有效候选是最新评分为空或不低于 0 的候选（负分表示 PM 看淡，"连续为负可从股票池移出"），少于 5 只时寻股；评分 ≥ 1 的候选少于 2 只时寻股；过期时间不晚于今天之后第 3 个交易日收盘的候选算临近过期，超过候选总数的一半算多数。三个数都可配置，"评分 ≥ 1"和"一半"照 Proposal 的字面意思不做成配置。理由：关注名额 8 只，有效候选少于 5 只时补充关注的来源不够，寻股一次加入几只又能回到下限以上；好候选只剩 1 只时，升级全靠它；临近过期的期限和冷却期相同，这些候选在下一次能寻股以前就会被移出
10. **寻股的冷却期从哪天算**：推荐从上一次寻股得出结论的那一天（结论时刻归属的交易日）算，那一天之后第 3 个交易日（可配置）起才能再开。收盘后得出的结论归属下一个交易日，所以两次寻股的收盘检查之间隔着 3 个不寻股的交易日。从开寻股的那天算的话，寻股在队列里等了几天（寻股预算用完、降级），刚跑完冷却期就过了；没有结论的寻股（系统故障、结论无效）不算，和复查日一样不把故障当作判断
11. **每周复盘的时间**：推荐下一个交易日在下一周（周一到周日）时，今天就是这周最后一个交易日，比如周五休市时是周四；不做成配置：改成固定的星期几还要另定那天休市时怎么办，用处不大。Proposal 的"默认每周最后一个交易日收盘后"改为"每周最后一个交易日收盘后"
12. **不续期的结论没有执行成**：复查类案件的结论是清仓或开仓方案（不续期），人工拒绝、确认超时、风控拒绝或者订单还没成交时，股票状态没变，日期仍然到期。推荐：下一次收盘检查照样开复查类案件，PM 在上下文里看得到上次的结果：没有续期的论点不能一直不复查
13. **同一次开出的案件的先后**：触发时刻相同时，队列按优先级、再按入队的先后启动。推荐按持仓、关注、候选评估、寻股、每周复盘的顺序给出，持仓和关注里按股票代码，候选评估按第 7 条：同一优先级里这就是启动的顺序
