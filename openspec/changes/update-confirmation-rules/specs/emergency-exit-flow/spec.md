# Spec Delta

## ADDED Requirements

### Requirement: 紧急退出的人工确认

通知配置的「紧急退出要确认」（confirmation-rules spec「确认规则的配置」）关闭时，紧急退出 SHALL NOT 请求人工确认，要清仓的股票直接按「一只股票的清仓」处理。

打开时，要清仓的股票 SHALL 先按下表处理它当天的确认，确认以后才按「一只股票的清仓」处理。每只股票每个交易日最多一个确认，指向它当天的代码触发的清仓方案：

| 情况 | 处理 |
| --- | --- |
| 这次运行里第一次处理它当天的清仓，原因是组合熔断或个股跌幅 | 请求紧急退出的确认（discord-notification spec「紧急退出的确认消息」）：原因的写法和开始紧急退出的告警相同（「告警」），当前持仓是这一轮账户数据里的股数；写一条 INFO。这一项到此结束：不作废方案、不撤单、不检查风控，不拿锁，止损单照挂 |
| 在等确认，还没有收到按钮的结果，当前时刻早于截止时刻 | 什么都不做 |
| 收到确认 | 这一轮就按「一只股票的清仓」处理，之后当天做到底（「要清仓的股票」）：价格回升、跌幅回到阈值以内也照样清仓 |
| 收到拒绝 | 这只股票当天的紧急退出结束；写一条 INFO，不告警 |
| 没有收到按钮的结果，当前时刻不早于截止时刻 | 报告确认消息已超时（discord-notification spec「结束确认」）；这只股票当天的紧急退出结束；告警 |
| 确认请求发不出去（通知不可用） | 按确认超时处理：这只股票当天的紧急退出结束；写一条 ERROR，写明股票和原因；告警 |

- 截止时刻 = 请求的时刻 + 确认超时（通知配置，默认 30 分钟）
- 每一轮先看有没有收到按钮的结果，再看截止时刻：截止时刻之前按下、截止以后的那一轮才处理的，按按钮的结果处理
- 收下按钮的结果：本人按下紧急退出的确认消息的按钮（discord-notification spec「按钮的处理」），紧急退出流程正在等这个方案的确认（已经请求，还没有处理到结果）时 SHALL 收下，留给之后的轮次处理；不在等的不收下，交给下单流程（bootstrap spec「模拟盘的装配」）
- 熔断时撤掉全部买单（「单日亏损熔断」）、收盘前不再开仓（emergency-exit spec「熔断状态」）SHALL 不等确认；每只持仓各请求一次确认，各自处理
- 本地备用止损 SHALL NOT 等确认：这一轮本地备用止损触发（「要清仓的股票」的第二行）的股票直接按「一只股票的清仓」处理，即使它在等确认，或者当天的紧急退出已经因为拒绝、超时、确认请求发不出去而结束。在等的确认消息报告已作废；之前请求过确认的，开始紧急退出的告警写的原因是本地备用止损
- 降级模式下照常请求确认
- 到收盘还在等确认的，见「告警」

- **THEN** 频道里没有确认消息；AAA 的清仓单已经建立：卖出 50 股

- **WHEN** AAA 最新价 92，做一轮

- **AND** 券商没有收到 P2 的撤单请求，AAA-STOP-1 仍是 30 股；P2 仍有有效预留；AAA 的清仓方案没有订单，也没有预留
- **AND** 没有推送开始紧急退出的告警
- **WHEN** 之后一轮

#### Scenario: 确认以后清仓

- **GIVEN** 接着「请求确认，等确认期间什么都不动」

#### Scenario: 截止前一刻确认

- **GIVEN** 紧急退出要确认打开；AAA 最新价 92 时做过一轮，已经请求确认
- **WHEN** 15:29:59Z 按确认，15:30:05Z 之后一轮
- **THEN** 确认消息显示已确认；AAA 的清仓单已经建立：卖出 50 股

#### Scenario: 拒绝以后当天不再紧急退出

- **GIVEN** 紧急退出要确认打开；AAA 最新价 92 时做过一轮，已经请求确认
- **WHEN** 15:05Z 按拒绝，之后一轮
- **THEN** 确认消息显示已拒绝；AAA 的清仓方案没有订单；没有告警
- **WHEN** AAA 最新价 91，之后一轮
- **THEN** 没有新的确认消息；券商没有收到 AAA 的订单，AAA-STOP-1 仍挂着

#### Scenario: 确认超时

- **GIVEN** 紧急退出要确认打开；AAA 最新价 92 时做过一轮，已经请求确认，一直没有人按
- **WHEN** 2026-10-14 15:30:00Z 之后一轮
- **THEN** 确认消息显示已超时
- **AND** 推送一条告警，写明 AAA 到截止时刻没有确认、没有执行、今天不再紧急退出 AAA、止损单照挂
- **AND** AAA-STOP-1 仍挂着 50 股；AAA 的清仓方案没有订单
- **WHEN** 之后一轮
- **THEN** 没有关于 AAA 的新告警和确认消息

#### Scenario: 按钮和超时同时

- **GIVEN** 紧急退出要确认打开；AAA 最新价 92 时做过一轮，已经请求确认；本人在 15:29:59Z 按了确认，回调还没送到
- **WHEN** 2026-10-14 15:30:00Z 之后一轮，然后回调送到
- **THEN** 确认消息显示已超时；紧急退出流程没有收下这次确认，回调抛错

- **THEN** 有一条 ERROR 写明 AAA 的紧急退出确认没有发出去和原因；告警也没有发出去，有一条错误日志

#### Scenario: 下一个交易日重新判定

## MODIFIED Requirements

### Requirement: 巡检里的紧急退出

盘中巡检的每一轮 SHALL 在第 3 步（对齐止损单，session-patrol spec「每一轮」）之后、收盘对账（close-reconciliation spec「巡检里的收盘对账」）之前做「紧急退出」这一步。这一步由下面几项组成，按顺序做：

1. 判定：当前时刻不在常规交易时段内（开盘 ≤ 当前时刻 < 收盘）时不做判定，也不做第 2、3 项。在时段内时，按「判定的输入」读数据，按「要清仓的股票」得出这一轮的熔断状态和要清仓的股票
2. 熔断已触发时撤掉全部买单，见「单日亏损熔断」
3. 要清仓的股票按代码顺序各一项，见「一只股票的清仓」
4. 报告结果：不论在不在交易时段都做，见「告警」

每一项和巡检的其他项一样（session-patrol spec「巡检的开始、间隔和停止」「一轮里的失败」）：停止时正在做的那一项做完（包括推送）再结束；一项出错只跳过这一项。

判定的频率就是巡检的间隔（session-patrol spec「巡检配置」，默认 15 秒）。判定用到的阈值都在已有的配置里：熔断比例（emergency-exit spec「紧急退出配置」，默认 0.07）、每只持仓生效的紧急阈值（来自它的开仓方案，没写时用风控配置的默认值 0.08，risk-rules spec）。要不要请求人工确认和确认超时取通知配置（confirmation-rules spec「确认规则的配置」、discord-notification spec「确认请求和截止时刻」）。本流程不另设配置项。

紧急退出默认不请求人工确认，见「紧急退出的人工确认」；降级模式下照常进行（degraded-mode spec）。

本 spec 的场景除非另有说明，都使用下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中；当天 13:30Z 开盘、20:00Z 收盘），交易日历是纽交所日历
- 风控、执行、紧急退出、巡检、通知的配置都用默认值：执行配置的「买单和止损单错开」打开（和模拟盘的装配一样），立即重试 1 次，状态未知的等待时长 30 秒；熔断比例 0.07；巡检间隔 15 秒；紧急退出要确认关闭，确认超时 30 分钟
- 执行模块已经完成一次对账，没有不一致；不处于降级模式；今天的熔断没有触发
- 券商账户：权益 10,000，前一交易日收盘时的权益 10,000（熔断线 700），现金 1,000
- 持仓，都能找到开仓订单，今天都没有开仓成交：
  - AAA 50 股，均价 100。开仓订单：板块"科技"，止损价 90，紧急阈值 0.08，2026-10-12 全部成交。AAA-STOP-1 挂着：卖出 50 股，止损价 90
  - BBB 100 股，均价 40。开仓订单：板块"医疗"，止损价 35，紧急阈值 0.15，2026-10-13 全部成交。BBB-STOP-1 挂着：卖出 100 股，止损价 35
- 行情：AAA 前一交易日收盘价 100，最新价 99；BBB 前一交易日收盘价 40，最新价 39.5。AAA 在最新价 92 及以下触及个股跌幅，BBB 在 34 及以下
- 没有未结束的订单，没有有效预留。方案在场景里给出，都已经通过风控并预留：
  - P2：减仓 AAA 20 股，限价单，限价 105
  - P5：买入 CCC，板块"能源"，100 股，限价单，限价 20，止损价 18
- "做一轮"指巡检在当前时刻做一轮，"之后一轮"指 15 秒以后的下一轮
- "AAA 的清仓方案"指交易日 2026-10-14、股票 AAA 的代码触发的清仓方案（emergency-exit spec「代码触发的清仓方案」）；"AAA 的清仓单"指这个方案的订单
- 券商正常受理，订单不成交，除非另有说明；"券商回报……变为……""券商持仓变为……"同 order-lifecycle spec 和 stop-protection spec 的约定
- "推送一条告警"指 discord-notification spec「告警」的一条消息
- "紧急退出要确认打开"指通知配置的「紧急退出要确认」打开，其余配置不变；"AAA 的确认消息"指 AAA 当天的紧急退出的确认消息（discord-notification spec「紧急退出的确认消息」）；"按确认""按拒绝"指本人在截止时刻之前按这条消息上的按钮，按钮的结果送达紧急退出流程
- "锁"指 session-patrol spec「执行模块和风控的调用串行」的那把锁

### Requirement: 一只股票的清仓

「紧急退出要确认」打开时，要清仓的股票先按「紧急退出的人工确认」处理，需要确认的在确认以后才做下面几步。

要清仓的每只股票 SHALL 在一次拿锁里依次：

1. 这只股票当天的清仓方案已经有订单：什么都不做（订单由巡检跟进）
2. 作废这只股票还没下单的方案：有有效预留、还没有订单的每个方案（开仓类和退出类都算，不论在等确认、等开盘还是等重试，当天的清仓方案除外），释放它的预留（risk-reservations spec）。下单流程之后再校验时得到"方案已结束"而作废（order-flow spec、pre-order-recheck spec「已经结束的方案」）
3. 这只股票还有没结束的订单（买单和卖单）：其中有还没记下撤单要求的，就撤掉这只股票的订单（order-lifecycle spec「提前撤单」）；已经都有撤单要求的不再撤。这一项到此结束，等之后的轮次
4. 没有没结束的订单：用风控检查当天的清仓方案（熔断取紧急退出的当前状态，降级取健康监控的当前状态，同 order-flow spec「提交方案」），通过或调整时做下单前再校验，再校验通过或调整时按它的结果提交订单（order-lifecycle spec「提交订单」）

第 4 步的结果 SHALL 按下表处理：

| 结果 | 处理 |
| --- | --- |
| 检查或再校验拒绝（可卖数量为 0） | 不下单；这只股票当天的紧急退出结束；告警 |
| 提交返回订单 | 订单交给巡检跟进：卖单等止损单撤掉才提交给券商，撤掉以后由巡检的跟进提交；之后的结果见「告警」 |
| 提交时券商超时或断线 | 订单记为状态未知（order-lifecycle spec「券商调用失败时状态未知」），交给巡检跟进 |

- 清仓股数是再校验时的可卖数量：撤单之前和撤单期间的成交都已经计入券商持仓
- 第 4 步出了别的错（数据库出错、券商的认证错误、意外的异常），按「一轮里的失败」处理，之后的轮次再从第 1 步来

### Requirement: 告警

紧急退出 SHALL 只为下面这些情况推送告警（discord-notification spec「告警」），并把同样的文字写一条 WARNING 日志：

| 情况 | 告警写明 |
| --- | --- |
| 一只股票开始紧急退出：这次运行里第一次按「一只股票的清仓」处理它当天的清仓（需要确认的，是确认以后的第一次） | 股票；原因：个股跌幅写参考价、最新价、跌幅和紧急阈值，组合熔断，本地备用止损写无保护仓位或错开中、最新价和止损价；这一项做了什么：作废的方案（动作、方案 ID），撤掉的订单（买卖方向、股数、方案 ID），已经建立的清仓单（股数），或者等订单都结束以后清仓，或者没有可卖的股数 |
| 熔断触发：这次运行里每个交易日第一次看到 | 前一交易日收盘时的权益、当前权益、单日亏损和它占前一交易日收盘时权益的比例、熔断比例；清仓全部持仓，撤掉全部买单，收盘前不再开仓。「紧急退出要确认」打开时写明每只持仓的清仓要确认 |
| 清仓单进入终态 | 全部成交：股票、卖出股数和成交均价。其他终态（已拒绝、已过期、已撤销）：股票、状态、累计成交和委托股数；今天不再清仓这只股票，剩下的持仓由止损单保护 |
| 之后的轮次里没有可卖的股数 | 股票；没有可卖的股数，紧急退出结束 |
| 到收盘还没有清仓单：当天开始、不在等确认的紧急退出，收盘以后的第一轮仍没有订单 | 股票；到收盘还没下清仓单（等撤单结束），今天不再清仓。同时拿锁释放当天清仓方案剩下的预留（有的话） |
| 紧急退出的确认超时 | 股票；到截止时刻没有确认，没有执行；今天不再紧急退出这只股票，止损单照挂 |
| 紧急退出的确认请求发不出去 | 股票；确认请求没有发出去，没有执行；今天不再紧急退出这只股票，止损单照挂 |
| 到收盘还在等确认：收盘以后的第一轮仍在等 | 股票；到收盘还没有确认，没有执行，今天不再紧急退出这只股票。同时报告确认消息已作废 |

- 其余只写 INFO 日志：撤单请求、等订单结束、作废的方案、建立清仓单（股数和状态）、请求紧急退出的确认、收到拒绝。等订单结束的每一轮各写一条
- 推送告警 MUST NOT 拿着锁。发不出去时按 discord-notification spec 只写错误日志，紧急退出照常继续，之后不重发
- 告警过什么只记在内存里：进程重启以后见「重启以后」

### Requirement: 重启以后

订单（包括撤单要求）、预留和止损保护都在状态库里；熔断状态（emergency-exit spec）、当天触发过哪些股票、紧急退出的确认走到哪里、告警过什么只在内存里。进程重启以后，巡检的第一轮 SHALL 按下表接着做：

| 重启之前 | 重启以后 |
| --- | --- |
| 清仓单已经建立、还没结束 | 巡检照常跟进；它结束时照样推送结果的告警（判定时把有持仓的股票当天的清仓单找回来）；不再推送开始紧急退出的告警 |
| 在等撤单结束，重启以后仍然触发 | 不再请求撤单；订单都结束以后清仓；再推送一次开始紧急退出的告警。「紧急退出要确认」打开、原因不是本地备用止损时，先再请求一次确认，确认以后接着做 |
| 在等撤单结束，重启以后不再触发 | 不再继续：已经撤掉的订单、作废的方案不恢复，不清仓 |
| 在等紧急退出的确认，重启以后仍然触发 | 再请求一次确认：发一条新的确认消息，截止时刻从重启以后请求的时刻算；按重启前那条消息上的按钮也送到这次的确认 |
| 在等紧急退出的确认，重启以后不再触发 | 不再请求确认；重启前那条消息上的按钮按下时没有送达（discord-notification spec「按钮的处理」的回调抛错），截止时刻以后按下显示已超时 |
| 紧急退出因为拒绝、超时或确认请求发不出去已经结束，重启以后仍然触发 | 再请求一次确认 |
| 熔断已触发 | 下一次判定重新算（emergency-exit spec「熔断状态」）；单日亏损仍达到熔断线时再告警一次 |
