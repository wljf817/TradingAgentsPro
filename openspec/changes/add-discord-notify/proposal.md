# Proposal

## Why

M2 的流程有两件事要找人：

- 告警：止损单挂不上（无保护仓位）、对账不一致、进入或退出降级模式、紧急退出执行以后，都要立即通知
- 人工确认：开仓方案通过风控以后要人按确认才能下单；被风控调整过的方案要在确认消息里标明「已被风控调整」及原因；人工拒绝或确认超时要释放预留

项目里至今没有任何通知的通道，M1 的各个变更都把告警和确认留给了 M2。简版和完整版都已经写定用 Discord 机器人（discord.py）推送告警、用按钮确认或拒绝、只接受指定用户的操作。

本变更的目的只有一个：**新建通知模块，并用 Discord 机器人实现它：往一个频道推送告警，发出带「确认」「拒绝」按钮的交易方案确认请求，把人的选择交给注入的回调。**

引用的 Proposal（完整版）章节：

- 「技术栈与部署」通知与人工确认一行：Discord 机器人（discord.py）推送告警，用按钮确认或拒绝，只接受指定用户的操作；同一节的可靠性要求：Discord token 存环境变量；案件工作流一行：用 DBOS 的持久化通知等待人工确认
- 「风控引擎与执行」：调整后的方案直接进入人工确认，确认消息里标明「已被风控调整」及原因；人工拒绝或确认超时时释放预留；通过后进入人工确认
- 「架构 · 风控与执行」：开仓类方案通过 Discord 按钮确认
- 「持仓与退出」退出路径表：哪些退出要人工确认（本变更只提供确认的通道，规则属于 M3「人工确认的规则」）
- 「故障处理」：降级模式告警通知
- 「记录、复盘与经验 · 程序日志」：人的确认、拒绝、超时和系统的告警要记进程序日志（M4 才有程序日志，见 Non-goals）

## What Changes

- 新增模块 `modules/notification/`，对应架构图「风控与执行」里的「人工确认」节点，以及「技术栈与部署」里的「通知与人工确认」：
  - 端口 `Notifier`：推送告警；发出一个方案的确认请求，返回确认消息的标识和截止时刻；调用方报告超时或作废时更新确认消息。发不出去时报通知不可用
  - 回调 `DecisionHandler`：人按下按钮以后，适配器把方案 ID 和「确认」或「拒绝」交给它；由「启动与装配」注入，以后转给等着这个方案的下单工作流
  - 确认的四种结果：已确认、已拒绝、已超时、已作废
  - 用例 `NotificationService`：推送告警；按「确认超时」（默认 30 分钟，可配置）算出截止时刻再发确认请求，被风控拒绝的方案不能请求确认；报告超时或作废。告警和报告结果发不出去时只写日志、不抛错，确认请求发不出去时抛错（见「需要人决定」第 1 条）
- 新增 `integrations/discord/`，用 discord.py 实现 `Notifier`：
  - 配置从 4 个环境变量读：`DISCORD_BOT_TOKEN`、`DISCORD_GUILD_ID`、`DISCORD_CHANNEL_ID`、`DISCORD_USER_ID`；缺少时指出缺少哪几个，token 不出现在代码、文件、日志、错误信息和测试输出里
  - 启动：登录、连上 Discord，并核对频道属于配置的服务器；失败时报错。关闭：断开连接
  - 告警和确认请求都发到同一个频道，都 @ 配置的用户，让手机收到推送；不会 @ 其他任何人
  - 确认消息写明方案（动作、股票、股数、订单类型和价格、止损价、紧急阈值、有效期）、截止时刻和方案 ID；被风控调整时写明「已被风控调整」、原来和调整后的股数，以及每条不通过的规则
  - 按钮：只有配置的用户能按，其他人只看到一条仅自己可见的拒绝；按下后先在 3 秒内应答 Discord，再在事件循环之外调用回调；回调成功以后去掉按钮、显示结果；回调失败时保留按钮、请人再按一次；过了截止时刻按下的按钮不交给回调，消息显示已超时；连按两次只算一次
  - 调用方报告的超时或作废覆盖消息上已经显示的结果；确认消息被删掉时什么也不做
  - 同一个方案重复请求确认（比如调用方超时后重试）只发一条消息
  - 进程重启以后，旧消息上的按钮照样能用：按钮自带方案 ID 和截止时刻，不依赖内存里的状态
  - 线程：discord.py 在自己的线程上跑自己的事件循环；同步的调用方把工作交给这个循环并等结果，等待有上限（默认 10 秒），超时或 Discord 报错都报通知不可用
- 新增依赖 discord.py
- 一组连真实 Discord 的冒烟测试，默认不运行；其中按按钮的部分要人在手机或电脑上操作

## Non-goals

- `/plan` 斜杠命令和方案解析：「手工录入方案」
- 进程启动时读配置、建立和关闭 Discord 连接、把回调接到 DBOS：「启动与装配」
- 环境变量模板、创建 Discord 应用和机器人、邀请进服务器、授权：「部署」
- 什么事件发什么告警、告警的文字，以及 DBOS 工作流怎样等确认、超时以后怎样释放预留：「下单流程」「紧急退出流程」「收盘对账」「健康监控接线」
- 哪些方案需要人工确认（紧急退出的确认开关、模型建议退出的规则、降级模式下的处理）：M3「人工确认的规则」
- 每日摘要、建议的推送、Reviewer 的修改建议：后面的里程碑
- 程序日志：M4 才有；在那之前，本变更的按钮操作、告警和错误写进 Python 的日志
- 告警和确认分频道、多个用户、备用通知通道：都不做，告警和确认用同一个频道
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `discord-notification`：通知模块和它的 Discord 实现：确认的结果和截止时刻、Discord 配置、启动和关闭、告警、确认消息、按钮的处理、结束确认、同步调用和失败

### Modified Capabilities

无。风控、执行等已有模块的规则不变；确认结果怎样影响预留，已经在 risk-reservations spec 里（人工拒绝、确认超时时释放），由「下单流程」调用。

## Impact

- **代码**：
  - 新增 `src/tradingagentspro/modules/notification/`（`__init__.py`、`ports.py`、`service.py`、`config.py`、`domain/confirmation.py`）
  - 新增 `src/tradingagentspro/integrations/discord/`（`__init__.py`、`config.py`、`messages.py`、`notifier.py`、`gateway.py`）
- **测试**：
  - `tests/modules/notification/`，测试替身 `tests/fakes/notifier.py`
  - `tests/integrations/discord/`：不连 Discord，用替身 Gateway 和替身按钮操作验证消息内容、按钮处理和线程模型
  - 冒烟测试连真实的 Discord，默认不运行，CI 也不运行
- **依赖**：新增 discord.py（顺带 aiohttp 等）；它自带类型标注，mypy 配置不用改；纯区域的白名单不变
- **配置**：`pyproject.toml` 登记 pytest 标记 `discord_bot`，默认的 `addopts` 排除它
- **对后续变更的影响**：
  - 「手工录入方案」：
    - `/plan` 用同一个机器人、同一个频道；用 `DISCORD_GUILD_ID` 注册服务器内的斜杠命令，只接受 `DISCORD_USER_ID` 的操作
    - 本变更的适配器只处理自己的按钮（custom_id 以 `confirmation:` 开头），别的交互不应答，斜杠命令由那个变更另外接上
  - 「启动与装配」：
    - 用 `DiscordConfig.from_env(os.environ)` 读配置；建 `DiscordNotifier`，注入时钟和回调；先 `start()` 再接受新订单，启动失败时整个程序启动失败；退出时 `close()`
    - 回调：把方案 ID 和结果用 `DBOS.send` 发给等着这个方案的工作流（工作流 ID 由方案 ID 推出，topic 固定）。回调在适配器的工作线程里调用，不在 DBOS 工作流里；抛错表示没送达，适配器会请人再按一次
    - 回调先确认这个方案的工作流还在等确认，不在等（已经超时、作废、因为确认请求发不出去按超时结束，或者根本没有这个工作流）就抛错，不发送。`DBOS.send` 发给已经结束的工作流也会成功，不先确认的话，按钮会显示已确认，这个方案却永远不会下单。比如请求确认超过发送超时、工作流按超时结束，消息却晚到了，人随后按了确认。回调抛错时按钮显示「没有送达，请再按一次」，过了截止时刻再按就显示已超时
    - 用 `NotificationConfig()` 的默认值建 `NotificationService`
  - 「部署」：
    - 环境变量模板加上 4 个变量
    - 机器人还不在服务器里时，才需要在 Discord 开发者后台建应用和机器人、邀请进服务器；「手工录入方案」还要 `applications.commands`
    - 频道里给机器人「查看频道」「发送消息」「嵌入链接」权限；「读取消息历史」只是冒烟测试读回消息、核对内容要用，程序本身不需要
    - 不需要特权 intent
  - 「下单流程」：
    - 开仓方案通过风控（包括被调整的）以后，调用 `NotificationService.request_confirmation`；在这个调用返回以后用 `DBOS.recv` 等，超时用 `NotificationConfig.confirmation_timeout`，这样工作流的截止时刻不早于消息上的截止时刻
    - 收到已确认就继续；已拒绝就释放预留、方案结束；等不到就调用 `finish_confirmation` 报告已超时，再释放预留
    - 收到同一个方案的多条消息时只用第一条
    - 让回调能判断这个方案的工作流是不是还在等确认（比如开始等之前用 `DBOS.set_event` 标记正在等，收到结果或超时以后改掉），见「启动与装配」的回调；结束以后收到的确认一律不算
    - 确认请求发不出去时怎么办，见「需要人决定」第 1 条
    - 告警：无保护仓位、再校验作废、再校验调整后按更小的股数下单（在通知里标明）
  - 「紧急退出流程」：执行以后立即推送告警
  - 「收盘对账」：启动时和收盘后的对账有不一致时推送告警
  - 「健康监控接线」：进入和退出降级模式时推送告警
  - M3「人工确认的规则」：用同一个 `request_confirmation` 让退出方案走人工确认；调度器作废等确认的方案时调用 `finish_confirmation` 报告已作废
  - M4 程序日志：把按钮操作（人的确认、拒绝、超时）和告警从 Python 日志改为写程序日志

## 需要人决定

已按你给的要求定下的，不再讨论：告警和确认用同一个频道；确认超时默认 30 分钟、可以配置；M4 之前告警之外的记录写 Python 日志。

1. **Discord 发不出去时怎么办**：「技术栈与部署」只写了用 Discord 推送告警和确认，「故障处理」没有把 Discord 列进健康监控，也没写发不出去时怎么办。Discord 断了，告警会丢；确认请求发不出去，方案就一直等不到回复。

   推荐：
   - 不另设备用通知通道，也不把 Discord 算作健康检查的一项、不因此进入降级。开仓本来就要人确认，Discord 断了开仓自然停下；紧急退出和止损不依赖 Discord，照常执行
   - 告警发不出去时写进日志（M4 以后是程序日志），调用方照常继续，不重试到成功。报告超时或作废发不出去时也一样：消息上的按钮留着，但过了截止时刻再按只会显示已超时
   - 确认请求发不出去时，这个方案按确认超时处理：释放预留，方案结束，由「下单流程」实现
   - 完整版「技术栈与部署」通知与人工确认一行补一句："Discord 发不出去时只写程序日志，不另设备用通道，也不算健康异常；确认请求发不出去的方案按确认超时处理"

   前两点已按推荐写进 spec（`NotificationService` 的告警和报告结果不抛错），不同意可以改；第三点由「下单流程」实现；Proposal 的修改在 tasks 1.1，等你决定以后再改。
