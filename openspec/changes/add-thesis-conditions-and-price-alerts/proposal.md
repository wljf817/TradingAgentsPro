# Proposal

## Why

PM 在关注论点里写了入场条件，在投资论点里写了目标价和证伪条件中代码能检测的部分，可现在没有代码去看它们：关注股的价格到了入场价、持仓到了目标价或跌破证伪价位，系统都不开案件。事件检测（add-event-detection）只做了价格和成交量异动、新闻、公告、财报和卖出成交，把这三类条件、moomoo 到价提醒和 OpenD 断线以后的补查留给了本变更。

本变更的目的只有一个：**按代码规则判断论点里的入场条件、目标价和证伪条件，满足的记成事件、排进案件；并把其中价格类的条件设成 moomoo 到价提醒，提醒推送时让事件检测立即判断。**

引用的 Proposal（完整版）章节：

- 「触发 · 1. 事件驱动」：事件来源里的"关注股的入场条件满足""持仓达到目标价，或证伪条件中代码能检测的部分触发""到价提醒"三条；「到价提醒的维护」一段（只覆盖价格、涨跌幅、成交量；论点更新或股票状态变化时同步增删；OpenD 在线才收得到推送，断线恢复后用实时行情补查）；持仓风险事件与紧急风险事件的分界；同一只股票的同一类事件每个交易日最多开一个案件
- 「案件类型」的事件案件和「最低研究要求」：入场条件满足、达到目标价或证伪条件触发至少派给 Quant
- 「风控引擎与执行 · 交易时段」：价格类的判断只在常规交易时段
- 「技术栈与部署」的数据源和券商两行：moomoo 行情和到价提醒推送
- 「故障处理」：OpenD 断线

已经定了的（不在本变更里讨论）：条件的格式（`contracts/thesis.py` 的 `Condition`：价格、当日涨跌幅、当日累计成交量，不低于或不高于；入场条件任一满足就算满足，证伪条件中代码能检测的部分可以没有、任一满足就算触发）；事件 ID 是 `<股票>:<交易日>:<种类>`、同一个事件 ID 只记一次（event-rules spec）；事件类别「入场条件满足」「达到目标价或证伪条件触发」和它们要求的子 agent Quant（case-types spec，已经在代码里）；持仓风险级别的事件开持仓风险事件、排队优先级最高。

## What Changes

- 论点条件（event-rules）：
  - 关注股的入场条件、持仓的目标价（换成"价格不低于目标价"）、持仓的证伪条件中代码能检测的部分，每组任一条件满足就是一个事件；候选没有论点，不判断
  - 证伪条件触发是持仓风险级别；达到目标价、入场条件满足不是
  - 和价格异动一样，只在「行情要是当天的」时判断：常规交易时段、有最新价、行情更新时刻不早于开盘
  - 新的事件 ID 种类 entry、target、invalidation：每只股票每个交易日每组最多一个；条件一直满足时每个交易日一个
- 事件检测（event-detection）：
  - 价格和成交量那一部分同时判断论点条件，用同一次取到的行情
  - 每一轮最后同步到价提醒；收到到价提醒的推送时立即开始下一轮
  - 条件只由每一轮按行情判断，推送不直接成为事件：OpenD 断线期间漏掉的推送，恢复以后的下一轮照样判断出来
- 到价提醒（新的 price-alerts）：股票池里关注股和持仓的论点需要哪些到价提醒；每一轮把行情源上系统设的提醒同步成需要的那一组；同步失败只写 WARNING，下一轮再试；推送叫醒事件检测
- moomoo 到价提醒（新的 moomoo-price-alerts）：用 OpenD 的到价提醒实现：备注认出系统设的提醒，类型、值的精度、每日一次、只在常规时段提醒；调用失败；推送的回调；和行情共用一个 OpenD 行情连接
- 行情（market-data、moomoo-quotes）：一只股票的行情加上当天常规时段的累计成交量，成交量条件要用；取快照的 volume，和最新价一样只在开盘 1 分钟以后给
- 启动与装配（bootstrap）：装配到价提醒，事件检测读它
- 完整版 Proposal：改三句话，见「需要人决定」的最后一节

## Non-goals

- 技术指标类的条件：`ConditionKind` 现在只有价格、涨跌幅、成交量，Proposal 说技术指标由事件检测层自己算，等 PM 能写这类条件时再加
- 盘前盘后判断条件：和价格异动一样只看常规时段
- 订阅 moomoo 的实时报价推送：条件用每一轮的快照判断，推送只用到价提醒的
- 检测 OpenD 断线和重连：每一轮都按行情判断条件，不需要知道什么时候断过（design D3）
- 到价提醒推送进健康监控：Proposal 的五项检查里没有
- 达到目标价以后自动卖出：仍由 PM 在案件里决定（Proposal「模型建议退出」）
- 修改替身：替身已经按入场条件满足事件给出开仓方案，其余事件案件给出持有或继续关注
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `price-alerts`：需要的到价提醒、同步、同步失败、推送
- `moomoo-price-alerts`：系统设的提醒、提醒的设置、调用失败、推送的回调

### Modified Capabilities

- `event-rules`：修改「事件的内容」（论点条件的类别、强度、引用、说明）「事件 ID 和去重」（entry、target、invalidation）；新增「论点条件」
- `event-detection`：修改「一轮」（论点条件、到价提醒）「什么时候做一轮」（推送叫醒）「读不到时」（到价提醒）「没成为事件的新闻和公告」（论点条件没满足不写日志）；新增「断线以后」
- `market-data`：修改「取行情」（成交量）
- `moomoo-quotes`：修改「快照的映射」（成交量）
- `bootstrap`：修改「模拟盘的装配」（到价提醒）

## 需要人决定

(a) 行为：

1. **条件只由每一轮按行情判断，到价提醒只用来叫醒事件检测**：推荐。到价提醒推送时事件检测立即做一轮，用快照判断，满足的成为事件；不推送时每 60 秒一轮照样判断。理由：主机常有短暂断网，只靠推送会漏；一份规则、一个来源，不用两路去重
2. **证伪条件触发是持仓风险事件（优先级 1），达到目标价是持仓事件（优先级 2），入场条件满足是关注股事件（优先级 4）**：推荐。理由：Proposal 把风险级别的负面事件算持仓风险事件，代码能检测的证伪条件触发就是论点被推翻的信号；目标价是收益目标，不是风险
3. **条件一直满足时每个交易日开一个案件**：推荐，不只在越过的那一刻开。理由：Proposal 规定同类事件每天最多一个；PM 不改论点就每天提醒一次，改了论点或降级就停；只在越过时开要另记上一次的状态
4. **只在常规交易时段判断，开盘 1 分钟以后才有最新价**：推荐。盘后财报跌破证伪价位，要到下一个开盘才有证伪条件触发事件（财报和新闻事件盘后照常开）。理由：和价格异动、紧急退出一样只看常规时段的价格，系统也只在常规时段下单
5. **到价提醒只设常规时段、每天最多推送一次**：推荐。理由：推送只用来提前判断，盘前盘后不判断；每天一次足够叫醒
6. **moomoo 手机 app 可能也会收到这些提醒**：没有核实。到价提醒存在 moomoo 账户上，app 里的到价提醒可能同步显示、触发时推送到手机。推荐接受，冒烟测试时你看一下 app；嫌吵可以在 app 里关掉到价提醒的通知，不影响程序收推送
7. **模拟盘上替身会开始自动出开仓方案**：替身升级的关注股入场条件是价格不高于参考价的 1.02 倍，通常马上满足，所以每只新升级的关注股在下一个常规时段开出入场案件、替身给出开仓方案、Discord 发确认消息；不确认就确认超时。推荐接受：M4 的验收要求替身的方案能在模拟盘下单
8. **证伪条件和紧急阈值同时越过**：证伪条件触发事件照样排队；紧急退出清仓以后这只股票变成候选，案件按候选开（"是否值得升级为关注"）。推荐不特殊处理。理由：少见，多一个候选案件；价格下跌事件已经按同样的方式处理

(b) 技术（我的选择，已经写进 spec 和 design）：

- 系统设的提醒用备注 `TAPro` 认出来，只增删这些；备注不同的（比如在 app 里手工设的）不动，它们的推送也只是叫醒一轮
- 每一轮同步一次：启动以后第一轮设齐；论点更新、升降级、买入卖出以后最多一轮（60 秒）跟上；股票池不另外通知。这 60 秒里条件已经按新论点判断，提醒晚到不影响事件
- 同步时先读系统设的提醒，读不到（OpenD 没开）这一轮不同步、写 WARNING；单个提醒设置失败（比如额度满了）写 WARNING，其余照做，下一轮再试。moomoo 每只股票每种提醒最多 10 个，股票池最多 30 只，到不了
- 推送的回调在 SDK 的回调线程里，只设一个 `threading.Event` 叫醒事件检测的线程；不碰数据库、不拿锁；不检测断线和重连
- 行情加 `volume`（当日常规时段累计成交量，股）；没有迁移
- 本机开发和主机连同一个 moomoo 账户时会互相删对方的提醒：只让推送失效，条件照样每轮判断；不处理

(c) **完整版 Proposal 改了三句话**（propose 时已改，你不同意 (a) 第 1 条时改回）：

- 同一节「到价提醒的维护」"程序要收到推送，OpenD 必须在线；断线恢复后，事件检测层用实时行情把这些条件补查一遍。"改为"程序要收到推送，OpenD 必须在线；事件检测层每一轮也用实时行情判断这些条件，推送只让它提前判断，断线期间漏掉的推送由恢复后的下一轮补上。"
