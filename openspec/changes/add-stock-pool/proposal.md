# Proposal

## Why

Proposal 规定股票池是系统关注范围的唯一来源：事件检测层只监控池内股票和持仓，PM 探索的结果也只能进入股票池；同一只股票能给出哪些结论，只由它的状态（候选、关注、持仓）决定。现在代码里还没有股票池，M3 后面的调度器（按股票状态定案件类型）、收盘检查（候选超期、复查日、寻股触发）和跟进审批都要用到股票状态。前面的变更也有两件事留给了股票池：

- 风控规则的 design D7：方案和持仓里的板块从哪来
- 交易日历的 proposal：案件侧的"每日"到 M3 再定，股票池的每天增删次数第一个用到

本变更的目的只有一个：**股票池保存每只股票的状态和记录，由代码强制执行增删、升降级、候选超期移出和成交后的状态变化规则。**

引用的 Proposal（完整版）章节：

- 「股票池与寻股」：字段表（状态、来源、理由与论点草稿、关注论点、最新评分、时间）和增删规则（代码强制执行）
- 「触发」开头的两张表：三种股票状态，以及每种状态允许的结论。本变更只做其中和股票池有关的：加入、移出、升级、保持、降为候选
- 「触发」通用规则的"升级为关注"：关注论点的五项内容；代码校验字段齐全和关注名额；升级不经过 Critic
- 「持仓与退出」的"清仓后的股票状态"：PM 发起的清仓由 PM 选择转为关注或移出；代码触发的清仓自动转为候选
- 「共享状态库」的表：股票池属于当前市场事实，写入者是股票池校验（代码）

## What Changes

- 新增股票池模块 `modules/stockpool/`：纯逻辑、配置、存储端口和用例。存储只定义端口，测试用 `tests/fakes/` 的内存实现
- contracts 新增三个文件，后续变更要用：
  - 股票状态：候选、关注、持仓。调度器、收盘检查、跟进审批都按它判断
  - 关注论点、催化剂和代码能检测的条件。下一个变更的投资论点共用催化剂和条件
  - 上市信息：交易所、证券类型、日均成交额、板块，加入股票池时由调用方从数据源查好传入
- 交易日历新增一项查询：某个时刻归属哪个交易日，用来划分案件侧的"每日"
- 股票池的操作：

  | 操作 | 谁发起 | 状态变化 | 代码校验 |
  | --- | --- | --- | --- |
  | 加入 | PM 探索或手动添加 | 不在池子里 → 候选 | 理由；股票代码存在、在允许交易的范围内、流动性达标；不在池子里；不在冷却期；池子容量；每天增删次数 |
  | 删除 | PM | 候选、关注 → 移出 | 理由；持仓不能删除；每天增删次数 |
  | 升级 | PM | 候选 → 关注 | 关注论点齐全；关注名额 |
  | 降为候选 | PM | 关注 → 候选 | — |
  | 保持 | PM | 候选不变，重置过期时间 | — |
  | 记录评分 | PM 的每次结论 | 不变，更新最新评分和上次复查时间 | 评分是 -2 到 +2 的整数 |
  | 超期移出 | 代码 | 候选 → 移出 | 过期时间已到 |
  | 买入成交 | 代码 | 关注 → 持仓 | — |
  | 代码触发的清仓 | 代码（止损单、紧急退出） | 持仓 → 候选 | — |
  | PM 发起的清仓 | PM 在结论里选择 | 持仓 → 关注（带关注论点）或移出 | 关注论点齐全 |

- 不通过时给出原因，不改变任何记录。移出以后在冷却期内不能重新加入
- 阈值都可配置，默认值：

  | 配置项 | 默认值 |
  | --- | --- |
  | 池子容量（候选和关注合计） | 30 |
  | 关注名额 | 8 |
  | 每天增删次数上限 | 10 |
  | 候选过期期限 | 10 个交易日 |
  | 重新加入的冷却期 | 5 个交易日 |
  | 流动性门槛（日均成交额） | 1,000 万美元 |
  | 允许的交易所 | 纽交所、纳斯达克 |
  | 允许的证券类型 | 普通股、ADR |

## Non-goals

- 寻股的触发条件（有效候选下限、高评分候选数量、临近过期）和两次寻股之间的冷却期：属于「收盘检查」
- 寻股的量化粗筛：M4，要先定数据源
- 候选评估案件和它的每天上限、新候选什么时候开案件：属于「收盘检查」
- 投资论点，以及 PM 用什么格式提交增删和升降级：属于下一个变更「案件类型与结论」
- 更新关注论点（包括续期时设下一个复查日、催化剂到期后换新的催化剂）：属于「复查日与催化剂」，它定复查日和截止日期的取值规则（默认 5 个交易日、3 到 20、往后推要理由等）。本变更只要求关注论点里有这两个字段、类型正确
- 技术指标类的条件：M4 的事件检测要自己算指标，到时候加。本变更只定义到价提醒能覆盖的价格、涨跌幅、成交量
- 按入场条件设置和同步到价提醒、检测条件是否满足：M4 的事件检测
- 股票状态变化时作废跟进：属于「跟进审批」
- 上市信息、日均成交额和板块从哪个数据源取，用哪套板块分类：M4 定数据源时一起定
- 股票池的表和 repo、增删写进程序日志、谁在什么时候调用这些操作、一次只处理一个操作的做法：M4

## 需要人决定

已决定（2026-10-08，人同意推荐做法）：

1. **案件侧的"每日"**（交易日历变更留给 M3）：一个交易日从上一个交易日收盘到这个交易日收盘，和"恢复后的第一个交易日"是同一条规则；周末和休市日并进下一个交易日。本变更的每天增删次数第一个用到，以后的每日调用预算、每天的候选评估上限也按它算
2. **板块从哪来**（风控规则 design D7 留给股票池）：股票加入股票池时，由代码从数据源写入板块（调用方传入），方案和持仓的板块都取股票池里的，PM 不填；用哪套板块分类跟 M4 的数据源一起定
3. **"允许交易的范围"**：纽交所、纳斯达克上市的普通股（含 ADR），不含 ETF、OTC 和杠杆产品，做成可配置

新发现的，已按推荐做法写进 spec，不同意可以改：

4. **池子容量算不算持仓**：推荐只算候选和关注。持仓已经有风控的最多持仓数管着；买进的股票不该占寻股的位置
5. **哪些移出要进冷却期**：Proposal 只写了"删除后"和"PM 清仓后选择移出"。推荐所有移出都进冷却期，包括候选超期移出：否则超期的候选第二天可能又被寻股加回来，来回增删
6. **哪些操作算每天的增删次数**：推荐只算 PM 和手动的加入、删除，被拒绝的不算。升降级、保持、记录评分、超期移出和成交后的状态变化都不算
7. **成交后的状态变化遇到上限**：关注股买入成交后的变化不会超限，但清仓后转为候选或关注可能超出池子容量或关注名额。推荐照常变化，不能因为上限挡住成交带来的状态；超出期间加入和升级被拒绝，直到降回上限以下
8. **上次复查时间指什么**：推荐是 PM 最近一次对这只股票给出结论的时刻，和最新评分一起记录
9. **手动添加的校验**：推荐和 PM 添加一样，走全部校验、计入每天增删次数和冷却期，不给人开例外
10. **多个入场条件之间的关系**：推荐任一条件满足就算入场条件满足。每个条件对应一个到价提醒，各自触发；需要同时满足的组合条件属于技术指标类，M4 再加
11. **一份论点有几个催化剂**：Proposal 写"催化剂及截止日期"，又写"每个催化剂写成结构化字段"。推荐每份论点只有一个催化剂，写最近的那一个；到期后按续期的规则写新的催化剂和截止日期。这样每份论点只有一个截止日期，收盘检查和跟进审批都简单
