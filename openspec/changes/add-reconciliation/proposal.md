# Proposal

## Why

执行模块现在只按客户端订单 ID 一笔一笔地问券商，这样问不出下面几种情况：

- 券商那边多出来、执行模块没提交过的订单，比如 moomoo 用备注当客户端订单 ID 时偶尔重复下的单
- 执行模块以为已经结束、其实还挂着的止损单，以及同一只股票的第二张止损单。两张止损单可能把同一批股票卖两次
- 券商持仓里，执行模块的订单解释不了的股票
- 券商受理过、后来又查不到的订单或止损单。按现有规则，它们会一直是状态未知，"等对账处理"。订单一直卡在状态未知，这只股票就永远不能下新订单，连卖出也不行

另外，Proposal 要求断线或重启以后先和券商对账，对完才恢复运行；每日收盘后也要全量对账，对不上就告警并暂停开仓。前面三个变更（订单状态机、止损保护、额度预留）都把这些留给了本变更。

本变更的目的只有一个：**执行模块和券商全量对账：补上停机期间漏掉的变化，结束查不到的订单和止损单，发现对不上的挂单和持仓就暂停开仓；启动之后要先对账，才接受新订单。**

引用的 Proposal（完整版）章节：

- 「订单生命周期」表里的这几行：
  - 断线或重启：恢复后先与券商对账（订单、成交、持仓、资金），以券商为准修正状态库，再恢复运行
  - 每日对账：每日收盘后与券商全量对账，并检查每只持仓都有有效的止损单、数量和持仓一致；不一致即告警并暂停开仓，缺止损单的按「止损单挂单失败」处理
  - 状态未知：暂停该股票的新订单，与券商对账后再决定
  - 防止重复提交：超时后先按客户端订单 ID 查询，确认未收到才重试
- 「架构」的"风控与执行"：执行模块断线或重启后先与券商对账
- 「风控引擎与执行」的"额度预留"：进程重启后，根据状态库和券商对账结果重建预留

## What Changes

- 执行模块增加对账，按这个顺序做：
  1. 读券商那边全部挂着的订单、全部挂着的止损单和全部持仓
  2. 拿读到的挂单和止损单，找出不一致
  3. 跟进每一笔未结束的订单
  4. 对齐有持仓、有在用的止损单或者是无保护仓位的股票的止损单
  5. 找出券商持仓里来历不明的股票
  6. 给出对账结果
- 不一致分三类：
  - **不认得的挂单**：券商挂着的普通订单，不是执行模块的哪一笔未结束订单。按客户端订单 ID 和券商订单号判断
  - **多出来的止损单**：一只股票在券商挂着的止损单多于一张，或者执行模块这只股票没有在用的止损单，券商那边却挂着一张。只比较张数，因为 Alpaca 改单时订单号会变
  - **来历不明的持仓**：券商有持仓，执行模块这只股票却没有成交过的买单，也没有未结束的买单
- 停机期间的成交、订单结束、止损单被撤或到期，由第 3、4 步按已有的跟进和对齐规则补上。这些不算不一致
- 对账时，受理过却按 ID 查不到的订单或止损单，如果第 1 步读到的挂单里也没有它，就当作已经结束：
  - 订单按截止时刻记为已撤销或已过期，累计成交保留已经记下的
  - 止损单记为已经结束，对齐时挂一张序号加 1 的新止损单
- 对账之前不接受新订单：执行模块新建以后，完成第一次对账之前，拒绝为任何方案新建订单
- 有不一致时暂停开仓：最近一次对账有不一致，就拒绝新的买单（买入和加仓），卖单照常；下一次对账没有不一致时恢复
- 对账不撤销任何挂单，也不修改别的东西，告警由调用方按对账结果发出
- 券商接口增加：读取全部挂着的订单、全部持仓（`Broker`），全部挂着的止损单（`StopBroker`）。止损保护存储增加读取需要对齐的全部记录
- 测试替身：假券商和假止损单接口可以列出挂单，测试可以安排券商那边另外挂着的单；内存止损保护存储增加对应的查询

## Non-goals

- 资金、已结算资金、交易记录的成交、费用和结算状态的核对，以及以券商为准修正状态库：交易记录和状态库方案要到 M2 才确定，见「需要人决定」第 3 条
- 核对预留：用对账之后的订单状态调用风控的"上报成交"和"释放"，由 M2 的下单工作流做，变更 5 已经这样定下。额度预留变更建议过的"每份有效预留都对应一个还没结束的方案或订单"要跨风控和执行两个模块，本变更不做，M2 拆变更时再看要不要
- 撤销不认得的挂单或多出来的止损单：只告警并暂停开仓，由人在券商 App 里处理。自动撤单有可能撤到执行模块自己的止损单（Alpaca 改单后订单号会变）
- 什么时候对账、由谁触发：启动时由 bootstrap 调用，收盘后由定时心跳调用，断线恢复后由健康监控调用，都在 M2 接入
- 断线以后重新要求对账：本变更只在启动后要求对账。断线期间提交的订单会进入状态未知，这只股票随之暂停；断线恢复后先对账、再恢复运行，交给变更 9 的降级模式
- 告警的发送：Discord 在 M2 接入
- 券商适配器（Alpaca 在 M2，moomoo 在 M7）和止损保护存储的数据库实现：M2

## Capabilities

### New Capabilities

- `reconciliation`：对账的流程、不认得的挂单、多出来的止损单、来历不明的持仓、结束查不到的订单和止损单、对账之前不接受新订单、有不一致时暂停开仓

### Modified Capabilities

- `order-lifecycle`：「提交订单」增加两条：还没对账时不能提交新订单，有不一致时不能提交新的买单；基准数据增加"执行模块已经完成一次没有不一致的对账"

- **代码**：全部在 `modules/execution/`

  - `domain/order.py`：`Order` 增加"受理过、查不到、券商挂单里也没有"时的结束方法
  - `ports.py`：`Broker` 增加 `working_orders`、`positions`；`StopBroker` 增加 `working_stops`；`ProtectionStore` 增加 `active`
  - `service.py`：`ExecutionService` 增加 `reconcile`，`submit` 增加两条检查；内部的跟进和对齐可以接收对账读到的挂单
  - `__init__.py`：导出新的名字
- **测试**：
  - `tests/fakes/` 里的假券商、假止损单接口和内存止损保护存储增加对应的操作
  - `tests/modules/execution/builders.py` 的执行用例默认先对账一次
  - 新增 `tests/modules/execution/domain/test_reconciliation.py`、`tests/modules/execution/test_reconciliation_service.py`
  - 已有的两个状态机性质测试里，"重启"之后先对账，并增加"对账"这一步
- **依赖**：无
- **文档**：完整版 Proposal「订单生命周期」表的"每日对账"一行，按「需要人决定」第 1、2 条修改，等人同意后再改
- **对后续变更的影响**：
  - 变更 8：紧急退出不会再被卡住的状态未知订单永远挡住；启动后同样要等第一次对账完成
  - 变更 9：建议券商断线时进入降级模式，连接恢复后先对账、再退出降级，满足"断线后先对账，再恢复运行"
  - M2：
    - bootstrap 启动时先对账，收盘后由定时心跳对账，按对账结果发 Discord 告警
    - 对账和其他执行调用要串行，同一笔订单不能同时被对账和下单工作流处理
    - Alpaca 适配器：`working_orders` 不列止损单，`working_stops` 只列止损单；改单还在替换的过程中时，新旧两笔只算一张
    - Alpaca 模拟盘账户关掉做空：万一挂出两张止损单，第二张卖单只会被拒，不会开出空头
    - 交易记录的费用和结算状态怎么核对，在 M2 拆变更时决定
  - M7：moomoo 适配器按备注找订单；查询订单列表限频，每 30 秒 10 次

## 需要人决定

1. **账户只给系统用**（已决定，2026-10-04）：「每日对账」没说券商那边出现系统不认得的挂单或持仓时怎么办。人决定账户只给系统用，想开仓也通过 PM 来开。所以凡是券商那边系统解释不了的挂单和持仓，都算不一致。
   - 推荐把「每日对账」一行补上一句：账户只给系统用，券商那边系统解释不了的挂单和持仓都算不一致
2. **暂停开仓什么时候解除**：「每日对账」只写了"不一致即告警并暂停开仓"，没写什么时候恢复。
   - 推荐：之后的对账没有不一致，就自动恢复开仓。对账可以随时再跑，比如人在 App 里处理完之后，不用等到下一个收盘
   - 自动修好的情况不算不一致，否则会无故暂停开仓。比如止损单到期被撤后又补挂上（Alpaca 的 GTC 单 90 天自动撤销），或者补上停机期间的成交
   - 推荐把「每日对账」一行补上：之后的对账没有不一致时恢复开仓
3. **交易记录的费用和结算状态**：「每日对账」要求核对交易记录的成交、费用和结算状态。但交易记录要到 M2 才有，Alpaca 模拟盘也不模拟费用，而且只有保证金账户，没有现金账户的结算。
   - 推荐：完整版不改，这部分放到 M2，在定交易记录和状态库方案时决定模拟盘核对哪些，费用和结算状态到 M7 接入实盘时再核对
