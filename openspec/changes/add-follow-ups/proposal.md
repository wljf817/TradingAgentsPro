# Proposal

## Why

Proposal 的三类驱动里，自定义跟进是 PM 针对某个具体原因申请的一次性检查，由调度器（代码）审批：没有引用具体对象的、和论点的催化剂重复的拒绝，原因相同的替换旧的，每只股票同时最多 2 个，触发时间最远 60 个交易日，每天的申请次数有上限；股票状态往下走时作废。前面的变更已经备好了零件：case-types spec 定了跟进申请的格式（原因类型、引用的对象、问题、可能采取的动作、触发时间）、跟进的触发（`FollowUpTrigger`：股票和问题）、跟进案件按开始时的状态定类型、跟进案件不能再申请跟进，并把"原因类型和引用的对象是否对应、触发时间的范围"留给本变更；review-dates spec 保证催化剂按规则引用日程项或事件；stock-pool spec 定了状态变化。但还没有东西审批申请、保存待执行的跟进、到点给出触发。

本变更的目的只有一个：**审批 PM 在结论里附的跟进申请（拒绝、批准或替换），保存待执行的跟进，到点给出跟进的触发，股票状态往下走时作废它们。**

引用的 Proposal（完整版）章节：

- 「触发」开头的驱动表：自定义跟进"PM 申请，调度器审批"，触发时间由 PM 指定
- 「触发 · 3. 自定义跟进」全节：和定时心跳的区别；允许和不允许的例子；申请必须写明的四项；防止重复的规则表；其他规则；跟进案件
- 「触发 · 2. 定时心跳」催化剂截止日期一条的最后一句：代码靠催化剂引用的日程项或事件判断自定义跟进是否绑定了催化剂

## What Changes

- 新增跟进模块 `modules/followups/`：纯逻辑、配置、存储端口和用例。存储只定义端口，测试用 `tests/fakes/` 的内存实现
- 跟进的记录：跟进 ID、股票、申请（原样保存原因类型、引用的对象、问题、可能采取的动作、触发时间）、来源案件、获批时刻、状态。状态有待执行、已触发、被替换、已作废，只有待执行的会变化
- 审批：调用方在结论通过 case-types 的结论校验和 review-dates 的检查以后，作为最后一项检查调用，传入股票、申请、来源案件和这份结论生效以后的论点的催化剂。不通过时返回原因、不改变记录，调用方当作结论校验不通过退回 PM；通过时保存为待执行的跟进。按顺序检查：

  | 顺序 | 检查 | 不通过时的原因 |
  | --- | --- | --- |
  | 1 | 引用了具体对象 | 没有引用具体对象（提示改为调整复查日） |
  | 2 | 原因类型和引用的对象对应：事件后反应引用事件，外部日程引用日程项，价格或指标观察引用代码能检测的条件 | 原因和引用的对象不符 |
  | 3 | 引用的不是论点的催化剂引用的那个日程项或事件 | 催化剂已经覆盖 |
  | 4 | 触发时间在现在之后 | 触发时间已过 |
  | 5 | 触发时间早于今天之后第 60 个交易日的收盘时刻 | 触发时间太远 |
  | 6 | 不替换的申请：这只股票待执行的跟进少于 2 个 | 待执行的跟进已满 |
  | 7 | 今天获批的申请少于每天的上限 | 申请次数已用完 |

- 替换：同一只股票已有原因相同（原因类型相同，且引用同一个对象）的待执行跟进时，新申请获批后替换它，旧的记为被替换；替换不算新增
- 到点触发：触发时间不晚于现在的待执行跟进记为已触发，按触发时间给出；每个就是一个跟进的触发（股票、申请时写下的问题）。跟进只触发一次
- 作废：股票的状态往下走（清仓，不论之后转为关注、候选还是移出；关注降为候选；移出股票池）时，这只股票待执行的跟进全部作废；关注股买入变成持仓时保留
- 可配置项：每只股票的待执行跟进上限 2 个；触发时间最远间隔 60 个交易日；每天的申请次数上限 5 次（按案件侧的"每日"划分，只算获批的申请，新增和替换都算）
- contracts 和 shared 不改：跟进申请、原因类型、催化剂和它的引用、代码能检测的条件、股票状态都已经在 contracts，交易日历已经有"时刻归属的交易日"，ID 生成端口已经在 shared

## Non-goals

- 跟进申请的格式、跟进案件不能再申请跟进、跟进案件按开始时的状态定类型：case-types spec 已经规定，本变更不重复
- 每天的申请次数怎么计入调用预算：属于「调用预算」
- 引用的事件或日程项是否存在、触发时间是否在日程项之后：本变更不检查（「需要人决定」第 7 条），日程项和事件从哪来由 M4 定数据源时定
- M4：
  - 跟进的表和 repo，存储只追加
  - 什么时候调用：结论校验之后审批；定时（或用持久化休眠在最早的触发时间）取得到点的跟进，转成 `FollowUpTrigger` 入队；股票池的每次状态变化以后交给本模块
  - 把这只股票待执行的跟进放进案件上下文；跟进案件的上下文带上原案件的结论和申请原因
  - 审批、拒绝、替换、作废和触发写进程序日志
- M5：PM 的提示写明跟进和复查日的区别、三种原因各引用什么、被拒绝的原因怎么改

## Capabilities

### New Capabilities

- `follow-ups`：跟进的记录和状态；审批的输入和结果、检查的顺序；引用的对象；不和催化剂重复；触发时间；原因相同时替换；每只股票的待执行跟进上限；每天的申请次数；到点触发；股票状态往下走时作废；跟进的配置

### Modified Capabilities

无。case-types spec「跟进申请的格式」已经写明原因和引用是否对应、触发时间的范围由「跟进审批」检查；跟进的触发不变。

## Impact

- **代码**：新增 `modules/followups/`：`__init__.py`、`config.py`、`ports.py`、`service.py`、`domain/__init__.py`、`domain/follow_up.py`、`domain/rules.py`。contracts、shared 和其他模块不改
- **测试**：新增 `tests/fakes/follow_ups.py`、`tests/modules/followups/`（`builders.py`、`test_config.py`、`domain/test_follow_up.py`、`domain/test_rules.py`、`test_service.py`、`test_state_machine.py`）
- **依赖**：无
- **文档**：人同意「需要人决定」以后，完整版 Proposal「触发 · 3. 自定义跟进」补上已决定和新发现的条目，每处一两句话
- **对后续变更的影响**：
  - 调用预算：每天的申请次数计入调用预算；跟进案件按持仓或关注用对应的预算（case-queue spec 已定）
  - M4：建表和 repo；按 design D11 接线：结论校验的最后一步审批，到点触发转成 `FollowUpTrigger`，股票池状态变化以后作废；读待执行的跟进放进案件上下文
  - M5：PM 的提示和上下文见 Non-goals

## 需要人决定

已决定（2026-10-08）：

1. **哪些状态变化让跟进作废**：只有往下走的变化作废：清仓（不论清仓后转为关注、转为候选还是移出）、关注降为候选、移出股票池；关注股买入变成持仓时跟进保留（跟进案件按开始时的状态定为持仓跟进，case-types spec 已经这样写）

新发现的，已按推荐做法写进 spec，不同意可以改：

2. **申请被拒绝以后怎么办**：Proposal 写"拒绝，并提示 PM 改为调整复查日"，没说结论还算不算。推荐和复查日的检查一样：调用方当作结论校验不通过，带着原因退回 PM 在同一个案件里修改（去掉跟进申请，或者改为在论点更新里调整复查日），计入重交次数。只丢掉跟进、照常执行结论的话，PM 不知道跟进没批，也就"提示"不到。审批获批即保存，所以放在结论校验的最后一步
3. **和哪份论点的催化剂比**：Proposal 写"论点里某个催化剂引用的对象"。推荐用这份结论生效以后的论点：附了论点更新时用更新里的催化剂，否则用现在的论点。PM 可能在同一份结论里把事件关联到催化剂上（只关联事件），又申请这个事件的跟进；和原来的论点比就放过了重复
4. **每天的申请次数怎么数**：推荐按案件侧的"每日"（时刻归属的交易日）划分，只算获批的申请，新增和替换都算，被拒绝的不算，之后触发或作废也不退还；默认每天 5 次。理由：被拒绝的申请不会开案件，算进去等于 PM 写错一次就少一次；替换也是一次申请，从记录直接数得出来，不用另记哪些是替换。持仓和关注最多 16 只，财报季一天几只股票发财报，每只申请一个"看盘后反应"，5 次够用；又把跟进开出的案件压在每天 5 个左右，和每天 3 个候选评估同一量级
5. **触发时间的范围怎么算**：推荐触发时间必须在现在之后，并且早于今天（现在归属的交易日）之后第 60 个交易日的收盘时刻，也就是触发时间归属的交易日不晚于那一天；不限于交易时段。和催化剂截止日期的"60 个交易日以后"同一个起点；只算上限、不查触发时间本身归属哪天，PM 写一个几十年后的时间也只是被拒绝，不会超出交易日历的范围
6. **跟进只触发一次**：Proposal 写"一次性检查"，没说跟进案件没有结论（系统故障、结论无效）时怎么办。推荐不重新触发：跟进的问题针对某个时点（"3 小时后看盘中反应"），晚了就没有意义；持仓和关注本来有复查日兜底；重新触发要把案件的结果传回本模块，多一条状态。和复查日的顺延不同：复查日不续期就一直到期，跟进没有这样的日期。到点时处于降级模式或预算用完，照常触发、入队，案件留在队列里，和收盘检查一样
7. **引用的事件或日程项要不要存在**：推荐本变更不检查。日程项从哪来要到 M4 定数据源时才定，竞争对手的财报、行业大会不一定在数据源里，检查存在会拒绝 Proposal 自己举的例子；编一个引用最多多开一个跟进案件，还受每只股票 2 个和每天上限的约束，复盘能发现。M4 定了数据源以后，需要时由一个「修改：跟进审批」加上
8. **每只股票的上限做成配置**：Proposal 只写"最多 2 个"。推荐和其他阈值一样做成配置项，默认 2；替换不算新增，已触发、被替换、已作废的不计入
