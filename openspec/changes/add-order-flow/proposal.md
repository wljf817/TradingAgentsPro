# Proposal

## Why

`/plan` 现在只能录入、不能下单：提交接口和确认按钮的回调都只会报「下单流程还没接上」。「盘中巡检」接手了订单提交以后的跟进，但从方案通过风控到订单交给执行模块之间的这一段还没有：没有人请求人工确认、等按钮，盘外确认的方案没有人等到开盘，也没有人做下单前再校验、调用 `execution.submit`。这一段要跨越几十分钟到几天（等确认、等开盘），中途程序可能重启，所以要用 DBOS 的持久化工作流来做。

本变更的目的只有一个：**把 `/plan` 录入的方案接上一条持久化的下单流程：风控检查并预留，请求人工确认，确认以后在常规交易时段内再校验并提交订单，订单交给盘中巡检；方案在下单以前结束时释放预留。**

引用的 Proposal（完整版）章节：

- 「风控引擎与执行」：
  - 开头一段：结果只有通过、调整、拒绝；调整只往小调，调整后的方案直接进入人工确认，确认消息里标明「已被风控调整」
  - 下单前再校验：提交订单前重新读取实时报价、券商持仓和可用资金，重跑风控；超过有效期或价格偏离过大，方案作废
  - 交易时段：只在常规交易时段下单；盘前盘后形成的方案等开盘执行，开盘时由再校验检查跳空
  - 额度预留：风控一次只处理一个方案；方案作废、人工拒绝或确认超时时释放
  - 最后一段：通过后进入人工确认，再交给执行模块
- 「订单生命周期」：
  - 开头一段：提交订单以后订单由执行模块独立跟踪（交给盘中巡检）
  - 表的「每日对账」（不一致即暂停开仓）、「止损单挂单失败」（补挂成功前禁止加仓）：决定已经确认、还没下单的开仓方案遇到这两种暂停时怎么办，见「需要人决定」第 1 条
- 「持仓与退出」：人工确认（开仓类默认必须确认）。`/plan` 录入的四种方案（含减仓、清仓）都要确认，已决定：M2 的完成标志包括「确认」
- 「故障处理」降级模式：暂停开仓和加仓，已经确认、还没下单的开仓方案在下单前再校验时作废；已经人工确认的退出方案照常执行
- 「技术栈与部署」：
  - DBOS 一行：持久化工作流，用持久化休眠等待、用持久化通知等待人工确认
  - 通知与人工确认一行：Discord 发不出去时只写程序日志；确认请求发不出去的方案按确认超时处理
  - 可靠性要求：进程崩溃后由 DBOS 从断点恢复

## What Changes

- `/plan` 的提交接口接上：读执行模块的账户数据和持仓的行情，拼成风控用的账户数据（不拿锁）；拿着全程序那把锁（session-patrol spec）做风控检查和预留，熔断取紧急退出的状态、降级取健康监控的状态；通过或调整的方案以方案 ID 为 DBOS 工作流 ID 启动这个方案的下单流程，返回风控结果，不等人工确认；拒绝的方案不启动
- 新增下单流程（DBOS 工作流，一个方案一个）：
  1. 请求人工确认（四种动作都要），用 DBOS 的持久化通知等按钮，等的时长就是确认超时（默认 30 分钟）；确认请求发不出去按确认超时处理
  2. 人工拒绝、确认超时：释放全部预留，流程结束；超时时把确认消息改为已超时
  3. 确认以后：到了生效的有效期就作废；盘中立即下单；盘外用持久化休眠等到下一个开盘
  4. 下单：读实时账户数据和行情，拿锁做下单前再校验，通过或调整（不再确认）就在同一次拿锁里提交订单；之后订单交给盘中巡检，流程结束
  5. 再校验拒绝（含降级、熔断时的开仓方案）、到有效期还没下单、最近一次对账有不一致：方案作废并告警；无保护仓位、同一股票有状态未知的订单、取不到当天的价格、读券商超时：等一会儿（默认 30 秒）再从再校验开始，直到有效期
- 确认按钮的回调接上：只在这个方案的下单流程正在等确认时把结果送给它，否则报错（按钮提示没有送达）。晚按的按钮不会显示已确认却不下单
- 进程重启或程序更新以后，进行中的下单流程由 DBOS 从断点继续：不重复请求确认、不重复下单，等确认、等开盘的接着等
- 告警（Discord）：已确认的方案作废、下单被券商拒绝、下单第一次出意外的错；其余结果只写 Python 日志（M4 才有程序日志，已决定）
- bootstrap：装配真实的提交接口和按钮回调，删掉「下单流程接上之前」的占位；DBOS 启动之前登记下单流程用到的部件；DBOS 打开 patching，程序更新以后照样恢复进行中的下单流程；停止时关完各部件立即退出，不等还在等确认、等开盘的工作流线程

## Non-goals

- 订单提交以后的跟进、成交上报、订单结束时释放预留：「盘中巡检」
- 紧急退出：取行情判断、撤单、清仓、本地备用止损、熔断时撤买单，以及紧急风险事件时作废这只股票还没下单的方案：「紧急退出流程」
- 收盘后的对账和对账不一致的告警：「收盘对账」；本变更只读最近一次对账的结果（经 `execution.submit`）
- 健康信号、进入和退出降级模式的判定和告警：「健康监控接线」；本变更只读健康监控的当前状态
- 人工确认规则的变化（紧急退出的确认开关、模型建议退出的确认和超时告警）：M3「人工确认的规则」
- 案件工作流、案件排队时作废等确认的开仓方案：M4
- 改变执行模块、风控、通知模块的任何行为；本变更不给模块加方法，用到的只读查询 `execution.order` 由「盘中巡检」加
- 部署机器上的端到端检查：整个「流程」组做完统一做
- 程序日志：M4；现在写 Python 日志
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `order-flow`：提交方案（风控检查、预留、启动下单流程）；风控用的账户数据；请求人工确认和确认的结果；按钮的结果只送给在等确认的方案；等开盘；下单前再校验和提交；提交的结果和重试；告警；持久化和恢复；执行模块和风控的调用串行；日志；下单流程配置

### Modified Capabilities

- `bootstrap`：「模拟盘的装配」的 `/plan` 一行改为下单流程的提交接口和回调，加「下单流程」一行；「DBOS」加启动前登记下单流程、打开 patching、启动时恢复进行中的下单流程；「停止」加不等下单流程的线程、立即退出；删除「下单流程接上之前」

## Impact

- **代码**：
  - 新增 `src/tradingagentspro/workflows/account_snapshot.py`（风控用的账户数据）、`workflows/order_flow.py`（每一步的用例、配置、告警文字）、`workflows/order_workflow.py`（DBOS 工作流和 step、提交接口 `OrderPlanIntake`、按钮回调 `deliver_decision`）
  - `bootstrap/app.py`：装配和 DBOS 配置；删除 `bootstrap/order_flow.py`；`bootstrap/cli.py` 加 `entry`，`pyproject.toml` 的命令入口改为它
  - modules、contracts、shared、integrations 不改
- **依赖**：无新依赖（DBOS 已经在用）
- **数据库**：没有新表和迁移；DBOS 在 `dbos` schema 里记下每个下单流程的步骤
- **测试**：新增 `tests/workflows/` 下的账户数据、下单流程（不连 DBOS）和工作流（真实 DBOS + testcontainers，要开着 Docker）测试；改 `tests/bootstrap/`
- **前置变更**：「盘中巡检」（`add-session-patrol`）要先 apply：用它的锁（`TradingApp.lock`）和执行模块的只读查询 `order`
- **对后续变更的影响**：
  - 「紧急退出流程」：作废这只股票还没下单的方案时释放它的预留，下单流程在再校验时得到「方案已结束」而作废；等确认中的方案怎样作废到时再定
  - M3「人工确认的规则」：改本变更的「请求人工确认」和「确认的结果」
  - M4 案件工作流：风控检查是案件的一个 step，之后启动同一个下单流程
- **文档**：`docs/实现路线.md` 的进度；人同意「需要人决定」以后改完整版 Proposal

## 需要人决定

1. **已经确认、还没下单的开仓方案遇到「对账不一致」和「无保护仓位」时怎么办，完整版没有写。** 「订单生命周期」的「每日对账」只写了「不一致即告警并暂停开仓」，「止损单挂单失败」只写了「补挂成功前禁止加仓」；「故障处理」对降级模式写明了「已经确认、还没下单的开仓方案在下单前再校验时作废」，这两种暂停没有写。
   推荐做法（spec 已按它写）：
   - 对账不一致：方案作废、释放预留、告警。和降级模式的处理一致；不一致要到之后的对账没有不一致才解除，M2 里下一次对账在收盘以后，等也多半等到有效期
   - 无保护仓位（只影响加仓）：等补挂成功再下单，到有效期还没补挂成功就作废并告警。「补挂成功前禁止加仓」是暂时的，盘中巡检每一轮都在补挂，多数情况几十秒内就恢复
   完整版的改法：「每日对账」一行的「不一致即告警并暂停开仓」后面加「（已经确认、还没下单的开仓方案作废）」；「止损单挂单失败」一行的「补挂成功前禁止加仓」后面加「（已经确认的加仓方案等补挂成功再下单，到有效期还没补挂成功就作废）」。不同意时按人的决定改 spec 和 design。
