# Proposal

## Why

Proposal 要求一份只追加的程序日志，实时记下所有模块、agent 和人的每个动作，用来排查故障、审计和复现。现在程序的动作（风控结果、确认、下单、订单和止损单的变化、对账、降级、紧急退出、告警）都只写进 Python 的日志，由 journald 保存：不能按方案、股票查，和技术诊断混在一起，也没有记下启动、停止和崩溃恢复。M4 后面的变更（股票池存储、跟进存储、任务和费用、事件检测、调度、案件工作流）都要把自己的动作写进程序日志，所以表和写入接口要先有。

本变更的目的只有一个：**建一份只追加的程序日志，把现在已有的风控引擎、执行模块、人和系统的动作写进去，并给以后的模块留同一个写入接口。**

引用的 Proposal（完整版）章节：

- 「记录、复盘与经验」开头的表：程序日志记下所有模块、agent 和人的每个动作，所有模块写入，你和 Reviewer 读，用来排查故障、审计、复现
- 「记录、复盘与经验 · 程序日志」：实时写入，只追加、不可修改、不可删除；每条的字段（时间、行为者、动作、对象、案件 ID、输入和输出的引用、耗时、token 和费用）；行为者和动作的表。本变更写其中风控引擎、执行模块、人、系统四行
- 「调度器与运行模块」的模块表：程序日志由所有模块实时写入，不归任何模块管理
- 别的章节里写明要进程序日志的几句：「订单生命周期」订单的每次状态变化；「交易记录」每次变化；「技术栈与部署」通知一行，Discord 发不出去时只写程序日志、不另设备用通道

已经定了的：

- 以前的变更留给本变更的（人已同意）：启动、停止改为写程序日志，并记下崩溃恢复（add-bootstrap-wiring）；人的确认、拒绝、超时和告警改为写程序日志（add-discord-notify）；订单的每次状态变化和交易记录写程序日志（add-session-patrol、add-trade-records）
- 拆分 M4 时定的：程序日志是状态库所在数据库里的一张只追加的表；只写现在已有的行为者，没有的（事件检测层、调度器、Agent 网关、股票池、跟进）由各自的变更用本变更的接口加；模型调用的完整输入和输出在 M5；Python 日志留给技术诊断和启动、停止的过程；巡检每一轮没有变化的不写；写入失败照常报错，不兜底；不做查看界面

## What Changes

- 新模块「程序日志」（`modules/programlog`）：条目、追加和读最近一条的存储接口、数据库实现、写入用例；新表 `programlog_entries`（迁移 v0004），只有追加和读取，没有修改和删除
- 每条记下：时间（时钟，UTC）、行为者、动作、对象、案件 ID、输入和输出的引用、说明、耗时、token、费用。现在的动作没有案件 ID、耗时、token 和费用，这几项为空
- 写进程序日志的动作：
  - 风控引擎：风控检查、下单前再校验、释放预留（下单流程、紧急退出、巡检的同步预留）
  - 执行模块：提交订单、订单变化（巡检的跟进，以及撤单和对账时跟进的订单）、撤单、止损单变化、无保护仓位和解除、对账（启动、收盘、恢复后）、等开盘
  - 人：`/plan` 录入方案、确认、拒绝、超时
  - 系统：启动、停止、崩溃恢复、进入和退出降级模式以及其间的变化、熔断、紧急风险退出、告警、请求确认、结束确认
- 这些动作原来的 Python 日志去掉，不留两份；Python 日志只留启动和停止的过程（bootstrap spec 要求的那些行，其中启动对账和第一次健康判定的结果两边都有）、技术问题（异常栈、券商和行情超时或断线、取不到数据、Discord 出错）和 Discord 适配器收到的按下和命令。紧急退出等撤单的每一轮不再写
- 通知模块记下自己发到 Discord 的东西（告警、确认请求、结束确认），发不出去的也记，写明原因：推送告警时调用方另给出告警针对的对象，报告确认结果时另给出方案 ID
- 启动：数据库升级以后写「启动」，上一次运行没有写「停止」就先写「崩溃恢复」；关闭数据库连接之前写「停止」，启动失败也写

## Non-goals

- 还没有的行为者和动作：事件检测层、调度器、Agent 网关、股票池、跟进；人修改配置或宪章、批准修改建议、手动添加股票；调用预算消耗。以后的变更用本变更的接口加
- 模型调用的完整输入和输出、上下文版本、token 和费用：M5；本变更只建这几列
- 案件 ID：「案件记录」「案件工作流」以后才有
- 状态库条目的引用格式：「状态库快照」决定；本变更的引用是方案 ID、确认消息的标识、交易日这类现成的标识
- 查看程序日志的界面、Reviewer 和查询工具读程序日志：人先用 SQL 查（`deploy/README.md` 写明连法和常用的查询）；Reviewer 和 `query_history` 在 M5、M6
- 数据库层面禁止修改和删除（触发器、权限）：程序没有修改和删除的接口，见 design
- 改变风控、执行模块：两个模块的代码和行为都不改，条目由调用它们的流程按返回的结果写
- Discord 适配器收到的东西（每次按下按钮、每条 `/plan` 命令）：照旧写 Python 日志（discord-notification spec、manual-plans spec），没有生效的按下和命令不进程序日志
- 部署：表随启动时的迁移建好，备份本来就覆盖整个数据库
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `program-log`：程序日志的条目和字段；只追加；写入失败；风控引擎、执行模块、人、系统各自的动作（什么时候写、对象、引用、说明）；不写进程序日志的东西

### Modified Capabilities

- `bootstrap`：「日志」写明程序的动作进程序日志，这里的日志只写启动和停止的过程和技术问题
- `order-flow`：「日志」改为写程序日志
- `session-patrol`：「无保护仓位的告警」「订单和止损单变化的日志」改为写程序日志
- `emergency-exit-flow`：「紧急退出的人工确认」「告警」改为写程序日志，等撤单的轮次不再写
- `health-monitoring`：「状态变化的告警和日志」「恢复后的对账」改为写程序日志
- `close-reconciliation`：「结果消息」的日志改为程序日志
- `discord-notification`：「告警」调用方给出对象、每条告警写程序日志；「结束确认」调用方给出方案、每次报告写程序日志
- `state-store`：「表的归属和迁移」加程序日志的表

## Impact

- **代码**：
  - 新增 `modules/programlog/`（`domain/entry.py`、`ports.py`、`repo.py`、`service.py`、`__init__.py`）和迁移 `bootstrap/migrations/versions/v0004_create_program_log.py`
  - `modules/notification/service.py`：构造参数加程序日志；`alert` 加对象，`finish_confirmation` 加方案 ID；告警、确认请求、结束确认写条目
  - `workflows/`：`order_flow.py`、`order_workflow.py`、`patrol.py`、`emergency_flow.py`、`health.py`、`reconciliation.py` 写条目、去掉对应的 Python 日志；新增 `workflows/entries.py`（几个流程共用的订单变化、方案和风控结果的条目）
  - `bootstrap/`：`app.py` 装配程序日志，`TradingApp` 加 `log`；`startup.py` 写启动、崩溃恢复、启动对账和第一次健康判定的条目；`logs.py` 只改说明
  - `integrations/discord/notifier.py`：去掉和通知模块的条目重复的三条 INFO；其余不改
  - 除了通知模块，已有的模块（包括风控、执行模块）和 contracts、shared 都不改
- **测试**：`tests/modules/programlog/`（数据库实现要开着 Docker）；`tests/fakes/` 加程序日志的内存存储；`tests/workflows/`、`tests/bootstrap/`、`tests/modules/notification/` 里断言 Python 日志的地方改为断言程序日志
- **依赖**：无
- **数据库**：一张新表、一个迁移；每天大约几百条
- **文档**：`docs/实现路线.md` 的进度；`deploy/README.md` 加一节「查看程序日志」
- **对后续变更的影响**：以后的模块在 service 里拿一个 `ProgramLog`、import 程序日志模块的包根就能写，不破坏分层（design D3）；新的行为者和动作加进程序日志模块的枚举

## 需要人决定

1. **「每条规则的检查结果」**：风控引擎的结果只列出不通过的规则（`RiskDecision.violations`），通过的规则不单独列。
   推荐做法：风控检查的条目写结果、最终股数和每条不通过的规则及说明，没列出的规则都算通过；不为此改风控模块。小问题，完整版不改。
2. **崩溃恢复怎样判定**：完整版只列了「崩溃恢复」这个动作，没说怎样算。
   推荐做法：启动时看程序日志里最近一条启动或停止；是启动，说明上一次运行没有走到停止，就先写一条崩溃恢复（写明上一次启动的时刻），再写这次的启动。停止在关闭数据库连接之前写，正常停止和启动失败都写，所以只有进程被杀、断电这类情况会算崩溃。spec 和 design 按这一条写。
3. **你怎样读程序日志**：完整版说读取者是你和 Reviewer，没说怎样读。
   推荐做法：先在部署机器上用 psql 查表，`deploy/README.md` 加一节写明连法和几条常用的查询（按时间、按方案 ID、按股票，design D11）；用得多了再加一个命令或 Discord 摘要。
4. **「不可删除」和部署的恢复、重置**：deployment spec 的「恢复备份」会让程序日志回到备份时刻，「全部重置」会清空它。
   推荐做法：「不可修改、不可删除」约束的是程序；恢复和重置是人对整个数据库的操作，照旧。小问题，完整版不改。
