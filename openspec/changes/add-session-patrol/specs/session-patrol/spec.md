# Spec Delta

## Purpose

盘中巡检随程序一直运行，每一轮跟进全部未结束的订单、按订单同步风控的预留、对齐持仓的止损单，发现无保护仓位时告警；执行模块和风控里会改变状态的调用都经一把进程内的锁一次只进行一个。

## ADDED Requirements

### Requirement: 巡检的开始、间隔和停止

程序 SHALL 在启动的最后一步开始盘中巡检（bootstrap spec「启动顺序」），巡检在自己的线程里运行：

- 开始后立即做第一轮；每一轮做完以后等「巡检配置」的间隔，再做下一轮。间隔从上一轮做完算起：一轮做得久，下一轮就晚开始，两轮不会同时进行
- 全天运行：交易日和非交易日、盘中和盘外都照常做每一轮。盘外不会提交新订单：订单的截止时刻不晚于当天收盘，过了截止时刻只撤单、不提交（order-lifecycle spec「提交订单」「先查询再提交」）
- 一轮由一项一项的处理组成：跟进一笔订单、同步一个方案的预留、对齐一只股票（连同它的告警）各是一项，见「每一轮」

程序停止时 SHALL 最先停巡检（bootstrap spec「停止」）：

| 停止时巡检在 | 处理 |
| --- | --- |
| 等下一轮 | 立即结束，不再做下一轮 |
| 做某一项 | 这一项做完、结果保存以后结束，不再开始下一项 |

巡检结束以后，程序才关闭 DBOS 和其他部件。

本 spec 的场景除非另有说明，都使用下面的基准数据：

- order-lifecycle spec 的基准数据和 stop-protection spec 的约定：当前时刻 2026-10-14 15:00Z（周三，盘中；当天收盘 20:00Z），方案 P1 到 P4，"持有 BBB 100 股，止损单已对齐"，"券商回报……变为……"，"券商持仓变为……"。券商没有 AAA 的持仓，不用 order-lifecycle spec 基准数据里的 AAA 100 股
- 执行配置用默认值：买单和止损单错开关闭，状态未知的等待时长 30 秒，立即重试 1 次；巡检配置用默认值：间隔 15 秒
- 每个有订单的方案都已经通过风控，按订单的委托股数预留（P1 预留 100 股），还没有上报过成交
- P5：买入 CCC，板块"能源"，100 股，限价 20，止损价 18，已经通过风控，预留 100 股
- "做一轮"指巡检在当前时刻做一轮，一轮里的调用都在这一刻完成；"之后一轮"指 15 秒以后的下一轮
- "未结束的订单"指没有进入终态的订单（order-lifecycle spec「订单状态和券商回报」）

#### Scenario: 开始后立即做第一轮

- **GIVEN** P1 已经提交，订单已提交
- **WHEN** 巡检开始
- **THEN** 不等间隔，券商立即收到按 P1 的查询

#### Scenario: 每一轮做完以后等间隔

- **GIVEN** P1 已经提交，订单已提交；一轮从 15:00:00Z 开始，15:00:03Z 做完
- **WHEN** 巡检继续运行
- **THEN** 下一轮在 15:00:18Z 开始

#### Scenario: 收盘以后照样跟进

- **GIVEN** P1 部分成交，累计成交 30，截止时刻 2026-10-14 20:00Z；券商持仓 BBB 30 股，BBB-STOP-1 挂着 30 股，止损价 45
- **WHEN** 2026-10-14 20:00:10Z 做一轮
- **THEN** 券商收到 P1 的撤单请求
- **WHEN** 券商回报 P1 变为撤销、累计成交 30，2026-10-14 20:00:25Z 做一轮
- **THEN** P1 已过期，累计成交 30；P1 没有有效预留

#### Scenario: 周末照样对齐止损单

- **GIVEN** 当前时刻 2026-10-17 15:00Z（周六）；持有 BBB 100 股，止损单已对齐，没有未结束的订单
- **WHEN** 券商回报 BBB-STOP-1 变为撤销（长期有效单到期），做一轮
- **THEN** 券商收到止损单 BBB-STOP-2：卖出 100 股，止损价 45

#### Scenario: 等下一轮时停止

- **GIVEN** 巡检做完一轮，正在等下一轮
- **WHEN** 程序停止
- **THEN** 巡检立即结束，没有再调用券商

#### Scenario: 做某一项时停止

- **GIVEN** P1 和 P5 都已经提交，订单已提交；巡检正在跟进 P1，券商对按 P1 的查询还没有响应
- **WHEN** 程序停止
- **THEN** 券商的响应回来、P1 的订单保存以后巡检结束
- **AND** 没有跟进 P5，没有同步预留，也没有对齐止损单
- **AND** 巡检结束以后程序才关闭 DBOS

### Requirement: 每一轮

巡检的每一轮 SHALL 依次做下面三步，每一步按给出的顺序一项一项处理：

1. 跟进订单：每一笔未结束的订单，按创建的先后各跟进一次（order-lifecycle spec，包括到截止时刻撤单、有撤单要求时撤单、状态未知满等待时长后再查询，以及跟进之后对齐这只股票的止损单）
2. 同步预留：每一个有有效预留（risk-reservations spec）并且已经有订单的方案，把订单的累计成交股数上报给风控（risk-reservations spec「成交时缩小预留」）；订单已经是终态的，再释放这个方案的预留（「方案或订单结束时释放预留」）。还没有订单的方案（等确认、等开盘、等再校验）不动，由下单流程处理
3. 对齐止损单：下面这些股票按代码顺序各处理一次，每只处理以后按「无保护仓位的告警」处理：
   - 券商那边有持仓的：这一步开始时读一次券商的全部持仓
   - 当前止损单还没结束（还没挂出去、挂着或状态未知）的
   - 是无保护仓位的

   范围和 reconciliation spec「对账」第 4 步相同。这一轮第 1 步跟进过订单（跟进没有出错）的股票，跟进时已经对齐过，这一步 SHALL NOT 再对齐，只按它现在的止损保护写日志和告警；其余的股票单独对齐一次（stop-protection spec「对齐止损单」）。止损单被券商撤销或到期后挂新的止损单、挂单或改单被拒以后的重试、状态未知满等待时长后的查询，都由每一轮的对齐完成

   不在同一轮里对齐两次：改单只是请求，几毫秒以后再对齐时券商可能还在改单（Alpaca 改单时生成新订单替换旧单，替换完成以前不接受第二次改单），第二次改单会被拒，这只股票就会被误标为无保护仓位

第 2 步覆盖所有已经结束的订单，不论它在哪里结束：巡检的跟进、提交时被券商拒绝、紧急撤单、对账，或者停机期间结束、重启时由启动对账查到。上报成交和释放都可以重复，结果不变。

#### Scenario: 部分成交到全部成交

- **GIVEN** P1 已经提交，订单已提交
- **WHEN** 券商回报 P1 变为已受理、累计成交 30，券商持仓变为 30 股，做一轮
- **THEN** P1 部分成交，累计成交 30；P1 的预留剩余 70 股
- **AND** 券商收到止损单 BBB-STOP-1：卖出 30 股，止损价 45
- **WHEN** 券商回报 P1 变为全部成交、累计成交 100，券商持仓变为 100 股，之后一轮
- **THEN** P1 全部成交；P1 没有有效预留
- **AND** 券商收到一次 BBB-STOP-1 的改单：100 股，止损价 45；第 3 步没有再改

#### Scenario: 提交时被拒的订单也释放预留

- **GIVEN** 提交 P1 时券商拒绝受理，P1 已拒绝；P1 仍然预留 100 股
- **WHEN** 做一轮
- **THEN** 券商没有收到和 P1 有关的调用
- **AND** P1 没有有效预留

#### Scenario: 重启后补上停机期间的成交

- **GIVEN** P1 已经提交，订单已提交，P1 预留 100 股
- **AND** 停机期间券商回报 P1 变为全部成交、累计成交 100，券商持仓变为 BBB 100 股
- **WHEN** 程序重启：启动对账跟进 P1，P1 全部成交；然后巡检开始第一轮
- **THEN** P1 没有有效预留
- **AND** 券商没有再收到 P1 的提交

#### Scenario: 还没有订单的方案不动

- **GIVEN** P5 还在等确认，没有订单
- **WHEN** 做一轮
- **THEN** P5 仍然预留 100 股
- **AND** 券商没有收到和 CCC 有关的调用

#### Scenario: 跟进时券商超时

- **GIVEN** P1 已经提交，订单已提交
- **WHEN** 15:00:00Z 做一轮，按 P1 查询时超时
- **THEN** P1 状态未知；P1 仍然预留 100 股
- **WHEN** 15:00:15Z 做一轮
- **THEN** 券商没有收到按 P1 的查询
- **WHEN** 券商回报 P1 变为已受理、累计成交 30，券商持仓变为 30 股，15:00:30Z 做一轮
- **THEN** 券商收到按 P1 的查询；P1 部分成交，P1 的预留剩余 70 股

#### Scenario: 止损单被券商撤销后重挂

- **GIVEN** 持有 BBB 100 股，止损单已对齐，没有未结束的订单
- **WHEN** 券商回报 BBB-STOP-1 变为撤销，做一轮
- **THEN** 券商收到止损单 BBB-STOP-2：卖出 100 股，止损价 45

#### Scenario: 有持仓、还没有止损单的股票

- **GIVEN** P1 全部成交，跟进 P1 时查询持仓断线，BBB 没有止损单（stop-protection spec「查询持仓失败时不做处理」）；券商持仓 BBB 100 股
- **WHEN** 做一轮
- **THEN** 券商收到止损单 BBB-STOP-1：卖出 100 股，止损价 45

#### Scenario: 挂单被拒以后下一轮补挂

- **GIVEN** 持有 BBB 100 股，BBB 是无保护仓位，BBB-STOP-1 挂单被拒、已经结束，没有挂着的止损单
- **WHEN** 做一轮，券商正常受理
- **THEN** 券商收到止损单 BBB-STOP-2：卖出 100 股，止损价 45；BBB 不再是无保护仓位

#### Scenario: 没有持仓也没有订单

- **GIVEN** 没有未结束的订单，没有有效预留，券商没有持仓，没有止损单
- **WHEN** 做一轮
- **THEN** 券商只收到一次读取全部持仓的请求

### Requirement: 无保护仓位的告警

每一轮第 3 步处理一只股票以后，这只股票是无保护仓位（stop-protection spec「挂单或改单被拒」）时，巡检 SHALL 按下表处理：

| 情况 | 处理 |
| --- | --- |
| 巡检开始以后第一次看到这一段无保护（按无保护开始的时刻区分一段） | 推送一条告警（discord-notification spec「告警」） |
| 同一段无保护，已经告警过 | 不再告警 |
| 告警过的股票不再是无保护仓位：补挂成功，卖完，或者不再需要对齐 | 写一条 INFO 日志，不推送 |

告警文字 SHALL 写明：股票；无保护开始的时刻（UTC，到分钟）；原因是止损单挂单或改单被券商拒绝；巡检每一轮都会重试，补挂成功之前不能加仓。

- 无保护仓位不论在哪里产生（巡检的跟进或对齐、下单流程的提交、紧急撤单、对账），都由之后一轮的对齐发现并告警
- 这一轮跟进过订单的股票，按跟进时对齐的结果告警
- 告警过的记录只在巡检的内存里：程序重启以后，还在继续的一段无保护再告警一次
- 推送告警时不拿锁（见「执行模块和风控的调用串行」）；发不出去时按 discord-notification spec 只写错误日志，这一段无保护不再重发

#### Scenario: 第一次发现时告警

- **GIVEN** P1 已经提交，订单已提交；券商会一直拒绝挂单
- **WHEN** 券商回报 P1 变为已受理、累计成交 30，券商持仓变为 30 股，15:00Z 做一轮
- **THEN** 跟进 P1 时 BBB-STOP-1 挂单两次被拒，第 3 步没有再对齐 BBB；BBB 是无保护仓位，开始时刻 15:00Z
- **AND** 推送一条告警，写明 BBB、2026-10-14 15:00 UTC、止损单挂单或改单被券商拒绝、补挂成功之前不能加仓

#### Scenario: 同一段无保护不重复告警

- **GIVEN** 接着「第一次发现时告警」，券商仍然一直拒绝挂单
- **WHEN** 之后一轮
- **THEN** BBB 仍是无保护仓位，开始时刻仍是 15:00Z
- **AND** 没有新的告警

#### Scenario: 补挂成功只写日志

- **GIVEN** 接着「第一次发现时告警」
- **WHEN** 券商恢复正常受理，之后一轮
- **THEN** BBB 不再是无保护仓位
- **AND** 有一条 INFO 日志写明 BBB 不再是无保护仓位，没有推送

#### Scenario: 新的一段无保护再告警

- **GIVEN** BBB 从 15:00Z 开始的一段无保护已经告警过，15:05Z 补挂成功，BBB 持有 100 股，止损单已对齐
- **AND** P2 已经提交，订单已提交；券商会拒绝接下来两次改单
- **WHEN** 券商回报 P2 变为已受理、累计成交 20，券商持仓变为 120 股，15:10Z 做一轮
- **THEN** BBB 是无保护仓位，开始时刻 15:10Z
- **AND** 推送一条告警，写明 2026-10-14 15:10 UTC

#### Scenario: 别处产生的无保护仓位

- **GIVEN** 持有 BBB 100 股；别的调用方跟进 P2 时改单被拒，BBB 从 15:00:05Z 起是无保护仓位，P2 已经全部成交，券商持仓 150 股
- **AND** 券商会拒绝接下来两次改单
- **WHEN** 15:00:15Z 做一轮
- **THEN** 推送一条告警，写明 BBB 和 2026-10-14 15:00 UTC

#### Scenario: 跟进时被拒，下一轮跟进时补挂

- **GIVEN** P1 已经提交，订单已提交；券商会拒绝接下来两次挂单
- **WHEN** 券商回报 P1 变为已受理、累计成交 30，券商持仓变为 30 股，做一轮
- **THEN** 跟进 P1 时 BBB 变为无保护仓位，第 3 步没有再对齐 BBB；推送一条告警
- **WHEN** 之后一轮
- **THEN** 跟进 P1 时挂上 BBB-STOP-2，BBB 不再是无保护仓位；有一条 INFO 日志，没有新的告警

#### Scenario: 重启以后再告警一次

- **GIVEN** 持有 BBB 100 股，BBB 从 15:00Z 起是无保护仓位，没有挂着的止损单，重启之前已经告警过；券商会一直拒绝挂单
- **WHEN** 程序重启，巡检做第一轮
- **THEN** 推送一条告警，写明 BBB 和 2026-10-14 15:00 UTC
- **WHEN** 之后一轮
- **THEN** 没有新的告警

#### Scenario: 告警发不出去

- **GIVEN** 持有 BBB 100 股，BBB 从 15:00Z 起是无保护仓位，巡检还没有告警过；券商会一直拒绝挂单；Discord 报错
- **WHEN** 做一轮
- **THEN** 写一条错误日志，含告警文字和失败原因；巡检照常做完这一轮
- **WHEN** Discord 恢复，之后一轮 BBB 仍是同一段无保护
- **THEN** 没有推送告警

### Requirement: 订单和止损单变化的日志

巡检 SHALL 把看到的变化各写一条 INFO 日志，不推送 Discord：

| 变化 | 日志的内容 |
| --- | --- |
| 跟进一笔订单前后，状态或累计成交变了 | 股票、方案 ID、买卖方向、变化前后的状态、累计成交和委托股数 |
| 第 3 步处理一只股票以后，当前止损单和巡检上次看到的不同（换了一张，或者状态、股数、止损价变了）；巡检开始以后第一次看到的止损单也算 | 股票、止损单的客户端订单 ID、状态、股数、止损价 |

没有变化时 SHALL NOT 写日志。别的调用方（比如下单流程的提交）里发生的变化，巡检在之后一轮看到时才写。

#### Scenario: 订单成交写日志

- **GIVEN** P1 已经提交，订单已提交
- **WHEN** 券商回报 P1 变为已受理、累计成交 30，做一轮
- **THEN** 有一条 INFO 日志，写明 BBB、P1、买入、已提交变为部分成交、累计成交 30 / 100
- **AND** 没有推送 Discord

#### Scenario: 换了一张止损单写日志

- **GIVEN** 持有 BBB 100 股，止损单已对齐；巡检已经做过一轮
- **WHEN** 券商回报 BBB-STOP-1 变为撤销，做一轮，挂上 BBB-STOP-2
- **THEN** 有一条 INFO 日志，写明 BBB、BBB-STOP-2、挂着、100 股、止损价 45

#### Scenario: 没有变化不写日志

- **GIVEN** 持有 BBB 100 股，止损单已对齐；巡检已经做过一轮；P1 已经全部成交
- **WHEN** 做一轮，券商那边没有任何变化
- **THEN** 巡检没有写日志

### Requirement: 一轮里的失败

巡检 SHALL 不因为任何失败而停下，按下表处理：

| 失败 | 处理 |
| --- | --- |
| 跟进、对齐里券商超时或断线 | 按 order-lifecycle spec「券商调用失败时状态未知」和 stop-protection spec「止损单的券商调用失败」处理，这一项照常结束 |
| 第 3 步读券商的全部持仓超时或断线 | 写一条 WARNING；这一轮不做第 3 步，下一轮再来 |
| 某一项出了别的错：券商的认证错误、数据库出错、意外的异常 | 写一条 ERROR，带异常栈，写明是哪一项；跳过这一项，接着做下一项 |
| 列出未结束的订单或有效预留时出错 | 写一条 ERROR，带异常栈；跳过这一步，接着做下一步 |

不论这一轮怎样结束，巡检都照常等间隔再做下一轮。

#### Scenario: 读全部持仓失败时这一轮不对齐

- **GIVEN** 持有 BBB 100 股，止损单已对齐，没有未结束的订单；读取券商的全部持仓时会超时
- **WHEN** 券商回报 BBB-STOP-1 变为撤销，做一轮
- **THEN** 没有挂新的止损单；有一条 WARNING 写明读取持仓失败，这一轮没有对齐止损单
- **WHEN** 读取持仓恢复正常，之后一轮
- **THEN** 券商收到止损单 BBB-STOP-2：卖出 100 股，止损价 45

#### Scenario: 跟进一笔订单时出了意外的错

- **GIVEN** P1 和 P5 都已经提交，订单已提交；跟进 P1 时券商回答 401
- **WHEN** 做一轮
- **THEN** 有一条 ERROR 写明跟进 P1 出错，带异常栈
- **AND** P5 照常跟进，预留照常同步，止损单照常对齐
- **WHEN** 之后一轮
- **THEN** 又跟进了 P1

#### Scenario: 状态库出错

- **GIVEN** 读状态库时出错
- **WHEN** 做一轮
- **THEN** 写了 ERROR，带异常栈
- **AND** 巡检没有停下，15 秒以后照常做下一轮

### Requirement: 执行模块和风控的调用串行

程序 SHALL 有一把进程内的锁，全程序只有一把。下面这些调用 SHALL 拿着这把锁进行，同一时刻只有一个在进行，不论调用方是巡检、`/plan` 的提交、下单工作流还是紧急退出：

- 执行模块：提交订单、跟进订单、两种提前撤单、单独对齐止损单、对账
- 风控：检查方案、下单前再校验、上报成交、释放预留

另外：

- 只读的查询可以不拿锁：账户数据、本地备用止损是否该触发、未结束的订单、一个方案的订单、一只股票的止损保护、需要对齐止损单的股票、有效预留的方案
- 拿着锁的线程可以再次拿锁，不会卡住
- 巡检每一项拿一次锁，做完就放开，不整轮拿着；同步一个方案的预留时，读订单、上报成交和释放在同一次拿锁里完成
- 推送告警时 MUST NOT 拿着锁：一次推送最多要等 Discord 的发送超时（默认 10 秒）

#### Scenario: 别的调用拿着锁时巡检等待

- **GIVEN** P1 已经提交，订单已提交；另一个线程拿着锁（比如 `/plan` 正在检查一个方案）
- **WHEN** 巡检开始一轮
- **THEN** 那个线程放开锁之前，券商没有收到按 P1 的查询
- **WHEN** 那个线程放开锁
- **THEN** 巡检跟进 P1

#### Scenario: 推送告警时不拿锁

- **GIVEN** 巡检第一次发现 BBB 的无保护，推送告警时 Discord 一直没有响应
- **WHEN** 巡检还在等这次推送
- **THEN** 另一个线程可以立即拿到锁

#### Scenario: 拿着锁的线程再次拿锁

- **GIVEN** 一个线程拿着锁
- **WHEN** 这个线程再次拿锁
- **THEN** 立即拿到，不会卡住

### Requirement: 巡检配置

巡检的阈值 SHALL 可以配置：

| 配置项 | 默认值 | 要求 | 理由 |
| --- | --- | --- | --- |
| 间隔 | 15 秒 | 大于 0 | 每一轮的 Alpaca 请求不超过 1 + 2 ×（要对齐的股票数）+ 3 ×（未结束的订单数）次；8 只持仓、2 笔订单约 23 次，每分钟约 92 次，不到 Alpaca 每分钟 200 次的一半；止损单挂上、被撤销后重挂最多晚 15 秒 |

#### Scenario: 默认配置

- **WHEN** 不改巡检配置
- **THEN** 间隔是 15 秒

#### Scenario: 修改间隔

- **GIVEN** 间隔改为 30 秒；一轮在 15:00:00Z 开始，立即做完
- **WHEN** 巡检继续运行
- **THEN** 下一轮在 15:00:30Z 开始

#### Scenario: 间隔不大于 0

- **WHEN** 间隔设为 0 秒或 -1 秒
- **THEN** 配置报错
