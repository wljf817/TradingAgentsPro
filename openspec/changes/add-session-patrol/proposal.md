# Proposal

## Why

程序启动、对账一次以后就只等停止信号：`workflows/` 还是空的，没有任何东西在定期跟进订单、对齐止损单。订单要靠反复跟进才能走到终态，成交以后才挂止损单，到截止时刻才撤单；预留要按成交缩小、订单结束时释放；止损单被券商撤销或过期要重新挂上，挂单失败要重试，变成无保护仓位要告警。执行模块和风控的这些用例 M1 已经写好，现在缺一个调用它们的循环。后面的「下单流程」到 `execution.submit` 就结束，订单交给它跟进；「紧急退出流程」「收盘对账」「健康监控接线」也要在这个循环里加检查。执行模块和风控都写明「一次只能有一个调用在处理，由调用方保证」，现在只有启动对账一个调用方，有了巡检和下单流程以后就有多个线程同时调用。

本变更的目的只有一个：**加一个随程序运行的盘中巡检：每一轮跟进全部未结束的订单、按订单同步预留、对齐持仓的止损单，发现无保护仓位时告警；并用一把进程内的锁把执行模块和风控的调用串行化。**

引用的 Proposal（完整版）章节：

- 「订单生命周期」：
  - 开头一段：订单由执行模块独立跟踪到终态，与案件分开
  - 订单状态一段：每次状态变化写入状态库、交易记录和程序日志（程序日志 M4 才有，M2 写 Python 日志，已决定）
  - 表的「部分成交」（剩余部分到有效期后撤单，释放对应预留）、「止损单有效期」（被券商撤销或到期时重新挂上）、「止损单挂单失败」（仍失败则告警，标记无保护仓位，补挂成功前禁止加仓）、「断线或重启」（恢复后先对账，再恢复运行）
- 「风控引擎与执行」：
  - 额度预留一段：风控一次只处理一个方案；订单被拒、部分成交后撤销按未成交部分释放；进程重启后根据状态库和对账结果重建预留
  - 交易时段一段：开仓、加仓、减仓和清仓只在常规交易时段下单（巡检全天运行，但不会在盘外提交订单，见 design D2）
- 「技术栈与部署」：DBOS 一行（DBOS 用于案件工作流、队列和定时心跳；巡检不是案件，见 design D1）；可靠性要求（执行模块恢复后先与券商对账）

## What Changes

- 新增 `workflows/patrol.py`：巡检 `SessionPatrol` 和它的配置
  - 生命周期：DBOS 启动以后开始，立即做第一轮，之后每一轮做完等一个间隔（默认 15 秒）再做下一轮；全天运行，不分交易日和交易时段；停止时等正在进行的那一项做完，不再开始下一项
  - 每一轮依次：
    1. 跟进每一笔未结束的订单（`execution.track`），订单有变化时写一条日志
    2. 同步预留：每个有有效预留、已经有订单的方案，把订单的累计成交报给 `risk.record_fill`，订单到了终态再 `risk.release`。在别处结束的订单（提交时被拒、紧急撤单、对账、停机期间）也一样补上
    3. 对齐止损单（`execution.protect`）：券商有持仓的股票，加上当前止损单还没结束、或者是无保护仓位的股票。止损单被券商撤销或过期后重挂、挂单失败后的重试，都由每一轮的对齐完成；止损单有变化时写一条日志
    4. 对齐以后是无保护仓位的股票推送告警，同一段无保护期间只告警一次；解除时只写日志
  - 一轮里任何一项出错（券商、数据库、意外的异常）：写日志，跳过这一项，接着做下一项；下一轮再来，巡检线程不会因此停下
- 进程内的锁：bootstrap 建一把可重入锁，全程序共用。执行模块和风控里会改变状态的调用都拿着它进行，巡检一项一项地拿，不整轮拿着；推送告警时不拿锁。以后的 `/plan` 提交、下单工作流、紧急退出都用同一把锁
- 执行模块和风控各加几个只读的查询（不改变任何行为）：未结束的订单、一个方案的订单、需要对齐止损单的股票；有有效预留的方案
- bootstrap：启动顺序在 DBOS 之后加一步「开始盘中巡检」；停止时最先停巡检，再关 DBOS、Discord、OpenD、数据库；`TradingApp` 带上这把锁，给以后的流程变更用
- `workflows/` 的说明和 README 的目录说明改为「流程：DBOS 工作流和盘中巡检这样的进程内循环」

## Non-goals

- `/plan` 提交、DBOS 下单工作流、确认按钮的回调、风控用的账户数据拼装：「下单流程」
- 取行情、紧急风险退出的判断、本地备用止损：「紧急退出流程」。它把这些检查加进巡检的每一轮
- 收盘后的定时对账和对账不一致的告警：「收盘对账」
- 健康信号（券商连接等）和进入、退出降级模式的告警：「健康监控接线」
- 订单和止损单的状态变化发 Discord：Proposal 只要求写程序日志
- 为后面几个变更预留检查的扩展点：它们到时直接改巡检的代码
- 改变执行模块、风控的任何行为：只加只读的查询
- 程序日志：M4；现在写 Python 日志
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `session-patrol`：巡检的开始、间隔和停止；每一轮的步骤（跟进订单、同步预留、对齐止损单）；无保护仓位的告警和去重；订单和止损单变化的日志；一轮里的失败；执行模块和风控调用的锁；巡检配置

### Modified Capabilities

- `bootstrap`：「启动顺序」在 DBOS 之后加「盘中巡检」一步；「停止」的关闭顺序最前面加盘中巡检；「模拟盘的装配」加盘中巡检和锁两行

## Impact

- **代码**：
  - 新增 `src/tradingagentspro/workflows/patrol.py`（`PatrolConfig`、`SessionPatrol`）；`workflows/__init__.py` 只改说明
  - `modules/execution/service.py` 加只读的 `open_orders`、`order`、`symbols_to_protect`；`modules/risk/service.py` 加只读的 `active_plan_ids`。包根导出不变（都是已经导出的类的方法）
  - `bootstrap/app.py`：建锁和巡检，启动和停止巡检，`TradingApp` 加 `lock`
  - contracts、shared、integrations 不改
- **测试**：新增 `tests/workflows/test_patrol.py`、`tests/workflows/test_patrol_thread.py`；`tests/modules/execution/`、`tests/modules/risk/` 补只读查询的测试；`tests/bootstrap/test_app.py` 补启动顺序和停止顺序
- **依赖**：无
- **文档**：README 目录说明一行；`docs/实现路线.md` 的进度；人同意「需要人决定」以后改完整版 Proposal 一句话
- **券商请求**：每一轮大约 1 + 2 ×（要对齐的股票数）+ 3 ×（未结束的订单数）次 Alpaca 请求，8 只持仓、2 笔订单时约 23 次，按 15 秒的间隔每分钟约 92 次，不到 Alpaca 每分钟 200 次的一半（design D7）
- **对后续变更的影响**：
  - 「下单流程」：工作流到 `execution.submit` 就结束，之后的跟进、成交上报和释放预留都由巡检做；方案在下单以前结束（作废、人工拒绝、确认超时、再校验拒绝）时由工作流自己释放预留。风控的检查、再校验和执行模块的提交都要拿 `TradingApp.lock`；读账户数据（`held_sector`）不用拿
  - 「紧急退出流程」：取行情、紧急退出的判断和本地备用止损加进巡检的每一轮，撤单和清仓卖单拿同一把锁
  - 「收盘对账」：收盘后的对账拿同一把锁；对账结束的订单，预留由巡检的下一轮释放
  - 「健康监控接线」：券商连接的信号可以取巡检读持仓的结果，到时再定

## 需要人决定

1. **额度预留的释放情况少了「订单过期」**：「风控引擎与执行 · 额度预留」写的是「方案作废、人工拒绝或确认超时、订单被拒、部分成交后撤销剩余部分（按未成交部分释放）」，没有写订单过期，也没有写一股没成交就撤销的订单。当日单到截止时刻或收盘时没成交完会过期，这是最常见的结束方式之一；risk-reservations spec 已经按「订单结束（撤销、过期、被拒）释放没成交的部分」规定，本变更的巡检也是这样做的。
   推荐做法：把这一句改为「预留在以下情况释放或调整：方案作废、人工拒绝或确认超时（全部释放）；订单结束，包括撤销、过期和被拒（按未成交部分释放）」。只改 Proposal 的措辞，spec 和代码不变。
