# Spec Delta

## MODIFIED Requirements

### Requirement: 程序日志的条目

程序 SHALL 把每个动作写成程序日志的一条记录。程序日志存在状态库所在的数据库里（表 `programlog_entries`，state-store spec「表的归属和迁移」），只由程序日志模块写入：别的模块、流程和启动程序都经它写，不直接写表。每条记录有：

| 字段 | 内容 |
| --- | --- |
| 编号 | 按写入的先后递增 |
| 时间 | 写入时从时钟读取的时刻；存为带时区的时刻，读回的是同一时刻，和数据库服务器、本机的时区都无关 |
| 行为者 | 风控引擎、执行模块、人、系统、股票池、调度器、Agent 网关，各自的动作见下面以「<行为者>的动作」为名的要求；以后的变更加别的行为者和动作 |
| 动作 | 行为者的一个动作 |
| 对象 | 动作针对的东西的标识：方案 ID、止损单的客户端订单 ID、股票代码、跟进 ID、task_id；针对整个券商账户写 `account`，针对整个程序写 `system` |
| 案件 ID | 动作所属的案件；不属于案件时为空 |
| 输入的引用、输出的引用 | 动作用到的、产生的东西的标识，比如确认消息的标识、交易日、状态库条目 ID；各是一组文字，可以为空 |
| 说明 | 动作的内容和结果，中文；可以为空 |
| 耗时、token、费用 | 可以为空；费用是金额，原样保存每一位小数 |

行为者和动作各是一组固定的值。案件 ID、耗时、token 和费用只在动作的要求写明时才有，其余为空。

#### Scenario: 写一条

- **GIVEN** 进程的本机时区是 UTC+14；时钟是 2026-10-14T15:00:00.123Z
- **WHEN** 写一条：行为者是人，动作是确认，对象是方案 ID P1，输入的引用是确认消息的标识 M1，说明是"买入 BBB"
- **THEN** 程序日志多了一条，读回的时间是 2026-10-14T15:00:00.123Z，行为者、动作、对象、输入的引用和说明都是写入的值
- **AND** 输出的引用为空，案件 ID、耗时、token、费用为空

#### Scenario: 可以为空的字段原样读回

- **WHEN** 写一条带案件 ID、耗时 1.5 秒、token 1200、费用 0.0123 的条目
- **THEN** 读回的案件 ID、耗时、token 和费用都和写入的相同，费用仍是 0.0123

## ADDED Requirements

### Requirement: Agent 网关的动作

Agent 网关的下面这些动作 SHALL 各写一条，行为者是 Agent 网关，对象是 task_id，案件 ID 是任务所属的案件：

| 动作 | 什么时候写 | 引用 | 说明 | 耗时、费用 |
| --- | --- | --- | --- | --- |
| 派发任务 | 一个请求派发出去，生成 Task（task-dispatch spec「派发的顺序」） | 输入：Task 的输入 | 发起者、目标、任务类型、股票、问题、截止时间（UTC）；PM 派发出去的任务写第几轮 | 空 |
| 拒绝任务 | 一个请求被拒绝，生成 Task 和被拒绝的 Result | 输入：Task 的输入 | 被拒绝的原因；发起者、目标、任务类型、股票、问题 | 空 |
| 生成 Result | 派发出去的任务生成 Result：完成、无信号、超时、失败（task-dispatch spec「子 agent 的输出变成 Result」「超时」「调用失败」） | 输入：Result 引用的条目 | 状态；完成写评分、置信度和评估窗口，无信号写原因，失败写原因和说明；有模型的写模型和是不是备用模型 | Result 的耗时和费用 |

- 先写入 Task 或 Result，再写条目；一次派发里的条目按请求的顺序写
- 每个 Task SHALL 只有一条派发任务或拒绝任务，每个 Result SHALL 只有一条：被拒绝的 Result 写在拒绝任务里，不另写生成 Result；已经有 Result 的任务再收到输出、调用失败或者记超时，SHALL NOT 再写；同时生成的两个 Result，只有写入了的那个写（task-dispatch spec「一个任务只有一个 Result」）
- 复用（task-dispatch spec「相同的任务」）和格式错误的请求不生成 Task，SHALL NOT 写
- 这三种条目的 token 为空

本 requirement 的场景使用 task-dispatch spec 的基准数据；子 agent 的主模型是 google/s-1，备用模型是 openai/s-2（model-fallback spec 的基准模型的配置）。

#### Scenario: 派发任务

- **WHEN** PM 派发价格请求
- **THEN** 程序日志有一条派发任务：行为者 Agent 网关，对象 T-1，案件 K-1，输入的引用 E-1，说明写明 PM 派给 Quant、价格反应、BBB、问题"财报后的放量上涨能否持续？"、截止时间 2026-10-14 15:05:00 UTC、PM 的第 1 轮
- **AND** 耗时、token 和费用为空
- **WHEN** Critic 派发新闻请求
- **THEN** 派发任务的说明写明 Critic 派给 News，没有轮次

#### Scenario: 拒绝任务

- **WHEN** PM 派发价格请求、AAA 的新闻请求
- **THEN** 程序日志依次有 T-1 的派发任务和 T-2 的拒绝任务
- **AND** 拒绝任务的说明写明"股票不是案件的股票"、PM 派给 News、事件影响评估、AAA；没有 T-2 的生成 Result

#### Scenario: 完成的 Result

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:01:30Z 收到 s-1 给出的基准信号，费用 0.02
- **THEN** 程序日志有一条生成 Result：对象 T-1，案件 K-1，输入的引用 E-1 和 E-2，耗时 90 秒，费用 0.02，说明写明完成、评分 1、置信度 0.6、评估窗口 5、模型 google/s-1、不是备用模型

#### Scenario: 无信号、超时和失败的 Result

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:01:30Z 收到 s-1 给出的基准无信号
- **THEN** 生成 Result 的说明写明无信号和原因"最近一期财报还没有进状态库，无法判断"，没有输入的引用
- **WHEN** 2026-10-14 15:05:00Z 记超时，费用 0.01
- **THEN** 生成 Result 的说明写明超时，耗时 5 分钟，费用 0.01
- **WHEN** 2026-10-14 15:01:30Z 收到 s-2 给出的评估窗口 4 的信号
- **THEN** 生成 Result 的说明写明失败、格式不合法、"评估窗口不在配置的选项里"、模型 openai/s-2、是备用模型
- **WHEN** 2026-10-14 15:02:00Z 调用方给出调用失败，说明"模型都不可用：google/s-1 连接失败；openai/s-2 连接失败"
- **THEN** 生成 Result 的说明写明失败、调用失败和这段说明

#### Scenario: 已经有 Result 时不再写

- **GIVEN** PM 派发价格请求（T-1）；2026-10-14 15:01:30Z T-1 完成
- **WHEN** 2026-10-14 15:02:00Z 收到评估窗口 20 的信号；或者 15:05:00Z 记超时
- **THEN** 没有新的条目，T-1 只有一条生成 Result

#### Scenario: 同时生成的 Result 只写一条

- **GIVEN** PM 派发价格请求（T-1）
- **WHEN** 2026-10-14 15:05:00Z 收到基准信号，同时记超时；两个调用都在对方写入以前读到 T-1 还没有 Result，记超时的先写入
- **THEN** 程序日志只有一条 T-1 的生成 Result，说明写明超时

#### Scenario: 复用不写

- **GIVEN** PM 派发价格请求（T-1），T-1 完成
- **WHEN** PM 派发价格请求
- **THEN** 复用 T-1；程序日志没有新的条目
