# Proposal

## Why

Proposal 规定 agent 之间只通过 Agent 网关转发的 Task 和 Result 协作：只有 PM 和 Critic 能派任务，目标只能是三个子 agent；PM 每个案件的任务数和轮次有上限，Critic 的补充研究单独计额；超限的直接返回「被拒绝」，相同的任务复用已有的 Result，超时返回「超时」。M3 前面的变更已经备好了零件：signal-format 定了子 agent 的输出（信号或无信号）和收到输出时的校验，并把"格式不合法记成 Result 的哪种状态""Task 带上股票"留给本变更；case-types 的结论校验要调用方传入"本案件派过任务的子 agent"和"状态是完成的 Result 出自哪个子 agent"。但还没有 Task 和 Result 的格式，也没有东西决定一个任务放行还是拒绝、数一个案件用了几个任务和几轮。

本变更的目的只有一个：**规定 Task 和 Result 的格式，以及 Agent 网关放行或拒绝 PM、Critic 派发的任务的规则。**

引用的 Proposal（完整版）章节：

- 「Task / Result 通信」全节：字段表、网关强制执行的规则、PM 如何调用子 agent、任务清单、最低要求
- 「架构」的「决策层：PM 与子 agent」（网关检查白名单、任务数和轮次，校验输出格式，把 Result 作为工具结果交回 PM；PM 最多派 2 轮）、「审核层：Critic」（经 Agent 网关要求补充研究）
- 「股票池与寻股」的寻股流程：探索模式可以向 Quant 或 Fundamentals 派发任务
- 「调度器与运行模块」运行约束里"每个 agent 调用有超时和重试次数"一句：只用来区分调用的超时和任务的截止时间
- 「Agent」表的"由谁调用"一列：子 agent 由 PM 或 Critic 经 Agent 网关调用；「信号统一格式」里"子 agent 的 Result 记为「失败」并注明格式不合法，不切换模型"一句

## What Changes

- contracts 新增 `contracts/task.py`：任务类型（任务清单）、发起者、任务请求、Task、Result 和它的状态、被拒绝和失败的原因
- Agent 网关模块（`modules/gateway/`）加上任务派发：domain 的派发规则和 Result 的生成、任务的存储端口、用例。存储只定义端口，测试用 `tests/fakes/` 的内存实现
- 任务清单：任务类型预先定义，每种只属于一个子 agent，Task 的目标由类型确定

  | 子 agent | 任务类型 |
  | --- | --- |
  | News | 事件影响评估、某日期以来的新闻汇总 |
  | Quant | 价格反应、趋势和支撑阻力、波动情况 |
  | Fundamentals | 财报对比预期、指引变化、估值位置 |

- Task：task_id、案件 ID、发起者（PM 或 Critic）、目标 agent、任务类型、股票、问题（只补充具体关注点）、输入（状态库条目引用）、派发时刻、截止时间（派发时刻加任务时限）、PM 的第几轮。发起者写任务请求（任务类型、股票、问题、输入），其余由网关填写
- Result：task_id、状态（完成、无信号、超时、失败、被拒绝）、输出（完成时是信号，无信号时是无信号）、引用的条目 ID（取自输出）、耗时和费用；失败和被拒绝带原因。一个 Task 只有一个 Result
- 派发规则（网关按请求的顺序逐个处理）：本案件有相同的任务、还在运行或结果是完成或无信号的，直接复用；否则按顺序检查，第一项不通过就返回「被拒绝」及原因，都通过就派发：

  | 顺序 | 检查 | 不通过时的原因 |
  | --- | --- | --- |
  | 1 | 单只股票的案件：任务的股票是案件的股票 | 股票不是案件的股票 |
  | 2 | 寻股：目标是 Quant 或 Fundamentals | 寻股只能派给 Quant 和 Fundamentals |
  | 3 | PM：这一次不超过轮次上限（默认 2 轮） | 轮次已用完 |
  | 4 | PM：本案件派发出去的任务少于上限（默认 6 个） | 任务数已用完 |
  | 5 | Critic：本案件派发出去的任务少于补充研究额度（默认 2 个），不占 PM 的任务数和轮次 | 补充研究额度已用完 |

- 子 agent 的输出变成 Result：合法的信号是完成，合法的无信号是无信号；格式不合法（结构错误，或者 signal-format 的两项检查不通过）是失败并注明格式不合法，不重新调用、不切换模型；调用方给出调用失败时是失败并注明调用失败；晚于截止时间收到的、到截止时间仍没有输出的是超时
- 给其他模块数：本案件的任务和 Result、PM 用掉的轮次和任务数、Critic 用掉的额度；派过任务的子 agent 和状态是完成的 Result 出自哪个子 agent，交给 case-types 的结论校验
- 可配置项：PM 的任务数上限 6 个、PM 的轮次上限 2 轮、Critic 的补充研究额度 2 个、任务时限 5 分钟
- contracts 其他文件和其他模块的代码不改：子 agent 的身份 `SubAgent`、信号 `Signal`、无信号 `NoSignal`、案件类型 `CaseType` 都已经在 contracts；case-types spec 只改措辞：被拒绝的任务不算派过任务

## Non-goals

- 子 agent 输出的格式、PM 结论里信号的检查：signal-format spec 已经规定，本变更只把检查的结果记成 Result
- 「备用模型」：调用哪个模型，每次调用的超时和重试，切换和熔断，什么时候算调用失败；Result 记录实际使用的模型和是否为备用模型
- 「调用预算」：每日预算、费用怎么算、预算用完时拒绝任务（Proposal"并受并发和调用预算约束"的预算部分）。本变更的费用由调用方给出
- 并发：案件的并发上限由 case-queue 管；一次 dispatch_tasks 里的任务怎样并行调用子 agent 由 M5 定
- M4：
  - Task 和 Result 的表和 repo（只追加），写进程序日志
  - 注入共享上下文：子 agent 只看到任务内容和共享事实
  - 什么时候调用：派发、调用子 agent、收到输出或失败；用持久化休眠睡到截止时间记超时
  - 把派过任务的子 agent 和完成的 Result 交给结论校验；Critic 补充研究的结果在 PM 回应时一并交给 PM
- M5：
  - 真正调用模型；子 agent 的输出以 JSON 文本交给网关
  - PM 和 Critic 的 `dispatch_tasks` 工具：把工具参数解析成任务请求，格式错误退回模型；把 Result 作为工具结果交回；什么阶段给哪个 agent 这个工具（第 12 条）
  - 提示里写明任务清单、各类型的含义、剩下的任务数和轮次
- 输入和引用的条目是否存在、是否在本案件的快照里：M4 定了状态库条目 ID 以后再定

## Capabilities

### New Capabilities

- `task-dispatch`：任务清单；任务请求、Task、Result 的格式；派发的顺序；相同的任务和复用；案件的股票；寻股派给谁；PM 的轮次和任务数；Critic 的补充研究额度；子 agent 的输出变成 Result；超时；调用失败；一个任务只有一个 Result；本案件的任务和用量；派发的配置

### Modified Capabilities

- `case-types`：「事件要求的子 agent」写明派过任务指派发出去的任务，被 Agent 网关拒绝的不算（第 9 条）；结论校验的检查本身不变

  - 其他模块不改

- **依赖**：无
- **文档**：人同意「需要人决定」以后，完整版 Proposal「Task / Result 通信」补上已决定和新发现的条目，每处一两句话
- **对后续变更的影响**：
  - 备用模型：在调用子 agent 时切换模型，全部失败时调用本变更的"调用失败"；Result 加上实际使用的模型；格式不合法不切换；每次调用的超时要放进任务时限里
  - 调用预算：预算用完时拒绝任务，加一项拒绝原因；Result 的费用按它的算法给出
  - M4、M5：见 Non-goals 和 design D10

## 需要人决定

已决定（2026-10-08）：

1. **格式不合法的 Result 记成什么状态**：记为「失败」并注明格式不合法，不切换模型（signal-format 已给出格式不合法和原因）。落实：说明里写 signal-format 给出的原因（结构错误指出是哪一项）；这个 Result 就是任务最终的 Result，不重新调用子 agent

新发现的，已按推荐做法写进 spec，不同意可以改：

2. **什么算相同的任务**：Proposal 只写"同一案件内相同的任务去重"。推荐任务类型（也就定了目标）、股票、问题、输入（不论顺序）都相同才算，不论发起者是谁。问题不同说明关注点不同，复用别人的 Result 就答非所问；Critic 要的补充研究通常问法和 PM 不同，正好需要重新看。代价是复用主要挡住模型重复发出的同一个请求，省下的费用不多；控制费用主要靠任务数上限
3. **复用哪些 Result、算不算数**：推荐只复用还在运行、或者结果是完成或无信号的任务；超时、失败、被拒绝的不复用，再派时是新任务，照常检查和计数，这样发起者可以在下一轮重试。复用不新建 Task，不算任务数，也不算轮次，发起者拿到的是原来那个任务的 Result
4. **一轮怎么数**：推荐 PM 的一次 `dispatch_tasks` 算一轮，但其中至少有一个任务派发出去才算；全部被拒绝或者全部复用的一次不算。否则 PM 写错股票、在寻股里派给 News，就白白用掉一轮。Critic 不计轮次，只受补充研究额度限制
5. **一轮里部分任务超限**：推荐按请求的顺序逐个检查，没超限的照常派发，超出的返回「被拒绝」；被拒绝的任务不算任务数、不占轮次。整轮拒绝的话 PM 什么都拿不到，Proposal 也写的是"超限的任务"被拒绝
6. **截止时间由谁定**：推荐由网关定：派发时刻加任务时限，默认 5 分钟，所有任务类型相同；发起者不写，否则模型会随意填。截止时间以后收到的输出或调用失败也记为超时，PM 不会在超时以后又收到同一个任务的信号。超时的任务算任务数，也算派过任务（case-types 已写明超时也算）。任务时限是整个任务的上限，每次调用的超时和重试由「备用模型」在这个时限之内安排
7. **Task 的股票**：signal-format 第 9 条要求 Task 带股票。推荐任务请求都写股票；单只股票的案件必须是案件的股票，不是的返回「被拒绝」，不由网关悄悄改掉；寻股由 PM 指定，不检查是否在粗筛出的名单里
8. **目标 agent 由任务类型确定**：推荐任务请求只写任务类型，不写目标，Task 的目标从任务清单推出。每种类型只属于一个子 agent，同时写两项只会多出"类型和目标对不上"这种错误；"目标只能是三个子 agent"由任务清单保证，不在清单里的类型是请求的格式错误，由 M5 退回模型
9. **被拒绝的任务算不算派过任务**：case-types 的事件要求写"派过任务就算，不论 Result 的状态"，「被拒绝」也是一种状态。推荐只算派发出去的任务（完成、无信号、超时、失败），被拒绝的没有交给子 agent，不算；否则 PM 派一个必定被拒绝的任务就满足了事件要求。修改 case-types spec 的措辞，结论校验的代码不变
10. **Result 的 ID**：Proposal 的 Result 没有单独的 ID，PM 的结论要"引用的 Result ID"。推荐一个 Task 只有一个 Result，用它的 task_id 作为 Result 的 ID；先到的为准，之后再收到输出或超时都不改变
11. **「某日期以来的新闻汇总」的日期写在哪**：推荐写在问题里，不另加字段。只有这一种类型需要日期；问题本来就补充具体关注点
12. **PM 回应质询时能不能派任务**：Proposal 的流程里 PM 派任务在提交结论以前，回应质询时没有提。推荐网关不按案件阶段区分，PM 在整个案件里共用任务数和轮次；M5 只在唤醒 PM 阶段给 PM `dispatch_tasks`，回应时需要的新信息由 Critic 的补充研究提供（结果在 PM 回应时一并交给 PM）
13. **寻股的任务数和轮次**：Proposal 没有给寻股单独的上限。推荐和其他案件相同（6 个、2 轮）：探索模式只判断是否值得加入候选，粗筛的量化数据已经在上下文里，任务只用来查几只拿不准的；寻股另有单独的调用预算
