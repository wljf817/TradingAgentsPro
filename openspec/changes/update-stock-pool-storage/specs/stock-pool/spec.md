# Spec Delta

## MODIFIED Requirements

### Requirement: 股票池的记录

股票池 SHALL 为池子里的每只股票保存一条记录：

| 字段 | 说明 |
| --- | --- |
| 状态 | 候选、关注、持仓 |
| 来源 | PM 探索或手动添加 |
| 理由与论点草稿 | 加入时填写 |
| 板块 | 加入时由调用方从数据源传入；交易方案和持仓的板块都取这里 |
| 关注论点 | 只有关注有，格式见「关注论点的格式」 |
| 投资论点 | 只有持仓有，格式见 case-types spec「投资论点的格式」 |
| 上次复查的那一天 | 关注论点或投资论点的复查日最近一次新设的那个交易日（review-dates spec「上次复查的那一天」），由调用方给出；只有关注和持仓有 |
| 最新评分 | PM 最近一次对这只股票给出结论时的评分；还没有时为空 |
| 加入时刻 | 加入股票池的时刻 |
| 上次复查时间 | PM 最近一次对这只股票给出结论的时刻；还没有时为空。PM 的每次结论都更新它，和"上次复查的那一天"不同 |
| 过期时间 | 只有候选有，见「候选的过期时间」 |
| 成为候选的时刻 | 加入或代码触发的清仓转为候选的时刻；降为候选的候选没有，关注和持仓也没有。收盘心跳拿它和案件记录判断新候选（close-check spec「候选评估」：降为候选的不是新候选） |

股票池 SHALL 给出池子里的全部股票，以及按股票代码给出一只股票的记录。移出以后这只股票不在池子里；股票池仍然记下它移出的时刻和原因（删除、超期、清仓后移出），用来判断冷却期，重新加入时换成新的记录。

记录评分：PM 每次对池子里的一只股票给出结论后，调用方 SHALL 把结论里的评分记到这只股票上，最新评分改为它，上次复查时间改为当前时刻。评分 MUST 是 -2 到 +2 的整数，否则报错。不在池子里的股票不能记录评分，原因是"不在池子里"。

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中），交易日历是纽交所日历
- 股票池里有三只股票，2026-10-14 这个交易日还没有增删：
  - AAA：候选，2026-10-13 15:00Z 由 PM 探索加入，成为候选的时刻也是 2026-10-13 15:00Z，板块"科技"，过期时间 2026-10-27 20:00Z，没有评分
  - BBB：关注，板块"医疗"，关注论点是基准关注论点，上次复查的那一天 2026-10-07
  - CCC：持仓，板块"能源"，投资论点是基准投资论点，上次复查的那一天 2026-10-07
- 基准上市信息：纽交所上市的普通股，日均成交额 5,000 万美元，板块"科技"
- 基准关注论点：
  - 看好理由"新品周期带动收入加速"
  - 入场条件一条：价格不高于 50
  - 催化剂"Q3 财报"，截止日期 2026-10-29，不引用日程项或事件
  - 证伪条件"毛利率连续两个季度下滑"
  - 复查日 2026-10-21
- 基准投资论点：和 case-types spec 的基准投资论点相同：
  - 买入理由"新品周期带动收入加速"
  - 催化剂"Q3 财报"，截止日期 2026-10-29，不引用日程项或事件
  - 目标价 60
  - 证伪条件"毛利率连续两个季度下滑"，其中代码能检测的部分一条：价格不高于 42
  - 复查日 2026-10-21
- "加入 DDD"指来源是 PM 探索、理由"放量突破，论点草稿：订单回暖"、上市信息是基准上市信息；"删除"的理由都是"论点不再成立"
- 升级、PM 发起的清仓转为关注没有写明论点时，带基准关注论点；买入成交没有写明论点时，带基准投资论点；没有写明上次复查的那一天时，都是 2026-10-14

#### Scenario: 记录评分

- **GIVEN** 基准数据
- **WHEN** 记录 AAA 的评分 1
- **THEN** AAA 的最新评分是 1，上次复查时间 2026-10-14 15:00Z

- **THEN** AAA 的最新评分是 -1，上次复查时间 2026-10-14 16:00Z；CCC 的最新评分是 2

#### Scenario: 评分超出范围

- **GIVEN** 基准数据
- **WHEN** 记录 AAA 的评分 3 或 -3
- **THEN** 报错，AAA 仍然没有评分

#### Scenario: 不在池子里的股票不能记录评分

- **GIVEN** 基准数据
- **WHEN** 记录 ZZZ 的评分 1
- **THEN** 被拒绝，原因是"不在池子里"

#### Scenario: 移出后不在池子里

- **GIVEN** 基准数据
- **WHEN** 删除 AAA
- **THEN** 池子里的股票是 BBB 和 CCC，AAA 不在池子里

#### Scenario: 每种状态有的字段

- **GIVEN** 基准数据
- **WHEN** 读 AAA、BBB、CCC 的记录
- **THEN** AAA 的成为候选的时刻 2026-10-13 15:00Z，没有关注论点、投资论点和上次复查的那一天
- **AND** BBB 的关注论点是基准关注论点，上次复查的那一天 2026-10-07，没有投资论点和成为候选的时刻
- **AND** CCC 的投资论点是基准投资论点，上次复查的那一天 2026-10-07，没有关注论点和成为候选的时刻

#### Scenario: 记录评分不改变上次复查的那一天

- **GIVEN** 基准数据
- **WHEN** 记录 BBB 的评分 2
- **THEN** BBB 的最新评分是 2，上次复查时间 2026-10-14 15:00Z，上次复查的那一天仍是 2026-10-07

### Requirement: 状态变化

股票池 SHALL 只按下表改变股票的状态。表里没有的组合：PM 发起的升级、降为候选、保持 SHALL 被拒绝，不改变记录，股票不在池子里时原因是"不在池子里"，否则是"状态不允许"；代码发起的操作（买入成交、清仓）SHALL 报错。

| 当前状态 | 操作 | 之后 |
| --- | --- | --- |
| 不在池子里 | 加入（PM 探索或手动添加） | 候选，设过期时间，成为候选的时刻是加入时刻 |
| 候选 | 升级 | 关注，关注论点和上次复查的那一天是调用方给出的，没有过期时间和成为候选的时刻 |
| 候选 | 保持 | 候选，重设过期时间 |
| 候选 | 删除 | 移出，原因是删除 |
| 候选 | 过期时间已到，代码移出 | 移出，原因是超期 |
| 候选 | 买入成交 | 持仓，投资论点和上次复查的那一天是调用方给出的，没有过期时间和成为候选的时刻 |
| 关注 | 降为候选 | 候选，去掉关注论点和上次复查的那一天，设过期时间，没有成为候选的时刻 |
| 关注 | 删除 | 移出，原因是删除 |
| 关注 | 买入成交 | 持仓，去掉关注论点，投资论点和上次复查的那一天是调用方给出的 |
| 持仓 | 买入成交 | 持仓，不变：投资论点和上次复查的那一天都不变 |
| 持仓 | 删除 | 拒绝，原因是"持仓不能删除"（见「删除」） |
| 持仓 | 代码触发的清仓（止损单、紧急风险退出） | 候选，去掉投资论点和上次复查的那一天，设过期时间，成为候选的时刻是当前时刻 |
| 持仓 | PM 发起的清仓，PM 选择转为关注 | 关注，去掉投资论点，关注论点和上次复查的那一天是调用方给出的 |
| 持仓 | PM 发起的清仓，PM 选择移出 | 移出，原因是清仓后移出 |

- 买入成交指这只股票的开仓方案（买入）的买单有成交，部分成交也算。调用方在成交时调用，带上开仓方案附的投资论点和给出开仓方案结论的那个交易日：买入那一天不等成交（review-dates spec「上次复查的那一天」）。持仓的买入成交是同一笔开仓单后续的成交，或者加仓，记录不变：加仓附的论点更新在给出结论时经「论点更新」保存，加仓单成交不改变股票池
- 清仓指持仓的股数变为 0，减仓不改变状态
- 候选买入成交：关注股的买单挂着时被降为候选，随后成交
- 论点和上次复查的那一天都由调用方给出，日期是否合规由 review-dates spec 检查，股票池只保存
- 加入、删除的校验见「加入候选」「删除」；升级的关注名额见「池子容量和关注名额」；过期时间见「候选的过期时间」

#### Scenario: 加入成为候选

- **GIVEN** 基准数据
- **WHEN** 加入 DDD
- **THEN** DDD 在池子里：候选，来源 PM 探索，理由"放量突破，论点草稿：订单回暖"，板块"科技"，加入时刻和成为候选的时刻都是 2026-10-14 15:00Z，过期时间 2026-10-28 20:00Z
- **AND** DDD 没有关注论点、投资论点、上次复查的那一天、最新评分和上次复查时间

#### Scenario: 候选升级为关注

- **GIVEN** 基准数据
- **WHEN** 以基准关注论点升级 AAA，上次复查的那一天 2026-10-14
- **THEN** AAA 是关注，关注论点是基准关注论点，上次复查的那一天 2026-10-14，没有过期时间和成为候选的时刻

#### Scenario: 候选保持

- **GIVEN** 基准数据
- **WHEN** 保持 AAA
- **THEN** AAA 仍是候选，过期时间改为 2026-10-28 20:00Z，成为候选的时刻仍是 2026-10-13 15:00Z

#### Scenario: 删除候选或关注

- **GIVEN** 基准数据
- **WHEN** 删除 AAA，再删除 BBB
- **THEN** 两只都被移出，原因是删除，移出时刻 2026-10-14 15:00Z
- **AND** 池子里只剩 CCC

#### Scenario: 候选超期由代码移出

- **GIVEN** 基准数据
- **WHEN** 当前时刻 2026-10-27 20:00Z，代码移出到期的候选
- **THEN** AAA 被移出，原因是超期

#### Scenario: 关注降为候选

- **GIVEN** 基准数据
- **WHEN** BBB 降为候选
- **THEN** BBB 是候选，没有关注论点、上次复查的那一天和成为候选的时刻，过期时间 2026-10-28 20:00Z

#### Scenario: 关注股买入成交变为持仓

- **GIVEN** 基准数据
- **WHEN** BBB 买入成交，开仓方案附基准投资论点，开仓方案的结论是 2026-10-13 给出的
- **THEN** BBB 是持仓，投资论点是基准投资论点，上次复查的那一天 2026-10-13，没有关注论点，也没有过期时间

#### Scenario: 候选买入成交也变为持仓

- **GIVEN** 基准数据
- **WHEN** AAA 买入成交
- **THEN** AAA 是持仓，投资论点是基准投资论点，上次复查的那一天 2026-10-14，没有过期时间和成为候选的时刻

#### Scenario: 加仓成交不改变持仓

- **GIVEN** 基准数据
- **WHEN** CCC 买入成交，传入的投资论点的目标价改为 65
- **THEN** CCC 的记录不变：投资论点仍是基准投资论点，上次复查的那一天仍是 2026-10-07

#### Scenario: 代码触发的清仓转为候选

- **GIVEN** 基准数据
- **WHEN** CCC 的止损单成交，持仓变为 0，代码触发的清仓
- **THEN** CCC 是候选，过期时间 2026-10-28 20:00Z，成为候选的时刻 2026-10-14 15:00Z，没有投资论点和上次复查的那一天
- **AND** 板块、来源、理由和最新评分都不变

#### Scenario: PM 清仓后转为关注

- **GIVEN** 基准数据
- **WHEN** CCC 由 PM 发起的清仓完成，PM 选择转为关注，关注论点是基准关注论点
- **THEN** CCC 是关注，关注论点是基准关注论点，上次复查的那一天 2026-10-14，没有投资论点

#### Scenario: PM 清仓后移出

- **GIVEN** 基准数据
- **WHEN** CCC 由 PM 发起的清仓完成，PM 选择移出
- **THEN** CCC 被移出，原因是清仓后移出，不在池子里

#### Scenario: 状态不允许的操作

- **WHEN** 以基准关注论点升级 BBB 或 CCC；AAA 或 CCC 降为候选；保持 BBB 或 CCC
- **THEN** 都被拒绝，原因是"状态不允许"，三只股票的记录都不变

#### Scenario: 对不在池子里的股票升降级或保持

- **GIVEN** 基准数据，删除 AAA
- **WHEN** 以基准关注论点升级 AAA 或 ZZZ；ZZZ 降为候选；保持 AAA

#### Scenario: 代码发起的操作遇到不对的状态

- **WHEN** ZZZ 买入成交；AAA 或 BBB 代码触发的清仓；BBB 由 PM 发起的清仓完成，PM 选择转为关注或者移出
- **THEN** 都报错，记录都不变

## ADDED Requirements

### Requirement: 论点更新

PM 在关注股或持仓的案件里附了论点更新（case-types spec「关注的结论」「持仓的结论」），结论和论点里的日期都通过校验以后，调用方 SHALL 把新的论点和之后的上次复查的那一天（review-dates spec「上次复查的那一天」：续期是今天，平时调整不变）存进股票池：

| 论点 | 要求的状态 | 之后 |
| --- | --- | --- |
| 关注论点 | 关注 | 关注论点和上次复查的那一天换成给出的 |
| 投资论点 | 持仓 | 投资论点和上次复查的那一天换成给出的 |

- 新论点整份替换原来的；记录的其他字段都不变，包括最新评分和上次复查时间（PM 的评分另由「记录评分」记下）
- 股票不在池子里时 SHALL 被拒绝，原因是"不在池子里"；状态和表里要求的不同时 SHALL 被拒绝，原因是"状态不允许"。被拒绝时不改变记录
- 论点更新不计入每天的增删次数
- 日期是否合规由 review-dates spec 检查，股票池只保存

#### Scenario: 关注论点的平时调整

- **GIVEN** 基准数据
- **WHEN** 更新 BBB 的关注论点：基准关注论点的复查日改为 2026-10-23，上次复查的那一天 2026-10-07
- **THEN** BBB 的关注论点是新的这份，复查日 2026-10-23；上次复查的那一天仍是 2026-10-07
- **AND** BBB 仍是关注，最新评分和上次复查时间不变

#### Scenario: 投资论点的续期

- **GIVEN** 基准数据
- **WHEN** 更新 CCC 的投资论点：基准投资论点的复查日改为 2026-10-19、目标价改为 65，上次复查的那一天 2026-10-14
- **THEN** CCC 的投资论点是新的这份，复查日 2026-10-19，目标价 65；上次复查的那一天 2026-10-14
- **AND** CCC 仍是持仓

#### Scenario: 论点和状态不符

- **GIVEN** 基准数据
- **WHEN** 更新 AAA 或 CCC 的关注论点；更新 AAA 或 BBB 的投资论点
- **THEN** 都被拒绝，原因是"状态不允许"，记录都不变

#### Scenario: 不在池子里的股票不能更新论点

- **GIVEN** 基准数据，删除 BBB
- **WHEN** 更新 BBB 或 ZZZ 的关注论点；更新 ZZZ 的投资论点
- **THEN** 都被拒绝，原因是"不在池子里"

#### Scenario: 论点更新不计入增删次数

- **GIVEN** 基准数据，每天增删次数上限 1
- **WHEN** 更新 BBB 的关注论点，更新 CCC 的投资论点，再加入 DDD
- **THEN** 都通过，DDD 成为候选

### Requirement: 股票池的存储

股票池的记录 SHALL 存在状态库的股票池表 `stockpool_entries` 里，按股票代码只追加（state-store spec「只追加的版本记录」）：记录有变化时写入这只股票的一个新版本，读取时取每只股票的最新版本。移出的股票的记录也留在表里，用来判断冷却期和当天的增删次数。

- 读回的记录 SHALL 和保存的完全相同：关注论点和投资论点的每一项（包括目标价和条件的值的每一位小数、催化剂的引用）、上次复查的那一天、带时区的各个时刻、移出的原因和理由
- 列出池子里的股票、数当天的增删次数 SHALL 只看每只股票的最新版本
- 用同一个数据库新建股票池时（相当于进程重启），SHALL 读到同样的池子：池子里的股票和它们的记录、移出的股票的冷却期、当天已经通过的增删次数
- 读写出错时照 state-store spec「读写出错时报错」：操作报错，MUST NOT 当作池子是空的或者这只股票不在池子里，也 MUST NOT 当作已经保存

#### Scenario: 记录原样读回

- **GIVEN** 基准数据存在数据库里，CCC 的投资论点的目标价改为 60.125，证伪条件里的价格改为 42.5；BBB 的关注论点的催化剂引用事件 V-7
- **WHEN** 删除 AAA，再读 AAA、BBB、CCC 的记录
- **THEN** BBB、CCC 的记录和保存的相同：目标价仍是 60.125，价格仍是 42.5，催化剂仍引用事件 V-7，上次复查的那一天仍是 2026-10-07
- **AND** AAA 的记录写明移出：原因是删除，理由"论点不再成立"，移出时刻 2026-10-14 15:00Z；加入时刻仍是 2026-10-13 15:00Z

#### Scenario: 重启后读到同样的池子

- **GIVEN** 基准数据存在数据库里，每天增删次数上限 2；加入 DDD，删除 AAA
- **WHEN** 用同一个数据库新建股票池
- **THEN** 池子里的股票是 BBB、CCC、DDD，记录和重启前相同
- **WHEN** 加入 AAA
- **THEN** 被拒绝，原因是"冷却期内"
- **WHEN** 加入 EEE
- **THEN** 被拒绝，原因是"增删次数已用完"

#### Scenario: 同一只股票的几个版本只算一次

- **GIVEN** 基准数据存在数据库里，每天增删次数上限 2
- **WHEN** 加入 DDD，以基准关注论点升级 DDD，再记录 DDD 的评分 1；然后加入 EEE
- **THEN** DDD 有 3 个版本；EEE 成为候选
- **WHEN** 加入 FFF
- **THEN** 被拒绝，原因是"增删次数已用完"

#### Scenario: 数据库连不上

- **GIVEN** 数据库连不上
- **WHEN** 列出池子里的股票；读 AAA 的记录；加入 DDD
- **THEN** 三个操作都报错：列出和读取不返回空，加入不给出被拒绝的原因

### Requirement: 同时进行的操作

几个案件、收盘心跳和成交的处理可能同时调用股票池。改变记录的操作和被拒绝的请求 SHALL 一个接一个进行：一个操作从读取记录、检查到保存和写程序日志，中间没有别的操作改变记录。所以容量、关注名额和每天增删次数的检查 SHALL NOT 因为同时进行而多放进一只股票。读取池子里的股票和一只股票的记录不用等别的操作。

#### Scenario: 同时加入，池子只剩一个名额

- **GIVEN** 基准数据，池子容量 3
- **WHEN** 同时加入 DDD 和 EEE
- **THEN** 一只成为候选，另一只被拒绝，原因是"池子已满"；候选和关注合计 3 只

#### Scenario: 同时升级，关注名额只剩一个

- **GIVEN** 基准数据，关注名额 2；加入 DDD
- **WHEN** 同时以基准关注论点升级 AAA 和 DDD
- **THEN** 一只是关注，另一只被拒绝，原因是"关注名额已满"；关注合计 2 只

#### Scenario: 同时删除，增删次数只剩一次

- **GIVEN** 基准数据，每天增删次数上限 1
- **WHEN** 同时删除 AAA 和 BBB
- **THEN** 一只被移出，另一只被拒绝，原因是"增删次数已用完"
