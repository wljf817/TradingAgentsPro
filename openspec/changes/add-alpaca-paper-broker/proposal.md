# Proposal

## Why

M1 的执行模块只通过两个端口和券商打交道：`Broker`（普通订单、持仓、账户）和 `StopBroker`（止损单），现在只有测试用的内存替身。M2 要让手工录入的方案在 Alpaca 模拟盘上走完下单、止损和对账，先得有这两个端口的 Alpaca 实现。

Alpaca 和端口约定之间有几处差别要在适配器里抹平：

- 改单会生成一笔新订单，旧单记为已替换；端口要求跟着替换找到现在的那一笔，累计成交还要包括替换之前的
- 订单状态有十几种，端口只认 5 种券商回报
- 模拟盘不收费，交易记录的费用要按配置估算（`add-trade-records` 的 design D5）
- Alpaca 只有保证金账户，要设成不做空、最大保证金倍数 1，按现金账户用（完整版「交易记录」最后一段）

本变更的目的只有一个：**用 Alpaca Trading API 实现执行模块的券商端口 `Broker` 和 `StopBroker`，并能把模拟盘账户设成按现金账户使用。**

引用的 Proposal（完整版）章节：

- 「技术栈与部署」的券商一行：模拟盘用 Alpaca Trading API，和实盘实现同一套券商接口，只在启动时切换；可靠性要求里 API key 存环境变量
- 「订单生命周期」：防止重复提交（客户端订单 ID，超时后先按它查询）、止损单有效期（GTC，被券商撤销或到期时重新挂上）、部分成交、加仓、主动减仓或清仓（先改止损单，券商确认后再下卖单）
- 「记录、复盘与经验」的「交易记录」最后一段：模拟盘（Alpaca）设为最大保证金倍数 1、不做空，按现金账户使用

## What Changes

- 新增 `integrations/alpaca/`，通过 Alpaca 的 REST 接口实现两个端口：
  - `AlpacaBroker`（`Broker`）：按客户端订单 ID 查询、提交当日有效单、撤单、查询一只股票的持仓、全部挂单（不含止损单）、全部持仓、账户
  - `AlpacaStopBroker`（`StopBroker`）：查询止损单（跟着替换找到现在的那一笔，累计成交包括替换之前的）、挂长期有效的止损单、改单、撤单、全部挂着的止损单（替换进行中的新旧两笔只算一张）
- Alpaca 的订单状态映射到端口的 5 种券商回报
- 费用按配置估算：一笔订单（止损单连同它的替换算一笔）有成交时记一笔佣金，佣金和风控的每笔佣金是同一个配置值
- 调用失败分类：超时、连不上、限频、服务端错误算券商不可用；提交、挂单、改单被拒算拒绝受理；查询查不到、撤单撤不了按端口约定正常返回
- 账户设置：把模拟盘账户设为不做空、最大保证金倍数 1，启动时调用
- 新增依赖 httpx

## Non-goals

- 装配：从环境变量读 API key、按模拟盘或实盘选择适配器、启动时调用账户设置，在「启动与装配」里做
- 跟进和对齐的频率、和限频的配合：「下单流程」「收盘对账」
- 券商连接作为健康监控的信号：「健康监控接线」
- 行情：不用 Alpaca 的行情接口，行情来自「moomoo 行情」
- 交易更新的 WebSocket 推送：用查询代替，端口本来就是先查询再处理
- 绕开 Alpaca 的防自成交保护：见「需要人决定」第 1 条
- moomoo 实盘适配器：M7
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `alpaca-broker`：Alpaca 适配器怎样实现执行模块的券商端口：状态映射、普通订单和止损单的各个操作、改单产生的替换、费用估算、调用失败的分类、账户设置和配置

### Modified Capabilities

无。执行模块的行为不变，端口的约定也不变。

## Impact

- **代码**：新增 `src/tradingagentspro/integrations/alpaca/`（`__init__.py`、`client.py`、`broker.py`、`stops.py`）
- **测试**：新增 `tests/integrations/alpaca/`：用 httpx 自带的 MockTransport 模拟 Alpaca，接口回报的样例取自 Alpaca 文档；另有一组连真实模拟盘的冒烟测试，默认不运行，CI 也不运行
- **依赖**：新增 httpx
- **对后续变更的影响**：
  - 「启动与装配」：从环境变量 `APCA_API_KEY_ID`、`APCA_API_SECRET_KEY` 读 key，建 Alpaca 客户端；启动时先调用账户设置，再对账；两个适配器的每笔佣金传风控配置里的值
  - 「部署」：环境变量模板加上两个 key；清空状态库时同时重置模拟盘账户，否则止损单的客户端订单 ID（`AAPL-STOP-1` 这样按序号生成）会和券商那边的旧订单重复，挂单被拒
  - 「下单流程」「收盘对账」：Alpaca 限频每分钟 200 次；对齐一只股票的止损单，每次改单多出的替换要多查一次
  - 「健康监控接线」：适配器抛出的 `BrokerUnavailableError` 可以作为券商连接的信号
  - 方案价格的最小变动单位：1 美元以上的价格只能到分，否则提交和挂单都被券商拒绝；止损价不合规时止损单永远挂不上。真正下单之前，在方案格式校验里加上这条，在拆「手工录入方案」时决定放在哪里
  - M7：moomoo 适配器实现同样的两个端口

## 需要人决定

1. **Alpaca 的防自成交保护和「订单生命周期」的加仓、部分成交两行冲突**

   Alpaca 会拒绝可能和自己反方向挂单成交的新订单，模拟盘也一样：
   - 同一只股票挂着止损卖单时，新的买单一律被拒
   - 挂着限价买单时，新的止损卖单一律被拒

   这和完整版「订单生命周期」的两行冲突：
   - 加仓：持仓一直挂着止损单，所以加仓的限价买单在 Alpaca 一定被拒
   - 部分成交：开仓买单部分成交、还没结束时，按已成交数量挂的止损单被拒

   推荐：模拟盘不绕开这条限制，执行模块也不改：
   - 加仓买单被拒，订单记为已拒绝、释放预留，和其他被拒的订单一样处理。模拟盘测不了加仓
   - 部分成交时止损单挂不上，按「止损单挂单失败」处理：告警、标记无保护仓位、由本地备用止损接管；买单结束以后，下一次对齐就能挂上止损单，恢复保护。这条路径在模拟盘上反而能经常测到（Alpaca 模拟盘约 10% 的订单会随机部分成交）
   - 绕开的办法都不划算：加仓前先撤止损单，实盘也会在买单挂着的这段时间没有券商止损单；把止损单改成 Alpaca 豁免的组合单（OCO），这种用法没有文档保证，还要改掉"一只股票一张止损单"的做法

   人同意的话：
   - 完整版「技术栈与部署」券商一行末尾加一句："模拟盘的 Alpaca 会拒绝可能和自己反方向挂单成交的订单：持仓挂着止损单时加仓被拒；开仓买单部分成交、还没结束时止损单挂不上，按「止损单挂单失败」处理。"
   - `docs/实现路线.md` M7 的完成标志"验证模拟盘测不了的部分"加上"加仓、部分成交时挂止损单"；moomoo 实盘有没有类似限制，到时一起核实
