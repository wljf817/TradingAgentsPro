# Proposal

## Why

从方案通过风控到成交，中间要经过人工确认、等开盘、订单挂单，可能持续几分钟到一个交易日。这段时间里账户数据还没有变化，所以后面的方案会看到完整的额度。几个方案各自都能通过，合在一起却会超限。资金不足时券商还会拒单，但组合合计风险、板块集中度、最多持仓数这几项只能靠风控自己守住。

变更 2 已经让规则把"其他方案的预留"作为输入计入额度，但还没有地方产生和维护这些预留。本变更的目的只有一个：**方案通过风控时立即占住额度，后续方案按剩余额度检查；成交时缩小预留，方案或订单结束时释放。**

引用的 Proposal（完整版）章节：

- 「风控引擎与执行」的"额度预留"：一次只处理一个方案；通过后立即预留资金、持仓名额、板块额度和风险额度；释放和调整的情况；重启后恢复预留
- 「调度器与运行模块」的排队规则：风控引擎一次只处理一个方案
- 「订单生命周期」的"部分成交"：剩余部分到有效期后撤单，释放对应预留

## What Changes

- **BREAKING** 交易方案 `TradePlan` 新增必填的方案 ID（UUID）。成交、释放和后续的确认、下单都靠它找到方案
- 风控模块增加预留的存储和用例。预留只在风控模块内部使用，不进 contracts：
  - domain：预留记录（方案、风控结果、累计成交、是否已释放），以及按剩余股数和当前持仓计算预留占用的额度
  - ports：预留的存储接口
  - service：三个操作
    - 检查：读出有效预留，调用变更 2 的判定；通过或调整时，按最终股数保存预留
    - 上报成交：传入累计成交股数，预留随之缩小
    - 释放：方案或订单结束时调用
- 同一个方案 ID 再次检查时，返回第一次的结果，不重复预留
- 测试替身：`tests/fakes/` 增加预留存储的内存实现
- 变更 2 的规则、判定和阈值都不改

## Non-goals

- 下单前再校验：变更 4。包括再校验时扣除方案自己的预留、调整后缩小预留、作废后释放
- 谁在什么时候调用"上报成交"和"释放"：由产生这些事件的变更接入。本变更只提供这两个操作，调用方见 design D7
- 预留的数据库实现（`repo.py`），以及"一次只处理一个方案"的具体做法和并发测试：M2 接 PostgreSQL 和 DBOS 时实现
- 停机期间漏掉的成交和订单结束怎么补：变更 7 对账。本变更只保证预留保存在存储里，重启后继续计入
- 风控结果、预留和释放写入程序日志和状态库的记录：程序日志在 M4，状态库方案在 M2 确定
- 方案 ID 怎么生成：由创建方案的一方负责（M2 是人工录入，以后是组装方案的 workflow），通过 ID 生成端口获取
- 紧急风险退出前释放同一股票的退出方案：变更 8，见「需要人决定」

## 需要人决定

已决定（2026-10-03，人同意推荐做法）：

1. **成交不在释放清单里**（变更 2「需要人决定」第 8 条）：Proposal 列了释放的情况，没有写成交后怎么办。决定：成交多少就把预留缩小多少，这部分转为持仓；全部成交时预留结束
   - 如果不缩小，已成交的部分会和持仓重复计算。开仓这一侧只是额度偏紧
   - 卖出这一侧会阻塞退出：持有 100 股，减仓 60 股、已成交 30 股时，可卖数量会算成 70 − 60 = 10，实际是 40。这和"保证退出不被阻塞"矛盾
2. **一股都没成交就到期的订单不在清单里**：清单只有"订单被拒"和"部分成交后撤销剩余部分"。模拟盘只支持当日有效单，没成交的限价单每天收盘都会过期，这是常见情况。决定：释放统一成两类
   - 方案在下单前结束（作废、人工拒绝、确认超时）：全部释放
   - 订单结束（撤销、过期、被拒）：释放没成交的部分
3. **"进程重启后重建预留"**：照字面要另写一套从头推算预留的逻辑。决定：预留保存在存储里，重启后直接读出继续计入；停机期间的成交和订单结束由对账调用"上报成交"和"释放"补上，不另写重建逻辑

留给后续变更（到时候再定）：

4. （变更 8）退出方案在等人工确认时，它的卖出预留会占住股数；同一股票这时触发紧急风险退出，可卖数量可能是 0，退出被阻塞。倾向：紧急退出检查前，先作废这只股票还没下单的退出方案并释放预留；已经在挂单的卖单，由执行模块先撤单再释放
5. （变更 4）变更 2「需要人决定」的第 6、7 条仍然待定：价格偏离只让开仓类方案作废；再校验结果为拒绝时作废，为调整时按更小的股数下单
