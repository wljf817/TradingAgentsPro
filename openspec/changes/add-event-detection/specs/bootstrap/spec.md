# Spec Delta

## MODIFIED Requirements

### Requirement: 启动顺序

`tradingagentspro run` SHALL 按下表的顺序启动，前一步完成才做下一步，全部完成后写「启动完成」，然后一直运行到收到停止信号：

| 步骤 | 做什么 | 失败时 |
| --- | --- | --- |
| 1 读环境变量 | 见「环境变量」 | 启动失败 |
| 2 数据库 | 连接状态库，升级到最新的迁移版本（state-store spec「表的归属和迁移」） | 启动失败 |
| 3 交易日历 | 按「交易日历的加载范围」加载纽交所日历 | 启动失败 |
| 4 装配 | 按「模拟盘的装配」建出全部部件，开始连接 OpenD（不等连上） | 启动失败 |
| 5 Alpaca 账户设置 | 不做空、最大保证金倍数 1（alpaca-broker spec「账户设置」） | 启动失败 |
| 6 启动对账 | 见「启动对账」 | 读取失败时启动失败；有不一致时照常继续 |
| 7 第一次健康判定 | 见「第一次健康判定」 | 不会失败；OpenD 连不上、处于降级模式都照常继续 |
| 8 Discord | 登录、注册 `/plan`、连接、核对频道（discord-notification spec、manual-plans spec） | 启动失败 |
| 9 DBOS | 见「DBOS」 | 启动失败 |
| 10 排队运行 | 开始排队运行（queue-runner spec「什么时候做一轮」）；先让开始运行了、还没出队的案件出队（queue-runner spec「重启以后」），第一轮在排队运行自己的线程里进行，启动不等它做完 | 启动失败 |
| 11 事件检测 | 开始事件检测（event-detection spec「什么时候做一轮」）；第一轮在事件检测自己的线程里进行，启动不等它做完 | 启动失败 |
| 12 盘中巡检 | 开始盘中巡检（session-patrol spec「巡检的开始、间隔和停止」）；第一轮在巡检自己的线程里进行，启动不等它做完 | 启动失败 |

- 对账和健康判定 SHALL 在 Discord 和 DBOS 之前完成：`/plan`、按钮、DBOS 恢复的工作流和排队运行启动的案件是新订单仅有的入口
- Alpaca 账户设置 SHALL 在对账之前：对账可能补挂止损单，补挂之前账户要已经是不做空的
- Discord SHALL 在 DBOS 之前：DBOS 恢复的工作流可能马上要请求确认
- 排队运行 SHALL 在 DBOS 之后开始：它启动的是案件工作流；在盘中巡检之前开始：巡检的健康判定读它的调度器心跳
- 事件检测 SHALL 在排队运行之后开始：它往队列里排案件
- 盘中巡检 SHALL 最后开始：它要调用券商、风控和 Discord，这些都要已经就绪，启动对账也要已经做完；停止时它最先停（见「停止」）

#### Scenario: 正常启动的顺序

- **WHEN** 正常启动
- **THEN** 日志依次写出：程序启动、数据库已升级、交易日历的范围、Alpaca 账户设置完成、启动对账没有不一致、健康正常、Discord 已连接、DBOS 已启动、排队运行已开始（写明间隔）、事件检测已开始（写明间隔）、盘中巡检已开始（写明间隔）、启动完成
- **AND** Alpaca 先收到账户设置，再收到读取挂单和持仓的请求

#### Scenario: 空数据库启动不改动券商

- **GIVEN** Alpaca 模拟盘有一笔不认得的挂单和一只不认得的持仓
- **WHEN** 正常启动
- **THEN** Alpaca 收到的写请求只有账户设置一个，其余都是读取
- **AND** 启动完成

#### Scenario: 启动以后巡检跟进停机前提交的订单

- **GIVEN** 状态库里有一笔已提交的买单 P1（买入 BBB 100 股，止损价 45），风控为它预留了 100 股；停机期间 Alpaca 那边 P1 全部成交，持仓 BBB 100 股
- **WHEN** 正常启动
- **THEN** 启动对账跟进 P1，P1 全部成交，挂上 BBB 的止损单
- **AND** 巡检的第一轮把 P1 的累计成交报给风控，P1 没有有效预留


### Requirement: 模拟盘的装配

`tradingagentspro run` SHALL 按模拟盘装配，各部件如下。全部模块共用同一个系统时钟和同一份交易日历；阈值都取各自配置的默认值，不读配置文件。

| 部件 | 装配 |
| --- | --- |
| 券商 | Alpaca 模拟盘：普通订单和止损单两个适配器共用一个客户端，key 来自环境变量；估算费用用的每笔佣金 SHALL 等于风控配置的每笔佣金（默认 2） |
| 执行模块 | 订单、止损保护、交易记录存在状态库；执行配置的「买单和止损单错开」SHALL 打开（Alpaca 不允许同一只股票的买单和止损卖单同时挂着），其余用默认值 |
| 风控 | 预留存在状态库；风控配置用默认值 |
| 股票池、跟进、案件记录 | 记录都存在状态库；股票池配置和跟进配置用默认值 |
| Agent 网关 | 任务、Result 和费用记录存在状态库；模型配置是替身的模型（stand-ins spec「替身的模型」），调用 agent 的是替身（stand-ins spec），替身配置用默认值；网关配置用默认值（普通预算 2.00、持仓保留预算 1.00、寻股预算 0.50） |
| 新闻和公告、公司数据、寻股粗筛 | 新闻源是 Alpaca 新闻、公告源是 SEC EDGAR、公司数据源是 Finnhub，寻股的日线来自 Alpaca、股票列表来自 moomoo（和行情共用一个 OpenD 行情连接）；Alpaca 的 key 和模拟盘的是同一组；记录都存在状态库；各自的配置用默认值，粗筛和股票池用同一份股票池配置 |
| 快照 | 存在状态库；读下面装配好的事件；快照配置用默认值 |
| 紧急退出、健康监控 | 各自配置的默认值 |
| 行情 | 行情源是 OpenD（默认 127.0.0.1:11111）；行情配置用默认值（参考股票 SPY） |
| 通知 | 通知通道是 Discord 机器人，配置来自环境变量；通知配置用默认值（确认超时 30 分钟，模型退出自动执行和紧急退出要确认都关闭） |
| `/plan` | 方案 ID 用随机 UUID；提交接口是下单流程的（order-flow spec「提交方案」） |
| 确认按钮的回调 | 紧急退出流程在等这个方案的确认时送给紧急退出流程（emergency-exit-flow spec「紧急退出的人工确认」），否则送给下单流程（order-flow spec「按钮的结果只送给在等确认的方案」） |
| 锁 | 全程序一把进程内的锁（session-patrol spec「执行模块和风控的调用串行」）；巡检（包括其中的紧急退出）和下单流程用的是同一把 |
| 盘中巡检 | 调用上面装配好的执行模块、风控和通知，用这把锁；巡检配置用默认值（间隔 15 秒）。每一轮里的紧急退出（emergency-exit-flow spec）另外调用上面装配好的紧急退出、健康监控和行情，用同一份通知配置；每一轮里的股票池跟上持仓（pool-position-sync spec）另外调用上面装配好的股票池、跟进和案件记录 |
| 下单流程 | 调用上面装配好的执行模块、风控、紧急退出、健康监控、行情、通知和案件记录，用这把锁和同一份通知配置（案件的方案的确认规则，order-flow spec「案件的方案」）；下单流程配置用默认值（重试间隔 30 秒） |
| 案件工作流 | 调用上面装配好的网关、案件记录、快照、股票池、跟进、事件、通知和程序日志；交给下单的是下单流程（order-flow spec「案件的方案」）；调度器配置、心跳配置和案件工作流配置用默认值，案件工作流和排队运行用同一份调度器配置 |
| 排队运行 | 排队的案件存在状态库；读上面装配好的股票池、紧急退出流程、健康监控和网关的预算，启动案件工作流，作废交给下单流程；排队运行的配置用默认值（间隔 5 秒） |
| 健康监控接线 | PM 和 Critic 还有没有可用的模型取网关的备用模型，持仓保留预算取网关的预算，调度器心跳取排队运行（health-monitoring spec「健康信号」） |
| 事件 | 事件存在状态库；事件规则的配置用默认值 |
| 事件检测 | 读上面装配好的股票池、执行模块（账户数据和已经结束的卖出）、行情、新闻和公告、公司数据和事件，排进排队运行，写程序日志；不用那把锁；事件检测的配置用默认值（间隔 60 秒） |

#### Scenario: 打开买单和止损单错开

- **WHEN** 按模拟盘装配券商
- **THEN** 执行模块的「买单和止损单错开」是打开的

#### Scenario: 估算费用用风控的每笔佣金

- **GIVEN** 风控配置的每笔佣金是默认值 2；Alpaca 那边有一笔全部成交的买单和一张全部成交的止损单
- **WHEN** 按模拟盘装配的两个券商适配器查询这两笔
- **THEN** 两笔回报的费用都是 2

#### Scenario: 巡检和以后的流程共用一把锁

- **WHEN** 正常启动
- **THEN** 巡检的间隔是 15 秒
- **AND** 启动给以后的流程用的锁，就是巡检用的那一把：另一个线程拿着它时，巡检不调用执行模块和风控

#### Scenario: 录入并确认一个买入方案

- **GIVEN** 正常启动；Alpaca 模拟盘账户的权益和现金都是 10,000，前一交易日收盘时的权益 10,000；OpenD 有 BBB 的行情，最新价 50
- **WHEN** 本人运行 `/plan buy symbol:BBB sector:医疗 quantity:20 limit:50 stop:45`
- **THEN** 回复风控通过：买入 BBB 20 股；频道里出现这个方案的确认消息
- **WHEN** 本人按确认消息的「确认」
- **THEN** 消息显示已确认
- **AND** Alpaca 收到一笔买单：客户端订单 ID 是这个方案的 ID，BBB 20 股，限价 50

#### Scenario: 盘中紧急清仓

- **GIVEN** 当前时刻在常规交易时段内；Alpaca 模拟盘账户的权益和前一交易日收盘时的权益都是 10,000，持有 AAA 50 股；状态库里有 AAA 全部成交的开仓订单（板块"科技"，止损价 90，紧急阈值 0.08），AAA-STOP-1 挂着 50 股；OpenD 的 AAA 前一交易日收盘价 100、最新价 92
- **WHEN** 正常启动，巡检做第一轮
- **THEN** Alpaca 收到 AAA-STOP-1 的撤单请求；Discord 收到一条告警，写明 AAA 开始紧急退出
- **WHEN** Alpaca 回报 AAA-STOP-1 已撤销，巡检做下一轮
- **THEN** Alpaca 收到一笔市价卖单：AAA 50 股，客户端订单 ID 是 AAA 当天的代码触发的清仓方案的 ID

#### Scenario: 按钮的结果按方案送给紧急退出流程或下单流程

- **GIVEN** 正常启动；紧急退出流程在等 AAA 当天的清仓方案的确认；方案 P1 的下单流程在等确认
- **WHEN** 本人按 AAA 的紧急退出的确认消息的「确认」
- **THEN** 紧急退出流程收下这次确认，下单流程没有收到
- **WHEN** 本人按 P1 的确认消息的「确认」
- **THEN** P1 的下单流程收到确认，紧急退出流程没有收到

#### Scenario: 排进的案件由替身跑到下单

- **GIVEN** 正常启动；Alpaca 模拟盘账户的权益和现金都是 10,000，前一交易日收盘时的权益 10,000；状态库的股票池里 BBB 是关注，有关注论点；OpenD 有 BBB 的行情，前一交易日收盘价 50，最新价 50；状态库里没有 BBB 的新闻、公告和财报；事件表里有 BBB 的入场条件满足事件 E-1
- **WHEN** 排进 E-1 的事件触发（BBB 的入场条件满足事件，事件 ID E-1）
- **THEN** 排队运行启动 BBB 的关注股事件，案件上下文的事件是 E-1；PM 替身给出开仓方案，Critic 替身通过；频道里出现这个方案的确认消息
- **WHEN** 本人按确认消息的「确认」
- **THEN** Alpaca 收到一笔买单：客户端订单 ID 是这个方案的 ID，来源案件是这个案件
- **AND** 这个案件结束：订单已提交

#### Scenario: 新案件排队时作废等确认的方案

- **GIVEN** 同上一个场景，频道里已经出现 BBB 的开仓方案的确认消息，本人还没有按；事件表里另有 BBB 的新闻事件 BBB:2026-10-14:news
- **WHEN** 排进 BBB:2026-10-14:news 的事件触发
- **THEN** 确认消息改为已作废；第一个案件结束：方案被作废；BBB 没有有效预留
- **AND** 之后排队运行启动 BBB 的关注股事件（新闻事件开出的）

#### Scenario: 事件检测排进的案件跑起来

- **GIVEN** 正常启动；状态库的股票池里 BBB 是关注，有关注论点；OpenD 有 BBB 的行情，前一交易日收盘价 100，最新价 94，量比 1，更新时刻在今天开盘以后
- **WHEN** 事件检测做第一轮
- **THEN** 事件表里有 BBB 的价格下跌事件；排队运行启动 BBB 的关注股事件，案件上下文的事件就是它
- **AND** PM 替身给出继续关注，这个案件结束

#### Scenario: 事件检测给止损单成交排卖出复盘

- **GIVEN** 正常启动；状态库里 CCC 的开仓订单全部成交，止损单 CCC-STOP-1 今天全部成交；Alpaca 没有 CCC 的持仓
- **WHEN** 事件检测做第一轮
- **THEN** 排队运行启动 CCC 的卖出复盘；Reviewer 替身交回复盘报告，这个案件结束

#### Scenario: 巡检里股票池跟上持仓

- **GIVEN** 正常启动；状态库的股票池里 BBB 是关注；状态库里有 BBB 部分成交的买单 P1，来源案件 K1，K1 的案件记录有开仓方案的结论，附投资论点；Alpaca 持有 BBB 30 股
- **WHEN** 巡检做一轮
- **THEN** 股票池里 BBB 是持仓，投资论点是 K1 的结论附的


### Requirement: 停止

程序启动完成以后收到 SIGTERM 或 SIGINT，SHALL：

1. 写一条 INFO：收到停止信号，开始停止
2. 按打开的相反顺序关闭：盘中巡检 → 事件检测 → 排队运行 → DBOS → Discord → OpenD 行情连接 → 数据库连接。每一项关闭写一条 INFO。盘中巡检按 session-patrol spec「巡检的开始、间隔和停止」停下：正在做的那一项做完才算关闭；事件检测按 event-detection spec「什么时候做一轮」、排队运行按 queue-runner spec「什么时候做一轮」停下：正在做的一轮做完才算关闭
3. 某一项关闭出错时写 ERROR（带异常栈），接着关闭下一项
4. 全部关完写「已停止」，以退出码 0 立即结束进程：SHALL NOT 等还在等确认、等开盘、等重试的下单流程和运行中的案件（它们由下次启动的 DBOS 恢复，order-flow spec「持久化和恢复」，case-workflow spec「崩溃恢复」）

启动过程中收到停止信号时，程序 SHALL 做完当前的启动（每一步都有超时），启动完成以后不再等待、直接停止；启动失败时按「启动失败」处理。停止过程中再收到停止信号，不另外处理。

#### Scenario: SIGTERM

- **GIVEN** 正常启动
- **WHEN** 收到 SIGTERM
- **THEN** 日志依次写出：收到停止信号、已关闭盘中巡检、已关闭事件检测、已关闭排队运行、已关闭 DBOS、已关闭 Discord、已关闭 OpenD 行情连接、已关闭数据库连接、已停止
- **AND** 退出码 0

#### Scenario: SIGINT

- **GIVEN** 正常启动，在终端里运行
- **WHEN** 按 Ctrl-C
- **THEN** 和收到 SIGTERM 一样停止，退出码 0，没有 KeyboardInterrupt 的异常栈

#### Scenario: 某一项关闭出错

- **GIVEN** 正常启动；关闭 OpenD 行情连接时报错
- **WHEN** 收到 SIGTERM
- **THEN** 有一条 ERROR 写明关闭 OpenD 行情连接出错
- **AND** 数据库连接照样关闭，日志写出已停止，退出码 0

#### Scenario: 启动过程中收到停止信号

- **GIVEN** 正在连接 Discord 时收到 SIGTERM
- **WHEN** 启动的其余步骤完成
- **THEN** 写出启动完成以后立即停止，按顺序关闭，退出码 0

#### Scenario: 停止时巡检正在跟进订单

- **GIVEN** 正常启动；巡检正在跟进一笔订单，Alpaca 对这次查询还没有响应
- **WHEN** 收到 SIGTERM
- **THEN** Alpaca 的响应回来、这笔订单保存以后才写出已关闭盘中巡检
- **AND** 之后才关闭事件检测、排队运行、DBOS、Discord、OpenD 行情连接和数据库连接，退出码 0

#### Scenario: 停止时有方案在等确认

- **GIVEN** 正常启动；一个方案的确认消息已经发出，还有 25 分钟才到截止时刻
- **WHEN** 收到 SIGTERM
- **THEN** 按顺序关闭，写出已停止，退出码 0，没有等到截止时刻
- **AND** 写出已停止以后进程立即结束；这个方案的下单流程由下次启动的 DBOS 恢复（order-flow spec「持久化和恢复」）
