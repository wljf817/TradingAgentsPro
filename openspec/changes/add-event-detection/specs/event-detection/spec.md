# Spec Delta

## Purpose

事件检测在自己的线程里一轮一轮地读行情、新闻、公告、财报日历和交易记录，按 event-rules spec 检测股票池里的股票的事件，把事件存进状态库、写程序日志、排进案件；并给每笔已经结束、有成交的卖出排一个卖出复盘。

## ADDED Requirements

### Requirement: 监控范围

事件检测 SHALL 只检测股票池里的股票（候选、关注、持仓，stock-pool spec）的价格、成交量、新闻、公告和财报发布，这些股票合称监控股票：

- 不在股票池里的持仓（`/plan` 买入的，pool-position-sync spec）和其他股票 SHALL NOT 检测，也不写程序日志
- 股票的状态用这一轮开始时读到的股票池
- 卖出成交不论股票在不在股票池里，见「卖出成交」

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中；当天 13:30Z 开盘、20:00Z 收盘），交易日历是纽交所日历；今天是 2026-10-14，回看起点是 2026-10-13 15:00Z
- 股票池：AAA 是候选，BBB 是关注，CCC 是持仓，都在 2026-10-01 加入；账户数据里 CCC 的紧急阈值 0.08，今天没有开仓成交。券商另外持有 ZZZ，是 `/plan` 买入的，不在股票池里
- 行情：AAA、BBB、CCC、ZZZ 的前一交易日收盘价都是 100，最新价 100，量比 1，更新时刻 2026-10-14 14:59:58Z
- 新闻源和公告源没有新闻和公告；状态库里没有新闻、公告、财报日历和事件；交易记录里没有卖出；排队表是空的
- 上一次取公告是 2026-10-14 14:57Z，所以这一轮不取公告，除非场景写明"这一轮取公告"
- "做一轮"指事件检测在当前时刻做一轮；"排进 K-n"见 queue-runner spec「排队」，新排进的案件 ID 依次是 K-1、K-2……
- "标题 t 的新闻""表单 f 的公告"和 event-rules spec 的说法相同：新闻 ID 101，发布时刻 2026-10-14 14:50Z；accession number 0000000001-26-000001，受理时刻 2026-10-14 14:50Z

#### Scenario: 不在股票池里的持仓不检测

- **GIVEN** ZZZ 最新价 85；新闻源有标题"ZZZ Files for Chapter 11"、只标注 ZZZ 的新闻
- **WHEN** 做一轮
- **THEN** 没有事件，没有排进案件
- **AND** 程序日志没有关于 ZZZ 的条目
- **AND** 新闻源和行情源被问到的股票里没有 ZZZ

### Requirement: 一轮

事件检测的每一轮 SHALL 开始时从时钟读一次检测时刻、读一次股票池，然后按下表的顺序做五部分；这一轮的检测时刻、交易日、回看起点（检测时刻减「回看时长」）和是否在常规交易时段都按这一次读的时刻算：

| 顺序 | 部分 | 什么时候做 | 读什么 |
| --- | --- | --- | --- |
| 1 | 卖出成交 | 每一轮 | 交易记录，见「卖出成交」 |
| 2 | 价格和成交量 | 检测时刻在常规交易时段里 | 账户数据（持仓的紧急阈值和今天开仓成交的均价）一次；全部监控股票的行情一次（market-data spec「取行情」） |
| 3 | 公告 | 启动以后的第一轮，以及距上一次取公告满「公告间隔」时，取到和取不到都算一次 | 公告源，见「取新闻和公告」 |
| 4 | 财报日历 | 每一轮 | 状态库里每只监控股票的财报日历（company-data spec「读取财报」） |
| 5 | 新闻 | 每一轮 | 新闻源，见「取新闻和公告」 |

- 每一部分按 event-rules spec 判断，股票按代码的顺序；同一只股票的公告按受理时刻、新闻按发布时刻、再按 ID 的顺序
- 公告和财报日历在新闻之前：同一轮里财报发布先记下，当天的新闻就不再成为事件
- 股票池是空的时候，第 2 到第 5 部分什么都不做，不向行情源、新闻源和公告源请求
- 盘前、盘后和休市日照常做第 1、3、4、5 部分

#### Scenario: 一轮里的先后

- **GIVEN** 这一轮取公告；CCC 最新价 95.5；公告源有 BBB 的 8-K（item 2.02），新闻源有 BBB 的标题"BBB Raises FY26 Guidance"的新闻
- **WHEN** 做一轮
- **THEN** 依次排进 K-1（CCC 的价格和成交量异动事件，持仓风险级别）、K-2（BBB 的财报发布事件）
- **AND** BBB 的新闻没有成为事件，程序日志的丢弃事件写明原因是当天已有财报发布事件

#### Scenario: 盘前不取行情

- **GIVEN** 当前时刻 2026-10-14 12:00Z；新闻源有 BBB 的标题"BBB to Acquire Widget Co"的新闻，发布时刻 2026-10-14 11:50Z
- **WHEN** 做一轮
- **THEN** 行情源和券商账户没有收到请求
- **AND** 排进 K-1：BBB 的新闻事件，事件 ID BBB:2026-10-14:news

#### Scenario: 休市日照常检测新闻

- **GIVEN** 当前时刻 2026-10-17 15:00Z（周六）；新闻源有 BBB 的标题"BBB to Acquire Widget Co"的新闻，发布时刻 2026-10-17 14:50Z
- **WHEN** 做一轮
- **THEN** 排进 K-1：BBB 的新闻事件，事件 ID BBB:2026-10-19:news

#### Scenario: 公告的间隔

- **GIVEN** 公告间隔 5 分钟；上一次取公告是 2026-10-14 14:55:01Z
- **WHEN** 做一轮
- **THEN** 公告源没有收到请求
- **WHEN** 当前时刻 2026-10-14 15:00:01Z，做一轮
- **THEN** 公告源收到一次请求

#### Scenario: 股票池是空的

- **GIVEN** 股票池是空的；交易记录里有 ZZZ 全部成交的卖单 P9，成交日 2026-10-14
- **WHEN** 做一轮
- **THEN** 行情源、新闻源和公告源都没有收到请求
- **AND** 排进 K-1：ZZZ 的卖出成交，客户端订单 ID 是 P9

### Requirement: 取新闻和公告

取新闻和公告 SHALL 向新闻和公告模块取全部监控股票从回看起点以来的新闻或公告（news-and-filings spec「取新闻」「取公告」），然后：

- 只判断这次新存下的：已经存下过的（之前的轮次、或者别的调用存下的）SHALL NOT 再判断
- 一条新闻或一份公告对它标注的每只监控股票各判断一次；标注的其他股票不判断
- 发布时刻（公告是受理时刻）早于这只股票加入股票池的时刻时，这只股票不判断它，没有成为事件，原因是加入股票池以前发布
- 8-K 和 8-K/A 的 item 2.02 按 event-rules spec「财报发布」判断，其余公告按「公告的初筛」，新闻按「新闻的初筛」

#### Scenario: 新存下的才判断

- **GIVEN** 新闻源有 BBB 的标题"BBB to Acquire Widget Co"的新闻
- **WHEN** 做一轮
- **THEN** 新闻源被问到的是 AAA、BBB、CCC，起始时刻 2026-10-13 15:00Z
- **AND** 排进 K-1：BBB 的新闻事件
- **WHEN** 之后一轮，新闻源仍给出这条新闻
- **THEN** 没有排进案件，没有新的程序日志

#### Scenario: 一条新闻标注两只监控股票

- **GIVEN** 新闻源有一条标题"BBB to Acquire AAA"、标注 AAA 和 BBB 的新闻
- **WHEN** 做一轮
- **THEN** 依次排进 K-1（AAA 的新闻事件）、K-2（BBB 的新闻事件）

#### Scenario: 加入股票池以前发布的

- **GIVEN** BBB 在 2026-10-14 14:55Z 加入股票池；新闻源有 BBB 的标题"BBB to Acquire Widget Co"的新闻，发布时刻 2026-10-14 14:50Z
- **WHEN** 做一轮
- **THEN** 没有排进案件；程序日志有一条丢弃事件，原因是加入股票池以前发布
- **AND** 这条新闻存下了，之后的快照里有它

### Requirement: 记下和排队

检测出的每个事件 SHALL 依次：

1. 记下这个事件（「事件的存储」）。已经有同一个事件 ID 的事件时，这不是新事件（event-rules spec「事件 ID 和去重」），后面两步都不做；新闻和公告按「没成为事件的新闻和公告」写丢弃事件
2. 写程序日志的检测到事件（program-log spec「事件检测层的动作」）
3. 处理是排队的，排进一个案件（queue-runner spec「排队」）：触发是事件，带股票、类别、是否持仓风险级别和事件 ID（case-types spec「触发」）；触发时刻是检测时刻

处理是交给紧急风险退出的事件只做前两步，不排队。

#### Scenario: 持仓风险事件排进案件

- **GIVEN** CCC 最新价 95.5
- **WHEN** 做一轮
- **THEN** 记下事件 CCC:2026-10-14:price_down
- **AND** 程序日志有一条检测到事件，对象 CCC:2026-10-14:price_down
- **AND** 排进 K-1：触发是 CCC 的价格和成交量异动事件，持仓风险级别，事件 ID CCC:2026-10-14:price_down；触发时刻 2026-10-14 15:00Z

#### Scenario: 交给紧急风险退出的不排队

- **GIVEN** CCC 最新价 91
- **WHEN** 做一轮
- **THEN** 记下事件 CCC:2026-10-14:price_down，处理是交给紧急风险退出
- **AND** 程序日志有一条检测到事件，写明交给紧急风险退出
- **AND** 没有排进案件

#### Scenario: 下一轮还越过阈值

- **GIVEN** CCC 最新价 95.5，做过一轮，排进了 K-1
- **WHEN** CCC 最新价 95，之后一轮
- **THEN** 没有新的事件，没有排进案件，没有新的程序日志

### Requirement: 没成为事件的新闻和公告

一条新闻或一份公告对一只监控股票判断以后没有成为事件时，SHALL 写一条程序日志的丢弃事件，写明原因：event-rules spec 的初筛原因（来源不在名单里、标注的股票太多、命中排除词、没有命中关键词、级别不够、表单不算），当天已有新闻或公告事件，当天已有财报发布事件，最近已有财报发布事件，加入股票池以前发布。

下面这些 SHALL NOT 写程序日志：价格和成交量没有成为事件（没达到阈值、当天已有同一个事件 ID 的事件、行情不是当天的）；财报日历上的发布还没到预计发布时刻或者已经有财报发布事件；不在监控范围的股票。

#### Scenario: 初筛没通过

- **GIVEN** 新闻源有 BBB 的标题"BBB Shares Are Trading Higher"的新闻；这一轮取公告，公告源有 BBB 的表单 4 的公告
- **WHEN** 做一轮
- **THEN** 没有排进案件
- **AND** 程序日志依次有两条丢弃事件：对象 BBB，输入的引用 0000000001-26-000001，原因表单不算；对象 BBB，输入的引用 101，原因没有命中关键词

#### Scenario: 价格没达到阈值不写

- **GIVEN** CCC 最新价 97
- **WHEN** 做一轮
- **THEN** 程序日志没有新条目

### Requirement: 卖出成交

每一轮 SHALL 读交易记录里已经结束的卖出（trade-records spec「已经结束的卖出」），成交日不早于回看起点归属的交易日；其中还没有排过卖出成交的（queue-runner spec「排过的卖出成交」），每条排进一个案件：触发是卖出成交，带股票和这条交易记录的客户端订单 ID（case-types spec「触发」），触发时刻是检测时刻。

- 止损单、紧急风险退出和本地备用止损的清仓单、案件的减仓和清仓、`/plan` 的卖出都算，不论股票在不在股票池里
- 卖出成交不是事件：不记下事件，不写检测到事件；排队由排队运行写程序日志
- 还没有结束的卖出（挂着、部分成交）这一轮不排，结束以后再排一次

#### Scenario: 止损单成交

- **GIVEN** 交易记录里 CCC-STOP-1 是止损单，全部成交，累计成交 100，成交日 2026-10-14
- **WHEN** 做一轮
- **THEN** 排进 K-1：触发是 CCC 的卖出成交，客户端订单 ID CCC-STOP-1，触发时刻 2026-10-14 15:00Z
- **WHEN** 之后一轮
- **THEN** 没有排进案件

#### Scenario: 部分成交的卖单结束以后排一次

- **GIVEN** 交易记录里 P5 是卖出 CCC 的卖单，部分成交，累计成交 40
- **WHEN** 做一轮
- **THEN** 没有排进案件
- **WHEN** P5 过期，累计成交 40，成交日 2026-10-14，之后一轮
- **THEN** 排进 K-1：CCC 的卖出成交，客户端订单 ID P5

#### Scenario: 不在股票池里的股票也复盘

- **GIVEN** 交易记录里 P9 是 `/plan` 卖出 ZZZ 的卖单，全部成交，成交日 2026-10-14
- **WHEN** 做一轮
- **THEN** 排进 K-1：ZZZ 的卖出成交，客户端订单 ID P9

#### Scenario: 回看起点以前的卖出不排

- **GIVEN** 交易记录里 P7 是卖出 CCC 的卖单，全部成交，成交日 2026-10-12；P8 全部成交，成交日 2026-10-13
- **WHEN** 做一轮
- **THEN** 只排进 K-1：CCC 的卖出成交，客户端订单 ID P8

#### Scenario: 没有成交的卖出不排

- **GIVEN** 交易记录里 P6 是卖出 CCC 的卖单，已撤销，累计成交 0
- **WHEN** 做一轮
- **THEN** 没有排进案件

### Requirement: 什么时候做一轮

事件检测 SHALL 在自己的线程里运行：

- 开始以后立即做第一轮；每一轮做完以后等「间隔」再做下一轮，间隔从上一轮做完算起
- 一轮出错时写一条 ERROR（bootstrap spec「日志」），这一轮剩下的不做，下一轮照常
- 处于降级模式时照常检测和排队：降级模式不开始新案件，新的触发照常排队（Proposal「故障处理」）
- 停止时：在等下一轮的立即结束；在做一轮的，这一轮做完以后结束
- 事件检测只读执行模块，SHALL NOT 拿执行模块和风控的那把锁（session-patrol spec「执行模块和风控的调用串行」）

#### Scenario: 开始以后立即做第一轮

- **WHEN** 事件检测开始
- **THEN** 不等间隔，交易记录和股票池立即被读一次

#### Scenario: 每一轮做完以后等间隔

- **GIVEN** 一轮从 15:00:00Z 开始，15:00:04Z 做完
- **WHEN** 事件检测继续运行
- **THEN** 下一轮在 15:01:04Z 开始

#### Scenario: 一轮出错

- **GIVEN** 这一轮读股票池时数据库出错
- **WHEN** 做一轮
- **THEN** 写一条 ERROR，这一轮没有排进案件
- **WHEN** 数据库恢复，之后一轮
- **THEN** 照常检测

#### Scenario: 降级时照常排队

- **GIVEN** 健康监控处于降级模式；CCC 最新价 95.5
- **WHEN** 做一轮
- **THEN** 排进 K-1：CCC 的价格和成交量异动事件

#### Scenario: 停止

- **GIVEN** 事件检测正在等下一轮
- **WHEN** 停止
- **THEN** 立即结束
- **GIVEN** 事件检测正在做一轮，新闻源还没有响应
- **WHEN** 停止
- **THEN** 新闻源响应、这一轮做完以后才结束

### Requirement: 读不到时

一部分读不到时 SHALL 按下表处理，其他部分照常：

| 读不到 | 处理 |
| --- | --- |
| 行情源不可用，或者读账户数据时券商不可用 | 这一轮不判断价格和成交量，写一条 WARNING |
| 行情源没有某只股票的数据 | 这只股票这一轮不判断价格和成交量 |
| 持仓在账户数据里没有这只股票（股票池还没跟上持仓） | 这只股票这一轮不判断价格和成交量 |
| 公告源不可用 | 这一轮不判断公告，写一条 WARNING；到下一次公告间隔再取 |
| 新闻源不可用 | 这一轮不判断新闻，写一条 WARNING；下一轮照常取 |
| 数据库出错（股票池、交易记录、财报日历、事件、新闻和公告、排队表） | 按「什么时候做一轮」的一轮出错处理 |

新闻源、公告源不可用时没有存下的新闻和公告，之后取到时仍是新存下的，照常判断：回看时长覆盖了这段时间。

#### Scenario: 行情源不可用

- **GIVEN** 行情源这一轮报行情不可用；新闻源有 BBB 的标题"BBB to Acquire Widget Co"的新闻
- **WHEN** 做一轮
- **THEN** 写一条 WARNING；没有价格和成交量的事件
- **AND** 排进 K-1：BBB 的新闻事件

#### Scenario: 行情源没有某只股票

- **GIVEN** 行情源没有 BBB 的数据；CCC 最新价 95.5
- **WHEN** 做一轮
- **THEN** 排进 K-1：CCC 的价格和成交量异动事件；BBB 没有事件

#### Scenario: 新闻源不可用以后补上

- **GIVEN** 新闻源这一轮报数据源不可用
- **WHEN** 做一轮
- **THEN** 写一条 WARNING，没有新闻的事件
- **WHEN** 新闻源恢复，给出 BBB 的标题"BBB to Acquire Widget Co"的新闻，之后一轮
- **THEN** 排进 K-1：BBB 的新闻事件

#### Scenario: 公告源不可用

- **GIVEN** 这一轮取公告，公告源报数据源不可用
- **WHEN** 做一轮
- **THEN** 写一条 WARNING
- **WHEN** 之后一轮（15:01Z）
- **THEN** 公告源没有收到请求
- **WHEN** 2026-10-14 15:05Z 做一轮
- **THEN** 公告源收到请求

### Requirement: 重启以后

进程重启以后，事件检测 SHALL：

- 按事件 ID 去重：重启以前记下的事件不再记下、不再排队
- 按排队表去重卖出成交：重启以前排过的不再排
- 回看起点以来、重启以前还没存下的新闻和公告照常判断；重启以前已经存下的不再判断
- 价格和成交量照常判断，当天已经有同一个事件 ID 的不再是事件

#### Scenario: 重启以后不重复

- **GIVEN** 重启以前记下了 CCC:2026-10-14:price_down，排进了 K-1；排进了 CCC-STOP-1 的卖出成交 K-2；存下并判断过 BBB 的新闻 101
- **WHEN** 用同一个数据库重启，CCC 最新价仍是 95.5，新闻源仍给出新闻 101，CCC-STOP-1 仍是全部成交，做一轮
- **THEN** 没有排进案件，没有新的事件

#### Scenario: 停机期间的新闻

- **GIVEN** 停机期间新闻源有了 BBB 的标题"BBB to Acquire Widget Co"的新闻，发布时刻 2026-10-14 09:00Z
- **WHEN** 2026-10-14 15:00Z 重启，做一轮
- **THEN** 排进 K-1：BBB 的新闻事件，触发时刻 2026-10-14 15:00Z
- **AND** 事件的发生时刻是 2026-10-14 09:00Z

### Requirement: 事件的存储

事件 SHALL 存在状态库所在的数据库里（事件表 events_detected，state-store spec「表的归属和迁移」），只由事件检测写入：

- 一个事件一行，事件 ID 不重复；只追加，写入以后 MUST NOT 被修改或删除
- 记下一个事件 ID 已经有了的事件时 SHALL NOT 写入，并告诉调用方不是新事件；同时记下同一个事件 ID 时只有一个写入成功
- 读回的事件和写入的完全相同：每一位小数、说明里的中文、引用的顺序；发生时刻和检测时刻读回的是同一时刻，和数据库服务器、本机的时区都无关
- 进程重启以后（用同一个数据库新建存储）SHALL 读到之前记下的全部事件
- 读写出错（数据库连不上、表不存在、存着的事件读不出来）时 SHALL 报错：MUST NOT 当作没有事件，也 MUST NOT 当作已经记下

#### Scenario: 原样读回

- **GIVEN** 进程的本机时区是 UTC+14
- **WHEN** 记下 event-rules spec 的 CCC:2026-10-14:price_down（强度 -0.045），重启，按事件 ID 读
- **THEN** 读到的和记下的完全相同：强度正好是 -0.045，发生时刻 2026-10-14 14:59:58Z，检测时刻 2026-10-14 15:00Z

#### Scenario: 同一个事件 ID 只写一次

- **WHEN** 记下 CCC:2026-10-14:price_down 两次，第二次的强度是 -0.05
- **THEN** 第一次是新事件，第二次不是；读到的强度是 -0.045
- **WHEN** 两个调用同时记下 BBB:2026-10-14:news
- **THEN** 只有一个是新事件，事件表里只有一行

#### Scenario: 读写出错

- **GIVEN** 数据库连不上
- **WHEN** 记下一个事件；按事件 ID 读；按股票读
- **THEN** 都报错，读不返回空

### Requirement: 读取事件

事件检测 SHALL 能：

- 按事件 ID 读一个事件；没有时为空
- 按一只股票和一个时刻 T 读这只股票检测时刻不早于 T 的事件，按检测时刻、再按事件 ID 排列；没有时为空

读取只读事件表。

#### Scenario: 按股票和时刻读

- **GIVEN** 记下了 BBB:2026-10-13:news（检测时刻 2026-10-13 14:00Z）、BBB:2026-10-14:price_up 和 BBB:2026-10-14:news（检测时刻都是 2026-10-14 15:00Z）、CCC:2026-10-14:price_down
- **WHEN** 读 BBB 自 2026-10-13 14:00Z 的事件
- **THEN** 依次是 BBB:2026-10-13:news、BBB:2026-10-14:news、BBB:2026-10-14:price_up
- **WHEN** 读 BBB 自 2026-10-13 14:00:01Z 的事件
- **THEN** 依次是 BBB:2026-10-14:news、BBB:2026-10-14:price_up
- **WHEN** 按事件 ID 读 AAA:2026-10-14:news
- **THEN** 为空

### Requirement: 事件检测的配置

事件检测的配置项 SHALL 可配置，默认值如下：

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| 间隔 | 60 秒 | 一轮做完以后等这么久再做下一轮 |
| 公告间隔 | 5 分钟 | 距上一次取公告满这么久才再取：SEC 一只股票一个请求 |
| 回看时长 | 24 小时 | 取新闻和公告的起始时刻、财报日历的预计发布时刻、卖出的成交日都从检测时刻往前这么久算起 |

三项都 SHALL 大于 0，否则配置报错。

#### Scenario: 默认配置

- **WHEN** 不传任何配置项新建配置
- **THEN** 间隔 60 秒，公告间隔 5 分钟，回看时长 24 小时

#### Scenario: 改回看时长

- **GIVEN** 回看时长 2 小时；新闻源有 BBB 的标题"BBB to Acquire Widget Co"的新闻
- **WHEN** 做一轮
- **THEN** 新闻源被问到的起始时刻是 2026-10-14 13:00Z

#### Scenario: 配置非法

- **WHEN** 间隔为 0 秒；或者回看时长为 -1 小时
- **THEN** 配置报错
