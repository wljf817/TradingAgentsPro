# Proposal

## Why

券商端止损单只管价格跌到止损价的情况。下面两种情况，Proposal 要求由代码直接清仓，不排队、不等模型：一只持仓当天跌得太快，超过 PM 设的紧急阈值；整个组合单日亏损触及熔断线。风控现在只检查方案里紧急阈值的范围，熔断状态由调用方传入；什么时候算触发、触发后卖什么，前面的变更都留给了本变更：

- risk-rules spec：紧急阈值的跌幅从什么价格算起
- 风控规则的 design D7：单日亏损熔断怎么判定、保持多久
- 止损保护的 design D8：代码触发的卖出（紧急退出和本地备用止损）怎样生成方案、经过风控

本变更的目的只有一个：**在常规交易时段判定紧急风险退出是否触发，给出要清仓的股票和代码生成的清仓方案，并提供当天的熔断状态。**

引用的 Proposal（完整版）章节：

- 「架构」的"不经过主流程的保护"：紧急风险退出由代码规则触发，只能减仓或清仓；紧急阈值由 PM 在方案中设定，没写时用默认值
- 「触发」的"持仓风险事件与紧急风险事件"：触及紧急阈值或组合熔断线，由代码直接走紧急风险退出，不开案件
- 「持仓与退出」的退出路径表"紧急风险退出"一行：持仓盘中跌幅超阈值、组合单日亏损触及熔断线；决定者是代码；只允许减仓或清仓
- 「风控引擎与执行」：
  - 开仓类规则：单日亏损熔断触发后禁止开仓
  - 减仓类规则：不受熔断等开仓类限制
  - 交易时段：紧急风险退出也只在常规交易时段下单
- 「故障处理」：降级模式下紧急风险退出照常有效

## What Changes

- 新增紧急退出模块 `modules/emergency/`。判定需要的数据都由调用方传入，模块不读取外部数据
- 个股跌幅：跌幅达到这只股票的紧急阈值时，清仓这只股票
  - 跌幅 =（参考价 − 最新价）÷ 参考价
  - 参考价是前一交易日的收盘价；今天有开仓成交的股票，参考价改用这笔成交的均价
  - 没有行情的股票不判定个股跌幅
- 组合熔断：单日亏损达到熔断线时，清仓全部持仓
  - 单日亏损 = 前一交易日收盘时的权益 − 当前权益
  - 熔断线 = 前一交易日收盘时的权益 × 熔断比例，比例可配置，默认 0.03
- 熔断状态：从触发时刻起到这个交易时段收盘都是"已触发"，其他时刻都是"没有触发"。触发以后权益回升也不解除。风控和下单前再校验的熔断输入由它给出，熔断期间开仓被拒绝
- 只在常规交易时段判定；时段之外不判定，什么都不返回
- 代码触发的清仓方案：市价单，卖出全部可卖数量，不填股数、限价和有效期。方案 ID 由股票和交易日确定，同一只股票在同一个交易日只有一个，重复判定时得到同一个方案，不会重复下单。本地备用止损触发后也用它生成方案
- 判定结果给出每只要清仓的股票的方案和原因（个股跌幅或组合熔断）。之后的流程（让路、风控检查、再校验、下单、通知）由 M2 的工作流编排，见 design D6

## Non-goals

- 紧急退出前撤掉这只股票还挂着的订单：要改执行模块，作为下一个变更「紧急撤单（修改：订单状态机）」，见「需要人决定」第 5 条
- 作废这只股票还没下单的退出方案、中止正在运行的案件：放到 M3 的调度器，见「需要人决定」第 5 条
- 紧急退出需要人工确认的开关：放到 M3「人工确认的规则」，见「需要人决定」第 4 条
- 减仓：紧急退出只清仓
- 实时行情、前一交易日收盘价和权益的来源，判定的频率，执行后通知：M2 接入
- 熔断状态的持久化：放在内存里，进程重启以后重新判定，见 design D4
- 清仓后股票转为候选、开候选评估案件和复盘案件：M3、M4 和 M6

## Capabilities

### New Capabilities

- `emergency-exit`：判定的时机和输入、个股跌幅、组合熔断、熔断状态、代码触发的清仓方案、判定结果、熔断比例配置

### Modified Capabilities

无。风控已经把熔断状态作为输入，清仓方案按已有的减仓类规则和再校验处理。

## Impact

- **代码**：新增 `src/tradingagentspro/modules/emergency/`
  - `domain/exit.py`：持仓输入、判定结果，以及参考价、个股跌幅、单日亏损、清仓方案的纯函数
  - `service.py`：`EmergencyService`，判定并记下熔断状态
  - `config.py`：`EmergencyConfig`，熔断比例
  - `__init__.py`：导出公开的名字
- **测试**：新增 `tests/modules/emergency/`：`domain/test_exit.py`、`test_service.py`、`test_config.py`，以及一个用风控用例检查清仓方案能通过检查和再校验的测试
- **依赖**：无。方案 ID 用标准库的 `uuid.uuid5`，它是确定性的，不在 Ruff 的禁用名单里
- **文档**（propose 时已更新）：完整版 Proposal「持仓与退出」增加紧急风险退出怎样触发；「风控引擎与执行」的"交易时段"一句改为只在常规交易时段判定。`docs/实现路线.md` 的进度清单增加「紧急撤单（修改：订单状态机）」
- **对后续变更的影响**：
  - 紧急撤单（下一个变更）：紧急退出前撤掉这只股票还挂着的买单和卖单；熔断触发时撤掉全部还挂着的买单。卖单不撤，紧急清仓就卖不全：可卖数量被挂着的卖单占着，止损单也为它让出了股数。买单不撤，清仓以后还会继续成交
  - 变更 9（降级策略）：本模块不依赖健康状态，降级模式下照常判定
  - M2：
    - 紧急退出工作流：判定 → 撤单 → 风控检查 → 再校验 → 下单 → 跟进 → 通知，见 design D6
    - 风控检查和再校验的熔断输入用本模块的熔断状态
    - 每只持仓生效的紧急阈值要能查到：和止损价一样，取这只股票最近一次有成交的开仓方案的值。订单记下它，还是存进状态库，拆变更时决定
    - 前一交易日收盘时的权益：Alpaca 账户的 `last_equity`
    - 本地备用止损触发后，用本模块的清仓方案走同一条流程
  - M3：
    - 调度器在紧急退出时，作废这只股票还没下单的退出方案并释放预留，中止这只股票正在运行的案件
    - 「人工确认的规则」增加紧急退出需要确认的开关
  - M7：moomoo 实盘的前一交易日收盘时的权益从哪里取，接入时再定

## 需要人决定

已决定（2026-10-04，人同意推荐做法）：

1. **跌幅从什么价格算起**：Proposal 只写了"持仓盘中跌幅"。决定：从前一交易日收盘价算；今天有开仓成交的，从这笔成交的均价算
   - 例外是必要的：盘后财报跌了 8%，PM 决定第二天开盘抄底。按前收盘价算，刚买进就会触发紧急清仓
   - 不用持仓均价：那就成了第二个止损价，和券商端止损单重复
2. **熔断触发后卖什么**：Proposal 把组合单日亏损触及熔断线列为紧急退出的触发条件，但没说卖哪些，也没有熔断线的默认值。决定：清仓全部持仓，收盘前不再开仓；熔断比例默认 0.03
   - 合计风险上限是权益的 5%，也就是全部止损都被打掉大约亏 5%。一天之内就亏到 3%，多半是大盘或板块整体下跌，剩下的止损很可能也会被打掉，还可能跳空
3. **盘前盘后触发**：「交易时段」说紧急风险退出"盘前盘后触发的在开盘时执行"。这样的话，盘前跌破阈值、开盘又涨回来，开盘照样会卖。决定：只在常规交易时段判定。盘前的跌幅开盘时还在，开盘后的第一个价格就会触发，效果一样；涨回来了就不卖
   - 完整版「交易时段」一句相应修改
4. **"可配置为需要人工确认"**：人工确认的流程到 M3 才有。决定：本变更不做这个开关，放到 M3「人工确认的规则」
5. **让路的两件事分开做**：撤掉这只股票还挂着的订单，要改执行模块，单独作为「紧急撤单（修改：订单状态机）」；作废还没下单的退出方案放进 M3 的调度器，调度器本来就负责作废方案，作废后用风控已有的"释放"释放预留

新发现的，已按推荐做法写进 spec，不同意可以改：

6. **熔断"当天一直保持"保持到什么时候**：风控规则的 design D7 写的是"触发后当天一直保持"，没说收盘以后算不算当天。推荐：保持到这个交易时段收盘。开仓只在盘中下单，收盘以后形成的方案在下一个交易日执行，那一天的熔断没有触发
7. **紧急清仓被拒以后当天不重试**：同一只股票每个交易日只有一个代码触发的清仓方案，这是不重复下单的保证。市价卖单被券商拒绝（比如停牌）以后，当天不再生成新的清仓方案；卖单结束以后，止损单恢复覆盖全部持仓
