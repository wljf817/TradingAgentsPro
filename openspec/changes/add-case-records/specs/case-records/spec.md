# Spec Delta

## Purpose

案件记录存下每个案件（三种驱动触发的，包括排队以后没有运行的，以及复盘案件）在进行和结束时的事实：触发、案件类型、结论、交易方案和它的审核、回应与风控结果、股票池增删的发现、结束原因和用量，供案件上下文、收盘心跳、查询工具和评估按案件、按股票读回。

## ADDED Requirements

### Requirement: 案件记录的内容

案件记录 SHALL 为每个案件保存一条记录：

| 项 | 内容 |
| --- | --- |
| 案件 ID | 案件入队时的 ID，和队列、Task、费用记录、程序日志里的案件 ID 相同 |
| 触发 | case-types spec「触发」的四种之一：事件、定时心跳的检查项、跟进、卖出成交 |
| 触发原因 | 调用方写的中文说明，比如事件的类别、心跳的检查项、跟进要回答的问题 |
| 股票 | 触发带的股票；寻股和每周复盘没有 |
| 触发时刻 | 案件在队列里的触发时刻（case-queue spec「队列的输入和决定」） |
| 案件类型 | 开始运行时确定的类型（case-types spec「开始运行时确定案件类型」） |
| 开始时刻 | 写开始运行的时刻 |
| 结论 | 通过校验的结论（case-types spec「结论的公共部分」到「跟进申请的格式」），给出它的模型（model-fallback spec「实际使用的模型」：模型和是不是备用模型），以及写结论的时刻（结论时刻） |
| 状态 | 见下表 |
| 结束原因 | case-stages spec「结束原因」之一 |
| 结束时刻 | 写结束或者写不再运行的时刻 |
| 耗时 | 结束时刻减开始时刻 |
| Task 数 | 本案件派发出去的任务数：PM 的任务数加 Critic 用掉的补充研究额度（task-dispatch spec「本案件的任务和用量」），被拒绝的不算，复用的不另算 |
| 调用次数 | 本案件调用模型的次数：Agent 网关为本案件记下的费用记录的条数（call-budget spec「费用的记录」），重试、切换备用模型的每次尝试各算一次，拿不到用量的尝试不算 |

状态 SHALL 是下表之一：

| 状态 | 什么时候 | 有的项 |
| --- | --- | --- |
| 进行中 | 写了开始运行，还没有写结束 | 案件 ID 到开始时刻；写了结论以后还有结论。没有结束原因、结束时刻和耗时，Task 数和调用次数还没有 |
| 已结束 | 写了结束 | 全部；没有结论就结束的没有结论 |
| 不再运行 | 排队以后没有开始运行就离开了队列（case-queue spec「排队的案件按现在的状态确定类型」） | 案件 ID、触发、触发原因、股票、触发时刻和结束时刻；Task 数和调用次数都是 0；没有案件类型、开始时刻、结论、结束原因和耗时 |

复盘案件和别的案件一样记录，只是没有结论。

本 spec 的场景除非另有说明，都使用下面的基准数据：

- 时刻都在 2026-10-14（周三），只写时刻；写入用的"现在"是写入时时钟的时刻
- 模型是 model-fallback spec 的基准模型的配置：PM 的主模型 p-1、第一个备用模型 p-2，Critic 的主模型 c-1
- 方案条款、投资论点、关注论点和"评分 n 的信号"是 case-types spec 的基准数据；基准方案条款是 100 股，限价单，限价 50，止损价 45，紧急阈值 0.08
- 案件：

  | 案件 | 触发 | 触发原因 | 股票 | 触发时刻 | 开始运行 | 案件类型 |
  | --- | --- | --- | --- | --- | --- | --- |
  | K-1 | 事件 | BBB 的新闻事件 | BBB | 14:50Z | 15:00Z | 关注股事件 |
  | K-2 | 定时心跳的检查项 | 股票池候选不足 | 没有 | 20:00Z | 20:05Z | 寻股 |
  | K-3 | 定时心跳的检查项 | CCC 的持仓复查日到期 | CCC | 20:00Z | 20:10Z | 持仓复查 |
  | K-4 | 事件 | AAA 的新闻事件 | AAA | 14:00Z | 不运行 | — |
  | K-5 | 事件 | CCC 的价格和成交量异动事件 | CCC | 14:55Z | 15:00Z | 持仓事件 |
  | K-6 | 卖出成交 | CCC 的止损单成交 | CCC | 15:58Z | 16:00Z | 卖出复盘 |

- 结论：
  - K-1：关注的结论，决定开仓方案，基准方案条款，附基准投资论点，PM 用 p-1 给出；交易方案 P-1（股票 BBB，板块"医疗"，买入，基准方案条款）
  - K-2：寻股的结论，加入 DDD（理由"放量突破"，评分 1 的信号）和 EEE（理由"盈利预期上调"，评分 2 的信号），删除 AAA（理由"论点不再成立"），PM 用 p-1 给出
  - K-3：持仓的结论，决定持有，附论点更新（基准投资论点，复查日改为 2026-10-28），PM 用备用模型 p-2 给出
  - K-5：持仓的结论，决定减仓，60 股，市价单，PM 用 p-1 给出；交易方案 P-5（股票 CCC，板块"能源"，减仓）
- "t 开始 K-n"指在 t 按上表写 K-n 的开始运行；"t 写 K-n 的结论"指在 t 写上面 K-n 的结论，有交易方案的连同方案；"t K-n 结束（原因，a，b）"指在 t 写结束，结束原因、Task 数 a、调用次数 b
- GIVEN 里的几步依次进行；一个 WHEN 里用"；"隔开的几种情况，各自从 GIVEN 的数据开始；用"接着""再""依次"连接的依次进行；同一个场景里的几组 WHEN、THEN，除非写"接着"，也各自从 GIVEN 的数据开始

#### Scenario: 进行中的案件

- **WHEN** 15:00Z 开始 K-1
- **THEN** K-1 的记录：触发是事件，触发原因"BBB 的新闻事件"，股票 BBB，触发时刻 14:50Z，案件类型关注股事件，开始时刻 15:00Z，状态进行中
- **AND** 没有结论、结束原因、结束时刻和耗时，Task 数和调用次数还没有
- **WHEN** 接着 15:20Z 写 K-1 的结论
- **THEN** 状态仍是进行中，结论是 K-1 的结论，模型 p-1、不是备用模型，结论时刻 15:20Z

#### Scenario: 已结束的案件

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 15:40Z K-1 结束（订单已提交，3，9）
- **THEN** 状态已结束，结束原因订单已提交，结束时刻 15:40Z，耗时 40 分钟，Task 数 3，调用次数 9
- **AND** 结论和结论时刻 15:20Z 不变

#### Scenario: 没有结论就结束

- **GIVEN** 20:10Z 开始 K-3
- **WHEN** 20:12Z K-3 结束（系统故障，0，2）
- **THEN** 状态已结束，结束原因系统故障，没有结论，耗时 2 分钟，Task 数 0，调用次数 2

#### Scenario: 不再运行的案件

- **WHEN** 14:30Z 写 K-4 不再运行
- **THEN** K-4 的记录：状态不再运行，触发是事件，触发原因"AAA 的新闻事件"，股票 AAA，触发时刻 14:00Z，结束时刻 14:30Z，Task 数和调用次数都是 0
- **AND** 没有案件类型、开始时刻、结论、结束原因和耗时

#### Scenario: 复盘案件

- **GIVEN** 16:00Z 开始 K-6
- **WHEN** 16:03Z K-6 结束（复盘完成，0，1）
- **THEN** K-6 的记录：触发是卖出成交，触发原因"CCC 的止损单成交"，案件类型卖出复盘，状态已结束，结束原因复盘完成，耗时 3 分钟，没有结论

#### Scenario: 寻股没有股票

- **WHEN** 20:05Z 开始 K-2
- **THEN** K-2 的记录没有股票，案件类型寻股，状态进行中

### Requirement: 写入的时刻

调用方 SHALL 在下表的时刻写入案件记录，写入用的"现在"从时钟读取：

| 时刻 | 写入 |
| --- | --- |
| 案件开始运行 | 开始运行：案件 ID、触发、触发原因、股票、触发时刻、案件类型；开始时刻是现在 |
| 结论通过校验（case-stages spec「唤醒 PM 和结论」） | 结论和给出它的模型；结论时刻是现在。结论有交易方案时同时写方案（见「方案记录」） |
| Critic 给出一次审核 | 这次审核和 Critic 用的模型 |
| Critic 不可用（case-stages spec「Critic 不可用」） | Critic 不可用 |
| PM 回应一轮质询 | 这次回应和 PM 用的模型 |
| 风控给出结果 | 风控结果 |
| 结论里的股票池增删执行以后 | 每一项增删和股票池的结果（见「股票池增删的发现」） |
| 案件结束 | 结束原因、Task 数、调用次数；结束时刻是现在 |
| 排队的案件不再运行 | 不再运行：案件 ID、触发、触发原因、股票、触发时刻；结束时刻是现在 |

- 案件记录 SHALL NOT 记案件的阶段、重交次数和质询轮次：这些只在调度器的案件状态里（case-stages spec「案件的状态」）。案件记录里的结论和结束原因是案件状态变化时写下的，不再交回案件状态
- 写案件记录 SHALL NOT 写程序日志：开案件、阶段变化、唤醒 PM 和 Critic 等调度器的动作，由做这些动作的流程写（program-log spec）

#### Scenario: 开始运行、结束和不再运行

- **WHEN** 15:00Z 开始 K-1，15:40Z K-1 结束（订单已提交，3，9）；14:30Z 写 K-4 不再运行
- **THEN** K-1 的开始时刻 15:00Z、结束时刻 15:40Z；K-4 的结束时刻 14:30Z，见「案件记录的内容」

#### Scenario: 结论通过校验

- **GIVEN** 20:10Z 开始 K-3
- **WHEN** 20:30Z 写 K-3 的结论
- **THEN** K-3 有结论（持有，附论点更新），模型 p-2、是备用模型，结论时刻 20:30Z，没有方案记录
- **GIVEN** 15:00Z 开始 K-1
- **WHEN** 15:20Z 写 K-1 的结论
- **THEN** K-1 有结论，结论时刻 15:20Z，并且有方案记录：方案 P-1，还没有审核、回应和风控结果，Critic 不可用为否

#### Scenario: Critic 的审核和 PM 的回应

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 写 Critic 用 c-1 给出的审核：质询，理由"止损太近"，质询"止损价 45 离限价只有 10%，财报前波动更大"，接着写 PM 用 p-1 给出的回应：维持，回应"财报前会把止损上移到 46"
- **THEN** K-1 的方案记录有一次审核（质询，c-1）和一次回应（维持，p-1），按写入的先后

#### Scenario: Critic 不可用

- **GIVEN** 15:00Z 开始 K-5；15:10Z 写 K-5 的结论
- **WHEN** 写 Critic 不可用
- **THEN** K-5 的方案记录：Critic 不可用为是，没有审核

#### Scenario: 风控结果

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论；写 Critic 用 c-1 给出的审核：通过，理由"风险收益比合理"
- **WHEN** 写风控结果：调整，股数 40，紧急阈值 0.08，有效期 2026-10-15 20:00Z，不通过的规则是请求股数下的单笔计划风险
- **THEN** K-1 的方案记录的风控结果就是写入的结果

#### Scenario: 股票池增删以后写发现

- **GIVEN** 20:05Z 开始 K-2；20:30Z 写 K-2 的结论
- **WHEN** 股票池执行 K-2 的增删以后写 K-2 的发现
- **THEN** K-2 有三项发现，见「股票池增删的发现」

#### Scenario: 不写程序日志

- **WHEN** 依次 15:00Z 开始 K-1、15:20Z 写 K-1 的结论、写 Critic 的审核、15:40Z K-1 结束（订单已提交，3，9）；14:30Z 写 K-4 不再运行
- **THEN** 程序日志都没有新条目

### Requirement: 方案记录

结论有交易方案的案件 SHALL 有一条方案记录：

| 项 | 内容 |
| --- | --- |
| 方案 | 结论通过时的交易方案：方案 ID、股票、板块、动作和条款（case-types spec「PM 写的交易方案」补上方案 ID、股票和板块以后的） |
| Critic 的审核 | 每次审核一项，按先后：结论、理由、质询、引用的 Result（case-stages spec「Critic 审核和 PM 回应的格式」），和 Critic 这次用的模型 |
| PM 的回应 | 每轮回应一项，按先后：决定、逐条回应、修改后的方案条款（只有修改有），和 PM 这次用的模型 |
| Critic 不可用 | 是否因为 Critic 不可用没有经过审核 |
| 风控结果 | 风控给出的结果：通过、调整或拒绝，最终股数、生效的紧急阈值和有效期、不通过的规则（risk-rules spec）；没有走到风控的没有 |

- 方案 SHALL 一直是结论通过时的方案：PM 修改的条款记在那一轮回应里，不改方案
- 方案以什么结束看案件的结束原因：被 Critic 否决、PM 撤回、风控拒绝、人工拒绝、确认超时、再校验作废、方案被作废的方案 SHALL 都留在方案记录里，和订单已提交的方案一样能读回
- 没有交易方案的案件 SHALL NOT 有方案记录

#### Scenario: 第一次审核就通过

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 依次写 Critic 用 c-1 给出的审核（通过，理由"风险收益比合理"）、风控结果（通过，股数 100），15:40Z K-1 结束（订单已提交，3，9）
- **THEN** K-1 的方案记录：方案 P-1，一次审核（通过，c-1），没有回应，Critic 不可用为否，风控结果通过、股数 100
- **AND** K-1 的结束原因是订单已提交

#### Scenario: 两轮质询以后仍有分歧

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 依次写：审核（质询）、回应（维持）、审核（质询）、回应（修改，新的条款 60 股，限价单，限价 50，止损价 46，紧急阈值 0.08）、审核（质询）、风控结果（通过，股数 60）
- **THEN** K-1 的方案记录有三次审核、两轮回应，按写入的先后；第二轮回应带着 60 股的条款
- **AND** 方案仍是 P-1 的基准方案条款（100 股，止损价 45）

#### Scenario: 被否决和撤回的方案

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 写审核（否决，理由"估值已经透支"），15:30Z K-1 结束（Critic 否决，2，4）
- **THEN** K-1 的方案记录：方案 P-1，一次审核（否决），没有回应和风控结果；K-1 的结束原因是 Critic 否决
- **WHEN** 写审核（质询）、回应（撤回，回应"同意等财报以后再看"），15:35Z K-1 结束（PM 撤回，2，5）
- **THEN** K-1 的方案记录：一次审核、一轮回应（撤回），没有风控结果；K-1 的结束原因是 PM 撤回

#### Scenario: 风控拒绝的方案

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论；写审核（通过）
- **WHEN** 写风控结果：拒绝，没有股数，不通过的规则是最多持仓数，接着 15:25Z K-1 结束（风控拒绝，3，6）
- **THEN** K-1 的方案记录的风控结果是拒绝、不通过的规则是最多持仓数；K-1 的结束原因是风控拒绝

#### Scenario: 退出方案有异议

- **GIVEN** 15:00Z 开始 K-5；15:10Z 写 K-5 的结论
- **WHEN** 写审核（质询，理由"跌幅还没有触及证伪条件"，质询"减仓理由只看了一天的走势"），接着写风控结果（通过，股数 60）
- **THEN** K-5 的方案记录：方案 P-5，一次审核（质询），没有回应，风控结果通过

#### Scenario: Critic 不可用的方案

- **GIVEN** 15:00Z 开始 K-5；15:10Z 写 K-5 的结论
- **WHEN** 写 Critic 不可用，接着写风控结果（通过，股数 60）
- **THEN** K-5 的方案记录：Critic 不可用为是，没有审核，风控结果通过
- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 写 Critic 不可用，接着 15:25Z K-1 结束（系统故障，2，4）
- **THEN** K-1 的方案记录：Critic 不可用为是，没有审核和风控结果；K-1 的结束原因是系统故障，结论仍在

#### Scenario: 没有方案的案件

- **GIVEN** 20:10Z 开始 K-3；20:30Z 写 K-3 的结论
- **WHEN** 20:31Z K-3 结束（没有交易方案，2，5）
- **THEN** K-3 没有方案记录

### Requirement: 股票池增删的发现

结论里的股票池增删执行以后，调用方 SHALL 把每一项写成一项发现：

| 结论 | 发现 |
| --- | --- |
| 寻股的结论 | 每只加入的候选一项、每只删除的股票一项，加入在前、删除在后，各自按结论里的顺序 |
| 候选的结论、关注的结论，决定移出 | 删除这只股票一项，理由是结论的理由 |
| 其他结论 | 没有 |

每项发现：

| 项 | 内容 |
| --- | --- |
| 增删 | 加入或删除 |
| 股票 | 加入或删除的股票 |
| 理由 | 加入的理由与论点草稿；删除的理由 |
| 信号 | 加入的候选的信号；删除没有 |
| 股票池的结果 | 通过；不通过时是股票池给出的原因（stock-pool spec「加入候选」「删除」） |

- PM 发起的清仓以后选择移出的，股票池在清仓卖单成交以后才移出（stock-pool spec），SHALL NOT 写成发现：这个选择在结论里

#### Scenario: 寻股的加入和删除

- **GIVEN** 20:05Z 开始 K-2；20:30Z 写 K-2 的结论
- **WHEN** 股票池加入 DDD 通过，加入 EEE 被拒绝（流动性不达标），删除 AAA 通过，接着写 K-2 的发现
- **THEN** K-2 的发现依次是：加入 DDD，理由"放量突破"，评分 1 的信号，通过；加入 EEE，理由"盈利预期上调"，评分 2 的信号，不通过，原因流动性不达标；删除 AAA，理由"论点不再成立"，没有信号，通过

#### Scenario: 候选和关注的结论移出

- **GIVEN** AAA 的候选评估 K-7 的结论决定移出，理由"成交萎缩，看不到催化剂"；BBB 的关注复查 K-8 的结论决定移出，理由"订单回暖没有兑现"
- **WHEN** 股票池删除 AAA 被拒绝（增删次数已用完），写 K-7 的发现；股票池删除 BBB 通过，写 K-8 的发现
- **THEN** K-7 有一项发现：删除 AAA，理由"成交萎缩，看不到催化剂"，没有信号，不通过，原因增删次数已用完
- **AND** K-8 有一项发现：删除 BBB，理由"订单回暖没有兑现"，通过

#### Scenario: 没有增删的结论

- **WHEN** 执行完结论以后读这个案件的发现：K-3 的结论是持有；AAA 的候选评估的结论决定升级；寻股的结论加入和删除都为空
- **THEN** 都没有发现，读到的是空

### Requirement: 重复写入和写入的顺序

案件记录的每一步 SHALL 只写一次：同一步再写时记录不变，也不报错。步骤是开始运行、不再运行、结论（连同方案）、Critic 不可用、风控结果、发现、结束。崩溃以后重新执行的步骤会再写一次，读到的仍是第一次写的。

Critic 的审核和 PM 的回应 SHALL 交替写：

| 写 | 方案记录里 | 结果 |
| --- | --- | --- |
| 审核 | 审核和回应一样多 | 加一次审核 |
| 审核 | 审核比回应多一次：上一次审核还没有回应 | 是这次审核的重复写入，记录不变 |
| 回应 | 审核比回应多一次 | 加一轮回应 |
| 回应 | 审核和回应一样多，至少一次审核：上一轮回应以后还没有新的审核 | 是这轮回应的重复写入，记录不变 |
| 回应 | 还没有审核 | 报错 |

写入的顺序不对时 SHALL 报错，记录不变：

- 没有写开始运行就写结论、Critic 不可用、审核、回应、风控结果、发现或结束
- 没有方案记录时写审核、回应、Critic 不可用或风控结果
- 写了不再运行的案件写开始运行；写了开始运行的案件写不再运行

#### Scenario: 再写开始运行和结论

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 15:21Z 再开始 K-1；15:22Z 再写 K-1 的结论
- **THEN** K-1 的开始时刻仍是 15:00Z，结论时刻仍是 15:20Z；方案记录仍是方案 P-1，没有审核

#### Scenario: 再写结束、不再运行和发现

- **GIVEN** 14:30Z 写 K-4 不再运行；15:00Z 开始 K-1；15:40Z K-1 结束（订单已提交，3，9）；K-2 写了三项发现
- **WHEN** 15:41Z K-1 结束（订单已提交，3，10）；15:42Z 写 K-4 不再运行；再写 K-2 的发现，只有加入 DDD 一项
- **THEN** K-1 的结束时刻仍是 15:40Z、调用次数仍是 9；K-4 的结束时刻仍是 14:30Z；K-2 仍是那三项发现

#### Scenario: 再写审核和回应

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论；写审核（质询）
- **WHEN** 再写同一次审核
- **THEN** 方案记录仍是一次审核
- **WHEN** 接着写回应（维持），再写一次这轮回应
- **THEN** 方案记录是一次审核、一轮回应
- **WHEN** 接着写审核（通过）
- **THEN** 方案记录是两次审核、一轮回应

#### Scenario: 写入的顺序不对

- **WHEN** K-1 没有开始就写 K-1 的结论；K-1 没有开始就写 K-1 结束
- **THEN** 都报错，没有 K-1 的记录
- **GIVEN** 20:10Z 开始 K-3；20:30Z 写 K-3 的结论（持有，没有方案）
- **WHEN** 写 K-3 的审核；写 K-3 的风控结果
- **THEN** 都报错，K-3 仍没有方案记录
- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论
- **WHEN** 还没有审核就写回应
- **THEN** 报错，方案记录没有回应
- **GIVEN** 14:30Z 写 K-4 不再运行；15:00Z 开始 K-1
- **WHEN** 15:05Z 开始 K-4；写 K-1 不再运行
- **THEN** 都报错；K-4 仍是不再运行，K-1 仍是进行中

### Requirement: 读取案件记录

案件记录 SHALL 提供下面的读取：

| 读取 | 给出 |
| --- | --- |
| 按案件 ID 读案件记录 | 这个案件的记录；没有这个案件的记录时报错 |
| 按案件 ID 读方案记录 | 这个案件的方案记录；没有交易方案的案件没有 |
| 按案件 ID 读发现 | 这个案件的发现，按写入的顺序；没有时为空 |
| 一只股票最近结束的案件 | 股票是这只股票、状态是已结束的案件，按结束时刻从晚到早，最多给定的个数；进行中和不再运行的不算 |
| 最近一次得出结论的案件 | 给定案件类型（针对一只股票的类型再给定股票），有结论的案件里结论时刻最晚的一个，进行中的也算；没有时没有 |

读取不写任何东西。

#### Scenario: 按案件 ID 读

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论；写审核（通过）；20:10Z 开始 K-3；20:30Z 写 K-3 的结论；K-2 写了三项发现

- **THEN** 案件记录是进行中、带 K-1 的结论；方案记录是方案 P-1 和一次审核；发现为空
- **WHEN** 按案件 ID 读 K-3
- **THEN** 没有方案记录
- **WHEN** 按案件 ID 读 K-2 的发现
- **THEN** 依次是 DDD、EEE、AAA 三项
- **WHEN** 按案件 ID 读 K-9 的案件记录，K-9 没有写过
- **THEN** 报错

#### Scenario: 一只股票最近结束的案件

- **GIVEN** CCC 的案件：15:00Z 开始 K-5、15:30Z K-5 结束（人工拒绝，2，6）；16:00Z 开始 K-6、16:03Z K-6 结束（复盘完成，0，1）；20:10Z 开始 K-3、20:12Z K-3 结束（系统故障，0，2）；20:15Z 写 CCC 的跟进 K-11 不再运行；20:20Z 开始 CCC 的持仓跟进 K-10，还在进行

- **WHEN** 读 CCC 最近结束的案件，最多 5 个

### Requirement: 案件记录的存储

案件记录 SHALL 存在状态库所在的数据库里，只由案件记录模块写入（state-store spec「表的归属和迁移」）：

- 案件表 `caserecords_cases`、方案表 `caserecords_proposals`：按案件 ID 只追加版本（state-store spec「只追加的版本记录」），记录有变化时写入一个新版本，读取时取最新版本
- 发现表 `caserecords_findings`：一项发现一行，只追加，写入以后 MUST NOT 被修改或删除
- 读回的记录 SHALL 和写入的完全相同：结论的种类和每一项（信号的置信度、目标价、条件的值的每一位小数，论点的日期）、模型和是不是备用模型、方案的条款、审核和回应的每一条文字、风控结果的股数、紧急阈值和有效期、不通过的规则；各个时刻存为带时区的时刻，读回的是同一时刻，和数据库服务器、本机的时区都无关
- 用同一个数据库新建案件记录时（相当于进程重启），SHALL 读到之前写入的全部记录，之后的写入接着前面的写
- 读写出错（数据库连不上、表不存在、存着的记录读不出来）时 SHALL 报错：MUST NOT 当作没有这个案件的记录、没有结束的案件或者没有得出结论的案件，也 MUST NOT 当作已经写入

#### Scenario: 原样读回

- **GIVEN** 进程的本机时区是 UTC+14；K-3 结论的信号置信度改为 0.65、论点更新的目标价改为 60.125；AAA 的候选评估 K-7 的结论决定移出

- **THEN** 读到的和写入的相同：K-3 的置信度 0.65、目标价 60.125、复查日 2026-10-28，模型 p-2、是备用模型；K-1 的开始时刻 2026-10-14 15:00Z，紧急阈值 0.075，有效期 2026-10-15 20:00Z
- **AND** K-7 的结论仍是候选的结论（决定移出），K-1 的结论仍是关注的结论（决定开仓方案）

#### Scenario: 重启以后接着写

- **GIVEN** 15:00Z 开始 K-1；15:20Z 写 K-1 的结论；写审核（质询）
- **WHEN** 用同一个数据库新建案件记录，写回应（维持）、审核（通过）、风控结果（通过，股数 100），15:40Z K-1 结束（订单已提交，3，9）

#### Scenario: 读写出错

- **GIVEN** 数据库连不上
- **WHEN** 开始 K-1；按案件 ID 读 K-1；读 CCC 最近结束的案件
- **THEN** 都报错
- **GIVEN** 空数据库，没有升级
- **WHEN** 读寻股最近一次得出结论的案件；写 K-4 不再运行
- **THEN** 都报错，不当作没有得出结论的寻股，也不当作已经写入
- **GIVEN** 15:00Z 开始 K-1；存着的 K-1 的记录缺了触发时刻

- **THEN** 都报错，不当作没有 K-1 的记录
