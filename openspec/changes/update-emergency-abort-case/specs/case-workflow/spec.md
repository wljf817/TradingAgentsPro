# Spec Delta

## ADDED Requirements

### Requirement: 紧急退出中止

一只股票开始紧急退出时，紧急退出流程按案件 ID 把中止交给这只股票正在运行的、复盘以外的案件（emergency-exit-flow spec「中止这只股票的案件」）。案件工作流 SHALL 在下表的时候收中止，收到就按 case-stages spec「方案被作废和紧急退出中止」结束：紧急退出中止：

| 什么时候收 | 收到以后 |
| --- | --- |
| 每次调用 PM（研究或回应）、Critic 以前 | 不再调用 |
| 每次派发任务以前：PM 的派发；Critic 的补充研究在生成新的一版快照以前 | 不派发，不生成新的一版快照 |
| 交给下单以前（「交给下单」） | 不交给下单那一侧：不检查风控、不预留、不请求确认 |
| 等下单那一侧送回结果时（「交给下单」） | 把方案交回下单那一侧作废（order-flow spec「案件中止时作废它的方案」） |

- 正在进行的一次调用、正在运行的任务 SHALL NOT 打断：交回以后照常处理（任务的 Result 照常记下，PM 的结论照常检查、生效），到上表的下一个时候结束。这期间案件已经按别的原因结束的（比如结论没有交易方案），中止不再处理（case-stages spec「已结束的案件和不适用的事件」）
- 有没有结论照 case-stages spec「结束原因」：唤醒 PM 时中止的没有结论，其余有
- 结束照「案件结束」：案件记录写结束原因紧急退出中止；程序日志的案件阶段变化写明紧急退出中止和有没有结论
- 复盘案件不会被中止（case-queue spec「紧急退出」），复盘时不收
- 进程重启以后，重启以前交来、还没收的中止照样在上表的时候收到（「崩溃恢复」）

本要求的场景使用「开始运行一个案件」的基准数据；"K-3 收到中止"指紧急退出流程把中止交给 K-3；"K-3 的减仓方案"指 K-3 的持仓的结论：减仓 60 股，市价单，方案 ID P-1。

#### Scenario: 调用 PM 时中止

- **GIVEN** K-3 开始运行，PM 的第一次调用还没交回
- **WHEN** K-3 收到中止；PM 交回派发新闻请求
- **THEN** 没有派发，没有 T-1；K-3 结束：紧急退出中止，没有结论
- **AND** K-3 的案件记录的结束原因是紧急退出中止
- **AND** 程序日志有 K-3 的唤醒 agent（PM、派发 1 个任务），之后有案件阶段变化：唤醒 PM → 已结束（紧急退出中止，没有结论）

#### Scenario: 任务运行时中止

- **GIVEN** K-3 的 PM 派发了新闻请求，T-1 在运行
- **WHEN** K-3 收到中止；T-1 完成
- **THEN** T-1 有完成的 Result；没有再调用 PM；K-3 结束：紧急退出中止，没有结论

#### Scenario: 结论生效以后中止

- **GIVEN** K-3 开始运行，PM 的调用还没交回
- **WHEN** K-3 收到中止；PM 提交 K-3 的减仓方案，通过
- **THEN** 案件记录有 K-3 的结论和方案记录 P-1；没有调用 Critic
- **AND** K-3 结束：紧急退出中止，有结论；P-1 没有交给下单那一侧

#### Scenario: Critic 审核时中止

- **GIVEN** K-3 的减仓方案在 Critic 审核，Critic 的调用还没交回
- **WHEN** K-3 收到中止；Critic 派发新闻请求
- **THEN** 没有生成 K-3 的第 2 版快照，没有派发；K-3 结束：紧急退出中止，有结论

#### Scenario: 交给下单以前中止

- **GIVEN** K-3 的减仓方案在 Critic 审核，Critic 的调用还没交回
- **WHEN** K-3 收到中止；Critic 通过
- **THEN** K-3 进入风控以后结束：紧急退出中止，有结论
- **AND** P-1 没有交给下单那一侧，案件记录没有风控结果

#### Scenario: 等下单那一侧时中止

- **GIVEN** K-3 的减仓方案 P-1 在等人工确认；另一种情况下 P-1 已确认，在等下单
- **WHEN** K-3 收到中止
- **THEN** 都结束：紧急退出中止，有结论；P-1 交回下单那一侧作废

#### Scenario: 中止以前已经结束

- **GIVEN** K-3 开始运行，PM 的调用还没交回
- **WHEN** K-3 收到中止；PM 提交持仓的结论：持有，通过
- **THEN** K-3 结束：没有交易方案，有结论
- **GIVEN** 另一种情况下 K-3 已经结束：订单已提交
- **WHEN** K-3 收到中止
- **THEN** K-3 仍是订单已提交

#### Scenario: 中止以后重启

- **GIVEN** K-3 的 PM 的第一次调用还没交回时 K-3 收到中止，之后进程退出
- **WHEN** 进程重启，PM 交回派发新闻请求
- **THEN** 没有派发；K-3 结束：紧急退出中止，没有结论

## MODIFIED Requirements

### Requirement: 案件的进展

案件工作流 SHALL 在案件开始和案件状态每次变化以后发布这个案件的进展。调用方读运行中的案件最新的进展：「排队运行」组出队列的快照（case-queue spec「队列的输入和决定」），紧急退出流程组出紧急退出的决定要的运行中的案件和方案（emergency-exit-flow spec「中止这只股票的案件」）：

| 项 | 内容 |
| --- | --- |
| 案件类型 | 开始时确定的案件类型 |
| 股票 | 寻股和每周复盘没有 |
| 案件状态 | case-stages spec「案件的状态」；由它推出是否还在调用模型的阶段和方案的阶段 |
| 现在的方案 | 方案 ID、股票、动作和条款；PM 修改过的条款已经代入；没有方案时没有 |

- 案件已经结束、没有这个案件、或者案件的运行出错停下时，SHALL 没有进展：它不是运行中的案件
- 进展只给调用方读，调用方 SHALL NOT 用它推进案件

#### Scenario: 开仓案件的进展

- **GIVEN** K-1 开始运行
- **WHEN** PM 提交 K-1 的开仓结论并通过；Critic 通过；下单那一侧给出风控通过、要人工确认；送回已确认
- **THEN** K-1 的进展依次是：唤醒 PM、在调用模型、没有方案；Critic 审核、在调用模型、方案 P-1 在审核；风控、不在调用模型、P-1 在审核；等人工确认、P-1 在等人工确认；等下单、P-1 在等下单
- **WHEN** 接着送回订单已提交
- **THEN** K-1 没有进展

#### Scenario: 没有方案的案件

- **GIVEN** K-6 开始运行
- **WHEN** PM 提交候选的结论：保持，通过
- **THEN** K-6 先后的进展是唤醒 PM、没有方案；之后没有进展

#### Scenario: 没有开始的案件

- **WHEN** 读 K-9 的进展，K-9 没有开始运行过
- **THEN** 没有进展

### Requirement: 交给下单

方案进入风控阶段时，案件工作流 SHALL 先收一次中止（见「紧急退出中止」），没有收到才把案件 ID、现在的方案和 Critic 审核的结果交给下单那一侧，它给出风控结果（risk-rules spec「风控的输入和判定」）和要不要人工确认（confirmation-rules spec「案件方案的确认」），或者风控检查出错。风控结果写进案件记录，案件状态按下表转换（case-stages spec「风控」）：

| 下单那一侧给出 | 案件状态 |
| --- | --- |
| 风控通过或调整，要人工确认 | 进入等人工确认 |
| 风控通过或调整，不要人工确认 | 进入等下单 |
| 风控拒绝 | 结束：风控拒绝 |
| 风控检查出错 | 结束：系统故障 |

之后案件工作流 SHALL 等下单那一侧按案件 ID 送回结果，每收到一个按下表转换，直到案件结束：

| 送回的结果 | 适用的阶段 | 案件状态 |
| --- | --- | --- |
| 已确认 | 等人工确认 | 进入等下单 |
| 已拒绝 | 等人工确认 | 结束：人工拒绝 |
| 已超时（包括确认请求发不出去） | 等人工确认 | 结束：确认超时 |
| 订单已提交 | 等下单 | 结束：订单已提交 |
| 再校验作废 | 等下单 | 结束：再校验作废 |
| 方案被作废（order-flow spec「作废案件的方案」） | 等人工确认、等下单 | 结束：方案被作废 |
| 出错 | 等人工确认、等下单 | 结束：系统故障 |

- 等的时候也收中止：收到时结束：紧急退出中止，并把方案交回下单那一侧作废（「紧急退出中止」）；中止和送回的结果按收到的先后处理
- 等待的时候不调用模型，案件工作流不设等待的时限：确认超时和方案的有效期由下单那一侧处理
- 送回的结果不适用于当前阶段时 SHALL 报错，案件的运行出错停下
- 释放预留由下单那一侧负责（case-stages spec「结束原因」的"要释放预留"）

#### Scenario: 风控通过、确认、下单

- **GIVEN** K-1 的方案 P-1 Critic 通过，进入风控
- **WHEN** 下单那一侧给出风控通过、要人工确认；送回已确认；送回订单已提交
- **THEN** 下单那一侧收到 K-1、P-1 和 Critic 审核的结果通过
- **AND** 案件记录写了风控结果；K-1 依次是等人工确认、等下单、结束：订单已提交

#### Scenario: 风控调整

- **WHEN** 下单那一侧给出风控调整（股数从 100 调为 40），要人工确认
- **THEN** 进入等人工确认，案件记录的风控结果是调整

#### Scenario: 不要人工确认的退出方案

- **GIVEN** K-3 的减仓方案 Critic 通过，进入风控
- **WHEN** 下单那一侧给出风控通过、不要人工确认；送回订单已提交
- **THEN** K-3 依次是等下单、结束：订单已提交；没有经过等人工确认

#### Scenario: 风控拒绝和出错

- **WHEN** 下单那一侧给出风控拒绝
- **THEN** 结束：风控拒绝，有结论
- **WHEN** 下单那一侧给出风控检查出错（读不到券商账户）
- **THEN** 结束：系统故障，有结论；案件记录没有风控结果

#### Scenario: 人工拒绝和确认超时

- **GIVEN** K-1 在等人工确认
- **WHEN** 送回已拒绝
- **THEN** 结束：人工拒绝
- **WHEN** 同样的情况下送回已超时
- **THEN** 结束：确认超时

#### Scenario: 再校验作废和出错

- **GIVEN** K-1 在等下单
- **WHEN** 送回再校验作废
- **THEN** 结束：再校验作废
- **WHEN** 同样的情况下送回出错
- **THEN** 结束：系统故障，有结论

#### Scenario: 方案被作废

- **GIVEN** K-1 在等人工确认
- **WHEN** 送回方案被作废
- **THEN** 结束：方案被作废，有结论
- **GIVEN** K-1 已确认，在等下单
- **WHEN** 送回方案被作废
- **THEN** 结束：方案被作废

#### Scenario: 等的时候收到中止

- **GIVEN** K-1 在等人工确认
- **WHEN** 送回已确认，之后 K-1 收到中止
- **THEN** K-1 依次是等下单、结束：紧急退出中止，有结论；P-1 交回下单那一侧作废
- **WHEN** 另一种情况下 K-1 收到中止以后，下单那一侧才送回已确认
- **THEN** K-1 结束：紧急退出中止，之后送回的已确认不改变它

#### Scenario: 盘后确认等到开盘

- **GIVEN** K-3 的减仓方案 2026-10-14 21:00Z 送回已确认，在等下单
- **WHEN** 到 2026-10-15 13:30Z 开盘以前都没有送回结果
- **THEN** K-3 仍在等下单，不调用模型
- **WHEN** 开盘以后送回订单已提交
- **THEN** 结束：订单已提交

#### Scenario: 不适用的结果

- **GIVEN** K-1 在等人工确认
- **WHEN** 送回订单已提交
- **THEN** 报错，K-1 的运行出错停下，没有进展
