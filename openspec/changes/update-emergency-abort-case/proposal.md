# Proposal

## Why

紧急退出流程现在只管券商这一侧：撤单、释放这只股票还没下单的方案的预留、清仓。这只股票正在运行的案件照样跑下去：PM 和 Critic 照常调用模型，方案照常交给下单、请求人工确认；被释放了预留的案件方案还挂着确认消息，要等到人按了按钮、再校验得到"方案已结束"，或者到截止时刻才结束。「排队运行」接上以后案件会真的运行，这个缺口就会出现。

本变更的目的只有一个：**一只股票开始紧急退出时，中止它正在运行的、复盘以外的案件，案件已经交给下单的方案随之作废。**

引用的 Proposal（完整版）章节：

- 「运行约束」的「排队规则」：每只股票一次一个案件，运行中不打断，紧急风险事件除外
- 「持仓与退出」的退出路径表：紧急风险退出"分钟级，可中止进行中的案件"；要人工确认时"每只股票的撤单和清仓等确认以后再做"（见「需要人决定」第 1 条）
- 「故障处理」的「紧急风险事件例外」：不排队，可中止同一股票正在运行的案件；同时作废这只股票还没提交订单的方案（开仓类和退出类）并释放预留；复盘案件不中止，这只股票排队的案件不动，等清仓卖单结束后按新的状态运行
- 「记录、复盘与经验」的程序日志表和案件记录：案件阶段变化、结束原因

已经定了的（不在本变更里讨论）：紧急退出的决定（case-queue spec「紧急退出」）和中止的结束原因（case-stages spec「方案被作废和紧急退出中止」）；排队运行的 `running_cases`、下单流程收作废的 `void_plan`、正在紧急退出的股票 `exiting()`（add-queue-runner 的 design D5、D6、D9）。本变更建在「排队运行」之上，在它归档以后实现。

## What Changes

- 紧急退出流程（emergency-exit-flow）：
  - 一只股票开始紧急退出时（推送开始紧急退出的告警的那一次处理，要确认的在确认以后），写完程序日志的紧急风险退出、拿锁以前，读运行中的案件，取得这只股票的紧急退出的决定，把中止按案件 ID 交给决定里的案件
  - 释放还没下单的方案的预留照旧在锁里、撤单和清仓以前做；案件的方案由中止的案件交回下单流程作废，`/plan` 的方案照旧（见「需要人决定」第 3 条）
  - 开始紧急退出的告警加上中止的案件（案件类型、案件 ID）
  - 在等紧急退出的确认、确认被拒绝或超时的股票不中止；等撤单的之后几轮不再中止
- 案件工作流（case-workflow）：
  - 收中止：每次调用 PM、Critic 以前，每次派发任务以前，交给下单以前，各收一次；等下单那一侧送回结果时也收。收到就按 case-stages spec 结束：紧急退出中止
  - 正在进行的一次调用、正在运行的任务不打断，交回以后照常处理，到下一个收中止的地方结束（见「需要人决定」第 2 条）
  - 在等人工确认、等下单时被中止：把方案交回下单那一侧作废
  - 案件记录写结束原因，程序日志写案件阶段变化，都照原来的「案件结束」
- 下单流程（order-flow）：
  - 新增「案件中止时作废它的方案」：按「作废案件的方案」的表处理，释放预留的原因写这只股票的紧急退出（预留通常已经被紧急退出释放，这时什么也不改）；已经确认的也不告警；不送回案件
  - 「结果送回案件」加上这一种不送回的情况
- 排队的案件不动：add-queue-runner 的 D9 已经让排队运行不启动正在紧急退出的股票的案件；清仓卖单结束的那一轮巡检里股票池先跟上持仓，紧急退出才结束，之后的一轮按新的状态确定类型。本变更不改排队运行的行为
- 完整版 Proposal「持仓与退出」退出路径表的紧急风险退出一行：要人工确认时等确认以后再做的事加上中止案件（见「需要人决定」第 1 条）

## Non-goals

- 排队运行本身：排队、启动、作废、正在紧急退出的股票（add-queue-runner）
- 紧急退出的触发和判定、清仓的步骤：不改；触发源（「触发」组）
- 复盘案件：不中止；M6 的复盘不在这里
- `/plan` 录入的方案：照旧由紧急退出释放预留、下单流程之后再校验时作废（见「需要人决定」第 3 条）
- 打断正在进行的模型调用或子 agent 任务
- 紧急退出流程自己写中止案件的程序日志条目：中止由开始紧急退出的告警（通知模块写进程序日志）和案件的阶段变化记下
- 不动 add-queue-runner、add-moomoo-quotes 两个变更目录
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

无

### Modified Capabilities

- `emergency-exit-flow`：新增「中止这只股票的案件」；修改「一只股票的清仓」（开始紧急退出时先中止案件，第 2 步案件的方案怎样作废）、「告警」（开始紧急退出的告警写中止的案件）
- `case-workflow`：新增「紧急退出中止」；修改「案件的进展」（紧急退出流程也读）、「交给下单」（送回结果时收中止，交回方案）
- `order-flow`：新增「案件中止时作废它的方案」；修改「结果送回案件」（案件中止交回的方案不送回）

## Impact

- **代码**：
  - `workflows/emergency_flow.py`：运行中的案件的端口（`RunningCases`），开始紧急退出时取得决定、交出中止，告警的文字
  - `workflows/case_workflow.py`：`PlanEvent.ABORTED` 的转换，各处收中止，被中止时交回方案，`abort_case`，运行中的案件换成队列的类型的 `queue_view`
  - `workflows/plan_handoff.py`：`PlanEvent.ABORTED`，`PlanHandoff.abandon`
  - `workflows/order_workflow.py`、`order_flow.py`：作废带原因（`VoidCause`），案件中止的作废不告警、不送回；`CasePlanHandoff.abandon`
  - `workflows/queue_runner.py`：`DbosCases.abort`，作废写明原因，`run_round` 用 `queue_view`
  - `modules/scheduler/domain/queue.py`：`emergency_decision` 只收运行中的案件和方案（design D6）
  - `bootstrap/app.py`：`DbosCases` 交给紧急退出流程
  - contracts、shared、别的模块不改；没有迁移
- **测试**（只在本地）：`tests/modules/scheduler/domain/`（`emergency_decision` 的参数）、`tests/workflows/`（紧急退出、案件工作流、下单工作流、排队运行）、`tests/bootstrap/`；`tests/fakes/cases.py` 记下中止
- **部署**：案件工作流和下单流程的步骤变了：部署前确认 `dbos.workflow_status` 里没有 PENDING 的 `case` 和 `order_plan`
- **文档**：完整版 Proposal「持仓与退出」退出路径表的紧急风险退出一行（简版不改）

## 需要人决定

1. **要人工确认时，什么时候中止案件**：Proposal 只说要确认时"每只股票的撤单和清仓等确认以后再做"，没说中止案件。
   推荐：确认以后再中止，和作废方案、撤单同一刻；在等确认、被拒绝或超时的不中止，案件照常运行。理由：等确认期间什么都不动是现有的规则，人拒绝了紧急退出时，正在分析这只股票的案件不该白白被中止；排队运行把正在紧急退出的股票也从确认以后算（add-queue-runner D9）。完整版 Proposal 退出路径表那一格已经照这个改为"每只股票的中止案件、撤单和清仓等确认以后再做"
2. **中止送到时案件正在调用模型（一次调用要几秒到几分钟）**：
   推荐：不打断，交回以后照常处理（比如 PM 的结论照常检查、生效），到下一次调用、派发、交给下单以前结束；方案不会交给下单。理由：一次调用是 DBOS 的一步，打断不了，费用已经花了；被中止的都是这只股票的持仓案件，结论生效只是记下结论和更新论点，不会下单
3. **`/plan` 录入的方案**：现在紧急退出释放它的预留，下单流程照常等确认，人按了确认以后再校验得到"方案已结束"作废并告警，或者到截止时刻超时；确认消息上的按钮留到那时。
   推荐：本变更不动。理由：它已经不会下单；`/plan` 现在只用来手工清理持仓，和紧急退出同时出现很少。要改也简单：紧急退出把它释放的 `/plan` 方案也交给它的下单流程作废
