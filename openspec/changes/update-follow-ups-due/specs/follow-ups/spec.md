# Spec Delta

## MODIFIED Requirements

### Requirement: 到点触发

调用方 SHALL 定时做到点触发，并给出把一个跟进排进案件的方式（queue-runner spec「一轮」）。到点触发取出触发时间不晚于现在的待执行跟进，按触发时间从早到晚、触发时间相同的按获批的先后，逐个先交给调用方排进一个案件，排进以后再把它记为已触发：

- 排进的案件的触发是 case-types spec「触发」里的跟进的触发：股票、跟进 ID、申请时写下的问题；触发时刻是这个跟进的触发时间
- 排进出错时 SHALL 把错误原样抛出：出错的这一个和它后面的跟进仍是待执行，下一次到点触发照样排进；前面已经排进的已触发
- 错过的话，下一次照样排进所有已经到点的跟进，不判断是不是太晚
- 到点触发 SHALL NOT 看股票状态、降级模式和调用预算：股票状态往下走的跟进已经作废；降级或预算用完时，开出的案件留在队列里（case-queue spec「降级模式」「调用预算」）；案件开始运行时按那时的状态确定类型（case-types spec「开始运行时确定案件类型」）
- 同一只股票同时到点的几个跟进各开一个案件，由队列依次运行（case-queue spec「同一只股票一次一个案件」）

#### Scenario: 到点的边界

- **GIVEN** CCC 申请事件申请（F-1）
- **WHEN** 当前时刻 2026-10-14 17:59:59Z，到点触发
- **THEN** 没有排进案件，F-1 仍是待执行
- **WHEN** 当前时刻 2026-10-14 18:00Z，到点触发
- **THEN** 排进一个案件：触发是 CCC 的跟进 F-1，问题"大单公布 3 小时后盘中反应如何？"，触发时刻 2026-10-14 18:00Z；F-1 已触发，CCC 没有待执行的跟进

#### Scenario: 错过以后一起给出

- **GIVEN** CCC 申请日程申请（F-1），再申请事件申请（F-2）；BBB 申请观察申请（F-3）
- **WHEN** 当前时刻 2026-11-20 15:00Z，第一次到点触发
- **THEN** 依次排进 F-2（触发时刻 10-14 18:00Z）、F-3（10-21 20:00Z）、F-1（11-19 14:30Z），三个都已触发

#### Scenario: 触发时间相同按获批的先后

- **GIVEN** CCC 申请事件申请（F-1）；当前时刻 2026-10-14 16:00Z，BBB 申请事件申请（F-2）
- **WHEN** 当前时刻 2026-10-14 18:00Z，到点触发
- **THEN** 依次排进 F-1、F-2

#### Scenario: 先排进再记为已触发

- **GIVEN** CCC 申请事件申请（F-1）
- **WHEN** 当前时刻 2026-10-14 18:00Z，到点触发，排进 F-1 的时候读 F-1 的状态
- **THEN** 读到的 F-1 仍是待执行；到点触发做完以后 F-1 已触发

#### Scenario: 排进出错

- **GIVEN** CCC 申请日程申请（F-1），再申请事件申请（F-2）；BBB 申请观察申请（F-3）；排进 F-3 时会出错一次
- **WHEN** 当前时刻 2026-11-20 15:00Z，到点触发
- **THEN** 报错；F-2 已排进、已触发，F-3 和 F-1 仍是待执行
- **WHEN** 再到点触发
- **THEN** 依次排进 F-3、F-1，两个都已触发；F-2 没有再排进

#### Scenario: 关注时申请、买入以后照常触发

- **GIVEN** BBB 申请观察申请（F-1），之后 BBB 买入成交变为持仓
- **WHEN** 当前时刻 2026-10-21 20:00Z，到点触发
- **THEN** 排进 F-1：股票 BBB，问题"站上 55 以后能不能守住？"；开出的案件按持仓跟进运行（case-types spec「开始运行时确定案件类型」）

### Requirement: 同时进行的调用

审批、取得待执行的跟进、读取一个跟进、到点触发和状态变化 SHALL 一次只进行一个：一个在进行时，别的等它做完再开始，不论调用方是哪个案件、定时任务还是股票池的变化。所以同时进行的几个调用，结果和它们按某个先后依次进行时相同：每只股票待执行的跟进、每天获批的申请都不超过上限，每个跟进的状态只变化一次。

- 只管一个进程之内：程序只有一个进程
- 这几个调用只读写跟进的记录、写程序日志；到点触发另外交给调用方排进案件，排进只写排队的案件和程序日志，不等别的调用。所以不会和别的模块互相等待

本要求的场景使用「跟进的记录」的基准数据。

#### Scenario: 两个审批同时进行

- **GIVEN** 每天的申请次数上限配置为 1
- **WHEN** CCC 申请日程申请，同时 BBB 申请观察申请
- **THEN** 一个获批，另一个被拒绝，原因是"申请次数已用完"
- **AND** 只有一个待执行的跟进

#### Scenario: 审批和到点触发同时进行

- **GIVEN** CCC 申请事件申请（F-1）；当前时刻 2026-10-14 18:00Z
- **WHEN** CCC 申请事件申请，触发时间改为 2026-10-15 15:00Z，同时到点触发
- **THEN** 结果是两者先后进行的某一种：到点触发在前的，排进 F-1、F-1 已触发，新申请获批为 F-2、F-1 没有被替换；审批在前的，新申请获批为 F-2、F-1 被替换，到点触发不排进案件
- **AND** F-1 的状态只变化了一次

## ADDED Requirements

### Requirement: 读取一个跟进

跟进审批 SHALL 按跟进 ID 给出这个跟进现在的记录（见「跟进的记录」），不论它是什么状态；调用方用它组出跟进案件的上下文（case-workflow spec「案件上下文」）。

- 没有这个跟进 ID 时 SHALL 报错，不当作没有跟进
- 读出错时按「跟进的存储」报错
- 读取不写程序日志

本要求的场景使用「跟进的记录」的基准数据。

#### Scenario: 读出已触发的跟进

- **GIVEN** CCC 申请事件申请（F-1）；当前时刻 2026-10-14 18:00Z 到点触发
- **WHEN** 读取 F-1
- **THEN** 得到 F-1：股票 CCC，申请就是事件申请，来源案件 K-1，获批时刻 2026-10-14 15:00Z，已触发

#### Scenario: 读取一个不存在的跟进

- **WHEN** 读取一个没有获批过的跟进 ID
- **THEN** 报错
