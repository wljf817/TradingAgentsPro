# Proposal

## Why

跟进审批 M3 就写好了，案件工作流也会保存 PM 申请的跟进，但没有任何代码定时去取到点的跟进：跟进批下来以后永远不会触发。三种驱动里只剩它还没接上。另外，完整版要求跟进案件的上下文带上原案件的结论和申请原因，现在的案件上下文只有申请时写下的问题。这个变更让获批的跟进到点时开出跟进案件，并且 PM 能看到这个跟进的来历。

## What Changes

- 排队运行的每一轮先做到点触发，再组快照：触发时间不晚于现在的待执行跟进，按触发时间、再按获批的先后，逐个排进一个案件，触发时刻是跟进的触发时间；同一轮就能启动它们。跟进最多晚一个排队运行的间隔（默认 5 秒）触发
- 到点触发改为每个跟进先排进案件、再记为已触发，都在跟进审批的锁里：排进出错时这一个和后面的跟进仍是待执行，下一轮照样排进，不会丢
- 跟进的触发多带一项跟进 ID；跟进审批加「读取一个跟进」，按跟进 ID 读出，不论状态
- 跟进案件的案件上下文多一项「跟进」：这个跟进的申请（原因类型、引用的对象、问题、可能采取的动作、触发时间）和提出申请的案件的结论
- 程序日志的「触发跟进」写在这个跟进的排队之后，输出的引用是排进的案件 ID；排队运行的一轮因此可能写排队和触发跟进
- 模拟盘的装配：排队运行另外调用跟进审批

## Capabilities

### New Capabilities

无

### Modified Capabilities

- `follow-ups`：「到点触发」改为先排进、再记为已触发，调用方给出排进的方式；「同时进行的调用」相应改写；加「读取一个跟进」
- `case-types`：「触发」里跟进的触发多带跟进 ID
- `queue-runner`：「一轮」开头加到点触发
- `case-workflow`：「案件上下文」加跟进案件的「跟进」一项
- `agent-calls`：「每个 agent 的输入和输出」的案件上下文表加「跟进」一项
- `program-log`：「调度器的动作」的触发跟进改写时机和引用，排队运行的一轮可以写排队和触发跟进
- `bootstrap`：「模拟盘的装配」的排队运行另外调用跟进审批，加一个到点的跟进开出案件的场景

## 引用的 Proposal 章节

- 完整版「3. 自定义跟进」：跟进只触发一次、到点时降级或预算用完照常入队、跟进案件的目标和案件上下文（原案件的结论和申请原因）
- 完整版「调度器」的排队优先级（持仓的心跳和跟进、关注股的心跳和跟进）和「所有获批的跟进都进入调度器队列」
- 完整版「技术栈与部署」：案件工作流、队列、定时心跳的那一行
- 简版的触发方式表（自定义跟进：PM 在结论中申请，代码审批）

## Non-goals

- 跟进审批的规则（引用的对象、催化剂重复、触发时间、替换、上限、作废）：M3 已经做完，不变
- 跟进案件的结论和校验（不能再申请跟进）：case-types spec 已有，不变
- 跟进触发时的股票状态、降级模式、调用预算检查：完整版规定照常入队，由队列和开始运行时确定类型处理
- 跟进到点的单独线程和单独配置：用排队运行已有的一轮和间隔
- 排进以后、记为已触发以前进程崩溃时的重复：下一轮会再排进一次，见 design 的风险

## 对后续变更的影响

- M4 只剩「论点条件与到价提醒」归档。本变更的 bootstrap delta 的「模拟盘的装配」是在那个变更改过的版本上改的，带着收盘心跳和到价提醒的内容；两个变更不论哪个先归档，这一节都不丢（tasks 1.2）
- M5 接入真的 PM 以后，跟进案件的 prompt 要用上上下文里的「跟进」一项

## 需要人决定

1. 完整版「技术栈与部署」写的是"用持久化休眠实现自定义跟进"。跟进存在状态库里，排队运行每一轮按时间取出到点的，重启以后照样能取到，不需要给每个跟进开一个休眠的工作流。推荐把这一句改成"自定义跟进由调度器每一轮检查到点以后排进队列"。这一条只是写法，我按推荐改了完整版这一句
2. 完整版「3. 自定义跟进」要求跟进案件的上下文带上原案件的结论和申请原因，现有的 case-workflow spec 漏了这一项。这一条照 Proposal 补上，不是新的设计，放在本变更里做
