# Spec Delta

## MODIFIED Requirements

### Requirement: 风控引擎的动作

风控引擎的下面这些动作 SHALL 各写一条，行为者是风控引擎：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 风控检查 | 首次检查得出结果：`/plan` 的提交接口（order-flow spec「提交方案」）；案件的方案交给下单流程（order-flow spec「案件的方案」）；紧急退出检查当天的清仓方案（emergency-exit-flow spec「一只股票的清仓」第 4 步） | 方案 ID | 没有 | 动作和股票；结果（通过、调整、拒绝）和最终股数；每条不通过的规则和它的说明，没有列出的规则都通过；通过或调整时写明按最终股数预留 |
| 下单前再校验 | 再校验得出结果，并且这一次没有转去等重试或等开盘：下单流程再校验以后作废或者提交了订单（order-flow spec「下单前再校验和提交」「提交的结果」）；紧急退出（同上第 4 步） | 方案 ID | 没有 | 结果和最终股数；不通过的规则和说明；通过或调整时写明预留改为最终股数；拒绝时写明方案作废 |
| 释放预留 | 流程释放一个方案剩下的预留，并且这个方案这时有有效预留（risk-reservations spec） | 方案 ID | 没有 | 原因，见下 |

释放预留的原因：

- 下单流程：人工拒绝；确认超时；确认请求没有发出去；到了有效期还没下单（写上最近一次没能下单的原因，有的话）；最近一次对账有不一致；启动下单流程失败；排队运行作废了方案（order-flow spec「作废案件的方案」），写上是哪只股票有新案件排队
- 巡检的同步预留（session-patrol spec「每一轮」第 2 步）：订单进入终态，写上订单的状态和累计成交
- 紧急退出：作废这只股票还没下单的方案，写上是哪只股票的紧急退出；到收盘还没有清仓单

没有有效预留时释放什么也不改，SHALL NOT 写释放预留：比如订单全部成交、预留已经随成交用完，或者方案已经被紧急退出作废。再校验拒绝时预留由再校验释放，写在下单前再校验的说明里，也不另写释放预留。

- **THEN** 程序日志有人的拒绝，没有新的 P1 的释放预留

### Requirement: 调度器的动作

调度器的下面这些动作 SHALL 各写一条，行为者是调度器。现在有跟进审批的动作（follow-ups spec）、生成快照（state-snapshot spec）、案件工作流的动作（case-workflow spec）和排队运行的动作（queue-runner spec）：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 批准跟进 | 跟进申请通过审批，新的跟进保存以后（follow-ups spec「审批的输入和结果」） | 新跟进的 ID | 没有 | 跟进的内容 |
| 拒绝跟进 | 跟进申请没有通过审批（follow-ups spec「审批的顺序」） | 股票 | 没有 | 不通过的原因；申请的内容，写法和跟进的内容相同，没写引用的写明没有引用 |
| 替换跟进 | 批准的跟进替换了这只股票原因相同的待执行跟进（follow-ups spec「原因相同时替换」），写在这次的批准跟进之后 | 被替换的跟进的 ID | 输入：替换它的新跟进的 ID | 被替换的跟进的内容 |
| 作废跟进 | 股票状态往下走，这只股票待执行的跟进作废（follow-ups spec「股票状态往下走时作废」）：每个作废的跟进一条，按作废时给出的顺序 | 跟进 ID | 没有 | 之前和之后的状态，不在股票池也不是持仓的写不在股票池；跟进的内容 |
| 触发跟进 | 到点触发把跟进记为已触发（follow-ups spec「到点触发」）：每个一条，按给出的顺序 | 跟进 ID | 没有 | 跟进的内容 |
| 生成快照 | 一版快照保存以后（state-snapshot spec「每种案件的快照」「新的版本」） | 快照的版本，比如 s1 | 输出：这一版的全部条目 ID，按条目的先后 | 股票，不针对单只股票的写"不针对单只股票"；生成的原因，第 1 版写"案件开始"；条目数 |
| 开案件 | 案件开始运行，案件记录的开始运行写下以后（case-workflow spec「开始运行一个案件」） | 案件 ID | 没有 | 案件类型；股票，不针对单只股票的写"不针对单只股票"；触发原因 |
| 案件阶段变化 | 案件状态的阶段变了（case-stages spec「案件的阶段」）：每次变化一条 | 案件 ID | 没有 | 之前和之后的阶段；有方案时写方案的动作和方案 ID；进入 PM 回应时写明第几轮质询，进入风控时写明 Critic 审核的结果，结束时写明结束原因和有没有结论 |
| 唤醒 agent | 案件工作流调用一次 PM、Critic 或 Reviewer，调用交回以后（case-workflow spec「PM 的研究」「Critic 审核」「PM 回应」「复盘案件」） | 案件 ID | 没有 | 哪个 agent；为什么唤醒：PM 是开始研究、交回任务的结果、退回重交（写明第几次和原因）或者回应第几轮质询，Critic 是第几次审核或者交回补充研究的结果，Reviewer 是复盘；交回了什么：派发几个任务、提交的结论的决定、回应的决定、审核的结论或者复盘报告的总结，调用成功时写实际使用的模型和是不是备用模型，调用失败时写网关给出的说明。耗时是这次调用从开始到交回的时间，费用是这次调用的费用 |
| 排队 | 一个案件排进队列、存下以后（queue-runner spec「排队」） | 案件 ID | 没有 | 触发原因；触发时刻（UTC） |
| 不再运行 | 排队的案件不再运行，案件记录的不再运行写下以后（queue-runner spec「不再运行」） | 案件 ID | 没有 | 触发原因；这只股票现在的状态，不在股票池里的写不在股票池里 |
| 方案作废 | 队列的决定作废一个方案，交给下单流程以前（queue-runner spec「作废方案」） | 方案 ID | 没有 | 动作和股票；写明这只股票有新案件排队 |

跟进的内容：股票、原因类型、引用的对象、触发时间（UTC）、要回答的问题、可能采取的动作。

- 批准、拒绝和替换跟进的案件 ID 是提出申请的案件；作废和触发跟进不属于案件，案件 ID 为空；生成快照的案件 ID 是快照所属的案件；开案件、案件阶段变化、唤醒 agent、排队和不再运行的案件 ID 是这个案件；方案作废的案件 ID 是给出这个方案的案件
- 调度器的动作里只有唤醒 agent 写耗时和费用
- 每个跟进、每版快照保存以后才写它的条目；写条目出错时照「写入失败」处理，已经保存的跟进和快照不撤回
- 取得待执行的跟进、没有跟进到点的到点触发、不作废跟进的状态变化 SHALL NOT 写程序日志；同一版快照再生成、生成快照时数据读不到（state-snapshot spec「同一版再生成」「数据读不到时」）也 SHALL NOT 写
- 阶段没有变的案件状态变化（结论退回 PM 重交）SHALL NOT 写案件阶段变化：退回的原因写在下一次唤醒 PM 的条目里
- 排队运行的一轮 SHALL NOT 另外写条目：只有作废、不再运行各写上表的一条，启动的案件由案件工作流写开案件；没有作废、不再运行和启动的一轮不写

- **AND** 它在 K-1 的案件记录写下不再运行以后

#### Scenario: 方案作废

- **GIVEN** queue-runner spec 的基准数据；运行中 K-1：BBB 的关注股事件，等人工确认，方案 P-1（买入 BBB）；排进 BBB 的新闻事件（14:58Z）
- **WHEN** 做一轮
- **THEN** 程序日志有一条方案作废：对象 P-1，案件 ID K-1，说明写明买入 BBB、BBB 有新案件排队
- **AND** 之后才有 P-1 的结束确认（已作废）和释放预留

### Requirement: 系统的动作

系统的下面这些动作 SHALL 各写一条，行为者是系统：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 启动 | 数据库升级到最新版本以后（bootstrap spec「启动顺序」第 2 步），这次运行的第一条 | `system` | 没有 | 版本号和模式（模拟盘） |
| 停止 | 程序结束运行、关闭数据库连接以前（bootstrap spec「停止」的关闭顺序里 OpenD 行情连接之后）；正常停止和写过启动以后的启动失败都写 | `system` | 没有 | 空 |
| 崩溃恢复 | 写启动以前，程序日志里最近的一条启动或停止是启动：上一次运行没有走到停止 | `system` | 没有 | 上一次启动的时刻 |
| 进入降级模式 | 健康判定从正常变为降级：巡检里（health-monitoring spec「状态变化的告警和日志」）；启动时第一次判定是降级（bootstrap spec「第一次健康判定」） | `system` | 没有 | 进入降级模式的时刻、异常的检查；启动时的写明是启动时 |
| 降级模式里的变化 | 降级时异常的检查变了；降级变为等待对账；等待对账变为降级 | `system` | 没有 | 现在的状态和异常的检查 |
| 退出降级模式 | 恢复后的对账做完，状态回到正常（health-monitoring spec「恢复后的对账」） | `system` | 没有 | 进入降级模式的时刻 |
| 熔断 | 这次运行里每个交易日第一次看到熔断触发，和熔断的告警同时（emergency-exit-flow spec「单日亏损熔断」） | `account` | 没有 | 前一交易日收盘时的权益、当前权益、单日亏损和它的比例、熔断比例 |
| 紧急风险退出 | 一只股票开始紧急退出（emergency-exit-flow spec「告警」的第一行），在这一项作废方案、撤单和提交之前 | 股票 | 输出：当天的清仓方案 ID | 原因，写法和开始紧急退出的告警相同 |
| 自动执行 | 案件的方案不要人工确认（order-flow spec「案件的方案」：模型退出自动执行打开、Critic 通过、不处于降级模式的退出方案），在它的风控检查之后 | 方案 ID | 没有 | 动作和股票；写明按模型退出自动执行，没有经过人工确认 |
| 告警 | 通知模块推送一条告警（discord-notification spec「告警」），发出去和发不出去都写 | 调用方给出的对象：方案 ID、股票、`account` 或 `system` | 没有 | 告警的全文；发不出去时写明没有发出去和原因 |
| 请求确认 | 通知模块请求人工确认，交易方案和紧急退出的都算（discord-notification spec「确认请求和截止时刻」），发出去和发不出去都写 | 方案 ID | 输出：确认消息的标识，发出去才有 | 截止时刻；紧急退出写原因和当前持仓；发不出去时写明没有发出去和原因 |
| 结束确认 | 通知模块报告确认消息的结果为已超时或已作废（discord-notification spec「结束确认」），改成和没改成都写 | 方案 ID | 输入：确认消息的标识 | 报告的结果；没改成时写明原因 |
| 调用预算用完 | 排队运行这次运行里每个交易日第一次看到一个预算用完（queue-runner spec「调用预算用完的日志」） | `system` | 没有 | 预算；交易日；今天的费用和额度；影响 |

- 启动失败发生在写启动以前（读环境变量、连接和升级数据库），程序日志里没有这次运行的条目
- 每个告警的对象由推送它的流程给出：下单流程是方案 ID；无保护仓位和紧急退出是股票，熔断是 `account`；收盘对账和启动对账是 `account`；降级模式是 `system`

#### Scenario: 正常启动

- **GIVEN** bootstrap spec 的基准数据
- **WHEN** 正常启动
- **THEN** 程序日志的第一条是启动，对象 `system`，说明写明版本号和模拟盘
- **AND** 没有崩溃恢复

#### Scenario: 正常停止

- **GIVEN** 正常启动
- **WHEN** 收到 SIGTERM
- **THEN** 程序日志的最后一条是停止，在盘中巡检、DBOS、Discord、OpenD 行情连接都关闭以后写

#### Scenario: 启动失败也写停止

- **GIVEN** bootstrap spec 的基准数据；Discord 登录失败
- **WHEN** 运行 `tradingagentspro run`
- **THEN** 启动失败；程序日志依次有启动、启动对账的对账和停止

#### Scenario: 读环境变量失败时不写

- **GIVEN** 没有 `APCA_API_SECRET_KEY`
- **WHEN** 运行 `tradingagentspro run`
- **THEN** 启动失败；程序日志没有新条目

#### Scenario: 上一次运行崩溃

- **GIVEN** 上一次运行 2026-10-14T13:00:00Z 写了启动，之后进程被杀，没有写停止
- **WHEN** 2026-10-14T14:00:00Z 正常启动
- **THEN** 程序日志先有一条崩溃恢复，说明写明上一次启动的时刻 2026-10-14 13:00:00 UTC，再有这次的启动

#### Scenario: 上一次正常停止

- **GIVEN** 上一次运行写了启动和停止
- **WHEN** 正常启动
- **THEN** 没有崩溃恢复

#### Scenario: 巡检里进入降级模式

- **GIVEN** health-monitoring spec 的基准数据
- **WHEN** 券商断开，15:00Z 做一轮
- **THEN** 程序日志有一条进入降级模式，说明写明 2026-10-14 15:00 UTC、券商连接

#### Scenario: 启动时处于降级模式

- **GIVEN** bootstrap spec 的基准数据；取行情时 OpenD 报错
- **WHEN** 正常启动
- **THEN** 程序日志有一条进入降级模式，说明写明启动时、数据延迟

#### Scenario: 降级模式里的变化

- **GIVEN** health-monitoring spec 的基准数据；券商断开，15:00Z 做一轮，进入降级
- **WHEN** 券商恢复，之后一轮
- **THEN** 程序日志有一条降级模式里的变化，说明写明各项检查已恢复，下一轮和券商对账

#### Scenario: 退出降级模式

- **GIVEN** health-monitoring spec 的基准数据；券商断开，15:00:00Z 做一轮；券商恢复，15:00:15Z 做一轮
- **WHEN** 15:00:30Z 做一轮
- **THEN** 程序日志依次有恢复后的对账（没有不一致）、退出降级模式（进入时刻 2026-10-14 15:00 UTC）和降级模式结束的告警

#### Scenario: 熔断

- **GIVEN** emergency-exit-flow spec 的基准数据；当前权益 9,300
- **WHEN** 做一轮
- **THEN** 程序日志有一条熔断，对象 `account`，说明写明 10,000、9,300、700（7.0%）、熔断比例 7.0%
- **WHEN** 之后一轮
- **THEN** 没有新的熔断

#### Scenario: 紧急风险退出

- **GIVEN** emergency-exit-flow spec 的基准数据；AAA 最新价 92
- **WHEN** 做一轮
- **THEN** 程序日志有一条紧急风险退出，对象 AAA，说明写明个股跌幅 8.0%、参考价 100、最新价 92、紧急阈值 8.0%，输出的引用是 AAA 当天的清仓方案 ID
- **AND** 它在 AAA 的清仓方案的风控检查之前，之后有开始紧急退出的告警

#### Scenario: 自动执行

- **GIVEN** order-flow spec「案件的方案」的数据；模型退出自动执行打开
- **WHEN** K3 交来 P3
- **THEN** P3 的风控检查之后有一条自动执行，对象 P3，说明写明清仓 AAA、按模型退出自动执行、没有经过人工确认
- **WHEN** 改为 Critic 审核的结果是有分歧
- **THEN** 没有自动执行，有 P3 的请求确认

#### Scenario: 告警

- **GIVEN** order-flow spec 的基准数据；当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认
- **WHEN** 2026-10-15 13:30Z，BBB 最新价 53
- **THEN** 程序日志有一条告警，对象 P1，说明是方案作废的告警全文

#### Scenario: 告警发不出去

- **GIVEN** health-monitoring spec 的基准数据；Discord 报错
- **WHEN** 券商断开，15:00Z 做一轮
- **THEN** 程序日志有一条告警，对象 `system`，说明是进入降级模式的告警全文，并写明没有发出去和原因
- **AND** 另有一条错误日志（discord-notification spec「告警」）

#### Scenario: 请求确认

- **GIVEN** order-flow spec 的基准数据
- **WHEN** 提交 P1
- **THEN** 程序日志有一条请求确认，对象 P1，说明写明截止时刻 2026-10-14 15:30 UTC，输出的引用是确认消息的标识

#### Scenario: 确认请求发不出去

- **GIVEN** order-flow spec 的基准数据；Discord 对发消息报错
- **WHEN** 提交 P1
- **THEN** 程序日志依次有请求确认（说明写明没有发出去和原因，没有输出的引用）和释放预留（原因是确认请求没有发出去）
- **AND** 没有人的超时

#### Scenario: 结束确认

- **GIVEN** order-flow spec 的基准数据；已经提交 P1，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 程序日志依次有人的超时、结束确认（对象 P1，说明写明已超时，输入的引用是确认消息的标识）和释放预留

#### Scenario: 结束确认没改成

- **GIVEN** order-flow spec 的基准数据；已经提交 P1，一直没有人按按钮；报告结果时 Discord 报错
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 结束确认的说明写明已超时、没有改成和原因；P1 照常释放预留

#### Scenario: 调用预算用完

- **WHEN** 排队运行做一轮
- **THEN** 程序日志有一条调用预算用完：行为者系统，对象 `system`，没有案件 ID，说明写明普通预算、交易日 2026-10-14、今天的费用 2.00、额度 2.00，以及关注股、候选和复盘的案件留在队列里
