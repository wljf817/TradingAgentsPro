# Proposal

## Why

Proposal 要求健康监控在系统健康异常时进入降级模式：保留止损单、暂停开仓、不执行没经人工确认的模型发起的退出，并告警；恢复后先对账，再恢复运行。现在代码里没有"系统是否健康"的判断，也没有降级模式这个状态。前面几个变更都把它留给了本变更：

- 对账：断线恢复后先对账、再恢复运行，交给降级模式
- 止损保护：券商持仓一直查询失败、止损单挂不上的断线情况，由健康监控处理
- 紧急退出：行情延迟或过时，由健康监控处理
- 交易日历：降级期间到期的事项顺延到"恢复后的第一个交易日"，由本变更决定是哪一天

本变更的目的只有一个：**健康监控根据五项检查判定是否进入降级模式，全部恢复并完成一次对账后退出，并给出恢复后的第一个交易日。**

引用的 Proposal（完整版）章节：

- 「架构」的"支撑模块"：健康监控监控模型 API、券商连接、数据延迟、调用预算和调度器心跳，异常时进入降级模式；PM 或 Critic 的主模型和备用模型全部不可用才算模型 API 异常
- 「调度器与运行模块」：
  - 健康监控监控这五项，决定是否进入降级模式
  - 普通预算用完后改用持仓保留预算，持仓保留预算也用完，健康监控才进入降级模式
- 「故障处理」：
  - 论点状态和系统健康状态分开记录；系统故障永远不被当作投资判断
  - 单个模型不可用时先换备用模型，不进入降级模式
  - 降级模式的各项处理：保留止损单、暂停开仓和加仓、告警、紧急风险退出照常有效、到期事项顺延到恢复后的第一个交易日、恢复后先对账
- 「订单生命周期」的"断线或重启"：恢复后先与券商对账，再恢复运行
- 「记录、复盘与经验」的程序日志：系统记录进入和退出降级模式

## What Changes

- 新增健康监控模块 `modules/health/`，判定需要的信号都由调用方传入，模块不读取外部数据
- 五项检查，任何一项异常就进入降级模式：

  | 检查 | 异常的条件 |
  | --- | --- |
  | 模型 API | PM 的主模型和备用模型全部不可用，或者 Critic 的全部不可用 |
  | 券商连接 | 券商断开 |
  | 数据延迟 | 常规交易时段内，行情超过数据延迟上限（默认 60 秒）没有更新；从开盘起算，盘外不检查 |
  | 调用预算 | 持仓保留预算用完 |
  | 调度器心跳 | 调度器超过心跳超时（默认 300 秒）没有心跳 |

- 三种状态：正常、降级、等待对账。降级和等待对账都算处于降级模式
  - 正常时任何一项检查异常，进入降级
  - 降级时五项检查全部恢复正常，转为等待对账
  - 等待对账时完成一次对账，回到正常；又有检查异常，回到降级
  - 降级期间完成的对账不算，要在全部恢复以后再对一次
- 健康监控给出当前状态：是否处于降级模式、哪些检查异常、什么时候进入的降级模式。调用方据此告警、写程序日志，并作为暂停开仓的依据
- 恢复后的第一个交易日：退出降级模式以后，第一个收盘的交易日。盘前或盘中恢复是当天，收盘后恢复是下一个交易日
- 状态放在内存里。进程新建以后是正常，下一次判定时重新算

## Non-goals

- 降级期间暂停开仓：要改风控，作为下一个变更「降级暂停开仓（修改：风控规则、下单前再校验）」，见「需要人决定」第 2 条
- 不执行没经人工确认的模型发起的退出：属于 M3 的「人工确认的规则」。模型建议退出默认就要人工确认，降级时即使打开了自动执行也不自动执行
- 到期事项顺延、恢复后补跑积压的持仓案件：M3 的定时心跳和调度器，用本变更给出的恢复后的第一个交易日
- 保留止损单、紧急风险退出照常有效：不用改，止损单的对齐和紧急退出都不看健康状态
- 五项信号从哪来：模型可用状态和调用预算来自 M3 的 Agent 网关，调度器心跳来自 M3 的调度器，券商连接和行情更新来自 M2 的适配器
- 判定的频率、告警的发送、写程序日志：M2
- 单个模型的熔断（连续失败后冷却）：属于 Agent 网关，M3 再定；本模块只看"PM、Critic 是否还有可用的模型"
- 新闻、公告等其他数据源的延迟：M4 接入这些数据源时再看

- `degraded-mode`：五项健康检查、进入和退出降级模式、当前状态、恢复后的第一个交易日、健康配置

### Modified Capabilities

无

## Impact

- **代码**：新增 `src/tradingagentspro/modules/health/`
  - `domain/health.py`：健康信号、检查项、状态，以及判定异常检查、状态转换、恢复后的第一个交易日的纯函数
  - `service.py`：`HealthService`，判定、记下对账、给出当前状态
  - `config.py`：`HealthConfig`，数据延迟上限和调度器心跳超时
  - `__init__.py`：导出公开的名字
- **测试**：新增 `tests/modules/health/`：`domain/test_health.py`（含状态机性质测试）、`test_service.py`、`test_config.py`
- **依赖**：无
- **文档**：
  - `docs/实现路线.md` 的进度清单增加「降级暂停开仓（修改：风控规则、下单前再校验）」（propose 时已更新）
  - 人同意「需要人决定」第 1 条后，完整版 Proposal「故障处理」写明恢复后的第一个交易日是哪天
- **对后续变更的影响**：
  - 降级暂停开仓（下一个变更）：风控的输入增加"是否处于降级模式"，用本模块的状态；处于降级模式时开仓类方案被拒绝
  - M2：
    - 定时判定：券商连接和行情更新来自适配器；还没有 Agent 网关和调度器时，这三项信号按正常传入
    - 等待对账时调用执行模块对账，完成后告诉本模块
    - 按状态变化告警、写程序日志
    - bootstrap 启动时先判定一次，再接受新订单
  - M3：
    - Agent 网关给出 PM、Critic 是否还有可用的模型，以及持仓保留预算是否用完；调度器写心跳
    - 「人工确认的规则」：处于降级模式时，模型发起的退出即使打开了自动执行也要人工确认
    - 定时心跳：降级期间到期、没有结论的复查日和催化剂截止日期，顺延到恢复后的第一个交易日；调度器恢复后按优先级补跑积压的持仓案件

## 需要人决定

1. **"恢复后的第一个交易日"是哪天**：「故障处理」说到期事项顺延到恢复后的第一个交易日，没说盘中恢复时算不算当天。
   - 推荐：退出降级模式以后第一个收盘的交易日。盘前或盘中恢复是当天，当天收盘的定时心跳就能补上；收盘后或休市日恢复是下一个交易日
   - 推荐在「故障处理」这一条后面补上这句话
2. **暂停开仓放在哪里**：Proposal 只说降级模式暂停开仓和加仓。推荐和单日亏损熔断一样做成风控的开仓类规则：风控多一项输入"是否处于降级模式"，处于降级模式时拒绝开仓类方案，原因是"降级模式"。风控和健康监控是架构图里不同的节点，所以单独作为下一个变更
   - 留给那个变更再定：已经人工确认、等着下单的开仓方案，在再校验时遇到降级模式怎么办。倾向：和熔断一样被拒绝，方案作废

新发现的，已按推荐做法写进 spec，不同意可以改：

3. **哪些恢复要先对账**：「故障处理」说"恢复后先对账"，对账的变更里倾向只在券商断线恢复后对账。推荐：不管因为哪一项进入降级，退出前都要在全部恢复以后完成一次对账。规则统一，对账也不贵
4. **数据延迟从什么时候算**：Proposal 没给阈值，也没说盘外怎么办。推荐：只在常规交易时段检查，从开盘起算，超过 60 秒（可配置）没有行情更新算异常；盘外行情本来就很少更新，不检查
