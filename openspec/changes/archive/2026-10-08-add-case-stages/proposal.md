# Proposal

## Why

Proposal 规定调度器推进案件的阶段：唤醒 PM → 等待结论 → 唤醒 Critic → 风控 → 人工确认 → 执行，案件在提交订单后结束。前三个 M3 变更已经能确定案件类型、校验结论、决定启动哪些排队的案件，但还没有东西记录一个案件走到了哪一步、下一步去哪、为什么结束。以前的变更也把几件事留给了本变更：

- 案件类型与结论：结论校验不通过以后退回 PM；Critic 的质询和 PM 回应的格式
- 案件队列：运行中的案件是否还在调用模型（`RunningCase.calling_models`）、方案所处的阶段（`PlanStage`）；方案被作废、案件被紧急退出中止以后案件怎么结束；风控拒绝、再校验作废以后案件结束（已决定）；案件因为故障没有结论时怎么结束

本变更的目的只有一个：**一个案件从唤醒 PM 到提交订单的状态机：每一步之后进入哪个阶段、什么时候结束、以什么原因结束。**

引用的 Proposal（完整版）章节：

- 「架构」的「调度器」（推进案件阶段）、「审核层：Critic」（通过、质询、补充研究、否决开仓方案；质询与回应最多 2 轮；退出类方案只审 1 轮、不能否决；有分歧时连同双方意见交给人）、「风控与执行」（风控结果、下单前再校验作废、人工确认、案件在提交订单后结束）
- 「调度器与运行模块」：案件流程第 1 到 6 步；运行约束的并发上限（只计唤醒 PM 到 Critic 审核结束的案件，复盘一直算）；排队规则（作废已交给人工确认的开仓方案，退出方案不作废）
- 「持仓与退出」的退出路径表：模型建议退出由 Critic 快速审核、最多 1 轮、不能否决，有异议时交给人
- 「风控引擎与执行」：调整后的方案直接进入人工确认并标明；下单前再校验作废；额度预留在方案作废、人工拒绝或确认超时时释放；通过后进入人工确认
- 「订单生命周期」第一段：案件在方案通过风控、提交订单后结束，订单由执行模块单独跟踪
- 「故障处理」：系统故障不当作投资判断；PM 或 Critic 的主备模型全部不可用才算模型 API 异常；紧急风险事件中止同一股票正在运行的案件

## What Changes

- 调度器模块增加案件状态机的纯逻辑，没有 service 和存储。一个不可变的案件状态，每个事件是一个方法，返回新的状态：

  | 阶段 | 调用模型 | 方案的阶段（给队列） |
  | --- | --- | --- |
  | 唤醒 PM：PM 研究并提交结论，校验不通过时修改再提交 | 是 | 没有方案 |
  | Critic 审核：包括 Critic 要求的补充研究 | 是 | 审核 |
  | PM 回应：逐条回应质询 | 是 | 审核 |
  | 风控 | 否 | 审核 |
  | 等人工确认 | 否 | 等人工确认 |
  | 等下单：已确认，等开盘和下单前再校验 | 否 | 等下单 |
  | 复盘：Reviewer 处理 | 是 | 没有方案 |

- 阶段转换：
  - 唤醒 PM：结论校验不通过时退回 PM 在同一个案件里修改再提交，最多重交 2 次，用完结束（结论无效）；结论通过、没有交易方案时结束；有交易方案时进入 Critic 审核
  - 开仓类方案：Critic 通过进入风控；否决时结束；质询时 PM 回应（维持、修改回到 Critic 审核，撤回时结束）；质询与回应满 2 轮以后 Critic 仍然质询，方案带着分歧进入风控
  - 退出类方案：Critic 只审一次、不能否决，通过或有异议都进入风控，有异议时带着分歧
  - Critic 的主备模型全部不可用：退出方案跳过 Critic 进入风控，注明 Critic 不可用；开仓方案的案件按系统故障结束
  - 风控通过或调整进入等人工确认，拒绝时结束；人工确认后等下单，人工拒绝或确认超时时结束；订单提交时结束，再校验作废时结束
  - 方案被作废（新案件排队）、紧急退出中止、系统故障随时结束案件；已结束的案件收到任何事件都不变，运行中的案件收到不适用的事件报错
- 结束原因：没有交易方案、订单已提交、Critic 否决、PM 撤回、风控拒绝、人工拒绝、确认超时、再校验作废、方案被作废、紧急退出中止、结论无效、系统故障、复盘完成。状态另外记下是否有有效结论：结论通过校验以前因系统故障、紧急退出或结论无效结束的，算没有结论，不当作投资判断
- 交给人工确认时，状态给出 Critic 审核的结果：通过、有分歧（确认消息附上 PM 和 Critic 双方的意见）、Critic 不可用（确认消息注明）。本变更里所有交易方案都进入等人工确认
- contracts 新增：案件的结束原因；Critic 审核的格式（通过、质询、否决，质询逐条写出）和 PM 回应的格式（维持、修改、撤回，逐条回应，修改时写新的方案条款）
- 可配置项：结论最多重交次数，默认 2；开仓方案质询与回应最多轮数，默认 2

## Non-goals

- 复查日和催化剂截止日期的取值、论点更新里的日期是否合理：属于「复查日与催化剂」
- 到期事项在案件没有结论时顺延到恢复后的第一个交易日、案件失败后怎么重开：属于「收盘检查」。本变更只给出案件结束时是否有结论
- 跟进申请的审批：属于「跟进审批」
- 派任务的白名单、任务数、PM 最多 2 轮任务、PM 回应时能否再派任务、Critic 补充研究的额度、Result 的格式和状态：属于「任务派发」。本变更只规定补充研究在 Critic 审核这一步里完成，不算一轮质询
- 评分的完整格式：属于「信号格式」
- 模型的超时、重试、切换备用模型和熔断；PM 用备用模型时限制结论：属于「备用模型」。本变更只接收"PM 失败""Critic 不可用"这样的结果
- 预算用完时 Agent 网关是否拒绝运行中案件的调用：属于「调用预算」
- 哪些方案可以不经人工确认：退出方案自动执行的开关、紧急退出的确认开关、确认超时的处理和告警、降级时模型发起的退出一律要确认：属于「人工确认的规则」。本变更里所有交易方案都进入等人工确认
- 唤醒 PM 和 Critic 时交给它们的上下文（案件类型的问题、事件、共享事实、上一个案件的结束原因）：M5「共享上下文」
- 案件状态存在哪里、事件从哪里来、按状态组出队列的快照、结束时释放预留和写案件记录、结论里方案以外的部分（论点更新、跟进申请、升降级、增删）什么时候生效、确认消息里写出双方意见和 Critic 不可用：M4
- 复盘案件的内容和 Reviewer 的步骤：M6

## Capabilities

### New Capabilities

- `case-stages`：案件的状态和阶段；唤醒 PM 和结论的重交；Critic 审核开仓方案和退出方案、质询轮次、补充研究；PM 回应；Critic 不可用；风控、人工确认和等下单；方案被作废、紧急退出中止、系统故障；复盘案件；结束原因和是否有结论；已结束的案件和不适用的事件；Critic 审核和 PM 回应的格式；案件阶段的配置

### Modified Capabilities

- `case-queue`：只改几个场景的写法，要求不变。原来有的场景让等下单的方案没有所属的运行中案件（或者同一只股票同时有两个运行中的案件），按本变更"订单提交以后案件才结束"，这种组合不会出现；改为等下单的方案都属于一个处在等下单阶段的运行中案件，涉及「降级模式」「新案件排队时作废开仓方案」「紧急退出」三项要求

队列的 `RunningCase.calling_models` 和 `PlanStage` 由本变更的状态推出；结论的校验沿用 case-types spec。

## Impact

- **代码**：
  - 新增 `contracts/review.py`：Critic 审核和 PM 回应的格式
  - `contracts/case.py` 增加案件的结束原因
  - 新增 `modules/scheduler/domain/stage.py`：阶段、Critic 审核的结果、案件状态和它的事件方法
  - `modules/scheduler/config.py`：`SchedulerConfig` 增加结论最多重交次数、质询最多轮数
  - `modules/scheduler/__init__.py`：增加导出
- **测试**：新增 `tests/contracts/test_review.py`、`tests/modules/scheduler/domain/test_stage.py`、`tests/modules/scheduler/domain/test_stage_machine.py`（性质测试）；`tests/modules/scheduler/test_config.py` 增加两个配置项
- **依赖**：无
- **文档**：人同意「需要人决定」以后，完整版 Proposal 在对应章节补上已决定和新发现的条目，每处一两句话
- **对后续变更的影响**：
  - 收盘检查：按案件结束时是否有结论决定到期事项顺延，不当作不续期
  - 任务派发：Critic 的补充研究在 Critic 审核阶段派发，结果在 PM 回应时一并交给 PM
  - 备用模型：PM 的主备模型全部失败时给出系统故障，Critic 的主备模型全部不可用时给出 Critic 不可用
  - 人工确认的规则：按 Critic 审核的结果决定退出方案能否自动执行（有分歧、Critic 不可用时都交给人）
  - M4：存案件状态，事件来了调用对应的方法；用状态给出 `RunningCase.calling_models` 和 `PendingPlan.stage`，状态变化以后取得队列的决定；案件以订单已提交以外的原因结束时释放方案的预留；紧急退出时只中止案件，不再对它的方案报作废；确认消息按 Critic 审核的结果附上双方意见或注明 Critic 不可用；结论通过校验时应用方案以外的部分
  - M5：PM 和 Critic 按本变更的格式输出；这只股票上一个案件的结束原因放进下一个案件的上下文

## 需要人决定

已决定（2026-10-08）：

1. **「退回 PM」**：风控拒绝、下单前再校验作废时 Proposal 写"退回 PM"，没有定义。决定：案件结束并记下原因，不在同一个案件里重来；PM 在这只股票的下一个案件上下文里能看到这条记录
2. **「推送给人决定」和人工确认合成一步**：质询 2 轮仍有分歧的开仓方案、Critic 有异议的退出方案，照常过风控，确认消息里附上 PM 和 Critic 双方的意见，人点确认就算做了决定
3. **Critic 的模型全部不可用**：退出方案跳过 Critic，直接交给人确认并注明 Critic 不可用；开仓方案所在的案件按失败处理（降级模式本来就暂停开仓）

新发现的，已按推荐做法写进 spec，不同意可以改：

4. **质询与回应的轮次怎么数**：Proposal 写"质询与回应最多 2 轮；2 轮后仍未通过，推送给人"，没说 PM 第 2 次回应以后 Critic 还看不看。推荐：一轮是 Critic 质询一次、PM 回应一次，PM 回应以后 Critic 总是再审一次，所以默认最多审 3 次；第 3 次只能通过、否决，或者仍然质询（算有分歧，带着双方意见交给人）。这样 PM 第 2 次回应已经说服 Critic 时不用打扰人。Critic 要求的补充研究在它这次审核里经 Agent 网关完成，不算一轮；结果在 PM 回应时一并交给 PM（Critic 直接通过时 PM 不需要看）
5. **退出方案的"只审 1 轮"**：推荐 Critic 只审一次：通过就进入风控；有异议时不交给 PM 回应，直接带着双方意见（PM 写方案的理由、Critic 的异议）进入风控和人工确认。模型建议退出要在当个案件内尽快完成，PM 的意见已经写在方案理由里。Critic 对退出方案给出否决时按异议处理，不让案件因为输出不合规而卡住
6. **PM 回应时修改方案**：推荐修改后的方案代替原来的，回到 Critic 审核，算作这一轮的回应；只能改方案条款（股数、限价、止损价、紧急阈值、有效期、允许价格偏离），按开仓方案的规则检查格式；不能改决定、动作和论点，要改这些就撤回，下一个案件再提
7. **结论校验不通过最多重交几次**：Proposal 没写。推荐默认 2 次（可配置）：多数原因（结论种类不对、续期缺论点更新、跟进案件又申请跟进）照着原因改一次就能通过，再留一次余量；用完仍不通过，案件以「结论无效」结束，和系统故障一样算没有结论，不当作投资判断
8. **什么叫"没有得出结论"**：「持仓与退出」和「故障处理」说因系统故障没有结论时不视为不续期，没说结论之后才出故障算不算。推荐：结论通过校验时就算有结论，之后方案怎样结束（Critic 否决、风控拒绝、确认超时、系统故障）都不改变；结论通过以前因系统故障、紧急退出中止或结论无效结束的，算没有结论，由「收盘检查」顺延到期事项。所以开仓方案因 Critic 不可用按系统故障结束时，结论里的续期仍然算数，只是方案不执行
9. **退出方案确认以后，排队的案件等到什么时候**：「调度器与运行模块」排队规则写退出类方案不作废，"排队的案件等确认结果出来后再运行"；「订单生命周期」写案件在提交订单后结束。盘后确认的退出方案要等开盘再校验、下单，这期间案件还在运行、占着这只股票。推荐按「订单生命周期」：排队的案件等这个案件结束（订单提交，或者方案因再校验作废等原因结束）再运行，排队规则的措辞改为"等这个案件结束后再运行"
