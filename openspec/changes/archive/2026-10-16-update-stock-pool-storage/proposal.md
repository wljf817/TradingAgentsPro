# Proposal

## Why

股票池在 M3 只有纯逻辑和存储端口，记录存在内存里，进程重启就没了。M4 的案件流程要用到的几样东西也还没有地方存：持仓的投资论点（买入时 PM 写的，之后的论点更新整份替换）、两种论点的"上次复查的那一天"（推后复查日的上限从这天算），以及 PM 在关注股和持仓的案件里写的论点更新。复查日与催化剂（add-review-dates 的 design D7）把"更新关注论点"留给了本变更。股票池的增删和校验结果也还没有写进程序日志；之后最多 3 个案件、收盘心跳和成交的处理会同时调用股票池，先读后写的检查要一个接一个进行（add-stock-pool 的 design D7 留到 M4）。

本变更的目的只有一个：**股票池把记录存进状态库，并保存后面的案件流程要用的论点；每次变化和校验结果写进程序日志。**

引用的 Proposal（完整版）章节：

- 「股票池与寻股」：字段表（状态、来源、理由与论点草稿、板块、关注论点、最新评分、时间）；增删规则由代码强制执行
- 「共享状态库」：股票池属于当前市场事实，写入者是股票池校验（代码）；写入带时间戳和版本号，只追加不覆盖；每类字段只有一个写入者
- 「触发 · 2. 定时心跳」：持仓复查日在买入时写进论点，续期时设下一个，任何案件里都能调整；推后的上限从上次买入或续期那天算，加仓不重新起算；关注复查日写在关注论点里，规则相同
- 「记录、复盘与经验 · 程序日志」：股票池一行（每次增删、校验结果、自动过期）；每条记录的字段，包括案件 ID

已经定了的：

- 拆分 M4 时定的：股票池的表用状态库的版本表，迁移 v0005；同时进行的操作由股票池自己串行；股票池的动作由股票池写进程序日志；论点和上次复查的那一天由调用方按 review-dates spec 检查、算好，股票池只保存；还没有调用方时不装配
- 以前的变更留给本变更的：更新关注论点、持仓的投资论点存进股票池（add-review-dates 的 design D7）；买入那一天是给出开仓方案结论的那一天，不等成交（review-dates spec，人已同意）

## What Changes

- 记录多三项：投资论点（只有持仓有）、上次复查的那一天（关注和持仓有）、成为候选的时刻（加入和代码触发的清仓时设，降为候选的没有；收盘心跳拿它判断新候选）。状态变化跟着改：升级、买入成交、PM 发起的清仓转为关注时，论点和上次复查的那一天由调用方给出；降为候选、代码触发的清仓去掉它们；持仓的买入成交（同一笔开仓单后续的成交、加仓）不改变记录
- 新的操作「论点更新」：PM 给关注股或持仓附的论点更新通过校验以后，调用方把新论点和上次复查的那一天存进股票池，整份替换。股票不在池子里、状态不对时拒绝
- 存储：状态库新表 `stockpool_entries`（迁移 v0005），按股票只追加；记录原样读回，重启后读到同样的池子，包括冷却期和当天的增删次数
- 同时进行的操作：改变记录的操作一个接一个进行，容量、关注名额和每天增删次数不会因为同时进行而多放进一只
- 程序日志：新的行为者「股票池」。加入、删除、升级、降为候选、保持、记录评分、论点更新每次请求写一条，被拒绝的写明原因；超期移出、买入成交、清仓每次变化写一条。PM 发起的操作带案件 ID，调用方传入

## Non-goals

- 装配：bootstrap 里建股票池的存储和用例、把它交给流程，由第一个调用股票池的变更做（案件工作流、方案接下单、收盘心跳）。迁移照常随启动执行
- 谁在什么时候调用：案件工作流把结论里的增删、升降级、评分和论点更新交给股票池；成交和清仓时调用买入成交、清仓（「方案接下单」「事件检测」）；收盘心跳移出到期的候选
- 论点里日期的检查：review-dates spec 已有，股票池不再检查
- 板块和上市信息从哪个数据源取：「财报日历与板块」
- 按论点设到价提醒、事件关联催化剂以外的用法：「论点条件与到价提醒」「事件检测」
- 人"手动添加股票"这个动作的条目：由接收手动添加的入口写，现在还没有这个入口；股票池照样写自己的加入条目
- 关注股挂着买单时被移出、随后成交：仍按 add-stock-pool 的设计报错，接线时处理

## Capabilities

### New Capabilities

无

### Modified Capabilities

- `stock-pool`：「股票池的记录」加投资论点、上次复查的那一天和成为候选的时刻；「状态变化」里升级、买入成交、清仓带上论点和上次复查的那一天，加入和代码触发的清仓设成为候选的时刻；新增「论点更新」「股票池的存储」「同时进行的操作」
- `program-log`：「程序日志的条目」加行为者股票池；新增「股票池的动作」
- `state-store`：「表的归属和迁移」加股票池的表

## Impact

- **代码**：
  - `modules/stockpool/`：`domain/entry.py`（记录的新字段和状态变化）、`service.py`（论点更新、新的参数、程序日志、锁）、新增 `repo.py`（表和数据库实现）、`__init__.py`
  - `modules/statestore/repo.py`：版本表加一种只读的列出：每个键的最新版本里，某几个时刻列不早于给定时刻的
  - `modules/programlog/domain/entry.py`：加行为者和动作
  - 新迁移 `bootstrap/migrations/versions/v0005_create_stock_pool.py`
- **测试**：`tests/modules/stockpool/`（数据库实现要开着 Docker）、`tests/modules/statestore/test_repo.py`、`tests/bootstrap/` 里表的清单
- **依赖**：无
- **数据库**：一张新表、一个迁移
- **文档**：完整版「股票池与寻股」的字段表加投资论点、上次买入升级或续期的那一天两行（「需要人决定」第 2 条）
- **对后续变更的影响**：
  - 案件工作流：结论通过校验以后按结论调用股票池的操作，带上案件 ID；组 `ThesisUpdate` 时原来的论点和上次复查的那一天从股票池取
  - 方案接下单：开仓单成交时带上开仓方案附的投资论点和给出结论的那一天调用买入成交
  - 收盘心跳：持仓和关注的复查日、催化剂截止日期从股票池的论点取
  - 跟进存储：跟进的"当天获批的次数"也要按时刻列出最新版本，可以用本变更给版本表加的列出

## 需要人决定

已决定（2026-10-16，编排者同意四条的推荐做法；第 1 条另外在和人确认，不影响本变更）：

1. **`/plan` 买进的持仓没有投资论点**（设计，请人定）：股票池里的持仓要有投资论点，才有复查日和催化剂截止日期，收盘心跳才会为它开复查案件；M2 的 `/plan` 方案没有论点。
   推荐做法：`/plan` 的方案和股票池无关，股票池里的持仓一定有投资论点。
   - `/plan` 的买入和加仓成交不调用股票池。`/plan` 买进的、不在池子里的股票不进股票池：没有复查日，不开案件，只受止损、紧急退出和对账保护。案件流程跑起来以后，不用 `/plan` 买股票池里的候选和关注
   - 股票池里的持仓股数变为 0 时，不是 PM 发起的清仓方案的（止损单、紧急退出，也包括 `/plan` 的清仓），都按代码触发的清仓转为候选；由「方案接下单」接线并写进它的 spec
   - M2 测试留在模拟盘里的持仓：开始跑案件流程以前用 `/plan close` 清掉，不给它们建记录（建记录要有投资论点）
   - 另一种做法是允许持仓没有投资论点，`/plan` 买入时直接建一条持仓记录。要多一条绕过加入检查的路，收盘心跳和持仓案件都要处理没有论点的持仓，不推荐
2. **投资论点存在哪里**（小问题，要改完整版的字段表）：完整版「共享状态库」把投资论点列为 agent 产出的结构化结果，经 Agent 网关写入；「股票池与寻股」的字段表只有关注论点。
   推荐做法：股票池保存持仓现在生效的投资论点，和关注论点一样由股票池写入；Agent 网关存的是 PM 在某个案件里写的那一份，是结论的一部分。一个是当前状态，一个是产出的结果，各有一个写入者，不违反"每类字段只有一个写入者"。完整版「股票池与寻股」的字段表加两行：投资论点（持仓有，买入成交时取开仓方案附的，论点更新时整份替换）；上次买入、升级或续期的那一天（推后复查日的上限从这天算，和"上次复查时间"不同）。「共享状态库」不改
3. **"成为候选的时刻"没有地方存**（小问题，范围）：完整版「定时心跳」的新候选是"加入股票池或代码触发的清仓转为候选以后、还没有候选评估得出结论的候选，降为候选的不算"。收盘检查规定新候选由调用方给出，但股票池只记了加入时刻：代码触发的清仓什么时候转为候选、一只候选是不是降为候选来的，现在哪里都没存。
   做法：本变更给记录加一项"成为候选的时刻"：加入和代码触发的清仓时设为当时，降为候选时为空；「收盘心跳」拿它和案件记录比（已写进 stock-pool spec 和 design D1）
4. **状态库的版本不带案件 ID**（小问题）：完整版「共享状态库」要求"案件里产生的条目还带案件 ID"，状态库的版本表只有键、版本号和写入时刻。
   推荐做法：版本表照旧；股票池里由案件引起的变化（加入、删除、升降级、保持、评分、论点更新），程序日志的条目带案件 ID，要追溯哪个案件改的看程序日志。案件产生的其他条目怎样带案件 ID，由「状态库快照」「案件记录」定。完整版不改
