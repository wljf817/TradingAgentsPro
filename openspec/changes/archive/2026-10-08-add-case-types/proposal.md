# Proposal

## Why

Proposal 规定调度器开案件时按"驱动方式 × 股票状态"确定案件类型，类型固定 PM 要回答的问题、允许的结论、最低研究要求和排队优先级；PM 提交的结论只能在案件类型允许的范围里选。M3 后面的案件队列（按优先级排）、案件阶段（唤醒 PM、收结论）、收盘检查（开心跳案件）、跟进审批（审批结论里的跟进申请）和任务派发（子 agent 的身份）都要用到案件类型和结论的格式。上一个变更「股票池」也把两件事留给了本变更：PM 用什么格式提交增删和升降级，以及投资论点。

本变更的目的只有一个：**按触发和开始运行时的股票状态确定案件类型，并按案件类型校验 PM 提交的结论。**

引用的 Proposal（完整版）章节：

- 「架构」的「调度器」：按"驱动方式 × 股票状态"确定案件类型，类型固定的四件事，九档优先级；「决策层」：结论的种类、正面回答问题并附评分、开仓方案和升级为关注引用至少 2 个不同子 agent 的 Result
- 「触发」开头的说明和两张表（三种驱动；每种股票状态允许的结论），复查类案件续期的要求，寻股和复盘；「事件驱动」的事件来源、持仓风险事件和「目标」表；「定时心跳」的检查项表；「自定义跟进」的申请四项和「跟进案件」；「通用规则」
- 「调度器与运行模块」的案件流程第 1 步（唤醒 PM 时交给它案件类型）和第 3 步（PM 在允许的范围内给出结论）
- 「Task / Result 通信」的「最低要求」：事件类型对应的子 agent 是下限
- 「Agent」的「PM 的交易方案」
- 「持仓与退出」的「清仓后的股票状态」：PM 发起的清仓由 PM 在同一个结论里选择转为关注或移出

## What Changes

- 新增调度器模块 `modules/scheduler/`，本变更只有纯逻辑和配置，导出纯函数，没有 service 和存储
- contracts 新增，后续变更和 M4、M5 都要用：
  - 子 agent 的身份：News、Quant、Fundamentals
  - 事件的类别：价格和成交量异动、新闻、公告、财报发布、关注股的入场条件满足、持仓达到目标价或证伪条件触发
  - 案件类型（14 种，见下表）
  - 投资论点：买入理由、催化剂、目标价、证伪条件（文字和代码能检测的部分）、复查日；复用关注论点的催化剂和条件
  - PM 的结论：持仓、关注、候选、寻股四种，每种只有这个状态允许的决定；交易方案（PM 写的部分）、论点更新、跟进申请、清仓后的去向、股票池增删、评分
  - 交易方案：把 `TradePlan` 按动作检查字段的规则抽成函数，PM 写的方案共用，`TradePlan` 的行为不变
- 案件类型：

  | 驱动 | 持仓 | 关注 | 候选 | 不针对单只股票 |
  | --- | --- | --- | --- | --- |
  | 事件 | 持仓风险事件（1）、持仓事件（2） | 关注股事件（4） | 候选股事件（6） | — |
  | 定时心跳 | 持仓复查、持仓催化剂复查（3） | 关注复查、关注催化剂复查（5） | 候选评估（7） | 寻股（8）、每周复盘（9） |
  | 自定义跟进 | 持仓跟进（3） | 关注跟进（5） | — | — |
  | 卖出成交 | — | — | — | 卖出复盘（9） |

  括号里是排队优先级，1 最高。复盘案件由 Reviewer 处理、不唤醒 PM，本变更只给类型和优先级
- 开始运行时按当时的股票状态确定类型：事件案件和跟进按当时的状态；定时心跳的检查项针对一个状态，开始时股票已经不在这个状态就不运行；跟进开始时已经是候选、或者不在股票池也不是持仓，就不运行
- 每份结论有一个主决定，持仓和关注的部分决定可以另外附论点更新和跟进申请：

  | 状态 | 决定 |
  | --- | --- |
  | 持仓 | 持有、加仓、减仓、清仓（必须选清仓后的去向） |
  | 关注 | 开仓方案（必须附投资论点）、继续关注、降为候选、移出 |
  | 候选 | 升级（必须附关注论点）、保持、移出 |
  | 寻股 | 增删股票池，每只加入的候选一个评分 |

- 结论的校验，给出第一项不通过的原因：

  | 顺序 | 检查 | 不通过时的原因 |
  | --- | --- | --- |
  | 1 | 结论的种类是案件类型对应的 | 结论不属于这个案件 |
  | 2 | 跟进案件没有再申请跟进 | 跟进案件不能再申请跟进 |
  | 3 | 复查类案件里持有、加仓、减仓、继续关注时附了论点更新（续期） | 续期缺少论点更新 |
  | 4 | 事件案件向事件类别要求的子 agent 派过任务 | 缺少事件要求的子 agent |
  | 5 | 开仓方案、加仓和升级引用的已完成 Result 来自至少 2 个不同子 agent | 研究不足 |

- 可配置项：开仓方案、加仓和升级至少引用几个不同子 agent，默认 2

## Non-goals

- 队列：排队、同一只股票一次一个案件、排队时用什么状态算优先级、新案件排队时作废开仓方案：属于「案件队列」
- 案件阶段的推进、唤醒 PM 时交给它什么、结论被拒绝后退回 PM、Critic 的质询和 PM 回应的格式：属于「案件阶段」
- 复查日和催化剂截止日期的取值（默认 5 个交易日、3 到 20、往后推要写理由、亏损时只能提前）、论点更新是否真的设了新的复查日和催化剂、把论点更新存进去：属于「复查日与催化剂」。本变更只检查续期时附了论点更新
- 什么时候开心跳案件、候选评估的每天上限、寻股的触发条件：属于「收盘检查」
- 跟进申请的审批（引用具体对象、和催化剂重复、替换、每只股票最多 2 个、最远 60 个交易日、每天次数、状态变化时作废）、原因类型和引用对象是否对应：属于「跟进审批」
- 派发任务、白名单（寻股只能派给 Quant 和 Fundamentals）、任务数、最多 2 轮、Result 的格式和状态：属于「任务派发」。本变更由调用方传入派过任务的子 agent 和已完成的 Result
- 评分的完整格式（置信度、评估窗口、数据时效等）：属于「信号格式」，本变更只有 -2 到 +2 的整数
- PM 用备用模型时限制结论：属于「备用模型」
- 事件检测（阈值、强度、怎么标注持仓风险级别、到价提醒）和事件的完整格式：M4
- 寻股的粗筛、PM 只能从粗筛结果里挑：M4
- 把结论交给股票池、风控和状态库（记录评分、增删、升降级、生成方案 ID、存投资论点）、案件上下文的组装、案件记录和按案件类型评估：M4、M6
- 复盘案件的内容：M6

## Capabilities

### New Capabilities

- `case-types`：触发、案件类型和它固定的问题、结论种类、优先级；开始运行时确定类型；事件类别要求的子 agent；PM 结论的格式（四种结论、交易方案、投资论点、跟进申请）；结论的校验；研究要求的配置

### Modified Capabilities

无。`TradePlan` 只是把检查字段的规则抽成函数，risk-rules spec 不变。

## 需要人决定

已决定（2026-10-08）：

1. **案件类型什么时候定**：案件排队期间股票状态可能变，比如止损成交后持仓变成候选。决定：开始运行时按当时的状态定类型；排在队里的复查案件，股票已经不在那个状态（比如持仓复查时已经不是持仓），就不再运行

新发现的，已按推荐做法写进 spec，不同意可以改：

2. **一份结论里有几个动作**：Proposal 把持有、更新论点、申请跟进并列为结论，但减仓时通常也要更新论点，续期本身就是改复查日。推荐：每份结论有一个主决定（持仓：持有、加仓、减仓、清仓；关注：开仓方案、继续关注、降为候选、移出；候选：升级、保持、移出；寻股：增删股票池），持仓和关注可以另外附一份论点更新和跟进申请；"更新论点""申请跟进"不单独作为结论，而是"持有"或"继续关注"附上的内容。加仓、减仓之后仓位还在，同样可以附；清仓、开仓方案、降为候选、移出会改变状态，原来的论点和待执行的跟进随之失效，不能附
3. **研究要求里的"开仓方案"包括加仓**：加仓和买入一样增加风险（风控也把两者都算开仓类），所以加仓方案也要引用至少 2 个不同子 agent 的 Result
4. **复查案件里加仓、减仓也要续期**：Proposal 只说复查类案件选持有或继续关注要设下一个复查日。复查案件里选加仓或减仓，仓位还在，不续期的话复查日一直停在过去。推荐：复查类案件里，结论之后股票还是这个状态的决定（持有、加仓、减仓、继续关注）都要附论点更新，下一个复查日写在里面
5. **论点更新是一份完整的新论点**：推荐论点更新整份代替原来的论点（持仓是投资论点，关注是关注论点），不只写改动的几项。续期就是附一份论点更新，下一个复查日、催化剂到期后新的催化剂和截止日期都写在里面；本变更只检查附了论点更新，复查日和截止日期是不是新的、取值是否合理由「复查日与催化剂」检查。只改一项也要整份重写，换来的是论点永远完整，不用合并
6. **定时心跳的检查项和跟进也绑定状态**：第 1 条说的是复查案件。推荐同样适用于候选评估（开始时已经不是候选就不运行）和跟进案件（按开始时的状态定为持仓跟进或关注跟进；开始时已经是候选、或者不在股票池也不是持仓，就不运行。股票池的状态往下走时跟进由「跟进审批」作废；关注股买入变为持仓时跟进保留，这是 2026-10-08 人同意的「跟进审批」的推荐做法）。事件案件按开始时的状态定类型；开始时股票已经不在股票池、也不是持仓，就不运行。寻股和复盘不看状态
7. **各类事件至少派给哪个子 agent**：Proposal 只举了新闻事件至少调用 News。推荐把事件来源里的"新闻和公告"拆成两类，因为公告归 Fundamentals 解读：

   | 事件类别 | 至少派给 |
   | --- | --- |
   | 价格和成交量异动 | Quant |
   | 新闻 | News |
   | 公告 | Fundamentals |
   | 财报发布 | Fundamentals |
   | 关注股的入场条件满足 | Quant |
   | 持仓达到目标价或证伪条件触发 | Quant |

8. **什么样的 Result 算数**：推荐研究要求只算状态是"完成"的 Result，无信号、超时、失败、被拒绝都不算：开仓要有两个子 agent 真正给出判断。事件要求的子 agent 只看派没派过任务，不看 Result 的状态：超时或失败时，Proposal 规定 PM 在缺少该信息的情况下继续
9. **PM 的开仓方案必须写紧急阈值**：「Agent」要求开仓和加仓方案写紧急阈值，「风控引擎与执行」又说没写时用默认值。推荐 PM 写的买入和加仓方案必须写紧急阈值，默认值只留给手工录入的方案；有效期和允许价格偏离 PM 可以不写，用下单前再校验已经定好的默认值
