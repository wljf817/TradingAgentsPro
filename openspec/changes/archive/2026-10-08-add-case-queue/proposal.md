# Proposal

## Why

Proposal 规定所有触发都进入调度器的队列，按优先级、受并发上限约束依次启动，同一只股票同一时间只跑一个案件；同一只股票有新案件排队时作废等人工确认的开仓方案；紧急风险事件不排队，可以中止同一只股票正在运行的案件。上一个变更「案件类型与结论」已经能按触发和状态确定案件类型和优先级，但还没有东西决定"下一个运行哪些案件"。以前的变更也把几件事留给了调度器：

- 风控规则「需要人决定」第 5 条（已决定）：同一只股票有新案件排队时，作废这只股票所有还没提交订单的开仓方案，不论是否已经确认
- 紧急风险退出「需要人决定」第 5 条和 design D6、额度预留「需要人决定」第 4 条、紧急撤单的 Non-goals：紧急退出时作废这只股票还没下单的方案、中止正在运行的案件，作废以后用风控已有的"释放"释放预留
- 降级策略的「对后续变更的影响」：恢复后按优先级补跑积压的案件

本变更的目的只有一个：**决定下一个运行哪些案件，以及新案件排队或紧急退出时作废哪些方案、中止哪个案件。**

引用的 Proposal（完整版）章节：

- 「架构」的「调度器」：按优先级从队列取出；每个触发各自开一个案件；同一只股票同一时间只跑一个案件，其余排队依次运行
- 「调度器与运行模块」：案件流程第 6 步（风控 → 人工确认 → 执行，案件结束）；运行约束的并发上限和每日调用预算；排队规则全部六条
- 「故障处理」：降级模式（恢复后先对账，再按优先级补跑积压的案件）和紧急风险事件例外
- 「持仓与退出」的退出路径表：紧急风险退出"分钟级，可中止进行中的案件"

## What Changes

- 调度器模块增加队列的纯逻辑，没有 service 和存储。输入是一份快照，输出是决定：
  - 快照：排队的案件（案件 ID、触发、触发时刻，按入队的先后）；运行中的案件（案件 ID、案件类型、股票、是否还在调用模型的阶段）；每只股票还没提交订单的方案（方案 ID、动作、阶段：审核、等人工确认、等下单）；股票的状态；正在紧急退出的股票；是否处于降级模式；普通预算、寻股预算是否用完
  - 队列的决定：启动哪些案件（带开始时确定的案件类型）、哪些排队的案件不再运行、作废哪些方案
  - 紧急退出的决定：给定一只股票，中止哪个案件、作废哪些方案
- 每次决定都按现在的状态确定排队案件的类型，确定不了的不再运行；其余按优先级、触发时刻、入队的先后依次检查，能启动的就启动，直到并发上限：

  | 排队的案件 | 不能启动的情况，跳过、看下一个 |
  | --- | --- |
  | 任何案件 | 处于降级模式 |
  | 针对单只股票、复盘以外的案件 | 这只股票有复盘以外的案件在运行，或者正在紧急退出 |
  | 寻股 | 已经有寻股在运行；寻股预算用完 |
  | 关注、候选的案件和复盘案件 | 普通预算用完 |

  持仓的五种案件在普通预算用完后照常启动，改用持仓保留预算。并发上限只计还在调用模型的案件；运行中的案件不被打断，紧急退出除外

- 作废：这只股票有复盘以外的案件在排队时，作废它已经交给人工确认、还没提交订单的开仓类方案（等人工确认或已确认等下单）；还在审核的方案和退出类方案不作废。每次决定都检查，所以新案件排队时、方案进入人工确认时都会作废
- 紧急退出：中止这只股票正在运行的、复盘以外的案件，作废这只股票还没提交订单的全部方案；排队的案件不动，等紧急退出结束后按新的状态运行
- 作废以后由调用方调用风控的释放（M4 接线）
- 可配置项：并发上限，默认 3

## Non-goals

- 案件状态机（唤醒 PM → Critic → 风控 → 人工确认 → 执行）、运行中的案件是否还在调用模型的阶段、方案被作废或案件被中止以后案件怎么结束、通知谁、风控拒绝或再校验作废以后案件结束（已决定：「退回 PM」就是案件结束、记下原因，不在同一个案件里重来）、案件因为故障没有结论时怎么结束：属于「案件阶段」
- 什么时候开心跳案件、候选评估的每天上限和按评分开、寻股的触发条件和冷却期、降级期间到期的复查日顺延到恢复后的第一个交易日：属于「收盘检查」
- 获批的跟进什么时候入队：属于「跟进审批」
- 普通预算、持仓保留预算和寻股预算怎么算、什么时候算用完、按交易日恢复：属于「调用预算」。本变更只接收"普通预算用完""寻股预算用完"两个标志
- 每个案件派发的任务数和任务级的并发：属于「任务派发」
- 确认超时、紧急退出需要人工确认的开关：属于「人工确认的规则」
- M2 手工录入的方案不属于任何案件，不在快照里：紧急退出时怎么作废它们，由 M2 的紧急退出流程处理；紧急退出的撤单和清仓卖单也是 M2 的流程
- 队列和运行中的案件存在哪里、什么时候调用、从各模块组出快照、执行决定（释放预留、启动和中止案件工作流、生成快照、写案件记录）、同一时间只执行一个决定、触发去重：M4

## Capabilities

### New Capabilities

- `case-queue`：快照和决定的格式；排队的案件按现在的状态确定类型；启动的顺序；并发上限；同一只股票一次一个案件（复盘例外、寻股一次一个、紧急退出期间不启动）；降级模式和调用预算下的启动；新案件排队时作废开仓方案；紧急退出时中止案件、作废方案；并发上限的配置

### Modified Capabilities

无。调度器的配置增加并发上限，case-types spec 的要求不变。

## Impact

- **代码**：
  - 新增 `modules/scheduler/domain/queue.py`：快照、决定、方案的阶段，队列的决定和紧急退出的决定两个纯函数
  - `modules/scheduler/config.py`：`SchedulerConfig` 增加并发上限
  - `modules/scheduler/__init__.py`：增加导出
  - contracts 不变
- **测试**：新增 `tests/modules/scheduler/domain/test_queue.py`、`tests/modules/scheduler/domain/test_queue_machine.py`（性质测试）；`tests/modules/scheduler/builders.py` 增加队列的基准数据；`tests/modules/scheduler/test_config.py` 增加并发上限
- **依赖**：无
- **文档**：完整版 Proposal 在「调度器与运行模块」和「故障处理」补上已决定和新发现的条目，每处一两句话
- **对后续变更的影响**：
  - 案件阶段：给出运行中的案件是否还在调用模型的阶段，以及方案的阶段；方案被作废、案件被中止以后结束案件
  - 收盘检查：同一时刻开出的心跳案件按想要的先后入队（候选评估按评分从高到低）
  - 调用预算：给出普通预算和寻股预算是否用完
  - 人工确认的规则：方案进入等人工确认、确认以后要触发一次队列的决定；确认超时的方案释放预留
  - M2 的紧急退出流程：手工录入的方案自己作废
  - M4：存队列，组快照，任何输入变化以后取得队列的决定并按顺序执行（先作废、释放预留，再结束不再运行的案件，最后启动）；紧急退出时先取得紧急退出的决定，中止案件、作废方案、释放预留，再撤单下清仓单；清仓卖单结束前把这只股票记为正在紧急退出

## 需要人决定

已决定（2026-10-08）：

1. **降级期间开不开新案件**：Proposal 只写了"恢复后先对账，再按优先级补跑积压的持仓案件"，没说降级期间开不开案件，也没说积压的非持仓案件怎么办。决定：降级期间不开始新案件，新的触发照常排队；恢复（对账完成，健康监控回到正常）后整个队列按优先级运行，持仓案件自然在前，非持仓的也不丢
2. **普通预算用完以后**：Proposal 写"普通预算用完后只处理持仓相关的案件"，没说其余案件怎么办。决定：只有持仓相关的案件（针对持仓状态的五种案件类型）照常启动，它们改用持仓保留预算；非持仓案件留在队列里，等下一个交易日预算恢复后按优先级运行。寻股用单独的预算，只看寻股预算是否用完；复盘案件用普通预算。预算怎么算、什么时候算用完属于「调用预算」，本变更只接收"普通预算用完""寻股预算用完"两个标志

新发现的，已按推荐做法写进 spec，不同意可以改：

3. **作废的范围从人工确认开始**：Proposal 写"运行中不打断"，又写"开仓类方案正在等人工确认、有新案件排队时作废"。推荐：还在 PM、Critic 审核和风控阶段的方案属于运行中的案件，不打断；方案进入等人工确认（以及已确认、等开盘、还没提交订单）时，只要这只股票有新案件在排队，就作废。所以这是一个随时成立的条件：新案件排队时检查一次，方案进入人工确认时也检查一次
4. **只有复盘案件以外的新案件会触发作废**：复盘不阻塞这只股票的其他案件，也不该让开仓方案作废
5. **并发上限只计还在调用模型的案件**：案件要执行完才结束，等人工确认可能要几个小时（夜里确认、确认后等开盘）。如果这些案件也占名额，三个等确认的案件就能让持仓风险事件一直排着。并发上限是为了不触发 API 频率限制，推荐：只计还在调用模型的案件（唤醒 PM 到 Critic 审核结束，复盘案件一直算）；风控、等人工确认、等下单的案件不计入，但仍然占着这只股票。上限只限制启动，已经在跑的案件不因为超出上限（比如调低配置以后重启）被中止
6. **寻股同一时间只跑一个**：寻股不针对单只股票，"一只股票一个案件"管不到它。两个寻股同时跑，会基于同一份快照加入重复的候选，也会按同一份快照估计池子容量和当天的增删次数。推荐：同一时间最多一个寻股案件，不做成配置；两次寻股之间本来就有冷却期，很少同时排着两个
7. **紧急退出进行中的股票不启动新案件**：紧急退出往往伴随同一只股票的持仓风险事件。中止运行中的案件以后，如果排队的持仓风险事件马上开始，PM 分析的是一只正在被清仓的股票，结论多半没用。推荐：这只股票的清仓卖单结束（成交、被拒或撤销）以前，它排队的案件不启动；结束以后按新的状态运行（代码触发的清仓转为候选：持仓复查不再运行，事件案件变成候选股事件）。复盘案件不受影响
8. **紧急退出不中止复盘案件**：复盘不下单、不产生方案，和"复盘不受一只股票一个案件的限制"一致
9. **排队期间确定不了类型就不再运行**：「案件类型与结论」定的是开始运行时确定类型、确定不了就不运行。排队时要按现在的状态算优先级，确定不了类型的案件没有优先级可排。推荐：每次决定都按现在的状态确定类型，确定不了的马上不再运行，不等轮到它。只有状态变走又变回来时（比如候选升级为关注又降回候选）两种做法结果不同，这时原来的检查项已经过时
10. **触发时间相同按入队的先后**：收盘检查一次开出的心跳案件触发时间相同。推荐：同优先级、同触发时间的案件按入队的先后启动；收盘检查按评分从高到低把候选评估入队，启动时也就按评分
