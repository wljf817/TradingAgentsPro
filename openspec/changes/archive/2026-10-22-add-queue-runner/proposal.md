# Proposal

## Why

M3 的「案件队列」只是一个纯函数：给它一份快照，它算出启动哪些排队的案件、哪些不再运行、作废哪些方案。M4 的「案件工作流」能跑完一个案件，「方案接下单」能把方案下到模拟盘，但现在没有排队的地方，也没有谁按队列的决定去启动案件：案件工作流和交接还没有装配，进程里一个案件都跑不起来。

本变更的目的只有一个：**让排进来的案件按 case-queue 的规则持久地排队、启动、作废和不再运行，并把它和案件工作流一起装配进程序。**

引用的 Proposal（完整版）章节：

- 「架构」的模块表和调度器一段：调度器管队列和优先级，只负责"什么时候做什么"，不调用模型、不下单；每次触发开一个案件，状态写入共享状态库
- 「运行约束」：并发上限只计还在调用模型的案件；普通预算用完只处理持仓案件，寻股看寻股预算；预算只在案件开始时看
- 「排队规则」：每只股票一次一个、每个触发一个案件、开始运行时按当时的状态定类型、新案件排队时作废已交人工确认的开仓类方案、全局按优先级启动
- 「故障处理」：健康监控检查调度器心跳；降级模式不开始新案件，新的触发照常排队，恢复以后按优先级运行积压的案件
- 「记录、复盘与经验」的程序日志表：调度器写排队、方案作废；系统写调用预算消耗
- 「技术栈与部署」：DBOS 一行（案件工作流、队列）；可靠性要求（进程崩溃后由 DBOS 恢复进行中的案件）

已经定了的（不在本变更里讨论）：case-queue spec 的全部规则；案件工作流给队列的接口（`start_case`、`case_progress`，add-case-workflow 的 design D3）；方案作废时下单那一侧报告确认消息已作废、释放预留（update-order-flow-case-plans 的交接说明）；预算用完的程序日志由本变更写（update-task-cost-storage 的「需要人决定」第 2 条）。

## What Changes

- 排队运行（新的 queue-runner）：
  - 排队：触发源交来触发和触发时刻，队列分配新的案件 ID，记下入队的先后，写程序日志的排队。排队的案件存在状态库里，进程重启不丢
  - 一轮：每隔一个间隔（默认 5 秒）组出队列的快照（排队的案件；运行中的案件和还没提交订单的方案取自案件的进展；股票池的状态；正在紧急退出的股票；是否处于降级模式；普通预算和寻股预算是否用完），取得队列的决定，按作废、不再运行、启动的顺序执行
  - 作废：写程序日志的方案作废，交给这个方案的下单流程去作废；下单流程报告确认消息已作废、释放预留，再把"方案被作废"送回案件，案件按 `CaseState.void()` 结束
  - 不再运行：写案件记录的不再运行和程序日志的不再运行；启动：开始运行案件工作流
  - 调度器心跳：排队运行最近一次做完一轮的时刻，交给健康监控
  - 调用预算用完：这次运行里每个交易日、每个预算第一次看到用完时写一条程序日志
- 下单流程（order-flow）：等确认、等开盘、等重试时收到作废就结束：确认消息改为已作废，释放预留，送回方案被作废；已经确认的方案作废时告警
- 案件工作流（case-workflow）：等下单那一侧的结果时，收到方案被作废就结束
- 健康监控接线（health-monitoring）：PM 和 Critic 还有没有可用的模型、持仓保留预算用完、调度器心跳改为取 Agent 网关和排队运行给出的，不再写死
- 启动与装配（bootstrap）：装配 M4 的网关（任务、费用、备用模型、预算，模型用替身）、新闻和公告、公司数据、寻股粗筛、快照、案件记录、案件工作流和交接、排队运行；新增环境变量 `FINNHUB_API_KEY`、`SEC_USER_AGENT`；DBOS 启动以前装上案件工作流，启动以后开始排队运行，再开始盘中巡检
- 程序日志（program-log）：调度器加排队、不再运行、方案作废；系统加调用预算用完
- 状态库（state-store）：调度器的两张表，迁移 v0013
- 部署（deployment）：Finnhub 的 key 放在主程序的环境变量文件里
- 完整版 Proposal「技术栈与部署」的 DBOS 一行改为：排队的案件存在状态库里，由调度器按排队规则决定启动哪些（见「需要人决定」第 1 条）

## Non-goals

- 触发源：事件检测、论点条件与到价提醒、收盘心跳、跟进到点（「触发」组）。本变更只提供排队的接口，没有谁调用它，部署以后队列一直是空的
- 紧急退出中止案件：`emergency_decision`、`PlanEvent` 的中止、案件在调用 agent 以前收中止（「紧急退出中止案件」）
- 手工开案件的命令：不做
- 案件的事后收益和复盘：M6
- case-queue 的规则、案件工作流里案件的步骤：不改
- 触发源在 DBOS 的 step 里排队时，step 重做会多排一个案件：由「触发」组各自处理
- 调用预算用完时推送告警：只写程序日志（见「需要人决定」第 4 条）
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `queue-runner`：排队、排队的案件的存储、一轮、作废方案、不再运行、启动、什么时候做一轮、调度器心跳、调用预算用完的日志、重启以后、排队运行的配置

### Modified Capabilities

- `order-flow`：新增「作废案件的方案」；修改「结果送回案件」（加方案被作废）
- `case-workflow`：修改「交给下单」（送回的结果加方案被作废）
- `health-monitoring`：修改「健康信号」（模型、持仓保留预算、调度器心跳三项的取值）
- `bootstrap`：修改「环境变量」「启动顺序」「模拟盘的装配」「第一次健康判定」「DBOS」「停止」
- `program-log`：修改「调度器的动作」（加排队、不再运行、方案作废）、「系统的动作」（加调用预算用完）
- `state-store`：修改「表的归属和迁移」（加调度器的两张表）
- `deployment`：修改「密钥」（加 Finnhub 的 key）

## 需要人决定

1. **完整版 Proposal 写的是用 DBOS 的持久化队列实现并发上限和优先级，本变更不用它**：装好的 DBOS 3.2.0 的队列做不到 case-queue 的规则：并发上限按整个工作流算，等人工确认的案件也占名额（规则只计还在调用模型的）；优先级在入队时就固定了（规则要按启动时的状态定类型和优先级）；分区队列（按股票分区，一只股票一次一个）里优先级只在分区内生效，各分区按随机顺序出队（`_queue.py` 里 `random.shuffle(partition_keys)`），全局的优先级不成立；也表达不了降级不启动、预算用完只跑持仓案件。
   推荐：排队的案件存在状态库里（调度器的两张表），由排队运行按 case-queue 的纯函数决定启动，DBOS 只负责每个案件的工作流。完整版「技术栈与部署」那一行已经照这个改了：删掉"用其持久化队列实现并发上限和优先级"，加上"排队的案件存在状态库里，由调度器按排队规则决定启动哪些"
2. **作废一个已经确认、在等开盘的开仓方案时要不要告警**：Proposal 只说标记为过期并作废、释放预留。
   推荐：已经确认的告警，写明方案作废、不会下单、原因是这只股票有新案件排队（和下单流程现有的"已经确认的方案作废"告警一样）；还在等确认的不告警，确认消息改为已作废。理由：人按了确认会以为它会下单，不会再回去看那条消息
3. **方案刚进入等人工确认时已经有案件排队**：排队运行每 5 秒做一轮，确认消息会先发出来，最多一轮以后改为已作废；这几秒里按了确认，盘中会直接下单。
   推荐：接受。理由：要避免就得让下单流程发确认以前先问队列，两个流程互相依赖，换来的只是少一条很快作废的消息；人几秒内按确认的情况很少，而且下单以后新案件照常运行
4. **调用预算用完时要不要推送告警**：Proposal 只在程序日志里列了调用预算消耗。
   推荐：只写程序日志，不推送。理由：普通预算和寻股预算用完只是案件晚一点跑，下一个交易日自动恢复；持仓保留预算用完时健康监控进入降级模式，那时已经有告警
