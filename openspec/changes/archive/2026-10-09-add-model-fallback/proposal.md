# Proposal

## Why

Proposal 要求每个 agent 配一个主模型和按顺序的备用模型，主模型不可用时由 Agent 网关自动切换；同一个模型短时间内连续失败要熔断；PM 或 Critic 的主模型和备用模型全部不可用才算模型 API 异常。前面的变更都把这部分留给了本变更：task-dispatch 规定了调用失败的 Result，"什么时候算调用失败由「备用模型」规定"，Result 还要加上实际使用的模型；degraded-mode 的健康检查要调用方传入"PM、Critic 是否还有可用的模型"，并把单个模型的熔断留给 Agent 网关；case-stages 已经按"Agent 网关对 Critic 返回失败"处理 Critic 不可用。但现在没有模型的配置，也没有东西决定一次调用换不换模型、换到哪个、哪个模型在冷却中。

本变更的目的只有一个：**主模型不可用时按顺序切换备用模型——什么算不可用、切换顺序、案件内不切回、熔断、厂商校验和用备用模型时限制结论，并给出 PM 和 Critic 是否还有可用的模型。**

引用的 Proposal（完整版）章节：

- 「Agent」开头一段（每个 agent 用哪个模型写在配置文件里）、Agent 表的"模型"一列（Critic 与 PM 不同厂商，包括双方的备用模型，启动时校验配置）、「备用模型」全段
- 「调度器与运行模块」：Agent 网关一行（主模型不可用时切换备用模型）；运行约束里"每个 agent 调用有超时和重试次数，重试用完后按顺序切换备用模型；主模型和备用模型全部失败，才返回「失败」Result 并告警"一句
- 「故障处理」开头两段：单个模型不可用时先切换备用模型，不进入降级模式；PM 或 Critic 的主模型和备用模型全部不可用才算模型 API 异常；子 agent 全部不可用时只返回「失败」Result
- 「架构」的「支撑模块」健康监控一条：单个模型不可用时先换备用模型

## What Changes

- 模型的配置：六个 agent（PM、News、Quant、Fundamentals、Critic、Reviewer）各一个主模型，可以按顺序配 0 个或多个备用模型；每个模型写厂商和模型名。缺少 agent、同一个 agent 的模型重复都是配置报错
- 厂商校验：Critic 的主模型和备用模型都必须和 PM 的主模型和备用模型不同厂商，不满足就配置报错；bootstrap 启动时构造配置，报错就拒绝启动
- 什么算不可用：一个模型在一次调用里的尝试都失败（超时、连接失败、限流、额度或余额用完、认证失败、服务端出错等调用错误），每个模型最多重试"重试次数"次。输出格式不合法不算不可用，在本变更看来是调用成功
- 每次尝试的超时：子 agent 默认 60 秒，并且不超过离任务截止时间还剩的时间，到了截止时间就停止、任务记超时；PM、Critic、Reviewer 默认 180 秒。配置保证主模型和第一个备用模型的全部尝试放得进任务时限
- 切换顺序：从本案件这个 agent 的起点开始按配置顺序逐个尝试，冷却中的直接跳过；全部不可用时给出调用失败和说明，作为告警的依据
- 案件内不切回：调用成功以后，成功用的模型就是本案件这个 agent 的起点，之后只往后换、不往回换；下一个案件从主模型开始；案件结束时清掉
- 熔断：按模型计、不分 agent。最近连续 3 次不可用都在 10 分钟以内就冷却 5 分钟，冷却中直接跳过；冷却结束以后试一次，成功恢复正常，又不可用就再冷却。状态放在内存里，进程重启以后从头算
- 还有可用的模型：主模型或任何一个备用模型不在冷却中就算有；PM、Critic 的这两项交给健康监控
- 实际使用的模型：调用成功时给出成功的模型和它是不是备用模型。contracts 的 Result 加上这一项：有输出的 Result（完成、无信号、格式不合法的失败）记下给出输出的模型
- 切换的事件：每次切换给出案件、agent、从哪个模型换到哪个、原因和时刻，调用方写进程序日志
- 备用模型的限制：PM 提交结论的调用用的是备用模型时，决定不能是开仓方案、加仓或升级（可配置，默认打开）；被限制时调用方按结论校验不通过退回 PM 重交
- 可配置项：重试次数 1、子 agent 的单次调用超时 60 秒、PM/Critic/Reviewer 的单次调用超时 180 秒、熔断的连续不可用次数 3、熔断的时间窗口 10 分钟、冷却时间 5 分钟、PM 用备用模型时不能提的决定（开仓方案、加仓、升级）

## Non-goals

- 「调用预算」：每日预算、预算用完时怎样、费用怎么算。本系统的调用预算用完不算模型不可用；本变更的"额度或余额用完"只指厂商返回的这类调用错误
- 「人工确认的规则」
- M4：
  - 把切换的事件、全部不可用写进程序日志，全部不可用时告警
  - 把 PM、Critic 是否还有可用的模型和冷却中的模型交给健康监控
  - bootstrap 从配置文件读取模型的配置，配置报错时拒绝启动
  - 案件结束时告诉网关；被限制的结论交给案件状态当作结论校验不通过；PM 和 Critic 全部不可用时交给案件状态（系统故障、Critic 不可用）
  - 案件记录里记下 PM 的结论和 Critic 的审核实际使用的模型
- M5：
  - 真正调用模型、PydanticAI 的接线；把调用异常归成本变更的调用错误；关掉厂商 SDK 自带的重试
  - 各 agent 用哪家哪个模型
  - 提示里告诉 PM 正在用备用模型、哪些决定不能提
- 按实际使用的模型统计评估：M6
- Critic 按开仓和退出、Reviewer 按每周复盘和卖出复盘分别配模型：见「需要人决定」第 10 条

## Capabilities

### New Capabilities

- `model-fallback`：模型的配置、厂商校验、什么算不可用、尝试的超时、切换顺序、案件内不切回、熔断、还有可用的模型、实际使用的模型、切换的事件、备用模型的限制、备用模型的配置

### Modified Capabilities

- `task-dispatch`：「Result 的格式」加上实际使用的模型；「子 agent 的输出变成 Result」由调用方给出给出输出的模型；「调用失败」写明是 model-fallback 的全部不可用，到了截止时间停止尝试时不给出调用失败
- `case-stages`：「唤醒 PM 和结论」写明 PM 用备用模型时提了被限制的决定也算结论校验不通过（只改措辞，调度器代码不改）

## 需要人决定

新发现的，已按推荐做法写进 spec，不同意可以改：

1. **可选限制限哪些决定、默认开不开**：「备用模型」的例子是"不能提开仓方案和升级为关注，只能做无动作、论点更新、退出类方案和跟进申请"，没提加仓，"只能做"的清单也漏了降为候选、移出、保持和寻股增删。推荐按 case-types 的决定列出不能提的：开仓方案、加仓、升级（加仓和开仓方案一样增加风险），其他决定都允许，寻股的结论没有决定、不限制；只限制 PM。默认打开：主模型是按评测选的，备用模型没有经过同样的评测；限制只在少数用到备用模型的案件里生效，错过的机会下一次事件或复查还会再看。Proposal 改为列出不能提的决定
2. **被限制的结论怎么办**：推荐和结论校验不通过一样，退回 PM 在同一个案件里重交，计入重交次数（最多 2 次），原因是"用备用模型时不能提这个决定"；PM 仍用这个备用模型，可以改为继续关注并申请跟进、论点更新等；重交用完按结论无效结束。直接结束案件会丢掉 PM 这次还能给的其他结论。case-stages spec 只改措辞
3. **子 agent 的重试和切换放不进 5 分钟**：运行约束说"重试用完后按顺序切换；全部失败才返回「失败」"，但子 agent 的任务只有 5 分钟，备用模型多、每次都超时的话试不完。推荐截止时间优先：每次尝试的超时不超过离截止时间还剩的时间，到了截止时间就停止，任务记超时（不是失败，也不告警）；配置保证主模型和第一个备用模型的全部尝试放得进任务时限（默认 2 次 × 60 秒 × 2 = 4 分钟），后面的备用模型在前面的很快失败时（连接失败、限流、认证失败通常几秒）才轮得到。PM、Critic、Reviewer 没有任务时限，输出也更长，单次超时另设 180 秒
4. **"额度或预算用完"指什么**：推荐指厂商返回的额度或账户余额用完；本系统自己的调用预算用完由「调用预算」处理，不算模型不可用，不切换也不计熔断，因为换了备用模型同样超预算。Proposal 改为"厂商的额度或余额用完"
5. **熔断数什么、冷却以后怎么试**：推荐数"不可用"（一个模型在一次调用里重试用完仍失败），不数单次尝试，和「什么算不可用」同一个口径；连续指中间没有成功，格式不合法的输出也算成功；最近连续 3 次都在 10 分钟以内就冷却 5 分钟。冷却结束以后不重新数满 3 次，而是试一次：成功恢复正常，又不可用就直接再冷却，免得故障没恢复时每次都再赔 3 次调用。按模型数、不分 agent，几个 agent 共用一个模型时一起数
6. **状态放在内存里**：熔断状态和案件里固定的起点都和健康监控一样放在内存里，进程重启以后从头算：所有模型从正常开始，第一次不可用以后照常切换和计数；不存储省掉一个端口和一张表。代价是重启时正在运行、已经切到备用模型的案件，剩下的调用从主模型开始（极少见）
7. **案件内固定哪个模型**：推荐以调用成功用的模型为准：切到备用模型并且成功以后，本案件这个 agent 之后的调用都从这个备用模型开始，只往后换、不往回换；全部不可用的调用不改变起点，下一次仍从原来的起点试。起点在冷却中或者不可用时往后换，后面没有了就是全部不可用，不回到前面的模型
8. **重试怎么做**：推荐每个模型重试 1 次（最多 2 次尝试），重试前不等待，不分错误种类。限流时马上重试多半仍失败，正好很快换到备用模型；认证失败、额度用完重试也没用，但失败很快、不花钱，不值得区分。厂商 SDK 自带的重试由 M5 关掉，次数由网关数
9. **什么算"厂商"**：推荐指模型出自哪家公司（比如 anthropic、openai、google），不是调用的平台：经云平台调用的 Claude 仍是 anthropic。厂商去掉首尾空白、转成小写再比较，避免大小写不同的同一家通过校验。同一个 agent 的主模型和备用模型不能重复
10. **Critic 和 Reviewer 按用途换模型**：Agent 表写 Critic "审核开仓方案建议用较强的模型，退出方案可用 flash 模型"、Reviewer "每周复盘用 Claude；卖出复盘可用便宜模型"，和"每个 agent 配一个主模型"不完全一致。推荐第一版每个 agent 一套主备模型，表里的写法当作选模型的建议：退出审核只有 1 轮、卖出复盘次数少，用同一套模型多花的钱不多；以后费用需要时再用修改类变更按用途拆开。Proposal 在表下补一句
