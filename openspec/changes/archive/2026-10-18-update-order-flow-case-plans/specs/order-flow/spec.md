# Spec Delta

## ADDED Requirements

### Requirement: 案件的方案

案件工作流把一个方案交给下单流程时（case-workflow spec「交给下单」），给出案件 ID、方案和 Critic 审核的结果（case-stages spec「案件的状态」：通过、有分歧、Critic 不可用）。下单流程 SHALL 按「提交方案」的第 1、2 步读账户数据、拿锁检查并预留，再按下表处理：

| 情况 | 处理 | 交给案件 |
| --- | --- | --- |
| 读券商账户超时、断线或出错 | 不检查、不预留、不启动下单流程；写一条 WARNING，写明方案 ID 和原因 | 风控检查出错 |
| 风控拒绝 | 不启动下单流程 | 风控结果 |
| 风控通过或调整 | 按 confirmation-rules spec「案件方案的确认」决定要不要人工确认、确认超时以后要不要告警，是否处于降级模式用这次检查读到的；以方案 ID 启动这个方案的下单流程，带上案件 ID、Critic 审核的结果和这两项决定 | 风控结果，以及要不要人工确认 |

- 不要人工确认的方案（模型退出自动执行）：风控检查以后写一条程序日志的自动执行（program-log spec「系统的动作」）；下单流程不请求确认，直接进入「等开盘」
- 案件的方案不写录入方案：录入方案是人用 `/plan` 的动作
- 案件工作流重放时（case-workflow spec「崩溃恢复」）不再检查、不另起下单流程，交给案件的仍是第一次的结果
- 之后的确认、等开盘、再校验和提交、告警、持久化和恢复，和 `/plan` 的方案相同，不同的地方写在「请求人工确认」「确认的结果」「告警」「日志」和「结果送回案件」里

本要求和「结果送回案件」的场景另外使用下面的数据：

- 案件 K1 交来 P1，Critic 审核的结果是通过；案件 K3 交来 P3，Critic 审核的结果是通过。"K1 交来 P1"指案件工作流以案件 ID K1、方案 P1 和 Critic 审核的结果交给下单流程
- "送回"指下单流程按案件 ID 送给案件的结果（case-workflow spec「交给下单」）
- 模型退出自动执行没有说明时是关闭的（默认值）

#### Scenario: 案件的开仓方案通过

- **WHEN** K1 交来 P1
- **THEN** 交给 K1 的是风控通过、最终 20 股、要人工确认
- **AND** BBB 有一份 20 股的开仓预留；频道里出现 P1 的确认消息，不附案件的意见
- **AND** 程序日志有 P1 的风控检查，没有录入方案

#### Scenario: 案件的方案被风控拒绝

- **GIVEN** 处于降级模式
- **WHEN** K1 交来 P1
- **THEN** 交给 K1 的是风控拒绝，原因是"降级模式"
- **AND** BBB 没有预留，频道里没有 P1 的确认消息，P1 没有下单流程

#### Scenario: 风控检查出错

- **GIVEN** 读券商账户时超时
- **WHEN** K1 交来 P1
- **THEN** 交给 K1 的是风控检查出错
- **AND** BBB 没有预留，没有确认消息；有一条 WARNING 写明 P1 和券商不可用

#### Scenario: 自动执行的退出方案

- **GIVEN** 模型退出自动执行打开
- **WHEN** K3 交来 P3
- **THEN** 交给 K3 的是风控通过、最终 10 股、不要人工确认
- **AND** 频道里没有 P3 的确认消息；程序日志在 P3 的风控检查以后有一条自动执行
- **AND** P3 有订单：卖出 AAA 10 股，市价单（止损单让出股数以后券商才收到，stop-protection spec「卖单先让出股数」）

#### Scenario: 自动执行打开时仍要确认的方案

- **GIVEN** 模型退出自动执行打开
- **WHEN** K1 交来 P1；K3 交来 P3，Critic 审核的结果是有分歧
- **THEN** 交给 K1、K3 的都是要人工确认，频道里各有一条确认消息
- **AND** 程序日志没有自动执行

#### Scenario: 降级模式下的退出方案要确认

- **GIVEN** 模型退出自动执行打开；处于降级模式
- **WHEN** K3 交来 P3
- **THEN** 交给 K3 的是风控通过、最终 10 股、要人工确认；频道里出现 P3 的确认消息

### Requirement: 结果送回案件

案件的方案的下单流程 SHALL 在下表的每个结局把结果按案件 ID 送回案件，`/plan` 录入的方案不送：

| 下单流程 | 送回 |
| --- | --- |
| 收下确认（「确认的结果」） | 已确认 |
| 收下拒绝 | 已拒绝 |
| 确认超时；确认请求发不出去 | 已超时 |
| 订单交给盘中巡检：提交返回订单（包括券商拒绝受理、状态未知），或者作废时这个方案已经有订单 | 订单已提交 |
| 确认以后（或者不要确认的方案）作废：再校验拒绝、到有效期还没下单、对账不一致 | 再校验作废 |
| 意料之外的错误让下单流程停下（比如释放预留时状态库出错） | 出错；送回以后下单流程停下 |

- 已确认在确认以后立即送回，然后才等开盘；不要确认的方案不送已确认
- 每个结局只送一次：进程重启以后已经送回的不再送
- 释放预留、告警和程序日志照「确认的结果」「下单前再校验和提交」「提交的结果」「告警」「日志」，送回结果不改变它们
- 等开盘、等重试时不送回：案件在等下单时一直等（case-stages spec「等下单」）

#### Scenario: 确认以后下单

- **GIVEN** K1 交来 P1
- **WHEN** 2026-10-14 15:05Z 按确认，券商受理 P1
- **THEN** 依次送回 K1：已确认、订单已提交

#### Scenario: 拒绝和超时

- **GIVEN** K1 交来 P1
- **WHEN** 按拒绝
- **THEN** 送回 K1：已拒绝；BBB 没有有效预留
- **WHEN** 同样的情况下一直没有人按到 2026-10-14 15:30Z
- **THEN** 送回 K1：已超时

#### Scenario: 确认请求发不出去

- **GIVEN** Discord 对发消息报错
- **WHEN** K1 交来 P1
- **THEN** 送回 K1：已超时；BBB 没有有效预留

#### Scenario: 盘后确认等到开盘

- **GIVEN** 当前时刻 2026-10-14 21:00Z；K1 交来 P1，生效的有效期 2026-10-15 20:00Z
- **WHEN** 21:05Z 按确认
- **THEN** 送回 K1：已确认；没有别的结果
- **WHEN** 到了 2026-10-15 13:30Z，BBB 最新价 50，券商受理 P1
- **THEN** 送回 K1：订单已提交

#### Scenario: 再校验作废

- **GIVEN** 当前时刻 2026-10-14 21:00Z；K1 交来 P1，21:05Z 按确认
- **WHEN** 2026-10-15 13:30Z，BBB 最新价 53
- **THEN** P1 作废，原因是"价格偏离"；依次送回 K1：已确认、再校验作废

#### Scenario: 到有效期作废

- **GIVEN** 案件 K4 交来 P4，Critic 审核的结果是通过；AAA 一直是无保护仓位
- **WHEN** 2026-10-14 19:59Z 按确认，到了 20:00Z 以后
- **THEN** P4 作废，原因是有效期；依次送回 K4：已确认、再校验作废

#### Scenario: 券商拒绝受理也是订单已提交

- **GIVEN** K1 交来 P1；券商会拒绝受理 P1
- **WHEN** 按确认
- **THEN** P1 的订单已拒绝，推送一条告警；依次送回 K1：已确认、订单已提交

#### Scenario: 自动执行的方案

- **GIVEN** 模型退出自动执行打开
- **WHEN** K3 交来 P3，P3 有订单
- **THEN** 只送回 K3 一个结果：订单已提交

#### Scenario: 意料之外的错误

- **GIVEN** K1 交来 P1；按拒绝以后释放预留时状态库会出错
- **WHEN** 按拒绝
- **THEN** 送回 K1：出错；P1 的下单流程出错停下
- **AND** 没有再送回别的结果

#### Scenario: 重启以后不重送

- **GIVEN** 当前时刻 2026-10-14 21:00Z；K1 交来 P1，21:05Z 按确认，已经送回已确认
- **WHEN** 程序在 2026-10-14 23:00Z 重启；2026-10-15 13:30Z 券商受理 P1
- **THEN** K1 一共收到两个结果：已确认、订单已提交

#### Scenario: /plan 的方案不送回

- **WHEN** 本人用 `/plan` 提交 P1，按确认，券商受理 P1
- **THEN** 没有送给任何案件的结果

## MODIFIED Requirements

### Requirement: 请求人工确认

下单流程开始以后，`/plan` 录入的方案 SHALL 立即请求人工确认（discord-notification spec「确认请求和截止时刻」「确认消息」），四种动作（买入、加仓、减仓、清仓）都要；案件的方案 SHALL 按「案件的方案」的决定：要人工确认的立即请求，不要的不请求，直接进入「等开盘」。确认消息用提交时的风控结果：股数是最终股数，调整时写明已被风控调整和原因。截止时刻是请求的时刻加上确认超时。

案件的方案的确认消息 SHALL 按 Critic 审核的结果附上案件的意见（case-stages spec「人工确认」，discord-notification spec「确认消息」），在请求确认时从案件记录读：

| Critic 审核的结果 | 附上 |
| --- | --- |
| 通过 | 不附 |
| 有分歧 | 这个案件的结论的理由（PM 的方案理由），方案记录里 Critic 的每次审核和 PM 的每轮回应，按先后 |
| Critic 不可用 | 注明 Critic 不可用，方案没有经过审核 |

请求确认时 MUST NOT 拿着锁。

确认请求发不出去（通知不可用：Discord 报错、超过发送超时、没有连接）时，SHALL 按确认超时处理（Proposal「技术栈与部署」）：释放这个方案的全部预留，写一条 ERROR，写明方案 ID 和原因；下单流程结束，不再请求。案件的方案「案件的方案」决定确认超时以后告警的，SHALL 推送告警（见「告警」）；其余不告警。

#### Scenario: 四种动作都请求确认

- **WHEN** 先后提交 P1、P2、P3、P4
- **THEN** 频道里依次出现四条确认消息：买入 BBB 20 股、减仓 AAA 4 股、清仓 AAA 6 股（扣除 P2 的 4 股卖出预留）、加仓 AAA 5 股
- **AND** 四条消息的截止时刻都是 2026-10-14 15:30Z

#### Scenario: 确认请求发不出去

- **GIVEN** Discord 对发消息报错
- **WHEN** 提交 P1
- **THEN** 提交接口返回通过，最终 20 股
- **AND** 之后 BBB 没有有效预留；有一条 ERROR 写明 P1 的确认请求没有发出去和原因
- **AND** 券商没有收到 P1 的订单，P1 的下单流程已经结束

#### Scenario: 有分歧的案件方案附上双方意见

- **GIVEN** K1 的结论的理由是"新品周期带动收入加速"；K1 的方案记录依次有：Critic 质询（理由"止损太近"，质询"止损价 45 离限价只有 10%"）、PM 维持（回应"财报前不调整"）、Critic 质询（理由"仍然太近"，质询"波动率上升"）、PM 修改（回应"止损放宽到 44"，新的条款止损价 44）、Critic 质询（理由"仍有分歧"，质询"仓位偏大"）
- **WHEN** K1 交来修改后的 P1（止损价 44），Critic 审核的结果是有分歧
- **THEN** P1 的确认消息附上：K1 的结论的理由，以及按先后的三次审核和两轮回应

#### Scenario: Critic 不可用的退出方案

- **WHEN** K3 交来 P3，Critic 审核的结果是 Critic 不可用
- **THEN** P3 的确认消息注明 Critic 不可用、方案没有经过审核

#### Scenario: 退出方案的确认请求发不出去

- **GIVEN** Discord 对发消息报错
- **WHEN** K3 交来 P3
- **THEN** AAA 没有 P3 的有效预留；推送告警，写明 P3 没有执行、止损单照挂；告警也没有发出去，有一条错误日志
- **AND** 券商没有收到 P3 的订单

### Requirement: 确认的结果

下单流程 SHALL 等确认的结果，按下表处理：

| 结果 | 处理 |
| --- | --- |
| 截止时刻之前按确认 | 进入「等开盘」；不再请求确认 |
| 截止时刻之前按拒绝 | 释放全部预留；下单流程结束；不告警 |
| 到截止时刻没有结果 | 报告确认消息已超时（discord-notification spec「结束确认」），释放全部预留；下单流程结束。案件的方案「案件的方案」决定超时以后告警的推送告警（见「告警」），其余不告警 |
| 确认请求发不出去 | 见「请求人工确认」 |

#### Scenario: 盘中确认后立即下单

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按确认
- **THEN** 确认消息显示已确认
- **AND** 券商收到 P1 的订单：买入 BBB 20 股，限价单，限价 50，当日有效
- **AND** BBB 的预留仍是 20 股：之后由盘中巡检跟进 P1 的订单（session-patrol spec）

#### Scenario: 人工拒绝

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:05Z 按拒绝
- **THEN** 确认消息显示已拒绝；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单，没有告警

#### Scenario: 确认超时

- **GIVEN** 已经提交 P1，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 确认消息显示已超时；BBB 没有有效预留
- **AND** 券商没有收到 P1 的订单，没有告警

#### Scenario: 案件的退出方案确认超时

- **GIVEN** K3 交来 P3，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 确认消息显示已超时；AAA 没有 P3 的有效预留
- **AND** 推送一条告警，写明 P3 确认超时、没有执行、持仓的止损单照挂

#### Scenario: 案件的开仓方案确认超时不告警

- **GIVEN** K1 交来 P1，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 确认消息显示已超时；没有告警

#### Scenario: 截止前一刻确认

- **GIVEN** 已经提交 P1
- **WHEN** 2026-10-14 15:29:59Z 按确认
- **THEN** 券商收到 P1 的订单

#### Scenario: 调整的方案按调整后的股数确认

- **GIVEN** 券商现金改为 505，已经提交 P1，结论为调整，最终 10 股
- **WHEN** 按确认，下单前再校验通过，最终 10 股（请求股数是预留的 10 股）
- **THEN** 券商收到 P1 的订单：买入 BBB 10 股

### Requirement: 告警

下单流程 SHALL 只为下面这些结果推送告警（discord-notification spec「告警」）：

| 结果 | 告警的内容 |
| --- | --- |
| 已经确认的方案作废：再校验拒绝、到有效期还没下单、对账不一致 | 方案作废、不会下单；动作、股票、股数、方案 ID；原因：再校验拒绝的写每条不通过的规则和说明，到有效期的写最近一次没能下单的原因（有的话），对账不一致的写暂停开仓 |
| 下单被券商拒绝 | 下单被券商拒绝；动作、股票、股数、方案 ID |
| 这个方案第一次出意外的错 | 下单出错和错误；动作、股票、方案 ID；每隔重试间隔重试，到有效期为止 |
| 案件的方案确认超时或确认请求发不出去，「案件的方案」决定超时以后告警（退出类方案） | 确认超时（或者确认请求没有发出去）、方案没有执行；动作、股票、股数、方案 ID；持仓的止损单照挂 |

不要人工确认的方案作废时，按第一行告警。

下面这些 SHALL NOT 告警，只写日志：人工拒绝、确认超时（确认消息已改为已超时）、确认请求发不出去（上表最后一行的除外）、等开盘、等重试、订单已提交、订单状态未知。

推送告警时 MUST NOT 拿着锁。告警发不出去时按 discord-notification spec 只写错误日志，下单流程照常继续。

#### Scenario: 再校验拒绝的告警

- **GIVEN** 当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认
- **WHEN** 2026-10-15 13:30Z，BBB 最新价 53
- **THEN** 告警写明：P1 作废，不会下单；买入 BBB 20 股；方案 ID；价格偏离：实时价 53 偏离限价 50 超过允许的 0.03

#### Scenario: 到有效期的告警

- **GIVEN** 已经提交 P4；AAA 一直是无保护仓位；2026-10-14 19:59Z 按确认
- **WHEN** 到了 2026-10-14 20:00Z 以后
- **THEN** 告警写明：P4 作废，不会下单；加仓 AAA 5 股；原因是到了有效期，最近一次没能下单的原因是 AAA 是无保护仓位

#### Scenario: 人工拒绝和确认超时不告警

- **GIVEN** 已经提交 P1 和 P2
- **WHEN** 按 P1 的拒绝，P2 一直没有人按到截止时刻
- **THEN** 没有告警

#### Scenario: 案件的退出方案确认超时的告警

- **GIVEN** K3 交来 P3，一直没有人按按钮
- **WHEN** 到了 2026-10-14 15:30Z
- **THEN** 告警写明：P3 确认超时，没有执行；清仓 AAA 10 股；方案 ID；持仓的止损单照挂

#### Scenario: 告警发不出去

- **GIVEN** 当前时刻 2026-10-14 21:00Z；提交 P1，21:05Z 按确认；之后 Discord 报错
- **WHEN** 2026-10-15 13:30Z，BBB 最新价 53
- **THEN** 有一条错误日志，含告警文字和失败原因
- **AND** P1 照常作废，BBB 没有有效预留，下单流程结束

### Requirement: 日志

下单流程和提交接口 SHALL 把每一步写进程序日志（program-log spec），对象是方案 ID：录入的方案（人的录入方案，只有 `/plan` 的方案有）、检查的结果（风控检查）、不要人工确认的方案的自动执行（系统的自动执行，在风控检查之后）、确认的结果（人的确认、拒绝、超时）、等开盘（等到的时刻）、再校验的结果（下单前再校验，转去等重试或等开盘的那几次不写）、提交的结果（提交订单：订单的状态和委托股数）、释放预留和原因。请求确认、报告确认已超时和推送告警由通知模块写（program-log spec「系统的动作」）。

- 等重试写 Python 日志的 WARNING 或 ERROR（见「下单前再校验和提交」「提交的结果」），不写程序日志；到有效期作废时，释放预留的原因写上最近一次没能下单的原因
- 送回案件的结果不另写程序日志：案件阶段的变化由案件工作流写（program-log spec「调度器的动作」）
- 进程重启以后，已经做完的步骤 SHALL NOT 再写一次
