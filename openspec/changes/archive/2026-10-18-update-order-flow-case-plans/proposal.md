# Proposal

## Why

下单流程现在只接 `/plan` 录入的方案。「案件工作流」把方案交到风控阶段以后，要有人接手：按确认规则决定要不要人确认、确认消息带上 Critic 的意见、下单以后把结果送回案件；成交以后股票池也要跟上（买入成交变为持仓、清仓以后转为关注、候选或移出）。M4 的完成标志「替身给出的方案能在模拟盘下单」缺的就是这一段。

本变更的目的只有一个：**案件的交易方案走下单流程到下单，结果送回案件，成交以后股票池跟上券商持仓。**

引用的 Proposal（完整版）章节：

- 「架构」的「风控与执行」（风控、下单前再校验、人工确认、执行模块；案件在提交订单后结束）、「审核层：Critic」（有分歧时连同双方意见交给你决定；Critic 不可用时退出类方案交给人确认并注明）
- 「持仓与退出」：退出路径表（模型建议退出默认要确认，超时不执行、保留止损单并告警；自动执行由人手动开启，Critic 有异议时不自动执行）；清仓后的股票状态（PM 发起的清仓按 PM 的去向，代码触发的清仓转为候选）
- 「风控引擎与执行」：通过后进入人工确认，开仓类默认必须确认
- 「订单生命周期」：案件在方案通过风控、提交订单后结束，订单由执行模块独立跟踪
- 「记录、复盘与经验」的「交易记录」：来源案件 ID，止损单记开仓或加仓的案件
- 「股票池与寻股」：板块记为 SPDR 板块 ETF 的代码；投资论点买入成交时取开仓方案附的

已经定了的：

- 交接的接口由「案件工作流」定（它的 design D4）：交接端口给出风控结果，之后的结果按案件 ID 送回；本变更实现下单那一侧。本变更要求它对 D4 做的修改见 design「前提」
- `/plan` 的持仓不进股票池：股票池里的持仓总有投资论点；股票池里的持仓不是 PM 决定清仓的，清仓以后转为候选。之后的「事件检测」不看不在股票池里的持仓
- `/plan` 的板块和股票池一样用板块 ETF 的代码

## What Changes

- 案件的方案（order-flow）：
  - 交接：首次检查并预留；通过或调整时按 confirmation-rules spec 决定要不要人工确认、超时以后要不要告警，以方案 ID 启动下单流程，带上案件 ID 和 Critic 审核的结果；读不到券商账户时给出风控检查出错
  - 不要确认的退出方案（模型退出自动执行）：不请求确认，写一条程序日志的自动执行，直接等开盘、再校验、下单
  - 要确认的：确认消息按 Critic 审核的结果附上双方意见，或者注明 Critic 不可用；退出类确认超时或确认请求发不出去以后告警，写明方案没有执行、止损单照挂
  - 每个结局按案件 ID 送回案件：已确认、已拒绝、已超时、订单已提交、再校验作废；意料之外的错误让下单流程停下以前送回出错
- 确认消息（discord-notification）：最后一项是案件的意见；整条超过 2000 字时截短意见
- 订单和交易记录带来源案件 ID（order-lifecycle、trade-records）：案件的方案是它的案件，止损单是止损价来自的开仓订单的案件；`/plan` 和紧急退出的没有
- 股票池跟上持仓（新的 pool-position-sync）：盘中巡检每一轮按券商持仓把股票池的状态补上：
  - 候选或关注有了持仓、最近的买单来自案件：买入成交，投资论点和那一天取那个案件的结论
  - 持仓没有了持仓：最近的订单是案件的清仓单并且全部成交，按 PM 的去向转为关注或移出；其余（止损单、紧急退出、`/plan` 清仓等）转为候选
  - 状态变了交给跟进审批，往下走时作废待执行的跟进
  - `/plan` 买入的持仓不进股票池
- 程序日志（program-log）：风控检查也写案件的方案；系统加一个动作「自动执行」
- `/plan` 的板块（manual-plans）：买入和加仓的 `sector` 改为 11 个板块的选项，选项名是中文板块名，方案里存板块 ETF 的代码
- 装配（bootstrap）：装配股票池、跟进和案件记录，交给下单流程和盘中巡检；案件工作流和交接仍不装配（「排队运行」装配）
- 完整版 Proposal 不改
- 运维（不写代码）：案件流程在模拟盘跑起来以前（「排队运行」部署以前），本人用 `/plan close` 清掉 M2 测试留下的持仓。它们不在股票池里，没有投资论点；板块是旧的中文名，清仓照常用持仓的板块

## Non-goals

- 案件工作流那一侧：交接以后案件阶段怎样转换（包括风控以后直接进入等下单）、等结果、写风控结果进案件记录：「案件工作流」（见 design「前提」）
- 新案件排队时作废方案、紧急退出中止案件：「排队运行」「紧急退出中止案件」。在那之前，紧急退出作废了案件的方案时，下单流程照现在的规则得出再校验作废或确认超时，照常送回
- 什么时候开始案件、装配案件工作流和交接：「排队运行」
- 卖出成交触发卖出复盘、事件检测不看股票池以外的持仓：「事件检测」
- 启动时把「模型退出自动执行」的开关状态写进程序日志：每个自动执行的方案各写一条（design D6）
- 下单那一侧的程序日志条目不写案件 ID（design D6）
- 确认消息的其余内容、按钮、确认超时、`/plan` 的其余字段：不改
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `pool-position-sync`：盘中巡检每一轮按券商持仓把买入成交和清仓交给股票池，状态变化交给跟进审批

### Modified Capabilities

- `order-flow`：新增「案件的方案」「结果送回案件」；修改「请求人工确认」（案件的方案按确认规则，附上 Critic 的意见，发不出去时退出方案告警）、「确认的结果」（退出方案超时告警）、「告警」（加确认超时没有执行的告警）、「日志」（加自动执行）
- `discord-notification`：修改「确认消息」，加案件的意见和截短
- `order-lifecycle`：修改「提交订单」，订单带来源案件
- `trade-records`：修改「交易记录的内容」，加来源案件 ID
- `session-patrol`：修改「每一轮」，第 3 步之后加股票池跟上持仓
- `program-log`：修改「风控引擎的动作」（风控检查也写案件的方案）、「系统的动作」（加自动执行）
- `manual-plans`：修改「子命令和字段」「字段的解析」「减仓和清仓的板块」，板块改为选项
- `bootstrap`：修改「模拟盘的装配」，装配股票池、跟进、案件记录

## Impact

- **代码**：
  - `workflows/order_flow.py`：案件方案的首次检查和确认规则、确认消息的意见、退出方案超时告警、下单带来源案件
  - `workflows/order_workflow.py`：`order_plan` 带上来源（`CaseSource`），各结局送回案件；`CasePlanHandoff` 实现交接端口
  - `workflows/pool_sync.py`（新）：股票池跟上持仓；`workflows/patrol.py` 每一轮加这一项
  - `workflows/emergency_flow.py`：提交订单时写明没有来源案件
  - `modules/notification/`：确认请求带案件的意见（`domain/confirmation.py`、`service.py`）
  - `modules/execution/`：订单和交易记录的来源案件；`submit` 接收来源案件；新增读取 `held_symbols`、`orders`
  - `modules/programlog/domain/entry.py`：动作「自动执行」
  - `integrations/discord/`：确认消息的意见和截短；`/plan` 的板块选项
  - `bootstrap/app.py`：装配股票池、跟进、案件记录
  - contracts、shared、调度器、股票池、跟进、案件记录模块不改
- **数据库**：没有迁移。订单和交易记录的来源案件存在已有的版本记录里，旧的记录读出来没有来源案件（design D5）
- **测试**：`tests/workflows/`（下单流程、下单工作流、股票池跟上持仓、巡检）、`tests/modules/execution/`、`tests/modules/notification/`、`tests/integrations/discord/`、`tests/bootstrap/`；`tests/fakes/` 的通知和执行替身跟着改
- **依赖**：无
- **前提**：「案件工作流」按 design「前提」的修改 apply 并归档（交接端口、送回的结果、案件阶段的转换都在它那里）
- **部署**：`order_plan` 的参数变了，部署前确认没有进行中的下单流程（add-order-flow 的部署规则）；部署以后股票池是空的，巡检这一项什么都不做
- **对后续变更的影响**：「排队运行」装配案件工作流时把 `CasePlanHandoff()` 交给它；作废方案时报告确认消息已作废、释放预留，下单流程之后照常送回结果，已结束的案件不理会

## 需要人决定

完整版 Proposal 对应章节的问题，推荐的做法已经写进 spec 和 design：

1. **双方意见太长，确认消息放不下**：「审核层：Critic」要求有分歧时「连同双方意见交给你决定」，Discord 一条消息最多 2000 字。两轮质询时意见有 PM 的理由、三次审核和两轮回应，接上真实模型以后可能超过。推荐：意见放在确认消息的最后，整条超过 2000 字时只截短意见，结尾是「…」，方案、截止时刻和方案 ID 不受影响；全文在案件记录里。M5 写 prompt 时限制理由和质询的长度，截短很少发生。完整版不用改
2. **PM 的清仓单只成交一部分、剩下的被止损单卖完，算谁发起的清仓**：「持仓与退出」只分 PM 发起和代码触发两种。推荐：看让持仓变为 0 的那一笔：清仓单全部成交才按 PM 的去向（转为关注或移出），其余都转为候选。一部分成交以后清仓单到期，持仓还在，PM 下一个案件会看到。完整版不用改
