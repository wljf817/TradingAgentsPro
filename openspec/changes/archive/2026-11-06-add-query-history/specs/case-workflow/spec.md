## MODIFIED Requirements

### Requirement: 案件上下文

由 PM 处理的案件开始时，案件工作流 SHALL 组出一份案件上下文（agent-calls spec「每个 agent 的输入和输出」），本案件 PM 和 Critic 的每次调用都用这一份：

| 项 | 来源 |
| --- | --- |
| 问题 | 开始时确定的案件类型的问题；跟进案件是申请时写下的问题 |
| 事件 | 事件案件的触发里的事件 ID 对应的事件（event-detection spec「读取事件」），整个事件原样给出：类别、是否持仓风险级别、来源、强度、发生时刻、说明、引用等（event-rules spec「事件的内容」） |
| 事件要求的子 agent | 开始时确定的案件类型 |
| 允许的决定 | 开始时确定的案件类型：持仓的结论是持有、加仓、减仓和清仓；关注的结论是开仓方案、继续关注、降为候选和移出股票池；候选的结论是升级、保持和移出股票池；寻股没有决定。关注复查和关注催化剂复查到上限（case-types spec「续期上限」）时去掉继续关注，连续续期次数取股票池现在的，可用额度取第 1 版快照 |
| 研究要求 | 研究要求的子 agent 数（case-types spec「研究要求的配置」）；寻股没有 |
| 关注论点 | 案件股票是关注时，股票池里现在的关注论点 |
| 投资论点 | 案件股票是持仓时，股票池里现在的投资论点 |
| 最近结束的案件 | 这只股票已经结束的案件（case-records spec「读取案件记录」），按结束时刻从晚到早，最多"近期案件数"个；每个写案件类型、结束时刻、结束原因和结论（没有结论的不写） |
| 历史索引 | 这只股票的历史案件数和交易数，都截到第 1 版快照的生成时刻：结束时刻早于它的已结束案件（case-records spec「读取案件记录」），这个时刻累计成交大于 0 的交易记录（trade-records spec「保存交易记录」） |
| 待执行的跟进 | 这只股票待执行的跟进的申请（follow-ups spec「跟进的记录」），按触发时间排列 |
| 跟进 | 跟进案件：触发里的跟进 ID 对应的跟进（follow-ups spec「读取一个跟进」）的申请，和提出申请的案件（跟进的来源案件）的结论（case-records spec「读取案件记录」）；其他案件没有 |

不针对单只股票的案件（寻股）只有问题，允许的决定为空，没有研究要求。事件案件的触发里的事件 ID 读不到事件时 SHALL 报错，不当作没有事件：事件检测先记下事件、再排进案件（event-detection spec「记下和排队」）。跟进案件的触发里的跟进 ID 读不到跟进、或者来源案件的记录没有结论时，同样 SHALL 报错：跟进是来源案件的结论通过检查时获批的，到点触发先有跟进、再排进案件（follow-ups spec「到点触发」）。

#### Scenario: 关注股事件的上下文

- **GIVEN** K-1 的触发里的事件是 E-1：BBB 的入场条件满足事件，来源行情
- **WHEN** K-1 开始运行，BBB 没有结束过的案件，也没有待执行的跟进
- **THEN** 案件上下文：问题"入场机会是否出现？"，事件是 E-1，事件要求的子 agent 是 Quant，允许的决定是开仓方案、继续关注、降为候选和移出股票池，研究要求 2 个子 agent，关注论点是基准关注论点；没有投资论点、最近结束的案件和待执行的跟进

#### Scenario: 持仓的上下文

- **GIVEN** K-3 的触发里的事件是 CCC:2026-10-14:news：CCC 的新闻事件，来源新闻源，强度 2，引用新闻 ID 101，说明写明标题"CCC Raises FY26 Guidance"
- **AND** CCC 已经结束的案件依次是：K-11（持仓复查，2026-10-07 结束，没有交易方案，结论是持有）、K-12（持仓事件，2026-10-09 结束，系统故障，没有结论）；CCC 有一个待执行的跟进，申请是基准跟进申请
- **WHEN** K-3 开始运行
- **THEN** 案件上下文：问题"这个事件是否削弱或推翻了论点？"，事件是 CCC:2026-10-14:news，各项和事件检测记下的完全相同，事件要求的子 agent 是 News，允许的决定是持有、加仓、减仓和清仓，研究要求 2 个子 agent，投资论点是基准投资论点
- **AND** 最近结束的案件依次是 K-12（系统故障，没有结论）、K-11（没有交易方案，结论持有）；待执行的跟进是基准跟进申请

#### Scenario: 读不到事件

- **GIVEN** K-3 的触发里的事件 ID 在事件检测里读不到
- **WHEN** K-3 开始运行
- **THEN** 组出案件上下文这一步报错

#### Scenario: 近期案件数的边界

- **GIVEN** CCC 已经结束了 4 个案件
- **WHEN** K-3 开始运行
- **THEN** 最近结束的案件是结束时刻最晚的"近期案件数"个
- **GIVEN** 近期案件数配置为 0
- **WHEN** K-3 开始运行
- **THEN** 没有最近结束的案件

#### Scenario: 寻股和跟进案件的上下文

- **WHEN** K-2 开始运行
- **THEN** 案件上下文只有问题"补充哪些候选？"，允许的决定为空，没有研究要求
- **GIVEN** K-3 的结论是持仓的结论：持有，附跟进申请 A（原因是事件后反应，引用事件 V-7；问题"大单公布 3 小时后盘中反应如何？"；可能采取的动作"加仓"；触发时间 2026-10-14 18:00Z），获批为 F-1，K-3 已结束
- **WHEN** 2026-10-14 18:00Z F-1 开出的持仓跟进 K-8 开始运行
- **THEN** 问题是"大单公布 3 小时后盘中反应如何？"，没有事件和事件要求的子 agent
- **AND** 跟进是：申请 A，来源案件 K-3 的结论（持有，附申请 A）；最近结束的案件里有 K-3；没有待执行的跟进（F-1 已触发）

#### Scenario: 读不到跟进

- **GIVEN** K-8 的触发是 CCC 的跟进，跟进 ID 在跟进审批里读不到
- **WHEN** K-8 开始运行
- **THEN** 组出案件上下文这一步报错

#### Scenario: 候选的上下文

- **WHEN** AAA 的候选评估开始运行
- **THEN** 允许的决定是升级、保持和移出股票池，研究要求 2 个子 agent

#### Scenario: 研究要求跟着配置

- **GIVEN** 研究要求的子 agent 数配置为 3
- **WHEN** K-1 开始运行
- **THEN** 案件上下文的研究要求是 3 个子 agent

#### Scenario: 到上限时没有继续关注

- **GIVEN** BBB 到上限
- **WHEN** BBB 的关注复查、关注催化剂复查开始运行
- **THEN** 允许的决定都是开仓方案、降为候选和移出股票池
- **WHEN** K-1 开始运行
- **THEN** 允许的决定是开仓方案、继续关注、降为候选和移出股票池

#### Scenario: 开不了仓时还有继续关注

- **GIVEN** BBB 的连续续期次数等于续期上限，第 1 版快照里持仓名额是 0
- **WHEN** BBB 的关注复查开始运行
- **THEN** 允许的决定是开仓方案、继续关注、降为候选和移出股票池

#### Scenario: 历史索引

- **GIVEN** K-3 第 1 版快照的生成时刻 2026-10-14 15:00Z
- **AND** CCC 有 3 个已结束的案件，其中 1 个结束时刻 15:10Z；CCC 有 2 条交易记录，这个时刻累计成交都大于 0；还有 1 条这个时刻累计成交 0，15:05Z 才成交
- **WHEN** K-3 开始运行
- **THEN** 历史索引是 2 个案件、2 笔交易
