# Spec Delta

## MODIFIED Requirements

### Requirement: 调度器的动作

调度器的下面这些动作 SHALL 各写一条，行为者是调度器。现在有跟进审批的动作（follow-ups spec）、生成快照（state-snapshot spec）、案件工作流的动作（case-workflow spec）、排队运行的动作（queue-runner spec）和收盘心跳的动作（close-heartbeat spec）：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 批准跟进 | 跟进申请通过审批，新的跟进保存以后（follow-ups spec「审批的输入和结果」） | 新跟进的 ID | 没有 | 跟进的内容 |
| 拒绝跟进 | 跟进申请没有通过审批（follow-ups spec「审批的顺序」） | 股票 | 没有 | 不通过的原因；申请的内容，写法和跟进的内容相同，没写引用的写明没有引用 |
| 替换跟进 | 批准的跟进替换了这只股票原因相同的待执行跟进（follow-ups spec「原因相同时替换」），写在这次的批准跟进之后 | 被替换的跟进的 ID | 输入：替换它的新跟进的 ID | 被替换的跟进的内容 |
| 作废跟进 | 股票状态往下走，这只股票待执行的跟进作废（follow-ups spec「股票状态往下走时作废」）：每个作废的跟进一条，按作废时给出的顺序 | 跟进 ID | 没有 | 之前和之后的状态，不在股票池也不是持仓的写不在股票池；跟进的内容 |
| 触发跟进 | 到点触发把排进了案件的跟进记为已触发以后（follow-ups spec「到点触发」）：每个一条，按排进的先后，写在这个跟进的排队之后 | 跟进 ID | 输出：排进的案件 ID | 跟进的内容 |
| 生成快照 | 一版快照保存以后（state-snapshot spec「每种案件的快照」「新的版本」） | 快照的版本，比如 s1 | 输出：这一版的全部条目 ID，按条目的先后 | 股票，不针对单只股票的写"不针对单只股票"；生成的原因，第 1 版写"案件开始"；条目数 |
| 开案件 | 案件开始运行，案件记录的开始运行写下以后（case-workflow spec「开始运行一个案件」） | 案件 ID | 没有 | 案件类型；股票，不针对单只股票的写"不针对单只股票"；触发原因 |
| 案件阶段变化 | 案件状态的阶段变了（case-stages spec「案件的阶段」）：每次变化一条 | 案件 ID | 没有 | 之前和之后的阶段；有方案时写方案的动作和方案 ID；进入 PM 回应时写明第几轮质询，进入风控时写明 Critic 审核的结果，结束时写明结束原因和有没有结论 |
| 唤醒 agent | 案件工作流调用一次 PM、Critic 或 Reviewer，调用交回以后（case-workflow spec「PM 的研究」「Critic 审核」「PM 回应」「复盘案件」） | 案件 ID | 没有 | 哪个 agent；为什么唤醒：PM 是开始研究、交回任务的结果、退回重交（写明第几次和原因）或者回应第几轮质询，Critic 是第几次审核或者交回补充研究的结果，Reviewer 是复盘；交回了什么：派发几个任务、提交的结论的决定、回应的决定、审核的结论或者复盘报告的总结，调用成功时写实际使用的模型和是不是备用模型，调用失败时写网关给出的说明。耗时是这次调用从开始到交回的时间，费用是这次调用的费用 |
| 排队 | 一个案件排进队列、存下以后（queue-runner spec「排队」） | 案件 ID | 没有 | 触发原因；触发时刻（UTC） |
| 不再运行 | 排队的案件不再运行，案件记录的不再运行写下以后（queue-runner spec「不再运行」） | 案件 ID | 没有 | 触发原因；这只股票现在的状态，不在股票池里的写不在股票池里 |
| 方案作废 | 队列的决定作废一个方案，交给下单流程以前（queue-runner spec「作废方案」） | 方案 ID | 没有 | 动作和股票；写明这只股票有新案件排队 |
| 收盘检查 | 收盘心跳把这次收盘检查的检查项都排进队列以后，没有检查项时也写（close-heartbeat spec「收盘检查的日志」） | 交易日，比如 2026-10-14 | 输出：这次排进的案件 ID，按排进的先后；没有时没有引用 | 开出的检查项：几个，每个的触发原因（和排队的触发原因写法相同），按排进的先后；没有时写没有要开的检查项。刷新了几只股票的财报；没有刷新成的，每只写股票和原因 |

跟进的内容：股票、原因类型、引用的对象、触发时间（UTC）、要回答的问题、可能采取的动作。

- 批准、拒绝和替换跟进的案件 ID 是提出申请的案件；作废和触发跟进不属于案件，案件 ID 为空；生成快照的案件 ID 是快照所属的案件；开案件、案件阶段变化、唤醒 agent、排队和不再运行的案件 ID 是这个案件；方案作废的案件 ID 是给出这个方案的案件；收盘检查不属于案件，案件 ID 为空
- 调度器的动作里只有唤醒 agent 写耗时和费用
- 每个跟进、每版快照保存以后才写它的条目；写条目出错时照「写入失败」处理，已经保存的跟进和快照不撤回
- 取得待执行的跟进、读取一个跟进、没有跟进到点的到点触发、不作废跟进的状态变化 SHALL NOT 写程序日志；同一版快照再生成、生成快照时数据读不到（state-snapshot spec「同一版再生成」「数据读不到时」）也 SHALL NOT 写
- 阶段没有变的案件状态变化（结论退回 PM 重交）SHALL NOT 写案件阶段变化：退回的原因写在下一次唤醒 PM 的条目里
- 排队运行的一轮 SHALL NOT 另外写条目：只有到点的跟进各写一条排队和一条触发跟进，作废、不再运行各写上表的一条，启动的案件由案件工作流写开案件；没有到点的跟进、作废、不再运行和启动的一轮不写

#### Scenario: 批准跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据
- **WHEN** CCC 申请日程申请
- **THEN** 程序日志有一条批准跟进，行为者是调度器，对象 F-1，案件 ID K-1，没有引用
- **AND** 说明写明 CCC、外部日程、日程项 S-9、触发时间 2026-11-19 14:30 UTC、问题"竞争对手 11 月 18 日发财报，之后对这只股票有什么影响？"和可能采取的动作"减仓"

#### Scenario: 拒绝跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据
- **WHEN** CCC 申请事件申请，不写引用
- **THEN** 程序日志有一条拒绝跟进，对象 CCC，案件 ID K-1；说明写明没有引用具体对象、事件后反应、没有引用、触发时间 2026-10-14 18:00 UTC
- **AND** 没有批准跟进

#### Scenario: 替换跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1）
- **WHEN** 当前时刻 2026-10-15 15:00Z，CCC 的案件 K-2 申请日程申请，触发时间改为 2026-11-30 14:30Z
- **THEN** 程序日志接着依次有批准跟进（对象 F-2，案件 ID K-2，说明写明触发时间 2026-11-30 14:30 UTC）和替换跟进（对象 F-1，案件 ID K-2，输入的引用是 F-2，说明写明触发时间 2026-11-19 14:30 UTC）

#### Scenario: 触发跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1），再申请事件申请（F-2）；BBB 申请观察申请（F-3）；调用方排进的案件依次是 K-11、K-12、K-13
- **WHEN** 当前时刻 2026-11-20 15:00Z，到点触发
- **THEN** 程序日志接着依次有 F-2、F-3、F-1 的触发跟进，都没有案件 ID，输出的引用依次是 K-11、K-12、K-13
- **AND** F-3 的说明写明 BBB、价格或指标观察、条件价格不低于 55、触发时间 2026-10-21 20:00 UTC

#### Scenario: 作废跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1），再申请事件申请（F-2）
- **WHEN** CCC 代码触发的清仓转为候选
- **THEN** 程序日志接着依次有 F-2、F-1 的作废跟进，都没有案件 ID，说明写明持仓变为候选

#### Scenario: 写条目出错时跟进已经保存

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；写程序日志时数据库会出错一次
- **WHEN** CCC 申请日程申请
- **THEN** 审批报错，不返回获批或拒绝
- **AND** F-1 已经保存，是待执行

#### Scenario: 没有动作时不写

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1）；BBB 申请观察申请（F-2）
- **WHEN** 取得 CCC 待执行的跟进；当前时刻 2026-10-14 18:00Z，到点触发；BBB 买入成交变为持仓
- **THEN** 程序日志都没有新条目

#### Scenario: 生成快照

- **GIVEN** state-snapshot spec 的基准数据
- **WHEN** 生成 K-1 的第 1 版
- **THEN** 程序日志有一条生成快照，行为者是调度器，对象 s1，案件 ID K-1，没有输入的引用，输出的引用依次是 K-1 第 1 版的 15 个条目 ID（state-snapshot spec「案件股票的条目」）
- **AND** 说明写明 BBB、案件开始、15 个条目

#### Scenario: 寻股和新的版本

- **GIVEN** state-snapshot spec 的基准数据；已经生成 K-1 的第 1 版
- **WHEN** 生成 K-2 的第 1 版；再按 state-snapshot spec「新的版本」的场景生成 K-1 的第 2 版
- **THEN** 程序日志接着依次有两条生成快照
- **AND** 第一条：对象 s1，案件 ID K-2，说明写明不针对单只股票、案件开始、7 个条目
- **AND** 第二条：对象 s2，案件 ID K-1，说明写明 BBB、"Critic 要核实财报后的价格反应"、16 个条目

#### Scenario: 写条目出错时快照已经保存

- **GIVEN** state-snapshot spec 的基准数据；写程序日志时数据库会出错一次
- **WHEN** 生成 K-1 的第 1 版
- **THEN** 报错
- **AND** K-1 的第 1 版已经保存

#### Scenario: 开案件

- **GIVEN** case-workflow spec 的基准数据
- **WHEN** K-1 开始运行；K-2 开始运行
- **THEN** 程序日志依次有 K-1 的开案件（行为者是调度器，对象 K-1，案件 ID K-1，说明写明关注股事件、BBB 和触发原因）、K-1 的生成快照、K-2 的开案件（说明写明寻股、不针对单只股票）、K-2 的生成快照

#### Scenario: 案件阶段变化

- **GIVEN** case-workflow spec 的基准数据
- **WHEN** K-1 开始运行，PM 提交开仓结论并通过，Critic 质询，PM 维持，Critic 通过，下单那一侧给出风控通过、要人工确认，送回已确认，送回订单已提交
- **THEN** K-1 依次有案件阶段变化：唤醒 PM → Critic 审核（买入，方案 P-1）；Critic 审核 → PM 回应（第 1 轮质询）；PM 回应 → Critic 审核；Critic 审核 → 风控（Critic 通过）；风控 → 等人工确认；等人工确认 → 等下单；等下单 → 已结束（订单已提交，有结论）
- **AND** 每条的对象和案件 ID 都是 K-1，没有耗时和费用

#### Scenario: 退回重交不写阶段变化

- **GIVEN** case-workflow spec 的基准数据
- **WHEN** K-6 的 PM 提交的结论退回一次（研究不足），再提交候选的结论：保持，通过
- **THEN** K-6 只有一条案件阶段变化：唤醒 PM → 已结束（没有交易方案，有结论）
- **AND** 第二次唤醒 PM 的条目写明第 1 次退回重交、原因研究不足

#### Scenario: 唤醒 agent

- **GIVEN** case-workflow spec 的基准数据；PM 的主模型是 p-1
- **WHEN** K-1 的 PM 用 p-1 派发价格请求和财报请求，这次调用的费用是 0.06、耗时 4 秒
- **THEN** 程序日志有一条唤醒 agent：对象 K-1，案件 ID K-1，说明写明 PM、开始研究、派发 2 个任务、模型 p-1、不是备用模型；耗时 4 秒，费用 0.06

#### Scenario: 唤醒失败和复盘

- **GIVEN** case-workflow spec 的基准数据
- **WHEN** K-4 的 PM 不可用；K-7 的 Reviewer 交回复盘报告，总结是"止损执行正常"
- **THEN** K-4 的唤醒 agent 写明 PM、调用失败和网关给出的说明
- **AND** K-7 的唤醒 agent 写明 Reviewer、复盘、总结"止损执行正常"

#### Scenario: 排队

- **GIVEN** queue-runner spec 的基准数据
- **WHEN** 排进 BBB 的新闻事件（14:58Z）
- **THEN** 程序日志有一条排队：行为者调度器，对象 K-1，案件 ID K-1，没有引用，说明写明 BBB 的新闻事件、触发时刻 2026-10-14 14:58 UTC

#### Scenario: 一轮排进到点的跟进

- **GIVEN** queue-runner spec 的基准数据；BBB 有一个待执行的跟进 F-1，问题"站上 55 以后能不能守住？"，触发时间 2026-10-14 14:59Z
- **WHEN** 做一轮
- **THEN** 程序日志依次有 K-1 的排队（说明写明 BBB 的跟进 F-1 和问题、触发时刻 2026-10-14 14:59 UTC）、F-1 的触发跟进（输出的引用是 K-1）、K-1 的开案件

#### Scenario: 不再运行

- **GIVEN** queue-runner spec 的基准数据；排进 CCC 的持仓复查日到期（13:30Z），之后 CCC 变为候选
- **WHEN** 做一轮
- **THEN** 程序日志有一条不再运行：对象 K-1，案件 ID K-1，说明写明 CCC 的持仓复查日到期、CCC 现在是候选
- **AND** 它在 K-1 的案件记录写下不再运行以后

#### Scenario: 方案作废

- **GIVEN** queue-runner spec 的基准数据；运行中 K-1：BBB 的关注股事件，等人工确认，方案 P-1（买入 BBB）；排进 BBB 的新闻事件（14:58Z）
- **WHEN** 做一轮
- **THEN** 程序日志有一条方案作废：对象 P-1，案件 ID K-1，说明写明买入 BBB、BBB 有新案件排队
- **AND** 之后才有 P-1 的结束确认（已作废）和释放预留

#### Scenario: 收盘检查

- **GIVEN** close-heartbeat spec 的基准数据；CCC 的复查日改为 2026-10-14，BBB 的截止日期改为 2026-10-14；公司数据源取 FFF 的财报时超时
- **WHEN** 收盘心跳在 2026-10-14 20:15Z 开始
- **THEN** 程序日志依次有 K-1、K-2 的排队和一条收盘检查：行为者是调度器，对象 2026-10-14，没有案件 ID，输出的引用依次是 K-1、K-2；说明写明开出 2 个检查项：CCC 的持仓复查日到期、BBB 的关注论点的催化剂截止日期到期；刷新了 7 只股票的财报，FFF 没有刷新和超时的原因

#### Scenario: 没有要开的检查项

- **GIVEN** close-heartbeat spec 的基准数据
- **WHEN** 收盘心跳在 2026-10-14 20:15Z 开始
- **THEN** 程序日志只有一条收盘检查：对象 2026-10-14，没有引用，说明写明没有要开的检查项，刷新了 8 只股票的财报
