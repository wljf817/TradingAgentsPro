## MODIFIED Requirements

### Requirement: 案件上下文

由 PM 处理的案件开始时，案件工作流 SHALL 组出一份案件上下文（agent-calls spec「每个 agent 的输入和输出」），本案件 PM 和 Critic 的每次调用都用这一份：

| 项 | 来源 |
| --- | --- |
| 问题 | 开始时确定的案件类型的问题；跟进案件是申请时写下的问题 |
| 事件 | 事件案件的触发里的事件 ID 对应的事件（event-detection spec「读取事件」），整个事件原样给出：类别、是否持仓风险级别、来源、强度、发生时刻、说明、引用等（event-rules spec「事件的内容」） |
| 事件要求的子 agent | 开始时确定的案件类型 |
| 允许的决定 | 开始时确定的案件类型：持仓的结论是持有、加仓、减仓和清仓；关注的结论是开仓方案、继续关注、降为候选和移出股票池；候选的结论是升级、保持和移出股票池；寻股没有决定。关注复查和关注催化剂复查到上限（case-types spec「续期上限」）时去掉继续关注，连续续期次数取股票池现在的，可用额度取第 1 版快照 |
| 研究要求 | 研究要求的子 agent 数（case-types spec「研究要求的配置」）；寻股没有 |
| 关注论点 | 案件股票是关注时，股票池里现在的关注论点 |
| 投资论点 | 案件股票是持仓时，股票池里现在的投资论点 |
| 最近结束的案件 | 这只股票已经结束的案件（case-records spec「读取案件记录」），按结束时刻从晚到早，最多"近期案件数"个；每个写案件类型、结束时刻、结束原因和结论（没有结论的不写） |
| 待执行的跟进 | 这只股票待执行的跟进的申请（follow-ups spec「跟进的记录」），按触发时间排列 |
| 跟进 | 跟进案件：触发里的跟进 ID 对应的跟进（follow-ups spec「读取一个跟进」）的申请，和提出申请的案件（跟进的来源案件）的结论（case-records spec「读取案件记录」）；其他案件没有 |

不针对单只股票的案件（寻股）只有问题，允许的决定为空，没有研究要求。事件案件的触发里的事件 ID 读不到事件时 SHALL 报错，不当作没有事件：事件检测先记下事件、再排进案件（event-detection spec「记下和排队」）。跟进案件的触发里的跟进 ID 读不到跟进、或者来源案件的记录没有结论时，同样 SHALL 报错：跟进是来源案件的结论通过检查时获批的，到点触发先有跟进、再排进案件（follow-ups spec「到点触发」）。

### Requirement: PM 的研究

唤醒 PM 阶段，案件工作流 SHALL 按案件上下文、最新一版快照和 PM 在本案件的对话（agent-calls spec「对话的每一轮」）调用 PM（研究），按 PM 的回复：

| 回复 | 处理 |
| --- | --- |
| 派发任务 | 以 PM 为发起者经 Agent 网关派发（task-dispatch spec「派发的顺序」）；派发出去的任务同时交给目标子 agent 运行，读派发时最新的一版快照（agent-calls spec「子 agent 的任务」）；全部有了 Result 以后，把这次回复和每个请求的 Task 和 Result（按请求的顺序）作为一轮加进对话，再调用 PM |
| 提交结论 | 按「结论的检查」检查 |
| 输出不合法 | 按 case-stages spec「唤醒 PM 和结论」：退回时把这次输出和原因作为一轮加进对话，再调用 PM；重交次数用完时结束 |
| 调用失败 | 见「模型全部不可用」 |

- 被拒绝和复用的请求 SHALL NOT 交给子 agent；超时、失败的任务照样交回 PM，PM 在缺少这些信息的情况下继续
- 调用预算用完 SHALL NOT 影响运行中的案件（call-budget spec「已经开始的案件」）

#### Scenario: 派发以后提交结论

- **GIVEN** K-1 开始运行
- **WHEN** PM 派发价格请求和财报请求；T-1、T-2 完成；PM 提交 K-1 的开仓结论
- **THEN** T-1、T-2 都交给了子 agent；PM 第二次调用时对话有一轮：派发任务，交回 T-1、T-2 和它们完成的 Result
- **AND** 结论按「结论的检查」检查

#### Scenario: 任务同时运行

- **WHEN** K-1 的 PM 派发价格请求和财报请求
- **THEN** T-2 在 T-1 有 Result 以前就开始运行

#### Scenario: 被拒绝和复用的请求

- **GIVEN** K-1 的 PM 已经派发过价格请求（T-1 完成）
- **WHEN** PM 再派发 AAA 的新闻请求和价格请求
- **THEN** AAA 的新闻请求被拒绝（不是案件的股票），价格请求复用 T-1；没有任务交给子 agent

- **WHEN** K-3 的 PM 派发新闻请求，T-1 超时；PM 提交持仓的结论：持有

- **WHEN** K-6 的 PM 派发价格请求，再提交结论

### Requirement: 结论的检查

PM 提交结论以后，案件工作流 SHALL 按下表的顺序检查，给出第一项不通过的原因：

| 顺序 | 检查 | 依据 |
| --- | --- | --- |
| 1 | 结论里的信号 | signal-format spec「结论里的信号」；"现在"是收到结论的时刻 |
| 2 | 备用模型的限制 | model-fallback spec「备用模型的限制」：提交结论的这次调用用的模型 |
| 3 | 结论的校验 | case-types spec「结论的校验」：派过任务的子 agent 和状态是完成的 Result 取本案件的（task-dispatch spec「本案件的任务和用量」）；是否到上限按股票池现在的连续续期次数和本案件最新的一版快照的可用额度 |
| 4 | 寻股加入的股票在粗筛名单里 | 寻股的结论里每只加入的股票都在本案件快照的粗筛名单里（state-snapshot spec「寻股的粗筛结果」）；不通过的原因写明哪只不在名单里 |
| 5 | 论点里的日期 | review-dates spec「检查论点里的日期」：结论里每一份新写的论点（见下面） |
| 6 | 跟进审批 | follow-ups spec「审批的输入和结果」：结论附了跟进申请时 |

第 5 项检查的论点和传入的事实：

| 结论和决定 | 论点 | 情形 |
| --- | --- | --- |
| 关注的结论，开仓方案 | 附的投资论点 | 新设 |
| 候选的结论，升级 | 附的关注论点 | 新设 |
| 持仓的结论，清仓，去向转为关注 | 附的关注论点 | 新设 |
| 持仓的结论，持有、加仓或减仓，附论点更新 | 论点更新 | 复查类案件里是续期，其他是平时调整；原来的论点和上次复查的那一天取股票池现在的 |
| 关注的结论，继续关注，附论点更新 | 论点更新 | 同上 |

- 今天：检查时现在归属的交易日
- 持仓的浮动盈亏比例：（快照里案件股票的最新价 − 快照的账户里这只持仓的均价）÷ 均价；没有最新价时用前一交易日收盘价；快照里没有它的行情时不传
- 日程项的日期：新论点的催化剂引用日程项时，按日程项的 ID 在本案件的快照里查条目，是财报发布的条目时取它的发布日；查不到或者不是财报发布时不传
- 跟进审批的催化剂：结论附了论点更新时是论点更新里的，否则是股票池现在的论点里的

不通过时 SHALL 按 case-stages spec「唤醒 PM 和结论」处理：重交次数没用完就把结论和原因作为一轮加进对话，再调用 PM；用完以后按结论无效结束。不通过的结论 SHALL NOT 生效：不记评分、不改股票池；跟进审批排在最后，前面不通过时跟进申请不审批，审批不通过时也不保存。

全部通过时见「结论生效」。

### Requirement: 结论生效

结论通过检查以后，案件工作流 SHALL 推进案件状态（case-stages spec「唤醒 PM 和结论」），写案件记录的结论和给出它的模型（有交易方案时连同方案，见「交易方案」），然后按下表让结论生效。评分（signal-format spec「结论里的信号」）SHALL 在改变股票状态以前记下：

| 结论 | 决定 | 生效 |
| --- | --- | --- |
| 持仓的结论 | 持有、加仓、减仓 | 记评分；附论点更新时更新投资论点，上次复查的那一天按 review-dates spec「上次复查的那一天」；加仓、减仓的方案进入 Critic 审核 |
| 持仓的结论 | 清仓 | 记评分；方案进入 Critic 审核。清仓后的去向和关注论点在清仓完成时由下单那一侧交给股票池 |
