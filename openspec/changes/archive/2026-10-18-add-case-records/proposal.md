# Proposal

## Why

Proposal 要求三种驱动触发的所有案件（包括没有调用 agent 的）和复盘案件都记进案件记录，PM、Critic、Reviewer 和评估从这里核实历史。现在案件只有 M3 的规则：调度器的案件状态不读写存储，PM 的结论、Critic 的审核和 PM 的回应、风控结果都还没有地方存，case-stages spec 说结束原因"记进案件记录，这只股票下一个案件的上下文里能看到"，model-fallback spec 说 PM 和 Critic 用的模型"由调用方写进案件记录"，也都还没有着落。「案件工作流」要在案件进行和结束时写记录、在案件上下文里给出这只股票的近期结论，「收盘心跳」要知道上一次寻股和候选评估什么时候得出结论，所以先建案件记录。

本变更的目的只有一个：**新建案件记录模块，在案件进行、结束时把每个案件（包括排队以后没有运行的）的触发、类型、结论、方案和审核、股票池增删的发现、结束原因和用量存下来，并按案件、按股票读回。**

引用的 Proposal（完整版）章节：

- 「记录、复盘与经验」：四部分记录的表（案件记录包括没有调用 agent 的案件，由代码在案件进行、结束和收益到期时写入，读取者是 PM、Critic、Reviewer）；「程序日志」的行为者表（调度器的动作）；「案件记录」的七张表；「查询工具」（`query_history` 按股票、时间和类型查案件记录）
- 「调度器与运行模块」：案件流程（结论、Critic 质询、PM 逐条回应、风控、人工确认，开仓方案被否决时方案记入日志）；运行约束（每个案件开始时生成快照）；排队规则（确定不了类型的案件不再运行）
- 「股票池与寻股」：增删都要写理由；寻股流程（PM 探索加入候选）；寻股的冷却期从上一次寻股得出结论的那一天算

已经定了的：

- 人在案件组探讨时同意（2026-10-17）：outcomes（事后收益）和 reviews（复盘）两张表放到 M6。日线是历史数据、免费，事后收益以后能补算；替身给出的信号没有评估的价值；复盘随 Reviewer 一起做
- M4 拆分时定的：模块 `modules/caserecords`，表名以 `caserecords_` 开头，迁移 v0012（v0011 是「状态库快照」）；写入方是以后的「案件工作流」「排队运行」，本变更只提供用例，不装配
- results 和 theses 不另存一份：Result 已经按案件 ID 存在 Agent 网关的表里；论点的内容是结论的一部分（存在 cases 的结论里），现在生效的论点在股票池里（design D4）
- 不存快照 ID：「状态库快照」把快照按案件 ID 和版本存，凭案件 ID 就能找到

## What Changes

- 新增模块 `modules/caserecords`，三张表：
  - cases：一个案件一条，按案件 ID 只追加版本。触发（case-types spec「触发」的四种之一）和触发原因、股票、触发时刻、案件类型、开始时刻、通过校验的结论和给出它的模型、结论时刻、状态（进行中、已结束、不再运行）、结束原因和结束时刻、耗时、Task 数和调用次数（没有调用 agent 的记为 0）
  - proposals：有交易方案的案件一条，按案件 ID 只追加版本。方案（方案 ID、股票、板块、动作和条款）、Critic 每次的审核和用的模型、PM 每轮的回应和用的模型、Critic 不可用、风控结果。被否决、撤回、拒绝的方案都留着，以什么结束看案件的结束原因
  - findings：结论里每一项股票池增删一行，只追加。寻股加入和删除的股票、候选和关注的结论决定移出的股票；理由、加入的候选的信号、股票池的结果（通过，或者不通过的原因）
- 写入的时刻：开始运行、结论通过校验、Critic 审核或不可用、PM 回应、风控给出结果、结论里的股票池增删执行以后、结束；排队的案件不再运行时写一条不再运行的记录。案件的阶段只在调度器的案件状态里，案件记录不记阶段（design D3）
- 每一步只写一次：同一步再写时记录不变（崩溃以后 DBOS 重新执行的步骤会再写一次）；写入的顺序不对时报错
- 读取：按案件 ID 读案件记录、方案记录和发现；一只股票最近结束的 n 个案件；某种案件类型（针对一只股票的类型按股票）最近一次得出结论的案件
- 写案件记录不写程序日志：案件记录本身就是记录；开案件、阶段变化等调度器的动作由做这些动作的流程写
- `contracts/conclusion.py`：`Conclusion` 联合类型把候选的结论排在关注的结论前面，候选决定移出的结论存成 JSON 以后读回仍是候选的结论（现在读回成关注的结论，design D7）
- `modules/statestore` 的 `VersionedStore` 加一个读取：每个键的最新版本里按筛选列选出、按一个时刻列从晚到早取前 n 个
- 迁移 v0012 建三张表
- 完整版 Proposal「记录、复盘与经验 · 案件记录」改两处（已改）：
  - 开头一句"包括没有调用 agent 的"后面加上"（比如排队期间股票状态变了、不再运行的案件）"
  - cases 表的关键字段去掉"快照 ID"、加上"结论"，末尾注明快照按案件 ID 查

## Non-goals

- outcomes（事后收益）和 reviews（复盘）两张表：M6（人已同意）
- theses 不另建表：每次复查时论点的变化和理由、复查日和催化剂截止日期的调整都在这次结论里；平仓时的论点结果（目标价达成、止损、论点推翻、催化剂过期）是评估的标注，随 M6 的评估一起做，见「需要人决定」第 2 条
- results 不另存：Result 按案件 ID 在 Agent 网关的表里读；prompt 版本随 M5 的 prompt 一起加
- 装配：bootstrap 不建案件记录的用例和存储，现在没有运行中的写入方；「案件工作流」接上时装配。三张表随启动时的迁移建好，一直是空的
- 案件的阶段、队列和排队的案件存在哪里（调度器的当前任务状态）：「案件工作流」「排队运行」
- 什么时候调用写入、从案件状态取结束原因、算 Task 数和调用次数：「案件工作流」「排队运行」；Agent 网关按案件读费用记录的接口随「案件工作流」加（design D9）
- 案件上下文给 PM 看哪些历史（近期结论取几个、怎样展示）：「案件工作流」
- `query_history`、案件上下文里历史案件的数量索引、代码算的统计查询：M5 的查询工具
- PM 的整段对话、校验不通过被退回重交的结论：不进案件记录
- 升级、论点更新、跟进申请被股票池或跟进审批拒绝的结果：不进案件记录，股票池和调度器的程序日志条目里有
- 事件 ID、跟进 ID 等触发对象的引用：现在还没有，由建出它们的「事件检测」「跟进到点」加
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `case-records`：案件记录：记录的内容和状态、写入的时刻、方案记录、股票池增删的发现、重复写入和写入的顺序、读取、存储

### Modified Capabilities

- `state-store`：修改「表的归属和迁移」，加案件记录的三张表 `caserecords_cases`、`caserecords_proposals`、`caserecords_findings`，属于案件记录模块

  - 迁移 `bootstrap/migrations/versions/v0012_create_case_records.py`（`down_revision = "0011"`）
  - 别的模块、workflows、bootstrap 的装配、shared 不改；程序日志不加行为者和动作
- **测试**：`tests/modules/caserecords/`（domain、service；repo 要开着 OrbStack）、`tests/fakes/case_records.py`（内存实现）、`tests/modules/statestore/` 补 `most_recent`、`tests/contracts/` 补结论的 JSON 往返；`tests/bootstrap/` 的表清单和最新迁移版本
- **依赖**：无
- **文档**：完整版 Proposal「案件记录」两处（见 What Changes）
- **数据库**：三张新表、一个迁移；本变更以后还没有写入方
- **并行的变更**：「状态库快照」（v0011）也改 state-store「表的归属和迁移」；本变更后归档，apply 时按它归档后的主 spec 重写 delta，v0012 接在 v0011 后面
- **对后续变更的影响**：
  - 「案件工作流」：在 design D3 表里的每个时刻调用写入；结束时给出 Task 数（task-dispatch spec 的用量）和调用次数（Agent 网关为本案件记下的费用记录条数，要给网关加按案件读的接口）；案件上下文用"最近结束的案件"和"按案件 ID 读"（跟进案件的原案件结论）
  - 「排队运行」：队列的决定里不再运行的案件逐个写不再运行

  - 「收盘心跳」：上一次寻股的那一天、新候选都用"最近一次得出结论的案件"

## 需要人决定

完整版 Proposal 对应章节的问题和本变更的做法，2026-10-17 都已经定了，做法已经写进 spec 和 design：

1. **"包括没有调用 agent 的"指什么**：开始运行的案件都会唤醒 PM 或 Reviewer，没有调用 agent 的只有排队以后不再运行的案件（case-queue spec「排队的案件按现在的状态确定类型」）。已定：不再运行的案件也记一条，状态是不再运行，只有触发、触发原因、股票、触发时刻和不再运行的时刻，Task 数和调用次数是 0；完整版改了一句（What Changes）
2. **平仓时的论点结果**：四种结果（目标价达成、止损、论点推翻、催化剂过期）和代码知道的事实不是一一对应（紧急风险退出不在四种里；持仓事件里 PM 清仓可能是论点推翻也可能是目标价达成），要另定标注规则；标注要用的事实都已经存下。已定：和事后收益一起放到 M6；完整版不改
3. **cases 缺结论**：完整版 cases 的关键字段没有结论，没有交易方案的结论（持有、继续关注、升级、寻股的增删）没有地方存。已定：cases 存通过校验的结论、给出它的模型和结论时刻；完整版 cases 的关键字段加了"结论"
4. **快照 ID**：「状态库快照」把快照按案件 ID 和版本存，凭案件 ID 就能找到（`SnapshotService.latest(case_id)` 给出最后一版）。已定：cases 不存快照 ID；完整版 cases 的关键字段去掉"快照 ID"，注明快照按案件 ID 查
5. **触发怎样记**：调度器的触发类型在调度器模块里，案件记录的 domain 不能 import。已定：只记触发的种类（四种）和调用方写的中文触发原因；事件 ID、跟进 ID 有了以后再加引用（design D8）
6. **调用次数的口径**：已定：Agent 网关为本案件记下的费用记录条数（重试、切换备用模型各算一次，拿不到用量的不算），由「案件工作流」结束时算好交给案件记录，按案件读费用记录的接口随它加（design D9）
7. **候选的结论读回成关注的结论**：现在的 `Conclusion` 联合类型按 JSON 读回时，候选决定移出的结论会读成关注的结论。已定：本变更把候选的结论排在关注的结论前面，加注释和往返测试（design D7）
