# Proposal

## Why

方案通过下单前再校验之后，还没有地方真正下单，也没有地方知道订单后来怎样了。订单要经过券商受理、部分成交、全部成交，也可能被撤销、被拒、过期，或者因为超时、断线而状态不明。处理不好会直接亏钱：

- 超时后直接重发，可能买两遍
- 没注意到部分成交，剩余部分会一直挂着
- 不知道订单结束了，它的预留就一直占着额度

变更 3 已经提供了"上报成交"和"释放"，但还没有调用方。本变更的目的只有一个：**执行模块按方案下单，把订单跟踪到终态：防止重复提交，按券商回报更新状态，到截止时刻撤单；给出累计成交和是否结束，供更新预留。**

引用的 Proposal（完整版）章节：

- 「订单生命周期」：
  - 订单状态和每次状态变化
  - 表里的"防止重复提交""状态未知""部分成交"（剩余部分到有效期后撤单、释放预留）三行
- 「风控引擎与执行」的"交易时段"（只在常规交易时段下单），以及"下单权限只在执行模块中"
- 「架构」的"风控与执行"中的执行模块：用客户端订单 ID 下单，跟踪订单到终态，案件在提交订单后结束
- 「记录、复盘与经验」的"交易记录"：订单记录包含其中来自订单本身的字段

## What Changes

- 新增执行模块 `modules/execution`：
  - domain：订单记录、8 种订单状态，以及状态怎么变。全部是纯函数
  - ports：券商接口（按客户端订单 ID 查询、提交、撤单）和订单存储接口
  - service：两个操作
    - 提交：按方案和再校验的结果建订单，再跟进一次
    - 跟进：查询券商并更新状态；到截止时刻撤单；状态未知时等一段时间再查，查清楚了再决定是否重新提交
  - config：状态未知时等多久再查询，默认 30 秒
- 一个方案最多一个订单，客户端订单 ID 就是方案 ID
- 订单都是当日有效单。截止时刻取方案生效的有效期和当天收盘中较早的那个，见「需要人决定」第 1 条
- 每次提交前先按客户端订单 ID 查询，查不到才提交。首次提交、超时后重试、进程重启后继续，都走这一条路
- 任何一次券商调用超时或断线，订单都进入"状态未知"。这只股票其他方案的新订单，在执行模块提交时被拦下，直到状态查清
- 测试替身：`tests/fakes/` 增加假券商和内存订单存储
- `OutsideSessionError`（在常规交易时段之外调用）从风控模块移到 `shared`，再校验和提交共用。风控的行为不变

## Non-goals

- 止损单：按成交数量挂止损、GTC 或每日重挂、挂单失败、减仓或清仓前先改止损单、加仓后改止损数量。这些属于变更 6
- 断线或重启后的全量对账和每日对账：变更 7。本变更只按客户端订单 ID 查询单笔订单
- 紧急风险退出要撤掉的挂单：变更 8。本变更只在截止时刻撤单
- 调用风控的"上报成交"和"释放"：由 M2 的下单工作流调用。本变更保证累计成交只增不减、进入终态后不再变化，所以工作流每次跟进后，按订单的最新状态调用即可，重复调用结果也不变（见 design D9）
- moomoo 适配器，以及它的 17 种订单状态到本变更券商回报的映射代码：M2。映射表写在 design D4
- 订单存储的数据库实现（`repo.py`）、跟进的频率和限频：M2
- 交易记录中的费用、结算状态和来源案件 ID：模拟盘查不到费用和结算；已结算资金在 M2 定状态库方案时一起设计；来源案件 ID 等 M4 有了案件记录再接上
- 订单状态写入共享状态库和程序日志：状态库方案在 M2 确定，程序日志在 M4
- 券商的成交推送：模拟盘没有，本变更只靠查询

## Capabilities

### New Capabilities

- `order-lifecycle`：提交订单、订单状态和券商回报、先查询再提交、到期撤单、状态未知、状态未知时暂停这只股票的新订单、保存订单，以及执行配置

### Modified Capabilities

无。`OutsideSessionError` 换了定义的位置，再校验的行为不变。

- **代码**：
  - 新增 `modules/execution/`：`__init__.py`、`config.py`、`domain/__init__.py`、`domain/order.py`、`ports.py`、`service.py`
  - `shared/trading_calendar.py` 增加 `OutsideSessionError`。`modules/risk/domain/recheck.py`、`service.py`、`__init__.py` 改为使用 shared 里的这个类，风控包根不再导出它
  - 新增 `tests/fakes/broker.py`、`tests/fakes/orders.py`、`tests/modules/execution/`
  - `tests/modules/risk/test_service.py` 改为从 shared import `OutsideSessionError`
- **依赖**：无
- **对后续变更的影响**：
  - 变更 6：
    - 按订单的累计成交挂止损单，部分成交也挂
    - 减仓和清仓的卖单提交前，先改止损单
    - 止损单的客户端订单 ID 由 ID 生成端口给出，不能用方案 ID
  - 变更 7：
    - 停机期间的成交和订单结束，由对账补上
    - 下面两种情况要告警：受理过的订单在券商查不到；同一个客户端订单 ID 在券商有两笔订单（见「需要人决定」第 3 条）
  - 变更 8：紧急退出前撤掉这只股票还在挂的卖单。由此结束的订单记为已撤销
  - M2：
    - 下单工作流依次做：再校验、提交、定时跟进到终态。每次跟进后按累计成交调用"上报成交"，进入终态时调用"释放"。提交被暂停时，等一段时间后从再校验重新开始
    - 实现 moomoo 适配器和订单存储的 `repo.py`
    - 选定跟进的频率，要符合 moomoo 查询订单的限频
  - 变更 3 design D7 原本写的是由变更 5 接入成交和订单结束。现在改为：变更 5 提供订单的最新状态，由 M2 的工作流调用风控（见 design D9）

## 需要人决定

已决定（2026-10-03，人同意推荐做法）：

1. **方案有效期跨多天，但订单只能当日有效**：「订单生命周期」说部分成交的剩余部分"到有效期后撤单"，而方案的有效期没有上限（变更 4），可以写成几天之后。模拟盘只支持当日有效单，收盘时券商会让订单自动失效。实盘、模拟盘和回放又要共用同一套代码，所以不能用 GTC。决定：订单最多挂到提交当天收盘
   - 截止时刻取生效的有效期和当天收盘中较早的那个。到截止时刻还没成交的部分，记为已过期，释放预留，方案结束，第二天不再重挂
   - 多天的有效期只在下单之前起作用，比如等人工确认、等开盘
   - 理由：隔了一夜，行情已经变了，要不要继续买，应该由 PM 重新判断。这样也保证了一个方案只有一个订单
2. **已撤销和已过期怎么区分**：Proposal 列了这两种状态，但没有定义。决定：券商报撤销或失效时，如果当前时刻不早于截止时刻，记为已过期，包括我们到期撤单和当日单收盘失效；否则记为已撤销。两者都释放没成交的部分，只是交易记录里的状态不同
3. **"确认未收到才重试"做不到完全确认**：moomoo 没有真正的客户端订单 ID，只能把它写进备注，再按备注查找。超时之后马上查，券商可能还没处理完这笔订单，于是查不到，重发就成了重复下单。决定：
   - 超时后先等一段时间再查，默认 30 秒，可以配置
   - 只有券商从来没受理过的订单才会重新提交；过了截止时刻就不再提交，订单记为已过期
   - 剩下的风险（券商超过等待时长才出现这笔订单）很少见，由变更 7 的对账发现同一客户端订单 ID 的两笔订单并告警，本变更不另外处理
