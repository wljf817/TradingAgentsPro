# Spec Delta

## ADDED Requirements

### Requirement: 调度器的动作

调度器的下面这些动作 SHALL 各写一条，行为者是调度器。现在只有跟进审批的动作（follow-ups spec）：

| 动作 | 什么时候写 | 对象 | 引用 | 说明 |
| --- | --- | --- | --- | --- |
| 批准跟进 | 跟进申请通过审批，新的跟进保存以后（follow-ups spec「审批的输入和结果」） | 新跟进的 ID | 没有 | 跟进的内容 |
| 拒绝跟进 | 跟进申请没有通过审批（follow-ups spec「审批的顺序」） | 股票 | 没有 | 不通过的原因；申请的内容，写法和跟进的内容相同，没写引用的写明没有引用 |
| 替换跟进 | 批准的跟进替换了这只股票原因相同的待执行跟进（follow-ups spec「原因相同时替换」），写在这次的批准跟进之后 | 被替换的跟进的 ID | 输入：替换它的新跟进的 ID | 被替换的跟进的内容 |
| 作废跟进 | 股票状态往下走，这只股票待执行的跟进作废（follow-ups spec「股票状态往下走时作废」）：每个作废的跟进一条，按作废时给出的顺序 | 跟进 ID | 没有 | 之前和之后的状态，不在股票池也不是持仓的写不在股票池；跟进的内容 |
| 触发跟进 | 到点触发把跟进记为已触发（follow-ups spec「到点触发」）：每个一条，按给出的顺序 | 跟进 ID | 没有 | 跟进的内容 |

跟进的内容：股票、原因类型、引用的对象、触发时间（UTC）、要回答的问题、可能采取的动作。

- 批准、拒绝和替换跟进的案件 ID 是提出申请的案件；作废和触发跟进不属于案件，案件 ID 为空
- 每个跟进保存以后才写它的条目；写条目出错时照「写入失败」处理，已经保存的跟进不撤回
- 取得待执行的跟进、没有跟进到点的到点触发、不作废跟进的状态变化 SHALL NOT 写程序日志

#### Scenario: 批准跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据
- **WHEN** CCC 申请日程申请
- **THEN** 程序日志有一条批准跟进，行为者是调度器，对象 F-1，案件 ID K-1，没有引用
- **AND** 说明写明 CCC、外部日程、日程项 S-9、触发时间 2026-11-19 14:30 UTC、问题"竞争对手 11 月 18 日发财报，之后对这只股票有什么影响？"和可能采取的动作"减仓"

#### Scenario: 拒绝跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据
- **WHEN** CCC 申请事件申请，不写引用
- **THEN** 程序日志有一条拒绝跟进，对象 CCC，案件 ID K-1；说明写明没有引用具体对象、事件后反应、没有引用、触发时间 2026-10-14 18:00 UTC
- **AND** 没有批准跟进

#### Scenario: 替换跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1）
- **WHEN** 当前时刻 2026-10-15 15:00Z，CCC 的案件 K-2 申请日程申请，触发时间改为 2026-11-30 14:30Z
- **THEN** 程序日志接着依次有批准跟进（对象 F-2，案件 ID K-2，说明写明触发时间 2026-11-30 14:30 UTC）和替换跟进（对象 F-1，案件 ID K-2，输入的引用是 F-2，说明写明触发时间 2026-11-19 14:30 UTC）

#### Scenario: 触发跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1），再申请事件申请（F-2）；BBB 申请观察申请（F-3）
- **WHEN** 当前时刻 2026-11-20 15:00Z，到点触发
- **THEN** 程序日志接着依次有 F-2、F-3、F-1 的触发跟进，都没有案件 ID
- **AND** F-3 的说明写明 BBB、价格或指标观察、条件价格不低于 55、触发时间 2026-10-21 20:00 UTC

#### Scenario: 作废跟进

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1），再申请事件申请（F-2）
- **WHEN** CCC 代码触发的清仓转为候选
- **THEN** 程序日志接着依次有 F-2、F-1 的作废跟进，都没有案件 ID，说明写明持仓变为候选

#### Scenario: 写条目出错时跟进已经保存

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；写程序日志时数据库会出错一次
- **WHEN** CCC 申请日程申请
- **THEN** 审批报错，不返回获批或拒绝
- **AND** F-1 已经保存，是待执行

#### Scenario: 没有动作时不写

- **GIVEN** follow-ups spec「跟进的记录」的基准数据；CCC 申请日程申请（F-1）；BBB 申请观察申请（F-2）
- **WHEN** 取得 CCC 待执行的跟进；当前时刻 2026-10-14 18:00Z，到点触发；BBB 买入成交变为持仓
- **THEN** 程序日志都没有新条目

## MODIFIED Requirements

### Requirement: 程序日志的条目

程序 SHALL 把每个动作写成程序日志的一条记录。程序日志存在状态库所在的数据库里（表 `programlog_entries`，state-store spec「表的归属和迁移」），只由程序日志模块写入：别的模块、流程和启动程序都经它写，不直接写表。每条记录有：

| 字段 | 内容 |
| --- | --- |
| 编号 | 按写入的先后递增 |
| 时间 | 写入时从时钟读取的时刻；存为带时区的时刻，读回的是同一时刻，和数据库服务器、本机的时区都无关 |
| 行为者 | 风控引擎、执行模块、人、系统、股票池、调度器，各自的动作见下面以「<行为者>的动作」为名的要求；以后的变更加别的行为者和动作 |
| 动作 | 行为者的一个动作 |
| 对象 | 动作针对的东西的标识：方案 ID、止损单的客户端订单 ID、股票代码、跟进 ID；针对整个券商账户写 `account`，针对整个程序写 `system` |
| 案件 ID | 动作所属的案件；不属于案件时为空 |
| 输入的引用、输出的引用 | 动作用到的、产生的东西的标识，比如确认消息的标识、交易日；各是一组文字，可以为空 |
| 说明 | 动作的内容和结果，中文；可以为空 |
| 耗时、token、费用 | 可以为空；费用是金额，原样保存每一位小数 |

行为者和动作各是一组固定的值。案件 ID、耗时、token 和费用只在动作的要求写明时才有，其余为空。

#### Scenario: 写一条

- **GIVEN** 进程的本机时区是 UTC+14；时钟是 2026-10-14T15:00:00.123Z
- **WHEN** 写一条：行为者是人，动作是确认，对象是方案 ID P1，输入的引用是确认消息的标识 M1，说明是"买入 BBB"
- **THEN** 程序日志多了一条，读回的时间是 2026-10-14T15:00:00.123Z，行为者、动作、对象、输入的引用和说明都是写入的值
- **AND** 输出的引用为空，案件 ID、耗时、token、费用为空

#### Scenario: 可以为空的字段原样读回

- **WHEN** 写一条带案件 ID、耗时 1.5 秒、token 1200、费用 0.0123 的条目
- **THEN** 读回的案件 ID、耗时、token 和费用都和写入的相同，费用仍是 0.0123
