# Proposal

## Why

健康监控（add-degraded-mode）能按健康信号判定降级模式，风控和下单流程也已经按 `health.status.degraded` 暂停开仓，但现在只有启动时判定一次，而且只写日志：程序运行中券商断线、OpenD 行情中断都不会进入降级模式，也不会告警；进入了降级模式（启动时）也没有人在各项恢复以后对账、让它回到正常。盘中巡检（add-session-patrol）有了一个全天运行、每 15 秒一轮的循环和一把全程序共用的锁，健康判定可以挂在它的每一轮上。

本变更的目的只有一个：**盘中巡检每一轮判定一次系统健康，状态变化时在 Discord 告警，各项恢复以后在锁里和券商对账、退出降级模式。** 顺带把启动时第一次健康判定的降级在 Discord 连上以后补发告警（bootstrap 留给本变更的一项）。

引用的 Proposal（完整版）章节：

- 「架构」的「支撑模块」：健康监控监控模型 API、券商连接、数据延迟、调用预算和调度器心跳，异常时进入降级模式（保留止损单、暂停开仓），并告警
- 「故障处理」：系统健康状态由健康监控负责；降级模式下保留所有止损单、暂停开仓（风控拒绝开仓、已确认未下单的开仓方案在再校验时作废）、告警通知、紧急风险退出照常有效；恢复后先对账
- 「订单生命周期」表的「断线或重启」一行：恢复后先与券商对账，以券商为准修正状态库，再恢复运行
- 「技术栈与部署」：健康监控是同一进程内自写的模块；通知与人工确认一行（告警发 Discord，发不出去时只写程序日志，不算健康异常）；可靠性要求（执行模块恢复后先与券商对账）

已经定了的（M1 和 M2 拆分时）：五项检查、三个状态和数据延迟只在盘中检查（degraded-mode spec）；离开降级模式总要在每一项都恢复以后对账一次，对账有没有不一致都算完成，不一致由执行模块自己暂停开仓；M2 里模型 API 和调用预算按正常传入；M2 的告警发 Discord，其余写 Python 日志。

## What Changes

- 盘中巡检每一轮在第 3 步（对齐止损单）之后做一项「健康判定」：拼好健康信号，让健康监控判定一次，按状态变化写日志和告警；收盘对账仍是一轮的最后一项
- 健康信号的来源：
  - 券商连接：这一轮第 3 步读券商全部持仓的结果，读到为连接，超时或断线为断开；不另外调用券商
  - 数据延迟：行情模块给出的参考股票（SPY）的更新时刻；取不到行情时按没有更新处理，并写 WARNING
  - 模型 API、调用预算按正常；调度器心跳按判定的时刻（M2 没有调度器，见 design）
- 告警只在进入和离开降级模式时发：正常 → 降级时写明异常的检查、已暂停开仓；对账完成、回到正常时写明已恢复开仓（对账有不一致时列出不一致、写明仍暂停开仓）。降级和等待对账之间来回、降级期间异常的检查变化只写日志
- 恢复后的对账：判定从降级变为等待对账的这一轮不对账；下一轮判定仍然没有异常（已经等待对账至少一轮）时，拿着锁让执行模块对账一次、告诉健康监控对账完成。对账读券商失败时留在等待对账，下一轮再来
- 第一次健康判定（启动时）的信号改为和巡检同一个取法（券商连接仍按正常：启动对账刚读过券商）；处于降级模式时，Discord 连上以后、DBOS 启动以前推送一条告警

## Non-goals

- 模型 API 和调用预算的真实信号：M4、M5（Agent 网关）。M2 按正常传入
- 调度器心跳的真实信号：调度器是 M4 的案件循环；本变更不为它预留接口
- 降级时不开始新案件、新触发排队、恢复后按优先级运行积压的案件：M3、M4
- 降级时风控拒绝开仓、已确认未下单的开仓方案作废：风控规则和下单流程已经按 `degraded` 输入处理，本变更不改
- 紧急退出、本地备用止损：「紧急退出流程」
- 巡检自己卡住时的看门狗：判定在巡检的一轮里，巡检卡住就没有判定；省略，见 design
- 健康状态持久化：degraded-mode spec 已定放在内存里，重启后重新判定
- 改变任何模块的行为：健康监控、执行模块、行情、通知都不改，也不加方法
- 部署机器上的检查：整个「流程」组做完统一做
- 程序日志：M4；现在写 Python 日志
- 省略的少见情况：见 design 的省略清单

## Capabilities

### New Capabilities

- `health-monitoring`：巡检里的健康判定（位置、锁、停止）；健康信号；状态变化的告警和日志；恢复后的对账；健康判定的失败

### Modified Capabilities

- `bootstrap`：「第一次健康判定」的信号按 health-monitoring spec 取，降级时在 Discord 连上以后推送告警

## Impact

- **代码**：
  - 新增 `workflows/health.py`：`HealthMonitor`（每一轮的判定、告警和恢复后的对账）、`read_signals`（拼健康信号，巡检和启动共用）、告警文字
  - `workflows/patrol.py`：构造参数加 `HealthMonitor`；第 3 步给出读券商全部持仓的结果；`run_round` 在第 3 步之后加「健康判定」一项
  - `bootstrap/startup.py`：第一次健康判定用 `read_signals`，日志用检查的中文名
  - `bootstrap/app.py`：装配 `HealthMonitor` 交给巡检；Discord 连上以后按第一次健康判定的结果推送告警
  - modules、contracts、shared、integrations 不改
- **测试**：新增 `tests/workflows/test_health.py`；改 `tests/workflows/builders.py`（巡检带上行情替身和健康监控）、`tests/workflows/test_patrol.py`、`tests/bootstrap/test_startup.py`、`tests/bootstrap/test_app.py`
- **依赖**：无
- **数据库**：无
- **券商请求**：不增加（券商连接取巡检已有的读取）；恢复时多一次对账。OpenD：每一轮多一次参考股票的快照请求（每 30 秒 2 次，限制是 60 次）
- **前置变更**：「下单流程」「收盘对账」先 apply：告警的发送时机照收盘对账的启动对账告警，恢复对账有不一致时的告警行用收盘对账的三类不一致的写法（`workflows/reconciliation.py`）
- **文档**：`docs/实现路线.md` 的进度
