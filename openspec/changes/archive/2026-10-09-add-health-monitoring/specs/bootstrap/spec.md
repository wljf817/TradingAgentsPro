## MODIFIED Requirements

### Requirement: 第一次健康判定

启动对账之后、Discord 和 DBOS 之前，程序 SHALL 让健康监控判定一次（degraded-mode spec），健康信号如下：

| 信号 | 取值 | 理由 |
| --- | --- | --- |
| PM、Critic 还有可用的模型 | 有 | 还没有 Agent 网关 |
| 持仓保留预算用完 | 没有 | 还没有 Agent 网关 |
| 调度器最近一次心跳 | 判定的时刻 | 还没有调度器 |
| 券商连接 | 正常 | 启动对账刚读过券商；读取失败时已经启动失败 |
| 行情最近一次更新的时刻 | 和盘中巡检的判定取法相同（health-monitoring spec「健康信号」）：行情模块给出的参考股票的更新时刻；取不到（OpenD 没开、没登录、出错）时为没有（启动以后还没取到过），并写一条 WARNING 写明原因 | 这次取到的更新时刻也算「程序启动以后最近一次取到的」 |

| 判定结果 | 处理 |
| --- | --- |
| 正常 | 写 INFO，继续启动 |
| 降级 | 写 WARNING，列出异常的检查；继续启动。风控按 degraded-mode spec 暂停开仓。Discord 连上以后、DBOS 启动以前推送一条告警（discord-notification spec「告警」），在启动对账的告警（如果有）之后 |

告警写明启动时处于降级模式，其余和 health-monitoring spec「状态变化的告警和日志」的「进入降级模式」相同：进入降级模式的时刻（这次判定的时刻）、异常的检查、已暂停开仓、止损单照常保留、各项恢复并和券商对账以后恢复开仓。告警发不出去时只写错误日志，照常继续启动。

这次判定的状态由盘中巡检接着用：巡检的判定仍是降级时不再告警，各项恢复以后照 health-monitoring spec「恢复后的对账」对账、回到正常。

#### Scenario: 盘中行情正常

- **WHEN** 正常启动
- **THEN** 健康是正常，启动完成
- **AND** Discord 没有收到健康的告警

#### Scenario: 盘中 OpenD 没开

- **GIVEN** 取行情时 OpenD 报错
- **WHEN** 正常启动
- **THEN** 有一条 WARNING 写明取不到行情和 OpenD 的错误
- **AND** 进入降级模式，异常的检查是数据延迟，有一条 WARNING 写明
- **AND** Discord 连上以后、DBOS 启动以前收到一条告警，写明启动时处于降级模式、数据延迟、已暂停开仓
- **AND** 启动完成

#### Scenario: 盘外 OpenD 没开

- **GIVEN** 启动时刻是 2026-10-14T12:00:00Z（美东 8:00，开盘前）；取行情时 OpenD 报错
- **WHEN** 正常启动
- **THEN** 有一条 WARNING 写明取不到行情
- **AND** 健康是正常（盘外不检查数据延迟），启动完成
- **AND** Discord 没有收到健康的告警

#### Scenario: 开盘后行情一直没有更新

- **GIVEN** 参考股票的行情停在前一个交易日收盘
- **WHEN** 正常启动
- **THEN** 进入降级模式，异常的检查是数据延迟，启动完成
- **AND** Discord 收到一条告警，写明启动时处于降级模式、数据延迟

#### Scenario: 启动对账和健康都要告警

- **GIVEN** Alpaca 模拟盘持有 CCC 100 股，状态库里没有 CCC 的订单；取行情时 OpenD 报错
- **WHEN** 正常启动
- **THEN** Discord 连上以后先收到启动对账的告警，再收到启动时处于降级模式的告警，之后 DBOS 才启动

#### Scenario: 健康的告警发不出去

- **GIVEN** 取行情时 OpenD 报错；Discord 连上以后，发告警时报错
- **WHEN** 正常启动
- **THEN** 有一条错误日志，含告警的文字和失败原因
- **AND** 启动完成

#### Scenario: 巡检第一轮仍是降级时不再告警

- **GIVEN** 取行情时 OpenD 一直报错
- **WHEN** 正常启动，巡检做完第一轮
- **THEN** 状态仍是降级
- **AND** Discord 一共只收到一条健康的告警（启动时的那一条）
