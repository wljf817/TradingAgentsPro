## MODIFIED Requirements

### Requirement: 任务清单

任务类型 SHALL 是下表的八种之一，每种只属于一个子 agent；Task 的目标 agent 就是任务类型所属的子 agent，所以目标只能是 News、Quant、Fundamentals：

| 任务类型 | 目标 |
| --- | --- |
| 事件影响评估 | News |
| 某日期以来的新闻汇总 | News |
| 价格反应 | Quant |
| 趋势和支撑阻力 | Quant |
| 波动情况 | Quant |
| 财报对比预期 | Fundamentals |
| 指引变化 | Fundamentals |
| 估值位置 | Fundamentals |

- 每种任务的输出都是 signal-format spec 的信号或无信号
- 问题只补充具体关注点；某日期以来的新闻汇总把起始日期写在问题里
- Quant 的任务另写周期和范围（见「任务请求的格式」）

本 spec 的场景除非另有说明，都使用默认配置和下面的基准数据：

- 当前时刻 2026-10-14 15:00Z（周三，盘中）
- 案件：K-1 是 BBB（关注）的关注股事件；K-2 是寻股；K-3 是 CCC（持仓）的持仓事件；K-4 是 BBB 的关注复查，在 K-1 结束以后运行
- 任务请求：
  - 价格请求：任务类型价格反应；股票 BBB；问题"财报后的放量上涨能否持续？"；输入 E-1；周期日线；范围 60 个交易日
  - 新闻请求：任务类型事件影响评估；股票 BBB；问题"大客户续约对明年收入的影响有多大？"；输入 E-2
  - 财报请求：任务类型财报对比预期；股票 BBB；问题"毛利率超预期能否持续？"；输入 E-3 和 E-4
  - "价格请求 n"指问题改为"问题 n"的价格请求，n 不同就是不同的任务；"新闻请求 n"同理
  - "AAA 的价格请求"指只把价格请求的股票改为 AAA，其他请求和股票同理
- "PM 派发 a、b"指 PM 在 K-1 里调用一次 dispatch_tasks，依次请求 a、b；"Critic 派发 a"同理；在别的案件里派发另外写明
- 新生成的 Task 按先后依次是 T-1、T-2……，派发时刻都是当前时刻，截止时间是 2026-10-14 15:05Z
- "T-n 完成""T-n 无信号"指 T-n 不晚于截止时间收到 signal-format spec 的基准信号、基准无信号；"T-n 超时"指到截止时间仍没有输出，记为超时；"T-n 失败"指 T-n 收到评估窗口 4 的信号，记为失败
- "PM 用了 r 轮、n 个任务"指本案件 PM 用掉的轮次和任务数（见「本案件的任务和用量」）
- GIVEN 里的几步依次进行；一个 WHEN 里用"；"或"或者"隔开的几种情况，各自从 GIVEN 的数据开始，互不影响；用"再""接着"连接的依次进行

#### Scenario: 每种任务类型的目标

- **WHEN** 请求的任务类型是事件影响评估、某日期以来的新闻汇总
- **THEN** 目标都是 News
- **WHEN** 请求的任务类型是价格反应、趋势和支撑阻力、波动情况
- **THEN** 目标都是 Quant
- **WHEN** 请求的任务类型是财报对比预期、指引变化、估值位置
- **THEN** 目标都是 Fundamentals

#### Scenario: 不在清单里的任务类型

- **WHEN** 请求的任务类型是"行业对比"
- **THEN** 请求格式错误

### Requirement: 任务请求的格式

PM 和 Critic 派发任务时 SHALL 为每个任务写一个任务请求：

| 项 | 说明 |
| --- | --- |
| 任务类型 | 任务清单里的一种，它决定了目标 |
| 股票 | 股票代码 |
| 问题 | 文字：在任务类型之外补充的具体关注点 |
| 输入 | 状态库条目 ID 的列表，可以为空；每个 ID 是非空的文字 |
| 周期 | 周线、日线、60 分钟线、15 分钟线之一；目标是 Quant 的任务必须写，别的任务不能写 |
| 范围 | 往前多少个交易日，到最新一根 K 线为止，正整数；目标是 Quant 的任务必须写，别的任务不能写 |

- 缺少任务类型、股票或问题，文字去掉首尾空白后为空，某项不符合上表，包含上表以外的项（包括目标 agent），都 MUST 是格式错误
- 格式错误的请求不生成 Task 和 Result，由调用方退回发起者
- 发起者不写在请求里：调用方按调用 dispatch_tasks 的是 PM 还是 Critic 给出

#### Scenario: 完整的请求

- **WHEN** 写价格请求、新闻请求、财报请求
- **THEN** 都格式正确
- **WHEN** 价格请求不写输入
- **THEN** 格式正确，输入为空

#### Scenario: 缺少一项或文字为空

- **WHEN** 价格请求分别缺少任务类型、股票、问题；问题是 "  "；股票是 ""；输入是 E-1 和 "  "
- **THEN** 都是格式错误

#### Scenario: 请求里写目标

- **WHEN** 价格请求另外写了目标 Quant
- **THEN** 格式错误

#### Scenario: Quant 的任务缺少周期或范围

- **WHEN** 价格请求不写周期；不写范围；范围是 0
- **THEN** 都是格式错误

#### Scenario: 别的任务写了周期或范围

- **WHEN** 新闻请求另外写了周期日线；财报请求另外写了范围 60 个交易日
- **THEN** 都是格式错误

#### Scenario: 不在表里的周期

- **WHEN** 价格请求的周期是月线
- **THEN** 格式错误

### Requirement: Task 的格式

Agent 网关 SHALL 为每个不复用的请求生成一个 Task，派发的和被拒绝的都有，包含：

| 项 | 说明 |
| --- | --- |
| task_id | 新生成 |
| 案件 ID | 派发任务的案件 |
| 发起者 | PM 或 Critic |
| 目标 agent | 任务类型所属的子 agent |
| 任务类型、股票、问题、输入、周期、范围 | 请求的原样内容 |
| 派发时刻 | 网关处理这次 dispatch_tasks 的时刻 |
| 截止时间 | 派发时刻加"任务时限"（见「派发的配置」） |
| PM 的轮次 | 发起者是 PM、并且派发出去的任务：这一次是 PM 在本案件的第几轮（见「PM 的轮次」）；Critic 的任务和被拒绝的任务没有 |

- 发起者不是 PM 或 Critic 时 MUST 报错：子 agent 和其他 agent 不能派任务
- Task 生成以后 SHALL NOT 被修改

#### Scenario: 派发出去的 Task

- **WHEN** PM 派发价格请求
- **THEN** 派发 T-1：案件 K-1，发起者 PM，目标 Quant，任务类型价格反应，股票 BBB，问题"财报后的放量上涨能否持续？"，输入 E-1，周期日线，范围 60 个交易日，派发时刻 2026-10-14 15:00Z，截止时间 2026-10-14 15:05Z，PM 的第 1 轮

#### Scenario: 被拒绝的请求也有 Task

- **WHEN** PM 派发 AAA 的价格请求
- **THEN** 生成 T-1，股票 AAA，没有 PM 的轮次；T-1 的 Result 是被拒绝

#### Scenario: Critic 的任务没有轮次

- **WHEN** Critic 派发新闻请求
- **THEN** 派发 T-1：发起者 Critic，目标 News，没有 PM 的轮次

#### Scenario: 只有 PM 和 Critic 能派任务

- **WHEN** 发起者是 News；或者是 Reviewer
- **THEN** 都报错，不生成 Task

### Requirement: 相同的任务

两个任务的任务类型、股票、问题、周期、范围都相同，输入的条目不论顺序也相同时，SHALL 算相同的任务，不论发起者是谁。本案件有相同的任务、并且它还没有 Result 或者 Result 是完成或无信号时，请求 SHALL 复用这个任务：

- 不生成新 Task，给出已有的 Task 和它的 Result；还没有 Result 时等它的 Result
- 复用不算任务数，也不算轮次
- Result 是超时、失败或被拒绝的任务 SHALL NOT 被复用：再派时按「派发的顺序」检查，派发出去就是新任务
- 只复用同一个案件的任务

#### Scenario: 复用完成的 Result

- **GIVEN** PM 派发价格请求，T-1 完成
- **WHEN** PM 派发价格请求
- **THEN** 复用 T-1，给出 T-1 的 Result，不生成新的 Task；PM 用了 1 轮、1 个任务

#### Scenario: 复用无信号，输入的顺序不同

- **GIVEN** PM 派发财报请求，T-1 无信号
- **WHEN** PM 派发财报请求，输入写成 E-4 和 E-3
- **THEN** 复用 T-1

#### Scenario: 不相同的任务不复用

- **GIVEN** PM 派发价格请求，T-1 完成
- **WHEN** PM 派发价格请求 1；输入改为 E-2 的价格请求；输入改为 E-1 和 E-2 的价格请求；任务类型改为趋势和支撑阻力的价格请求
- **THEN** 都派发 T-2，PM 的第 2 轮

#### Scenario: 周期或范围不同不复用

- **GIVEN** PM 派发价格请求，T-1 完成
- **WHEN** PM 派发周期改为周线的价格请求；或者范围改为 20 个交易日的价格请求
- **THEN** 都派发 T-2，PM 的第 2 轮

#### Scenario: 同一次里的重复请求

- **WHEN** PM 派发价格请求、价格请求
- **THEN** 派发 T-1，第二个请求复用 T-1；PM 用了 1 轮、1 个任务
- **WHEN** 接着 T-1 完成
- **THEN** 两个请求得到的都是 T-1 的 Result

#### Scenario: 超时和失败的不复用

- **GIVEN** PM 派发价格请求，T-1 超时
- **WHEN** PM 派发价格请求
- **THEN** 派发 T-2，PM 的第 2 轮；PM 用了 2 轮、2 个任务
- **GIVEN** PM 派发价格请求，T-1 失败
- **WHEN** PM 派发价格请求
- **THEN** 派发 T-2

#### Scenario: 被拒绝的不复用

- **GIVEN** PM 派发 AAA 的价格请求，T-1 被拒绝
- **WHEN** PM 派发 AAA 的价格请求
- **THEN** 生成 T-2，同样被拒绝，原因是"股票不是案件的股票"

#### Scenario: Critic 复用 PM 的任务

- **GIVEN** PM 派发新闻请求，T-1 完成
- **WHEN** Critic 派发新闻请求
- **THEN** 复用 T-1；Critic 用了 0 个补充研究额度

#### Scenario: 轮次用完以后仍可以复用

- **GIVEN** PM 派发价格请求，再派发新闻请求，已经用掉 2 轮；T-1 和 T-2 都完成
- **WHEN** PM 派发价格请求
- **THEN** 复用 T-1，不被拒绝

#### Scenario: 不复用别的案件的任务

- **GIVEN** PM 在 K-1 派发价格请求，T-1 完成
- **WHEN** PM 在 K-4 派发价格请求
- **THEN** 派发 T-2，K-4 的第 1 轮

### Requirement: 派发的顺序

PM 或 Critic 调用一次 dispatch_tasks 时，Agent 网关 SHALL 按请求的顺序逐个处理，每个请求得到下面三种结果之一：

- 复用：本案件有可以复用的相同任务（见「相同的任务」），给出那个 Task 和它的 Result，不再检查
- 被拒绝：按下表的顺序检查，第一项不通过时生成 Task 和被拒绝的 Result，原因是这一项的原因
- 派发：全部通过，生成 Task，由调用方交给目标子 agent

| 顺序 | 检查 | 适用于 | 不通过时的原因 |
| --- | --- | --- | --- |
| 1 | 单只股票的案件：任务的股票是案件的股票（见「案件的股票」） | PM、Critic | 股票不是案件的股票 |
| 2 | 寻股：目标是 Quant 或 Fundamentals（见「寻股派给谁」） | PM、Critic | 寻股只能派给 Quant 和 Fundamentals |
| 3 | 目标是 Quant 的任务：范围不超过这个周期的上限（见「派发的配置」） | PM、Critic | 范围超过上限 |
| 4 | 这一次的轮次不超过"PM 的轮次上限"（见「PM 的轮次」） | PM | 轮次已用完 |
| 5 | PM 在本案件派发出去的任务少于"PM 的任务数上限"（见「PM 的任务数」） | PM | 任务数已用完 |
| 6 | Critic 在本案件派发出去的任务少于"Critic 的补充研究额度"（见「Critic 的补充研究额度」） | Critic | 补充研究额度已用完 |

- 后面的请求按前面处理完以后的情况处理：前面派发的计入任务数，也能被后面相同的请求复用
- 被拒绝的 Result 直接交回发起者，不调用子 agent；发起者在缺少该信息的情况下继续

#### Scenario: 一次派发几个任务

- **WHEN** PM 派发价格请求、新闻请求、财报请求
- **THEN** 依次派发 T-1（目标 Quant）、T-2（News）、T-3（Fundamentals），都是 PM 的第 1 轮；PM 用了 1 轮、3 个任务

#### Scenario: 有的派发有的被拒绝

- **WHEN** PM 派发价格请求、AAA 的新闻请求、财报请求
- **THEN** 派发 T-1；T-2 被拒绝，原因是"股票不是案件的股票"；派发 T-3；PM 用了 1 轮、2 个任务

#### Scenario: 多项不通过时给出第一项

- **GIVEN** PM 派发价格请求，再派发新闻请求，已经用掉 2 轮
- **WHEN** PM 派发 AAA 的财报请求
- **THEN** 被拒绝，原因是"股票不是案件的股票"
- **GIVEN** PM 在 K-2 派发 DDD 的价格请求，再派发 EEE 的价格请求，已经用掉 2 轮
- **WHEN** PM 在 K-2 派发 DDD 的新闻请求
- **THEN** 被拒绝，原因是"寻股只能派给 Quant 和 Fundamentals"

#### Scenario: 范围超过上限

- **WHEN** PM 派发范围改为 505 个交易日的价格请求
- **THEN** 生成 T-1，Result 是被拒绝，原因是"范围超过上限"，不算轮次和任务数
- **WHEN** PM 派发范围改为 504 个交易日的价格请求
- **THEN** 派发 T-1
- **WHEN** Critic 派发周期改为 15 分钟线、范围 6 个交易日的价格请求
- **THEN** 被拒绝，原因是"范围超过上限"，不算补充研究额度

### Requirement: 派发的配置

派发的阈值 SHALL 是可配置项：

| 配置项 | 说明 | 默认值 | 要求 |
| --- | --- | --- | --- |
| PM 的任务数上限 | 每个案件 PM 派发出去的任务最多这么多个 | 6 | 正整数 |
| PM 的轮次上限 | 每个案件 PM 最多派这么多轮 | 2 | 正整数 |
| Critic 的补充研究额度 | 每个案件 Critic 派发出去的任务最多这么多个 | 2 | 正整数 |
| 任务时限 | 截止时间是派发时刻加这么久 | 5 分钟 | 大于 0 |
| 周线的范围上限 | 周期是周线的任务最多这么多个交易日 | 1260 | 正整数 |
| 日线的范围上限 | 周期是日线的任务最多这么多个交易日 | 504 | 正整数 |
| 60 分钟线的范围上限 | 周期是 60 分钟线的任务最多这么多个交易日 | 20 | 正整数 |
| 15 分钟线的范围上限 | 周期是 15 分钟线的任务最多这么多个交易日 | 5 | 正整数 |

不满足要求时 MUST 配置报错。

#### Scenario: 默认配置

- **WHEN** 不传任何配置项新建配置
- **THEN** PM 的任务数上限 6，PM 的轮次上限 2，Critic 的补充研究额度 2，任务时限 5 分钟，周线、日线、60 分钟线、15 分钟线的范围上限依次是 1260、504、20、5

#### Scenario: 配置不合法

- **WHEN** PM 的任务数上限配置为 0；PM 的轮次上限配置为 0；Critic 的补充研究额度配置为 0；任务时限配置为 0 秒；日线的范围上限配置为 0
- **THEN** 都配置报错

#### Scenario: 改成别的值

- **GIVEN** PM 的轮次上限配置为 1
- **WHEN** PM 派发价格请求，再派发新闻请求
- **THEN** 新闻请求被拒绝，原因是"轮次已用完"
- **GIVEN** PM 的任务数上限配置为 1
- **WHEN** PM 派发价格请求、新闻请求
- **THEN** 价格请求派发，新闻请求被拒绝，原因是"任务数已用完"
- **GIVEN** Critic 的补充研究额度配置为 1
- **WHEN** Critic 派发新闻请求 1、新闻请求 2
- **THEN** 新闻请求 1 派发，新闻请求 2 被拒绝，原因是"补充研究额度已用完"
- **GIVEN** 任务时限配置为 10 分钟
- **WHEN** PM 派发价格请求
- **THEN** T-1 的截止时间是 2026-10-14 15:10Z
- **GIVEN** 日线的范围上限配置为 100
- **WHEN** PM 派发范围改为 101 个交易日的价格请求
- **THEN** 被拒绝，原因是"范围超过上限"

### Requirement: 任务的存储

Agent 网关 SHALL 把 Task 和 Result 存在状态库所在的数据库里（任务表 gateway_tasks、Result 表 gateway_results，state-store spec「表的归属和迁移」），只由 Agent 网关写入：

- 只追加：Task 生成时写入，Result 生成时写入；写入以后 MUST NOT 被修改或删除
- 读回的 Task 和 Result 和写入的完全相同：输入的顺序、周期和范围、信号的每一项、费用的每一位小数、耗时、原因、说明、模型和是不是备用模型；派发时刻、截止时间读回的是同一时刻
- 进程重启以后（用同一个数据库新建存储），SHALL 读到之前写入的全部 Task 和 Result：复用、轮次和任务数接着算，之前派发的任务照样能生成 Result
- 读写出错（数据库连不上、表不存在、存着的 Task 或 Result 读不出来）时 SHALL 报错：MUST NOT 当作没有任务或者任务还没有 Result，也 MUST NOT 当作已经写入
- 几个案件可以同时派发、同时生成 Result：每个案件的检查只看本案件的任务，互不影响
- 同一个案件的派发 SHALL 由调用方依次进行：一个案件一次只在一个阶段（case-stages spec「案件的阶段」），PM 和 Critic 不会同时派发。生成 Result 可以和派发同时进行

本 requirement 的场景里，子 agent 的主模型是 google/s-1，备用模型是 openai/s-2（model-fallback spec 的基准模型的配置）；"重启"指用同一个数据库新建存储和 Agent 网关，之后新生成的 Task 接着编号。

#### Scenario: 重启以后接着算

- **GIVEN** PM 派发价格请求、新闻请求；T-1 完成，T-2 还没有 Result
- **WHEN** 重启，PM 派发价格请求、财报请求
- **THEN** 价格请求复用 T-1；财报请求派发 T-3，PM 的第 2 轮；PM 用了 2 轮、3 个任务
- **WHEN** 接着 T-2 收到基准无信号
- **THEN** T-2 是无信号

#### Scenario: 原样读回

- **GIVEN** PM 派发财报请求（T-1）；2026-10-14 15:03:00Z T-1 收到 s-2 给出的基准信号，费用 0.0073
- **WHEN** 重启，取得 K-1 的任务
- **THEN** T-1 的输入依次是 E-3、E-4，派发时刻 2026-10-14 15:00Z，截止时间 2026-10-14 15:05Z，PM 的第 1 轮
- **AND** T-1 的 Result 是完成：输出是基准信号（置信度 0.6，数据截至 2026-10-14 14:30Z，引用的条目 E-1 和 E-2），耗时 3 分钟，费用 0.0073，模型 s-2、是备用模型

#### Scenario: 读回没有周期和范围的任务

#### Scenario: 读写出错
