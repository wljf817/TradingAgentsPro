# AI Agent 美股交易系统需求 Proposal（简版）

本文只列已确定的核心设计，详细规则见[完整版](AI%20Agent%20美股交易系统需求%20Proposal.md)。

以代码调度器为核心的多 agent 美股交易系统。只有出现值得关注的事件或检查到期时才开「案件」，由 PM 带领子 agent 研究并给出结论；交易方案经 Critic 审核、代码风控和人工确认后执行。所有行为写入日志，用于评估每个 agent 是否贡献 alpha。

## 基本原则

- 只有 PM、子 agent、Critic、Reviewer 调用模型；触发、调度、风控、下单都是确定性代码
- PM 是唯一决策者；agent 之间不直接对话，只通过 Agent 网关转发的 Task / Result 协作
- 共享状态库是所有 agent 读取事实的唯一来源，同一案件读同一份快照
- 任何交易都必须通过代码风控，开仓必须人工确认
- 现金账户，只做多，不做空、不用保证金；只在常规交易时段下单

## 架构

![架构图](Proposal图.png)

| 模块 | 类型 | 职责 |
| --- | --- | --- |
| 事件检测层 | 代码 | 监控股票池和持仓，事件达到阈值才进入队列 |
| 调度器 | 代码 | 队列与优先级、确定案件类型、推进案件阶段；不做交易判断 |
| Agent 网关 | 代码 | 检查规则和预算，调用模型，校验输出格式 |
| PM | 模型 | 派发研究任务，提交结论或交易方案 |
| News / Quant / Fundamentals | 模型 | 子 agent，按任务解读新闻、量价、基本面，输出统一格式的信号 |
| Critic | 模型 | 审核 PM 的交易方案，与 PM 使用不同厂商的模型 |
| 风控引擎 | 代码 | 检查方案风险，结果为通过、调整或拒绝 |
| 执行模块 | 代码 | 唯一能下单的模块，管理订单、止损单和对账 |
| 健康监控 | 代码 | 发现异常时进入降级模式 |
| Reviewer | 模型 | 每周复盘和每笔卖出复盘，结果写入经验库 |

## 案件从哪来

| 驱动 | 触发方式 | 用途 |
| --- | --- | --- |
| 事件驱动 | 事件检测层实时检测，价格类条件用 moomoo 到价提醒 | 对价格异动、新闻公告、财报等外部变化做出反应 |
| 定时心跳 | 每个交易日收盘由代码检查 | 例行检查：复查日和催化剂截止日期到期、有新候选、股票池候选不足时寻股 |
| 自定义跟进 | PM 在结论中申请，代码审批 | 针对某个具体原因的一次性检查，问题由 PM 自己写 |

股票池是系统监控范围的唯一来源。新股票由人手动添加或 PM 寻股加入，先进入「候选」。股票状态决定案件允许的结论，和驱动方式无关：

| 状态 | 允许的结论 |
| --- | --- |
| 持仓 | 持有、加仓、减仓、清仓、更新论点、申请跟进 |
| 关注 | 开仓方案、继续关注、更新关注论点、降为候选、移出、申请跟进 |
| 候选 | 升级为关注、保持、移出 |

每个触发各自开一个案件，不合并；同一只股票同一时间只跑一个案件，其余排队依次运行。排队时持仓相关的案件优先，其次是关注股，再次是候选股，寻股和复盘最后。

## 一个案件怎么走

1. 调度器开案件，确定要回答的问题和允许的结论，唤醒 PM
2. PM 通过 Agent 网关向子 agent 派发任务，最多 2 轮
3. PM 提交结论并附评分，大多数案件以「无动作」结束。开仓和升级为关注必须引用至少 2 个不同子 agent 的结果
4. 交易方案交给 Critic：可以通过、质询或要求补充研究。开仓方案可以被否决；退出方案不能，有分歧时交给人决定
5. 风控引擎检查并预留额度 → 下单前用实时数据再校验 → 人工确认 → 执行模块下单

## 持仓与退出

每份投资论点都写明买入理由、催化剂及截止日期、目标价、证伪条件和复查日。论点成立就继续持有，不按固定天数退出。

| 退出路径 | 触发 | 人工确认 |
| --- | --- | --- |
| 券商端止损单 | 价格触及止损价 | 不需要 |
| 紧急风险退出 | 代码规则，比如跌幅超过紧急阈值、组合触及熔断线 | 不需要，执行后通知 |
| 模型建议退出 | PM 判定论点推翻、复查时不续期或达到目标价 | 默认需要 |

## 风控与执行

- 风控按单笔风险和组合合计风险检查。开仓类规则限制资金（只用已结算资金）、仓位和板块集中度；减仓类规则保证退出不被阻塞
- 提交订单前重新读取实时数据，再跑一次风控；超出有效期或价格偏离过大，方案作废
- 盘前盘后照常开案件，形成的方案等开盘执行
- 买入成交后挂券商端止损单；用客户端订单 ID 防止重复提交；每日收盘后与券商全量对账

## 故障与降级

- 模型 API、券商连接、数据或预算出现异常时进入降级模式：保留止损单、暂停开仓、不做新的由模型发起的退出，并告警
- 系统故障不当作投资判断：复查到期但因故障没有结论时，顺延处理
- 紧急风险退出不依赖模型，降级时照常有效

## 记录与评估

- 记录分四部分：程序日志（实时记录所有程序行为）、案件记录（三种驱动触发的所有案件，包括没有调用 agent 的）、交易记录（像银行流水，每笔买入、卖出、止损单一条，带状态、成交价、费用、结算状态和来源案件 ID）、状态库（即共享状态库）。PM 和 Critic 按需查询，不自动注入上下文
- 复盘：每周由定时心跳触发一次；每笔卖出后复盘一次，止损单自动退出由事件驱动，主动退出成交后自动开始。复盘结果写入经验库
- 信号按相对板块 ETF 的超额收益评估，按 agent、模型和案件类型分别统计
- 规则、prompt、阈值的修改由 Reviewer 提出建议，经人确认后才生效

## 技术栈

| 组件 | 选型 |
| --- | --- |
| 案件工作流、队列、定时任务 | DBOS |
| Agent 调用和数据格式 | PydanticAI、Pydantic |
| 存储 | PostgreSQL |
| 行情、到价提醒和交易 | moomoo OpenAPI + OpenD |
| 公告和财报原文 | SEC EDGAR |
| 模型 | 子 agent 用 flash 模型；PM 用较强的模型；Critic 与 PM 不同厂商 |
| 通知与人工确认 | Discord 机器人 |
| 开发工具 | uv、Ruff、mypy、pytest、GitHub Actions CI |
| 部署 | 一台常开机器，Docker 运行 PostgreSQL |
